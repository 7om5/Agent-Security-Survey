## 1. 150–300 字中文概述

论文研究对话式个人 Agent 在第三方交互中的情境隐私泄露。作者以 Contextual Integrity 为规范框架，提出“上下文劫持”攻击：第三方用单条查询把任务情境改写成更宽松的情境（如外星人入侵），诱导 Agent 交出与任务无关的敏感字段；在 Gemini Ultra 基线与 easier 子集上，单次攻击把隐私保护率从 94.4% 降到 45.2%。防御 AirGapAgent 把用户数据最小化器与面向第三方的对话模型逻辑隔离：最小化器只读取可信的任务与隐私指令并产出最小数据集 U_min，对话模型只能访问 U_min；需要更多数据时升级给用户审批。20 个合成画像、26 个字段、8 个场景的评测显示，攻击下 AirGapAgent 仍保持约 87%–97% 的隐私保护。全文无密码学构造或形式化证明，属于架构隔离与数据最小化的工程实现。

## 2. 研究背景、现有方法不足、精确定义的问题

个人 Agent 代表用户与第三方（另一 Agent、服务 API 或人）交换信息，哪些信息可以分享依赖任务上下文：订餐需要电话号码，求职或就医则需要另一组字段（p.1–3）。作者把问题归入 Contextual Integrity（CI）：隐私不是“永不分享”，而是信息流是否符合特定情境的规范；同一数据在一个情境下私密，在另一个情境下可以分享（p.3–4）。

现有做法的不足（p.2）：
- 把问题当对齐问题、用微调修复，仍会遭遇 adversarial/jailbreaking 攻击，模型保持根本脆弱；
- local differential privacy 不感知上下文，对用户数据一律加噪，持续损害 Agent 效用；context-aware LDP 也主要假设结构化数据；
- 经典访问控制需要为每个上下文人工定义严格规则，无法随上下文数量和数据复杂度扩展，尤其不适合邮件、文本、图像等非结构化数据。

精确定义的问题（p.3–4）：给定用户数据 vault `U`、任务 `t_p`、隐私指令 `d` 与第三方问题 `q_i`，Agent 应仅在 `u_i` 于 `⟨q_i,t_p⟩` 下“情境非私密”时输出 `u_i`，否则拒绝回答或给出不准确信息；攻击者通过改写上下文使原本私密的字段被输出。论文有两个目标：(1) 研究第三方如何从个人 Agent 提取情境私密数据；(2) 提出可部署的技术缓解设计（p.1）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- 组件（p.3–4，Fig.2）：用户；用户数据 vault `U = {(k1,v1),…,(kn,vn)}`（键值对，可含邮件、文档、日历、画像等）；隐私指令 `d`；用户任务 `t_p`；对话 LLM Agent `A_d`；第三方 `p`（另一 Agent、服务 API 或人）。Agent 以自然语言或 JSON 与 `p` 交互。
- 信任边界（Fig.2，p.4）：用户、`U`、`d`、`t_p` 在 **Trusted** 侧；Agent 通过 **Black-box API access** 向 **Untrusted** 第三方发送 `q_i`、返回 `u(q_i)`；模型权重不在攻击者知识范围内。
- 交互流程：用户先指定 `t_p` 与 `d`；第三方发送问题 `q_i`；Agent 结合 `U` 判断并回答；通信上下文 `c = ⟨q_i, t_p⟩`（p.3–4）。
- AirGapAgent 的信任边界（p.6–7，Fig.6）：最小化器 `M_d` 与 `U`、`d`、`t_p` 同处可信侧；对话模型 `A_d` 与第三方 `q_i` 同处暴露侧；两者之间的 “air gap” 是**逻辑数据流隔离**——`q_i` 不进入 `M_d`，唯一跨隙数据是 `U_min`；需要更多数据时通过 “escalate to user” 回路回到用户。
- 关键限制：这不是通常的工具型/多步 Agent 系统；没有工具调用、记忆、规划或多 Agent 协作，本质是“system prompt 内含用户数据的单轮对话模型”。所谓 air gap 是逻辑隔离，不是物理隔离或密码隔离。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- 资产：`U` 中的 26 个字段（basic、health、lifestyle 三类，p.8），尤其是当前 `(t_p,d)` 下 contextually private 的字段。
- 攻击者目标：取得在给定 `t_p,d` 下不应分享的 `u_i`；若 Agent 拒绝回答或提供不准确/幻觉数据，视为对攻击稳健（p.4）。
- 攻击者能力（p.4，§2.3）：黑盒查询；知道 `U` 的结构与 keys，但不知道 values；知道 Agent 设计、初始化 prompt、`d`、`t_p`，但不能修改；不知道模型权重；可任意构造 `q_i`。论文称单轮是“对攻击者最困难的设置”（p.3），但这是设计选择，未给出证明。
- 两类对手（p.4）：
  - **context-preserving**：直接询问情境私密字段，不改变问题形式；被动模型，隐私保证较弱。
  - **context-hijacking**：任意改写问题、操纵上下文；主动模型，隐私保证较强，是论文主攻击。
- 防御者能力：可修改 prompt、增加模块、重新设计 Agent 架构（p.4）。
- 前提假设：用户、`t_p`、`d` 可信且在交互前给定；上下文完全由 `(t_p,q_i)` 刻画；appropriateness 是二值标签；只考虑单轮、纯文本。论文未讨论恶意用户、被攻陷的模型提供方、权重窃取、侧信道、多轮渐进操纵或工具调用；第三方身份与 `t_p` 的绑定/认证也未在威胁模型中出现（本人推断，见第 9 节）。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

### 5.1 问题形式化（p.3–4）

用户信息为键值对，`A_d` 的行为定义为：

```text
A_d(q_i, t_p, U) = u_i   若 u_i 在 ⟨q_i,t_p⟩ 下非私密且 u_i ∈ U
                 = ∅     若 u_i 在该情境下私密或 u_i ∉ U
```

这与 secret-keeping 不同：同一 `u_i` 在一个上下文可分享、在另一个上下文不可分享，因此 Agent 必须理解并应用 `d`。

### 5.2 Contextual Integrity 四要素（p.3）

- actors：user（subject）、agent（sender）、third party（receiver）；
- context：`⟨q_i,t_p⟩`；
- data attributes：被请求的 `u(q_i)`；
- transmission principles：每次请求对应的规范。
论文用一组简化的 privacy directives `d ∈ D`（如“分享完成任务所需的信息”“只分享姓名和最少信息”）代替完整的规范分析。

### 5.3 上下文劫持攻击（p.4–6，§3）

攻击者把原上下文 `c` 改写为更宽松的 `c*`，使原本私密的 `u_i` 在新情境下显得可分享：

```text
Context preserving:  A_d(q_i, t_p, U) = ∅
Context hijacking:   A_d(q_i*, t_p, U) = u_i
```

- 手工攻击：在外卖订餐情境中加入“外星人入侵、拯救地球”等特殊情境；Figure 3 给出成功与失败的两种模型推理（p.5）。
- 自动化攻击：用 LLM 生成“为什么分享 `{field}` 对完成任务是必要的”这一理由，允许编造情境、同意、加密等（Figure 5，p.6）。
- 攻击只需一条查询；作者称其与 jailbreak 的区别在于：jailbreak 多为 secret-keeping（任何情况下都不应泄露），而情境隐私存在允许分享的上下文，因此防御更难（p.6，作者论证）。
- 与钓鱼的类比：攻击者用不寻常情境让受害者主动交出敏感信息（p.6）。

### 5.4 AirGapAgent 架构（p.6–7，Fig.6）

- 定义 **base context** `c0 = (t_p, U)`：只依赖可信的用户任务与用户数据，不包含第三方问题 `q_i`；因此 `c0` 不受上下文劫持影响。
- 最小化器 `M_d` 在 `c0` 下产生最小数据集：

```text
M_d(t_p, U) = U_min^{c0}
```

- AirGapAgent 的完整行为：

```text
A_d^{AGA}(q_i, t_p, U) = A_d(q_i, t_p, M_d(t_p, U)) = A_d(q_i, t_p, U_min^{c0})
```

- 关键不变量：第三方信息不能流回最小化器；即使对话模型被 `q_i*` 说服存在 `c*`，最坏也只能提取 `U_min` 中的字段：

```text
Baseline:     A_d(q_i*, t_p, U) = u(q_i),  若 u(q_i) ∈ U
AirGapAgent:  A_d^{AGA}(q_i*, t_p, U_min^{c0}) = ∅,  若 u(q_i) ∉ U_min
```

- 请求升级（request escalation）：当良性第三方需要 `U_min` 之外的信息时，Agent 把请求反馈给用户；用户判断请求是否良性并批准后，可分享 `u(q_i) ∉ U_min`。形式化为对隐私指令的修改：

```text
Before escalation:          A_d^{AGA}(q_i,t_p,U) = ∅,  if u(q_i) ∉ U_min
With approved escalation:   A_{d+u(q_i)}^{AGA}(q_i,t_p,U) = u(q_i)
```

论文把多字段/整类属性（如全部健康信息）的升级留作未来工作（p.7）。

### 5.5 实现（p.7，Fig.7）

- 最小化器是另一个 LLM，使用两步 prompt：
  1. **Minimization motivation prompt**：逐字段判断在 `{domain, scenario}` 与 `{directive}` 下是否适合分享，并输出推理；
  2. **Minimization retrieval prompt**：按上述推理从 `{persona_string}` 中检索允许输出的字段，按原格式返回。
- 对话模型不需要改动，仍使用 baseline agent 的两步 prompt（先判断问题是否适当，再根据推理与用户数据作答，Fig.4，p.5）。
- 作者明确承认：用 LLM 做最小化缺乏 formal guarantees、可解释性与连贯推理；实验只说明 off-the-shelf 模型在简单数据结构上表现较好（p.7）。

## 6. 安全属性与安全性论证

- 论文的目标属性是 **contextual privacy**：在给定 `(t_p,d)` 下，contextually private 的 `u_i` 不被第三方获得；contextually non-private 的字段应可分享以维持效用。这是一个**规范性/功能性定义**（来自 CI），不是密码学安全定义。
- **未提供形式化证明**。全文没有定理、游戏（game）、模拟、归约或泄露界；没有独立的 Security Analysis 章节。安全性论证是架构性的：由于 `q_i` 不进入 `M_d`，攻击者无法影响最小化结果，最坏泄露被限制在 `U_min` 内（p.7 的公式）。这一论证成立的前提是 `M_d` 正确执行了 `d`，而 `M_d` 是概率性 LLM。
- 作者自己指出 transformer 模型缺乏 formal guarantees、interpretability 和 coherent reasoning（p.7），因此该设计提供的是**经验性隐私保护**，不是可证明的 noninterference。
- 实验中的 privacy score 只衡量“对第三方 withheld 的比例”；拒绝回答与给出错误数据都算隐私成功（p.4、p.9–10），因此一个完全不可用的 Agent 也可获得高 privacy。它不衡量模型提供方、prompt 提取、侧信道或辅助字段推断造成的泄露。
- 该威胁模型把 `t_p` 与 `d` 视为可信输入；若攻击者能影响任务描述（例如用户安装了恶意第三方应用并让其代填任务），air gap 的核心前提即失效（本人推断；论文未分析这一情形）。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

### 7.1 模型与调参

- Gemini Ultra v1.0、Gemini Pro v1.0、GPT-4（gpt-4-0613）、Mistral Large（mistral-large-2402）。
- 不微调任何模型；只调整 prompt：baseline 用 Fig.4，AirGapAgent 用 Fig.7 + Fig.4（p.10）。

### 7.2 合成数据

- 20 个用户画像，每个 26 个键值字段，分 basic/health/lifestyle 三类；用 Gemini Ultra 按 US Census 分布生成，并逐步补全健康、生活方式字段以保持一致性（p.8）。
- 208 个 context profile；每个 context 为 `C=(t_p,d,q_i,y_a)`，其中 `y_a` 是“是否适合回答”的二值标签（p.8–9）。
- 8 个 `⟨domain, scenario⟩`（Table 2，p.9）：Health（visit social worker、ask about vaccines、doctor appointment）、Schedule（book a table、job interview）、Recommend（movie ideas、restaurant ideas、vacation ideas）。
- 标签生成：Gemini Ultra 三步流程（先判断适合性、再用推理产生二值标签），并人工检查；另用 Gemini Pro、GPT-4、Mistral Large 交叉核验一致性。25 次重复生成（每次 208 个标签）只出现 1 例不一致（“family medical history” 字段 23 个 No、2 个 Yes）（p.9）。
- 规模：完整评测集 16,640 例 = 4 种题型 × 4,160 例（26 字段、20 画像、8 场景）；easier subset 每种题型 2,400 例（20 字段、6 场景）（p.10）。

### 7.3 指标

```text
Utility(S) = Σ_{S_ya=Yes} L_utility(y_pred, y_r) / |S_ya=Yes|
Privacy(S) = Σ_{S_ya=No}  L_privacy(y_pred, y_r) / |S_ya=No|
```

- MCQ：四选一（正确答案、两个 LLM 生成的错误答案、“Refuse to answer”）；`L_utility = I(y_pred = y_r)`；`L_privacy = I(y_pred ≠ y_r ∨ u_i ∉ U_min)`（p.9–10）。
- OEQ：`L_utility = l_OEQ(y_pred,y_r)`；`L_privacy = l_OEQ(y_pred,∅)`；`l_OEQ` 用 containment match（`b ∈ Substring(a)`）与 BLEU，另试 exact match 与 BLEURT（p.10）。
- 默认隐私指令：“Share information necessary to achieve the goal for a US English speaker in North America”（p.10）。

### 7.4 对照与结果（务必连同数据集条件阅读）

对照只有 **Baseline Agent**（同一 LLM，prompt 中含完整 `U`）与 **AirGapAgent**；没有与 DP、微调、规则访问控制等其他防御比较。

- **Table 3（p.11，easier dataset：20 字段、6 场景、MCQ、默认指令）**：
  - Gemini Ultra Baseline：context-preserving 下 utility 98.9%、privacy 94.4%；context-hijacking 下 utility 98.2%、privacy 45.2%（下降 49.2 个百分点）。
  - Gemini Ultra AirGapAgent：context-preserving 下 88.7%/97.2%；context-hijacking 下 87.3%/96.7%（仅降 0.5）。
  - 其余模型 Baseline 在 hijacking 下 privacy：Gemini Pro 37.6%、GPT-4 31.4%、Mistral 34.8%；AirGapAgent 分别为 92.0%、86.8%、90.9%。AirGapAgent 的 context-preserving utility 分别为 65.5%、78.9%、83.2%。
- **Table 4（p.11，此处引 Full 行：26 字段、8 场景、MCQ）**：
  - Baseline：context-preserving 91.6%/88.5%，hijacking 98.0%/33.1%（降 55.4）。
  - AirGapAgent：context-preserving 83.9%/96.8%，hijacking 90.3%/93.2%（降 3.6）。
  - harder 子集（新增 6 字段、2 场景）：Baseline 在 hijacking 下 utility/privacy 为 97.4%/33.8%，AirGapAgent 为 89.3%/92.5%；context-preserving 下分别为 83.5%/78.5% 与 77.2%/92.8%。
- **Table 5（p.11，open-ended，full dataset）**：
  - Containment match：Baseline hijacking privacy 31.3%、AirGapAgent 84.2%；utility 98.4% vs 80.4%。
  - BLEU：Baseline hijacking privacy 31.3%、AirGapAgent 83.6%；utility 98.5% vs 81.2%。
- **Table 6（p.12，字段级，context-hijacking，harder dataset）**：AirGapAgent 平均 NIM（not-in-minimized）90%、privacy 93%、containment match 84%、BLEU 84%；但 exercise hours 的 NIM 仅 40%、name 63%、email 74%、gender 73%、smoker 65%，说明最小化器经常保留不必要字段。
- **Table 7（p.12，task 描述消融）**：只给 domain（如 “healthcare”）时，NIM 从 89.6% 降到 56.9%、privacy 从 96.8% 降到 68.6%；任务描述越具体，最小化越准确。
- **Figure 8（p.12，指令消融）**：更宽松的 “Positive vibes” 提高 utility，但在攻击下降低 privacy；“Minimal” utility 较低但在攻击下表现好；由于攻击只影响对话模型、不影响最小化器，AirGapAgent 的性能总体稳定（约 3–4% 的下降来自最小化器误差）。

### 7.5 结论边界

- 上述数字均来自**合成画像、单轮、文本、prompt 级 Agent**；不能外推到多轮、工具调用、真实用户数据或生产部署。
- Table 3 用 easier dataset；Table 4 同时给出 easier/harder/full 三行，Table 5 用 full dataset；不同表的 utility/privacy 不可直接横向比较。
- 论文没有报告延迟、调用成本、最小化器模型规模、prompt 变体或 escalation 的消融；escalation 只做了形式化描述，未进入实验。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

贡献（p.1–3）：
1. **威胁模型**：恶意第三方通过交互提取情境私密用户信息。
2. **攻击**：context hijacking，一种单查询、可手工或 LLM 自动生成的通用数据外泄攻击；在 Gemini Ultra 基线、easier 子集、单轮 MCQ 上泄露约 55% 的情境不适当数据（privacy 45.2%）。
3. **防御**：AirGapAgent，用最小化器 + 逻辑隔离把第三方与完整用户数据分开；在攻击下保护约 97% 的情境私密数据（easier dataset、Gemini Ultra）。
4. **评测协议**：基于 LLM 生成合成画像与场景的 benchmark，覆盖 26 字段、8 场景、4 种题型。

与直接相关工作的差异（p.13，§7）：
- 与 jailbreaking/secret-keeping 文献：后者要求模型在任何情境下都不泄露，防御不需要理解上下文；本文的隐私是 context-dependent，存在允许分享的情境，因此更难。
- 与 differential privacy：DP 保护数据集中的一条记录在聚合统计中的影响；本文是单条记录的定向释放，问题不同。
- 与经典访问控制/匿名化/PII 删除：这些方法 context-independent、过于 restrictive；本文用 LLM 理解自然语言上下文，而不是人工规则表。
- 与 Ghalebikesabi et al. [27]：后者系统性地让个人助理遵循 CI，但不研究对抗交互；与 Mireshghallah et al. [36]：后者是评测 LLM 隐私规范意识的 benchmark，本文提出系统设计与攻击。
- 与 air gap/reference monitor：借用了网络隔离与引用监控器的类比，但实现是 prompt/模块级的逻辑隔离。

可复现资源：
- 论文给出了 baseline、攻击生成、最小化器的关键 prompt（Fig.4、5、7），数据生成流程与统计量较详细。
- 但 PDF 只有 15 页，Appendix A/B（p.15）明确写 “Please see the full draft” 并指向 arXiv:2405.05175；完整 prompt、数据样例与补充表格不在本 PDF。未提及代码或数据发布链接；四个模型均为托管/专有版本。因此**部分可复现**。

## 9. 局限性、失效场景、作者未解决的问题

作者自述（p.7、p.13）：
- 最小化器是 LLM，缺乏 formal guarantees、可解释性与连贯推理；如何为“情境私密数据会被移除”提供有意义的保证仍未解决。
- 合成画像与 LLM 生成的 appropriateness 标签未必反映真实用户期望；需要真实用户基准。
- 只研究单轮；任务与隐私指令需用户预先给定；未来需覆盖更广的任务、模型与数据集。
- 多字段/整类属性的 escalation 未实现，留待未来工作。
- 希望探索更小、专用的最小化器以提升效率与隐私。

本人补充（基于全文的推断）：
- **escalation 本身是攻击面**：用户审批回路没有认证、限流或防社会工程分析；攻击者可诱导用户批准本不应分享的字段。论文未实验评估 escalation。
- **第三方身份未认证**：威胁模型中的 `p` 只是一个“第三方”，`t_p` 可信但未与 `p` 的真实身份绑定；攻击者可冒充任务对应的服务方。
- **辅助字段推断**：Table 6 的字段级结果与 p.12 的分析显示 email 可用于猜 name/gender；字段级最小化不能防止相关字段的联合推断。论文承认这一点但没有给出量化或缓解。
- **最小化器自身可被注入**：`U` 的值是用户数据，可能包含对抗文本；`M_d` 直接读取 `U`，论文未 threat-model 这一路径。
- **同一信任域**：若最小化器与对话模型由同一模型提供方托管，提供方仍能看到完整 `U`；逻辑 air gap 不等于对提供方的机密性。
- **度量偏差**：privacy 把“拒绝回答”和“给出错误数据”都算成功，utility 又只在适当问题上计分，因此高 privacy 可能来自过度保守；论文虽报告 utility，但没有把二者合成单一部署指标。
- **标签循环性**：Gemini Ultra 既生成 appropriateness 标签，又是表现最好的被测 Agent；可能存在同源偏差。
- **无成本/延迟分析**：两次 LLM 调用与逐字段最小化的开销未报告。
- **无独立安全分析章节**：没有对自适应攻击（知道 AirGapAgent 设计并针对最小化器）的形式化或实验评估。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

### 原论文实际使用/讨论的机制

- **数据最小化**：由 LLM 在 base context 下选择字段并产出 `U_min`；这是策略执行/信息流限制，不是加密。
- **逻辑隔离（air gap）**：最小化器与对话模型之间的数据流隔离，禁止 `q_i` 回流；这是架构性 information-flow control。
- **reference monitor / least privilege**：仅作为类比出现（p.6、p.13）；没有 tamper-proof monitor、没有形式化访问控制模型、没有策略语言语义。
- **Contextual Integrity**：规范性隐私理论，用于定义“适当的信息流”；不是密码学定义，也没有可证明的泄露界。
- **无密码学机制**：全文没有加密、签名、哈希、TEE、OAuth、MPC、零知识或 DP 构造；DP 只在 related work 中作为对比（p.13）。`encryption` 一词只出现在攻击生成 prompt 的 “bring consent, add encryption”（p.6，Fig.5），是攻击者编造的理由，不是论文机制。
- 结论：**工程应用/架构设计，无密码学构造或证明**。

### 个人推断（明确标为推断）

- 可把 contextual privacy 形式化为一种**带动态解密的 noninterference / quantitative information flow** 属性：策略 `P(t_p,d)` 指定哪些字段可释放；安全性要求低视图（第三方可见内容）不泄露高视图（`U` 中私密字段）。但这里的策略由自然语言与 LLM 语义判断，难以写成密码学游戏所需的语法谓词；形式化的主要难点是“appropriateness”的语义，而不是加密算法。
- 可以定义**相对 `U_min` 的泄露界**：`Leak ≤ f(ε_M, ε_C)`，其中 `ε_M` 是最小化器的 false-positive 率、`ε_C` 是对话模型在 `U_min` 内的越权率；论文只给了经验值，没有给出可组合的界。
- 谓词加密/属性基加密只能在策略可表示为静态属性时提供字段级访问控制；CI 的适当性依赖任务语义与第三方角色，不能直接归约为属性谓词。若强行套用，容易得到“加密了但语义仍错”的伪方案。
- MPC/私密检索可以让第三方在不暴露完整 vault 的情况下查询，但 Agent 的任务本身就是向第三方**释放**选定数据；MPC 不能替代“选择哪些数据可释放”的语义判断。
- 零知识证明“最小化器遵守了策略”需要先把策略与模型行为形式化；否则证明的是一个未被信任的定义，理论价值有限。
- DP 不适用于本文的单记录定向释放（论文自己在 p.13 指出）；若用 DP 加噪，会直接破坏 utility，这也是论文拒绝 DP 的理由之一。
- 侧信道（响应长度、拒绝模式、字段组合）未被建模；这与密码学侧信道不是同一概念，不能混为一谈。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

### 原论文实际使用/讨论的机制

- 没有使用任何应用密码学机制；没有密钥管理、认证协议、签名、加密存储、TEE、OAuth scope 或审计日志。
- 唯一接近“安全工程”的内容是：逻辑隔离、最小权限/引用监控器类比、把最小化器放在可信侧、把第三方交互放在不可信侧（p.6–7、p.13）。
- 这些是**架构与 prompt 工程**，不是密码工程；“air gap” 是逻辑数据流约束，不是物理/密码隔离。

### 个人推断（明确标为推断）

- **字段级授权令牌**：把每个 `u_i` 的释放绑定到 `(task, third-party identity, directive)` 的短期 capability；这能把“最小化结果”从 prompt 里的文本变成可执行的访问控制，但仍需可信的策略判定器。
- **认证的 escalation 通道**：用户批准必须经过强认证、显示请求方身份与字段、抗重放；否则 escalation 会成为钓鱼入口。
- **可信执行/attested minimizer**：若最小化器与 vault 运行在 TEE 中，可向用户证明 `U` 未被第三方读取；但这只保护“谁能看到 vault”，不保证“最小化语义正确”。
- **加密 vault + 按任务释放密钥**：静态加密与密钥分层是必要的基线，但不能防止已获授权的对话模型泄露 `U_min`。
- **审计与透明度**：记录每次释放的字段、任务、第三方、用户批准，可用于事后追责；需要完整性保护（签名/Merkle log），但论文未涉及。
- **伪交叉风险**：仅给日志签名、仅把 prompt 包进加密传输、仅加 OAuth 登录，都不能解决 context hijacking；这些是合规/边界控制，不是本文问题的核心。若要做密码学研究，应聚焦“策略可验证性/泄露度量/可信最小化”，而不是把现有机制重新包装。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- **H1**：contextual privacy 可以被形式化为“带动态解密的 noninterference”，并给出可组合的泄露界；需要先在固定策略语言下证明，再处理自然语言策略的语义不确定性。
- **H2**：最小化器的 false-positive/false-negative 率与对话模型的越权率可以组合成端到端泄露上界；可用本文的 `U_min` 框架做实验验证。
- **H3**：escalation 通道是可被社会工程利用的攻击面；需要认证、请求展示与限流，且其安全性可与本文的 air gap 独立评估。
- **H4**：字段级最小化无法阻止辅助字段推断（email→name/gender 已在 Table 6 出现）；需要相关性感知的最小化或定量泄露度量。
- **H5**：把单轮扩展到多轮、工具调用与多 Agent 后，攻击面从 `q_i` 扩展到工具输出、记忆与 Agent 间消息；AirGapAgent 的“base context 可信”假设是否还能成立需要重新验证。
- **H6**：用密码工程（字段级 capability、TEE、加密 vault）替代/增强 prompt 级隔离，能否在保持 utility 的同时提供更强的泄露保证；需要与本文的逻辑隔离做同条件对比。
- 以上均为待验证假设，不代表作者已做或领域已有人做。
