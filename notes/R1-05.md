## 1. 150–300 字中文概述

本文提出 ISOLATEGPT，把传统操作系统/浏览器的执行隔离思想迁移到“第三方 LLM 应用共享上下文”的 Agent 系统。系统采用 hub-and-spoke 架构：可信 hub 由确定性 operator、LLM planner 和中央记忆组成；每个 App 在独立进程的 spoke 中运行，拥有专属 LLM、记忆和 App，只能通过 hub 中转的 ISC 协议交换结构化消息，跨 App 的数据流与不可逆动作需用户授权。作者用增强后的 InjecAgent benchmark（1,598 条攻击）比较非隔离基线 VANILLAGPT，报告 VANILLAGPT 平均攻击成功率 20.2%，ISOLATEGPT 仅在 7.6% 攻击上弹出权限对话框且全部带警告；四个案例研究显示攻击被阻断。功能上在 LangChain benchmark 上与基线持平，75.73% 查询的性能开销低于 30%。论文不含密码学构造、形式化安全定义或证明，隔离是 OS 进程级系统机制，保护效果依赖用户拒绝带警告的授权请求。

## 2. 研究背景、现有方法不足、精确定义的问题

LLM 正从模型扩展为支持第三方 App 的独立系统（ChatGPT、Gemini、Alexa 等），App 以自然语言功能描述 + API 端点形式被加载进共享上下文，LLM 可自动在 App 间交换数据并调用外部服务（p.2–3, §II-A, Fig.1）。问题在于：第三方 App 不可信，且自然语言接口本身模糊、不精确，App 可窃取共享记忆中的数据、篡改其他 App 行为，或在无攻击者时因指令冲突/词义错位造成数据误暴露（p.3–4, §II-B）。

作者指出，浏览器与移动 OS 经历过从同源策略到 sandbox/进程隔离的演化，而当前 LLM 系统“仍处于早期，未对多 App 安全执行与协作提供任何严肃保护”（p.4, §II-C）。本文要回答的不是“是否存在攻击”，而是一个系统设计问题：**执行隔离能否用于自然语言驱动的 Agent 系统、需要什么样的隔离与中介接口，以及功能与性能代价多大**（p.1 Abstract; p.5 §IV）。与纯攻击论文不同，本文的贡献是架构蓝图、原型和评估方法（p.2 Contributions）。

**章节结构说明**：论文没有独立的 Related Work 章节，相关工作在 §II-C（浏览器/移动 OS 隔离）与 §VIII（结论）中简要定位；也没有独立的 Discussion/Limitations 章节，讨论见 §VII-C/D 与 §VIII，局限散见于 §IV-C3、§V-A、§VII-B、脚注 6 与 Appendix B（本人对全文结构的观察）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **Hub（可信中介，类比 kernel）**（p.5–6, §IV-A, Fig.2）：`Hub Operator` 是无 LLM 的确定性模块，负责拦截用户请求、调用 planner、在 hub 与 spoke 间路由消息；`Hub Planner` 是 LLM，判断请求是否需要 App、选择 primary/secondary App 并推断所需数据；`Hub Memory` 保存跨 App 的全局交互历史、摘要知识和实体键值对。Fig.2 还画出 Spoke management、Permission management、Permission records、ISC Protocol 等子模块。
- **Spoke（每个 App 的隔离执行空间）**（p.6–7, §IV-B）：包含 `Spoke Operator`（无 LLM、确定性）、`Spoke LLM`（每个 App 专属，可为 GPT-4/LLaMA 或微调模型）、`Spoke Memory`、以及 App 本身。每个 App 配专属 LLM 是相对部署系统的关键区别：不同 App 可用不同/微调 LLM（p.7）。
- **Vanilla spoke**（p.7, §IV-B4）：无 App 的通用或专用 LLM spoke，用于纯 LLM 查询、多 App 结果的无共享合成，以及类似隐私浏览的“无历史上下文”模式。
- **交互流程**（p.5 Fig.2; p.6 §IV-A4; p.7 §IV-B5）：用户请求 → hub operator/planner 选 App 与数据 → 创建/调用 spoke 并传数据（需用户许可）→ spoke LLM 规划并调用 App → 缺数据时经 hub 向用户索取 → 需要其他 App 时走 ISC → 结果经 hub 返回用户。
- **信任边界**：hub 与宿主系统可信；每个 spoke 内的 App 不可信；spoke 之间互不信任且彼此不知道对方存在；自然语言内容（邮件、网页）可能恶意；用户是授权决策者。Fig.2 用绿色标出 hub/spoke operator 为非 LLM 的确定性中介（p.5 图注）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

**资产**：hub 与 spoke 记忆中的用户敏感数据（姓名、生日、护照、信用卡、病历等）、其他 App 持有的数据、系统能力/外部服务调用、App 与 LLM 的行为完整性（p.4–5, §III-A–B; p.9 §V）。

**攻击者能力**（p.4, §III-B）：
- 可在 App Store 部署恶意 App，或诱导用户从店外安装恶意 App；
- 可向良性 App 投递恶意内容（如恶意邮件/网页），从而以外部对手身份行动；
- 目标包括：(i) 影响/控制其他 App 或 LLM 的执行；(ii) 窃取系统记忆或另一 App 中的数据。

**信任假设**（p.5, §III-C）：
- LLM 与宿主系统可信、未被攻陷、无直接害意，但仍可能被 prompt injection 攻击；
- App 不可信；
- App 处理的内容可能恶意；
- 自然语言指令的解释与应用本质上是模糊、不精确的（作者将其作为显式假设，而非仅攻击者行为）。

**范围**（p.5, §III-D）：
- In scope：阻止恶意 App 的对抗行为、阻止恶意内容经良性 App 传播到系统；阻止因自然语言歧义导致的 App/LLM 被意外影响与数据误暴露。
- Out of scope：单个 App 内部的攻陷（例如 App 处理恶意邮件时被 prompt injection）；但“阻止其传播到其他 App”仍在范围内。
- 未给出形式化 threat model 或安全游戏；上述为自然语言描述。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

本文无数学公式、无密码协议，核心是系统架构与中介协议。

1. **进程级执行隔离**（p.6; p.17 Appendix A-A）：hub 与每个 spoke 运行在独立进程中；用 `seccomp` 限制可调用系统调用（仅保留 exit、sigreturn、read、write 等必要项），用 `setrlimit` 限制 CPU 时间、虚拟内存、文件大小；App 网络请求限制在其 root domain（eTLD+1），数据外发经用户许可。作者明确称这是 Chrome 等部署系统常用的 sandbox 实践，不是新原语。
2. **Hub 中介的查询生命周期**（p.6, §IV-A4）：operator 拦截请求 → planner 选 primary/secondary App 并推断数据 → 多候选时让用户选择 → memory 取数 → 创建/调用 spoke 并传数据（需许可）。Hub planner 的计划还用于后续对跨 App 请求做“是否符合原计划”的交叉检查（p.8）。
3. **Spoke 内规划与执行**（p.7, §IV-B5）：spoke operator 把用户查询、hub 提供的数据、本 spoke 记忆、ISC 广播的功能列表交给专属 LLM 生成逐步计划；缺数据经 hub 向用户索取；不可逆动作（发邮件、购买）必须获得显式用户同意（p.7; p.18 Appendix A-D）。
4. **ISC（inter-spoke communication）协议**（p.7–9, §IV-C, Fig.3）：
   - spoke 之间不能直接通信，只能经 hub；只允许 operator 之间交换消息，LLM 不得直接收发；
   - 消息格式为 `<Spoke-sID, functionality, request|response message>`；App 需预先声明功能名与请求/响应数据类型；格式不符的消息直接丢弃；
   - hub 分配**临时会话标识符** `Spoke-sID` 并嵌入消息，防止 App 虚构不存在的协作，同时不直接暴露 App 名称/功能；作者脚注承认对手仍可用侧信道推断协作对象（p.8 footnote 6）；
   - 协议步骤 1、3、5 需要用户同意（Fig.3 图注）。
5. **权限模型**（p.8–9; p.18 Appendix A-D, Fig.4）：三类权限——permanent、session、one-time；覆盖 App 选择、spoke 间通信、数据发往远端主机。永久权限不可用于不可逆动作；用户可随时撤销。权限对话框包含 hub 对请求是否“符合原计划/预期”的评估与警告（Fig.4 右侧 Malicious request 示例）。
6. **实现**（p.17 Appendix A; p.19 Appendix B）：LangChain 0.1.10、LlamaIndex 集成、Python 3.9、Redis 5.0.1、约 6K 行代码；以个人助理聊天机器人形式实现；源码在 GitHub `llm-platform-security/SecGPT`（IsolateGPT-AE 分支）并归档 Zenodo。

**关键设计取舍**：隔离牺牲了 App 间的自然协作，ISC 用“结构化消息 + hub 中转 + 用户筛查”重建受控协作；作者明确说当前没有可靠的自动恶意自然语言检测，因此把人工筛查作为协议一部分（p.8, §IV-C3）。

## 6. 安全属性与安全性论证（如果没有证明，明确写“未提供形式化证明”）

论文主张的安全属性可归纳为：

- **执行隔离/防篡改**：App 的 LLM 只能在其 spoke 执行空间内实现该 App 的指令，无法改变其他 spoke 或 hub 的执行（p.10, §V-B1; Fig.5）。
- **中介与信息流控制**：跨 App 数据流必须经 hub operator，且受结构化格式、hub 计划交叉检查与用户许可约束（p.7–9, §IV-C; p.11 Fig.6）。
- **授权/最小权限（工程意义）**：App 选择、跨 App 数据共享、数据外发均需用户同意；不可逆动作不能永久授权（p.8–9; p.18）。
- **协作完整性**：临时 `Spoke-sID` 与格式校验防止 App 虚构协作或发送畸形消息（p.8）。

**论证性质**：全文**未提供形式化安全定义、定理、游戏或证明**。作者使用“by design”论证（隔离使共享内存攻击面消失）加经验评估（§V 称为 “Protection Analysis”，实际是 benchmark + 案例研究）。安全论证依赖四个未形式化的前提：(1) 宿主 OS 的进程隔离与 seccomp 正确；(2) hub（含 LLM planner）不被攻陷；(3) 用户会拒绝带警告的权限请求；(4) App 功能描述与格式在商店上架前经过审查（p.8 footnote 5）。其中 (3) 在附录 B 被明确写成复现假设：数据窃取与误暴露案例要求评审者拒绝权限请求（p.19）。因此论文的“保护”是**条件性、经验性**的，而非可证明的。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

**环境与基线**（p.9, §V; p.19 Appendix B）：两个系统均用 OpenAI GPT-4 API（version 0613），Ubuntu 20.04.6 LTS，AMD Ryzen 9 3900X 12-Core，32GB RAM；基线 VANILLAGPT 提供相同功能但 App 共享执行环境、不隔离。附录 B 说明所有评估用 GPT-4 0613，需 OpenAI 与 LangChain API key。

**攻击评估**（p.9–10, §V-A, Table I）：
- 使用 [13] 的 App 安全 benchmark（参考文献 [13] 即 InjecAgent；该项目永久排除清单中的 XX-01，仅作为本文实验工具记录，不纳入 124 篇语料）。作者在其“enhanced setting”上增加 544 条针对系统记忆的攻击，总计 **1,598** 条；覆盖 App 互相攻陷、App 间数据窃取、系统数据窃取。
- 指标：VANILLAGPT 用 A1（攻陷第一个 App 的成功率）、A2（攻陷第二个 App）、Total ASR；ISOLATEGPT 因攻击成功取决于用户授权，报告 **PA**（权限对话框出现率）与 **WR**（出现对话框中带警告的比例），而非同口径 ASR。
- 核心结果（Table I, p.10）：VANILLAGPT 全类平均 ASR **20.2%**（A1 22.9%、A2 81.3%）；ISOLATEGPT 平均 PA **7.6%**，且这些对话框中 **100%** 带警告。分类示例：App compromise–Physical harm，VANILLAGPT 29.0% vs ISOLATEGPT PA 7.4%/WR 100%；App data stealing–Financial data，33.0% vs PA 19.1%；System data stealing 三类为 2.2%/5.6%/1.8% vs PA 0.0%/5.1%/0.0%。
- **重要口径**：20.2% 与 7.6% 不是同一指标，不能直接相减或称为“ASR 降至 7.6%”；7.6% 只是触发权限请求的比例，真正是否成功还取决于用户拒绝（p.10 明确说明；p.19 复现假设）。
- 作者观察：VANILLAGPT 上不少攻击被 LLM guardrail 拦住；A2 显著高于 A1，可能与上下文变长后更易被 jailbreak/prompt injection 有关（p.10，作者推测）。

**案例研究**（p.10–13, §V-B, Figs.5–8）：
1. App compromise：恶意 Quick Ride 在 VANILLAGPT 中让 Metro Hail 报价 +$10；ISOLATEGPT 中因各 spoke 独立 LLM 而失败（p.10–11, Fig.5）。
2. Data stealing：被恶意邮件攻陷的 Gmail 试图从 GDrive 取 “SSN” 文件并外发、删除邮件；VANILLAGPT 成功且可抹痕；ISOLATEGPT 的 ISC 请求触发警告，用户拒绝后失败（p.11, Fig.6）。注意此案例属于“单个 App 内已被攻陷、阻止其向外传播”的 in-scope 情形。
3. Inadvertent data exposure：Travel Mate 模糊地索取“任何已有个人信息”，VANILLAGPT 把此前 Health Companion 收集的病历数据一并给出；ISOLATEGPT 因跨 App 数据共享需显式许可而阻止（p.11–12, Fig.7）。
4. Uncontrolled system alteration：Creative Muse（要求虚构）与 Symptom Solver（要求客观诊断）指令冲突；VANILLAGPT 混合两种指令给出“messy result”，ISOLATEGPT 只执行最相关 App 的指令（p.12–13, Fig.8）。

**功能评估**（p.13, §VI, Table II–III）：使用 LangChain benchmarks [15]，四类查询：无 App（42 条）、单 App（20 条）、多 App（20 条，最多 13 个）、多 App 协作（21 条，最多 5 个）。Table II：单 App 与多 App 的 steps/overall 正确率两者均为 1.00；多 App 协作两者均为 steps 0.76、overall 0.95；无 App 的文本相似度 edit distance 0.34 vs 0.33、string score 0.71 vs 0.70。作者结论是功能与基线相同（p.13）。Table III 给出错误分解，且明确百分比只针对错误样本；多 App 协作中两者错误分布相同（如 incorrect response 各 14.29%），无 App 中 unexpected response 各 97.62%、context window exceeded 各 2.38%。

**性能评估**（p.14–15, §VII, Table IV, Fig.9）：共 103 条查询（20+20+21+42）。Table IV 的端到端平均时间（秒，冷启动）：
- 单 App：32.013 → 39.210（约 +22.5%）；
- 多 App：30.292 → 49.256（约 +62.6%）；
- 多 App 协作：31.683 → 59.984（约 +89.3%）；
- 无 App：19.502 → 21.422（约 +9.8%）。
作者报告 **75.73%** 的查询开销低于 30%，90/95 分位分别为 **1.24× / 1.80×**；并称与 Gazelle 等进程隔离原型（加载网站约 +44%）相当或更好（p.14）。额外时间主要来自 hub planning 与 spoke memory extraction（多 App 场景分别占额外时间的 17.18%/80.43%；协作场景 28.87%/67.67%，p.14–15）。成本上，对 10% benchmark 查询测得 ISOLATEGPT 成本为 **1.85×**（p.15, §VII-D）。

**消融**：无严格消融实验；Table IV 的组件时间分解用于归因开销，作者仅提出启发式、prompt 模板、并行化等未评估的优化（p.15）。

**可复现性**（p.19–20 Appendix B）：Artifact 提供 E1 保护案例（5 人分钟 + 5 计算分钟）、E2 性能（5 + 20）、E3 功能（5 + 3）；并说明 LLM 概率性导致结果可能需重复运行。

## 9. 局限性、失效场景、作者未解决的问题

论文无独立 Limitations 章节；以下为作者明确承认、散见于正文/脚注/附录，或可由原文直接支持的局限：
- **权限模型是初步的**：只覆盖有限用例，完整自动化权限模型与 UX 被列为正交的未来工作（p.9; p.18）。
- **依赖人工筛查自然语言消息**：作者说目前没有万无一失的自动检测机制，用户需手动筛查跨 spoke 消息，存在疲劳与误判（p.8, §IV-C3）。
- **保护依赖用户拒绝警告**：附录 B 明确要求复现时拒绝带警告的权限请求（p.19）；若用户点“Allow”，数据窃取/误暴露案例会成功。这是可用性与安全的直接张力。
- **Hub 的评估不是证明**：hub 基于可信 planner、vetted App 描述和自身记忆判断请求是否异常，作者称“难以操纵、因而合理可靠”，但这是论证而非形式化保证（p.9）。Hub planner 本身是 LLM，仍在 TCB 内。
- **单 App 内攻陷不在范围**：App 处理恶意邮件时被注入属于 out of scope，只阻止向外传播（p.5, §III-D）。
- **侧信道**：临时标识符不直接暴露 App 名称，但作者脚注承认对手可用侧信道推断协作对象（p.8 footnote 6）。
- **隔离粒度有限**：进程隔离 + seccomp/setrlimit + eTLD+1 网络限制；论文未描述每 App 的文件/网络 capability 模型，也没有内核级最小权限证明（p.17；前半句为原文事实，后半句为本人推断）。
- **性能与成本**：冷启动下多 App 协作约 +89%，10% 查询成本 1.85×；作者提出优化但未实现/评估（p.14–15）。
- **评估范围**：仅 GPT-4 0613、单一硬件、LangChain benchmark；benchmark 本身被作者承认可能不覆盖真实复杂场景（p.14 “Benchmark limitations”）；攻击 benchmark 的 system-memory 描述符假设也被作者指出偏理想化（p.10）。
- **无形式化验证**：没有对隔离/中介协议做模型检验或证明；安全结论全部是经验性的（全文）。
- **未做用户研究**：权限对话框的警告是否被理解、疲劳程度、误拒率均无实验（全文未见 user study；这是本人对全文范围的事实性观察）。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**原论文已做：无。** 本文是系统隔离架构，**没有使用任何密码学原语，没有密码学安全定义、构造或证明**。文中的 “isolation / trusted hub / permission / ephemeral identifier / integrity” 都是系统机制词汇：
- 进程隔离、seccomp、setrlimit、eTLD+1 限制是 OS/网络安全机制（p.17）；
- `Spoke-sID` 是 hub 分配的会话标识，用于防止虚构协作与隐藏 App 身份，不是密码学 nonce、MAC 或认证凭证（p.8）；
- 消息“完整性”来自 hub 中转、格式校验与进程边界，不是签名/MAC（p.8–9）；
- 权限是 UI + 策略执行，不是密码学 capability 或 token（p.18）。
因此应明确记为：**系统机制，无密码学构造/证明**。本人评分推断：按项目口径本文的理论密码学相关度约 1/5（可类比 reference monitor/非干扰，但没有密码学问题内核）。

**个人推断（明确标为推断，未在论文中实现）**：
- **形式化中介与非干扰**：可把 hub-and-spoke 抽象为“带中介的理想功能”：任一不可信 spoke 的输出，只有经 hub 授权通道才能影响另一 spoke 的状态。可尝试用信息流非干扰（non-interference）或 UC 风格理想功能刻画，把“用户同意”建模为唯一 declassification 点。这是系统安全的形式化，不必然需要密码学；只有在跨主机/跨信任域时才需要认证通道。
- **ISC 的认证缺口**：当前 ISC 依赖同一宿主内的进程边界与 hub 可信；`Spoke-sID` 可被能观察/注入 IPC 的对手伪造或重放。若部署到多主机、边缘或第三方托管场景，需要 hub 签发的、绑定 session/functionality/时效的认证凭证（MAC/签名/能力令牌），并定义不可伪造性、不可重放、作用域不扩张与可撤销性。这是明确的密码学接口，但论文未做。
- **权限授予的密码学语义**：可把 permanent/session/one-time 权限形式化为可衰减、可撤销的 capability，研究“用户同意”与“最小权限”在多 App 组合下是否保持不变量。论文的权限模型只是工程枚举，没有安全定义。
- **审计与归因**：hub 记录所有跨 spoke 消息，天然是审计点；可研究对审计日志的完整性保护与选择性披露。但仅“给日志签名”不能保证语义正确，属于易夸大的伪交叉（见第 11 节）。
- **不能由密码学解决的部分**：自然语言歧义、App 功能描述与真实行为不一致、用户是否理解警告，这些是语义/人因问题，密码学原语不能直接解决；论文的核心保护也主要来自隔离与用户决策，而非任何密码假设。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**原论文实际使用（仅系统机制）**：
- 进程隔离：hub/spoke 分进程，`seccomp` 限制 syscall，`setrlimit` 限制 CPU/内存/文件（p.17）。
- 网络 egress 限制到 App 的 eTLD+1，数据外发需用户许可（p.17; p.18）。
- ISC 的结构化消息格式、hub 中转、operator-only 通道、临时 `Spoke-sID`、格式校验（p.8–9）。
- 权限模型：permanent/session/one-time，权限记录与警告（p.18; Fig.4）。
- **没有** TLS、签名、MAC、加密存储、密钥管理、OAuth/OIDC、TEE、零知识证明等密码机制。论文未讨论密钥生命周期、撤销令牌、跨主机认证。

**个人推断的工程接口（明确标为研究推断）**：
- **App 清单/功能格式签名**：上架时由商店对功能描述、请求/响应 schema 签名并在 hub 侧校验，可防元数据替换；但论文假设“上架前已审查”（p.8 footnote 5），未做签名。
- **Hub 签发的 ISC 能力令牌**：把 `Spoke-sID` 升级为绑定 `(session, caller, callee, functionality, expiry)` 的 MAC/签名令牌，支持衰减与撤销；可在保持 hub 中介的同时，让多主机部署下的消息可认证。需要测量签名/MAC 对延迟的影响（当前多 App 协作已约 +89%，见 p.14）。
- **认证 IPC**：若 hub 与 spoke 跨主机/跨容器，进程边界不再提供安全，需 mTLS 或基于密钥的通道认证；这是应用密码工程的直接切入点。
- **审计日志完整性**：对 hub 记录的跨 App 消息做哈希链/签名，支持事后取证与用户可验证；但必须与“语义是否正确”区分。
- **权限凭证化**：把用户授权做成可验证凭证（如限定 App、数据类别、时长、是否可转授），解决多 App 组合下的最小权限与撤销；与 OAuth scope/Token 的思想相近，但需要针对 Agent 间转发重新定义不扩张性。
- **伪交叉警示**：仅把现有 OAuth 流程包进 App 选择、仅给执行日志签名、仅用 ZK 证明“某一步 LLM 运行过”，都不能解决本文真正的问题——跨 App 信息流是否被授权、App 行为是否与描述一致、用户是否理解风险。论文的隔离与权限是必要背景，但把它们直接称为“密码学创新”是夸大。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- **H1（IPC 认证缺口）**：在非同一信任域（多容器/多主机）部署时，ISOLATEGPT 的 `Spoke-sID` 与格式校验不能阻止能注入 IPC 的对手伪造/重放跨 spoke 请求；可构造中间人实验测量伪造成功率。当前论文只在单宿主、可信 OS 假设下评估（p.5, p.17）。
- **H2（能力令牌不扩张）**：将 ISC 消息替换为 hub 签发的、可衰减的 capability token，在保持功能正确率（Table II 口径）的同时，应能把“未授权跨 App 数据流”从依赖用户拒绝变为可验证拒绝；需定义并测试作用域不扩张与撤销一致性。
- **H3（警告疲劳）**：论文 7.6% 的 PA 与 100% WR 只在特定 benchmark 上测得（p.10）；在更接近真实的混合良性/恶意请求流中，用户对警告的拒绝率可能显著下降，从而使实际保护率低于论文隐含值。需用户研究验证，不能把 100% WR 当作保护率。
- **H4（功能等价边界）**：Table II 显示多 App 协作 steps 0.76、overall 0.95（两者相同），但只在 21 条 LangChain 查询上；在更长程、跨 5 个以上 App、含不可逆动作的任务上，“无功能损失”是否成立需扩展 benchmark 验证。
- **H5（隔离的 TCB 假设）**：若 hub planner 被 prompt injection 或记忆污染影响，其“计划交叉检查”与警告可能失效；可测试对 hub planner 的间接注入是否能把恶意跨 App 流标记为 benign。论文把 hub 视为可信但承认 LLM 仍可被注入（p.5），未做该实验。
- **H6（性能-密码开销）**：在多 App 协作已约 +89% 的冷启动开销上，再加入每消息签名/MAC/令牌验证，是否会突破论文的 30% 阈值（75.73% 查询）需要实测；这是应用密码工程可行性的关键数据。
- 以上均为待验证假设；本文没有提供这些实验，也不能据此判断领域无人做过。
