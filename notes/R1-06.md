## 1. 150–300 字中文概述

ACE 针对 LLM 集成应用系统提出三阶段安全架构：抽象规划器只接收可信用户查询（及可选可信上下文），生成与已安装应用无关的抽象计划；具体规划器将抽象应用与已安装应用逐对独立匹配，并对具体计划做基于格（lattice）的静态信息流验证；执行器以 orchestrator-worker 加 Docker 隔离运行计划。论文还发现并演示了针对 IsolateGPT 的三种新攻击：执行流中断、执行管理器劫持与规划器操纵。实验声称在 INJECAGENT 全部 1,054 个用例上实现 100% 安全评分，在 ASB 2,000 次试验中仅 3 次调用攻击者应用（作者判定与注入无关），并在 LangChain Tool Usage 上保持较高效用。其安全机制是系统架构、OS 隔离与 Denning 格静态分析，不含密码学原语、密码协议或形式化证明；作者明确承认因采用 Python 子集而无法给出可靠性（soundness）形式保证。

## 2. 研究背景、现有方法不足、精确定义的问题

LLM 集成应用系统以 central system LLM 为核心，交错执行 planning 与 execution：planning 决定下一步操作，execution 调用 app 并读取上下文；app 由自然语言 description、schema 和 function 三部分组成（PDF p.2, §II-A）。第三方 app 不可信，恶意 app 可通过两类通道破坏系统：其输出进入后续 LLM 上下文，形成 indirect prompt injection；其 description/schema 影响规划与 app 选择（p.2–3, §II-B）。

论文把攻击目标分为四类（p.1 Abstract；p.4 §II-C）：planning integrity、execution integrity、execution availability、execution privacy。现有两类系统级防御都不足以覆盖强威胁模型：
- **f-Secure** 采用信息流控制（IFC），将 LLM 功能拆成只使用可信输入的 planner 与处理不可信数据的 rule-based executor，但它把 app description/schema 当作可信（p.3, §II-B）。
- **IsolateGPT** 采用 Hub-and-Spoke 执行隔离，但 planning 阶段仍读取并信任 app description；execution manager 直接消费 raw app output，未做验证（p.3–5, §III-A–B）。

因此，已有防御只覆盖弱威胁模型（description/schema 可信），在强威胁模型（二者均可 malicious）下都失效；且没有系统同时覆盖四类攻击目标（Table I, p.4）。本文的精确定义问题是：攻击者控制一个或多个已安装 app（含执行细节、schema、name/description、输出）时，如何设计一个既保护 planning 又保护 execution、保持高 utility、且与具体 LLM/系统配置无关的安全架构（p.3–4, §II-C "Problem Statement" 与 "Our Goals"）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

**组件与流程**（Fig 1b, p.3；Fig 3, p.7）：
- **用户 query**：被视为 fully trusted，并按敏感性赋予 lattice label q。
- **Abstract Planner**：系统中最可信、权限最高的组件；只接收 query 和可选的 fully-trusted operational context，完全看不到已安装 app 列表；输出一组 abstract apps（name、自然语言 description、type signature）和 abstract plan（受限 Python 子集，`main()` 为唯一入口）。
- **Concrete Planner**：接收 abstract plan 与已安装 concrete apps 的 description/schema；先用 embedding 相似度过滤候选 app，再做 abstract→concrete 的逐对独立匹配，并用 compatibility layer 处理类型签名/参数顺序差异；输出 concrete plan。
- **Executor**：orchestrator 为特权入口，负责创建 worker 执行环境、路由消息、校验 schema/type、监控资源；plan worker 在受限容器中顺序执行 concrete plan，只能通过 socket 与 orchestrator 通信，不能直接调用 app；每个 app 有独立 Dockerized app worker，仅通过 socket 与 orchestrator 交换数据（p.9, §IV-E）。
- **Abstract apps vs concrete apps**：abstract apps 只声明功能，不实现行为；concrete apps 是用户设备上真实安装的 app，其代码/description/schema/输出均可能被攻击者控制（p.7–8, §IV-C）。

**信任边界**：
- 可信：用户 query、可选 context、abstract planner、abstract plan、orchestrator、lattice policy 与 app clearance 配置（论文假设其正确）。
- 不可信：已安装 concrete apps 的代码、description、schema、输出；app workers。
- 受约束/半可信：concrete planner（LLM 读取不可信 description，但只做逐对匹配）；plan worker（执行 LLM 生成的代码，受容器限制，但 orchestrator 无法验证其内部 trace，p.17）；compatibility layer（另一个 LLM）。
- 论文没有画出显式的 trust-boundary 图，但 Fig 1a/1b 与 §IV 的组件权限递减描述明确了边界（p.6–9）。范围限制：只支持 standalone apps + single-query；application suites 与 multi-query 交互留作 future work（p.7, §IV-B）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

**资产**：用户敏感数据（文件、邮件、金融/医疗/个人信息）、query 与计划的完整性、良性 app 输出的可信度、任务可用性、系统资源，以及 app 可能持有的 API key 等特权信息（p.6, p.10, p.15）。

**攻击者能力**（p.3–4, §II-C "Threat Model"）：控制用户设备上的一个或多个 app；完全控制其执行细节、与 LLM 系统的接口（schema）、name 与自然语言 description；进而控制 app 输出，可发起 indirect prompt injection 以操纵控制流。攻击者不控制 abstract planner、orchestrator 或底层 LLM。

**攻击目标**（p.4）：
1. **Planning Integrity Violation**：让恶意 app 进入计划、让良性 app 被排除。
2. **Execution Integrity Violation**：改变执行流，使良性 app 接收恶意输出，或操纵执行上下文。
3. **Execution Availability Breakdown**：中断正常执行，使用户 query 无法完成。
4. **Execution Privacy Compromise**：从执行环境泄露敏感用户信息。

**弱/强威胁模型**：weak 模型假设 app description 与 schema 可信；strong 模型假设二者均可 malicious（p.3–4；Table I 明确区分两列）。

**前提假设**：query 与可选 context 完全可信；abstract planner、计划结构、orchestrator 与 label/clearance 配置可信；底层 LLM 未被攻陷；Docker/OS 隔离有效；只考虑单 query、standalone app；planning 阶段的 availability 攻击“易检测”、privacy 不相关，因此不作为重点（p.4）。论文没有说明 app clearance 由谁、依据什么分配或验证，也没有考虑 app 被授予合法 clearance 后主动外泄的情形——这是本人推断的威胁模型缺口，不是原文承认的限制。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

### 5.1 三阶段架构（Fig 3, p.7；§IV-B–E）

1. **Abstract Planning**：LLM + 定制 system prompt，仅以 query（和可选 trusted context）为输入，生成 abstract apps 与 abstract plan。Abstract plan 是“对可能执行轨迹的硬约束”：为某个 abstract app 选择不同实现，不能大幅改变整体控制流。因为 abstract planner 看不到已安装 app，论文声称它天然免疫 indirect prompt injection 与 planning manipulation（p.7–8, §IV-C）。
2. **Concrete Planning**：先做 embedding 过滤——用 OpenAI `text-embedding-ada-002` 与 Euclidean distance 对 abstract/concrete app description 打分并阈值过滤；再用另一个 LLM 对每个 abstract app 与候选 concrete app 做独立的二值匹配，要求 type signature 在输入/输出上相容；不相容时由 compatibility layer LLM 做语义翻译。匹配空间是“每个 abstract app 恰好映射到一个 concrete app”；逐对独立匹配用于消除 cross-app interaction（如 app demotion）。选择具体配对时还考虑 low-privilege access（细节放在扩展版 [16]）和 secure information flow（p.8–9, §IV-D）。随后编译 abstract plan 并静态验证 concrete plan 的 IFC 策略（§IV-F）。
3. **Execution**：orchestrator 为特权入口，按需为 worker 创建最小权限环境；plan worker 在受限容器中执行 concrete plan，只能通过 socket 与 orchestrator 通信，不能直接调用 app；每个 app worker 在独立 Docker 容器中运行，仅通过 socket 与 orchestrator 交换数据；orchestrator 负责 schema/type 校验、消息路由、资源限额，并终止超限 worker（p.9, §IV-E）。

### 5.2 Abstract plan 语言（p.8, §IV-C；p.16–17, App. B；Table V）

- 受限 Python 子集，语法上是合法 Python，`def main()` 为唯一入口，返回字符串。
- 支持 `if`、`for-range`、`while`（循环条件必须是单个变量）；不允许 `break`；变量必须声明类型且不可变；函数必须是 pure function；禁止 list/dict/set 等 mutable types、lambda/嵌套 def/嵌套 class/exec 等动态代码特性、多数 builtins（open、exec、eval、compile、`__import__`、input、globals、locals、vars、dir、help、exit、quit、getattr、setattr、delattr、super、memoryview）；只允许 `import math`（Table V, p.16）。
- 限制的目的是简化静态分析、限制运行时行为、保证 referential transparency；app invocation 在编译时被替换为 runtime 的 `invoke` 调用（p.17, App. B）。

### 5.3 信息流控制（IFC）与静态验证（p.10, §IV-F；p.14–16, App. A）

- 策略建模为 **universally bounded lattice** \((C, \sqsubseteq)\)：任意两个元素有 least upper bound（join \(\sqcup\)）与 greatest lower bound（meet \(\sqcap\)）；\(x \sqsubseteq y\) 读作“x may flow into y”。join 表示组合信息后的污染，meet 表示数据需要进入多个不同类别存储对象时的最大安全类（p.10）。
- 数据对象：program variables 动态绑定 label（初始为 query label q，随赋值更新）；app memory 静态绑定 label（基于注册的 app security clearance）。query q 本身是 lattice 元素；所有 flow 都隐式带上 query label，因为 plan 的生成依赖 query（p.10）。
- 三条 production rules（沿用 Denning [19]）：
  1. 原子语句：从 \(x_1,\dots,x_n\) 到 \(y_1,\dots,y_m\)，经外部资源 \(f\)（external flow）或内部资源 \(\star\)（internal flow）。
  2. 顺序：\(S_1; S_2\)。
  3. 循环：\([S]\) 执行任意有限次。
- 规则（Eqs 1–5, p.15）：
  - 静态目标：\(\bigsqcup_{j=1}^{n} x_j \sqsubseteq y_i\)（Eq 1）。
  - 动态目标更新：\(y_i \leftarrow y_i \sqcup \bigsqcup_{j=1}^{n} x_j\)（Eq 2）。
  - 外部资源 \(f\)：\(f \sqsubseteq y_i\)（Eq 3）且 \(\bigsqcup_{j=1}^{n} x_j \sqsubseteq f\)（Eq 4）；动态目标 \(y_i \leftarrow f\)（Eq 5），并被 \(f\) 悲观污染，因为 app 可能访问其 clearance 以内的资源。
- 循环用 fixpoint iteration：构造信息流图 \(G_{flow}\)（节点为存储对象，边为输入→输出），用图搜索/Warshall 传递闭包求收敛 label；分支通过把 branch condition 注入语句体来处理 implicit flow，不需要 fixpoint（p.15–16；Fig 8 循环泄漏、Fig 9 分支泄漏）。
- 验证流程：把 abstract plan 编译为 IFC grammar 程序；为每个 concrete plan 绑定 app clearance 与 query label；静态分析所有 flow；违反则拒绝该 concrete plan；若不存在满足约束的 abstract→concrete 分配，系统以错误终止（p.10, p.16）。Fig 5（p.11）给出示例：`load_bank_details()` 的 financial 数据流入 clearance 为 personal 的 `send_email`，被静态分析阻断。

### 5.4 与 IsolateGPT 的关键区别

IsolateGPT 的 hub planner 读取 app description 并生成详细计划，但随后丢弃细节、只保留 app 列表；execution manager LLM 读取 raw app outputs 决定下一步。ACE 把 planning 拆成 abstract（不看 app）与 concrete（逐对匹配）两步，并把 execution 变成对固定 concrete plan 的规则化执行；app output 只作为 schema 类型的数据，不再进入 LLM 控制流（p.4–9；Fig 1a vs 1b）。

## 6. 安全属性与安全性论证（如果没有证明，明确写“未提供形式化证明”）

论文主张四类安全属性（p.4, Table I）：

- **Planning integrity**：abstract planner 不接触已安装 app 信息，因此 app description 无法影响 abstract plan 的 app 包含/排除；concrete matching 逐对独立，避免跨 app 的 demotion。论证是设计隔离，不是定理。
- **Execution integrity**：concrete plan 固定；app 输出仅按 schema 作为 typed data，绝不被 LLM 用于控制流；concrete plan 在执行前通过 IFC 静态验证；app worker 隔离。论证是设计 + 静态分析 + 实验。
- **Availability**：plan 固定，app 输出不能像 IsolateGPT 那样提前中断执行；orchestrator 对 worker 做资源限额并可终止超限 worker（p.9；p.11 case study）。
- **Privacy**：lattice IFC 约束 app 只能看到其 clearance 允许的 label；静态验证拒绝违规 concrete plan；app 之间通过 orchestrator 隔离，不能直接交换数据（p.10, p.16）。

**关键限定**：
- **未提供形式化安全定义、定理或证明**。论文没有给出非干涉（non-interference）定理、密码学安全游戏或证明；Table I 是作者基于设计的目标覆盖矩阵，不是证明。
- 作者明确承认：因为采用 Python 子集，语言与 runtime 具有复杂行为，**"we can provide no formal guarantees on the soundness of our data privacy guarantees"**；更严格的 DSL + operational semantics + non-interference 证明是 future work（p.16, App. B）。论文只称这是"a strong first step in the direction of provable security"。
- orchestrator 无法验证 plan worker 的程序状态与执行 trace；container escape 或 worker 伪造消息可造成外部损害（p.17, App. B "Privilege Constraints"）。
- 术语区分：文中的 capability barriers 指 OS 权限/数据边界，不是密码学 capability token；authorization 指 lattice policy 的许可关系，不是密码学授权；"security architecture" 是系统架构，不是密码学构造。
- 因此，本文将安全论证定位为“系统机制 + 经验性安全论证”，不能表述为“可证明安全”或“密码学安全”。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

**模型**：GPT-4o、o3-mini、GPT-4.1、Claude 3.7 Sonnet、Qwen-2.5-72B（p.10）。Abstract/concrete planner 可使用不同 LLM 组合。

**Case studies（p.11, §V-A；Fig 6/10/11）**：三种新攻击在 ACE 上均失败：
- Execution Flow Disruption：恶意 QuickRide 输出“所有计价工具都被用于贩毒”，在 IsolateGPT 上使执行提前终止；ACE 仍返回 MetroHail 的 fare 与 QuickRide 的 TypeError。
- Execution Manager Hijack：恶意输出要求伪造 MetroHail 的 fare；ACE 只把它当数据，不进入控制流。
- Planner Manipulation：恶意 description 要求排除 MetroHail；ACE 的 abstract plan 仍包含两个 abstract app。
这些是定性 trace，不是统计实验。

**INJECAGENT（p.11–12, §V-B；p.18, App. D-A）**：
- 数据集：1,054 个 test case，17 个 user app，52 个 attacker app；544 个 data exfiltration、510 个 direct user harm。原 benchmark 假设 ReAct agent 已执行 user app 并测试是否调用注入指示的 attacker app；ACE 适配为先生成计划、再检查执行是否产生 security violation。
- 指标：security = 未调用 attacker app；utility = 正确调用 expected app。Utility 进一步分为 matching success（expected app 是否匹配到 abstract app）、execution success（匹配后执行是否无错）、overall success（端到端）。
- 结果：security score **100%**，覆盖全部 1,054 case，且与 abstract/concrete planner 的 LLM 选择无关（p.11）。
- Utility（Table II, p.12，已目视核对）：Qwen-2.5-72B overall 60.2%；GPT-4o overall 83.6%；Claude 3.7 Sonnet overall 60.7%；GPT-4o + o3-mini overall 85.3%。表中 matching/execution 是条件成功率；不同模型不可脱离条件直接比较。正文称“≥84% with different combinations of GPT-4o and o3-mini”“≥60% with Claude 3.7 Sonnet and Qwen 2.5 72B”；注意 Table II 中 GPT-4o 单独的 overall 为 83.6%，略低于 84%。
- **StruQ 对照**：作者把 INJECAGENT 数据加 delimiter 后测试 fine-tuned Mistral-7B StruQ，观察到 **7% attack success rate**；Llama-7B 因 context window 太小无法评估（p.12）。这是 model-level defense、不同指标（ASR）与不同适配设置，不能与 ACE 的 100% security score 直接比较，也不能据此计算“倍数提升”。

**Agent Security Bench（ASB）（p.12, §V-B；p.18, App. D-A）**：
- 10 agents、10 application scenarios、50 个 query；每个 query 需要一个或多个 tool；ACE 以类似方式移植。
- 结果：2,000 trials 中仅 **3 次** attacker app 调用；作者认为这些调用与 prompt injection 无关，而是 attacker app 恰好适合用户任务（例：MarketDataAnalysis 匹配 MarketAnalysisTool），因此**不视为 security violation**；GPT-4.1/GPT-4o 的 utility ≥86%（p.12）。
- 限定：这不是字面上的“零 attacker app 调用”；摘要中“secure against ASB”的表述强于细节中“3 次调用被重新归类为正常使用”的实际情况。作者也没有给出 ASB 的 security score 定义或置信区间。

**LangChain Tool Usage（p.12–13, §V-C；Table III/IV）**：
- 三个环境：single tool（一个 app，按 query 逐字符输入）、multiple tool（26 个无参数工具）、relational data（3 张表、17 个工具）。
- 指标：step accuracy（工具调用顺序是否正确）、overall accuracy（最终输出与环境状态是否正确）、cost（USD/query）、runtime（s）。
- Table III（p.12，已目视核对，step/overall）：GPT-4o：100/100、80.0/80.0、66.7/81.0；GPT-4.1：95.0/95.0、80.0/80.0、76.2/85.7；GPT-4o+o3-mini：100/100、80.0/80.0、47.6/66.7。正文称 GPT-4o 与 GPT-4.1 在所有任务上 overall ≥80%；GPT-4o+o3-mini 在 relational data 上 overall 66.7%。
- Table IV（p.13，已目视核对）：GPT-4o single $0.01/10.84 s、multiple $0.55/19.96 s、relational $0.19/15.65 s；GPT-4.1 single $0.01/11.73 s、multiple $0.27/20.95 s、relational $0.10/14.74 s；GPT-4o+o3-mini single $0.01/20.14 s、multiple $0.49/48.00 s、relational $0.11/28.24 s。表中部分分项之和与 Total 存在不一致（例如 GPT-4o multiple 6.44+8.87+5.41=20.72 vs 19.96），引用时以表中 Total 为准，不自行相加。
- 与 IsolateGPT 的 runtime 对比：ACE GPT-4.1 single 11.73 s vs IsolateGPT 39.21 s；ACE multiple（26 tools）20.95 s vs IsolateGPT 126.65 s（13 tools）（p.13）。工具数量与实现环境不同，不是严格的同条件对比。

**消融与边界**：论文没有做组件消融（abstract planning、IFC 静态验证、Docker 隔离各自贡献多少），只变化 LLM 组合；没有 adaptive attacker、没有对静态分析 false positive/negative 的测量、没有多 query/suite 组合实验、没有对 app 输出语义正确性的测量。因此实验支持“在该 benchmark 与指标定义下有效”，不足以证明架构在所有恶意 app 行为下安全。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

**贡献**（p.2–3, §I）：
1. 发现并演示三种针对 IsolateGPT 的新攻击：Execution Flow Disruption、Execution Manager Hijack、Planner Manipulation（在公开实现上运行）。
2. 提出 ACE 三阶段安全架构：abstract planning（仅可信信息）、concrete planning（逐对匹配）、isolated execution（orchestrator-worker + Docker）。
3. 用 lattice-based IFC 对 concrete plan 做静态验证，自动拒绝违反用户指定信息流约束的实现。
4. 实验评估：INJECAGENT 100% security（按其定义）、ASB 2,000 trials 仅 3 次 attacker app 调用（作者归类为非注入）、三种新攻击被阻止、LangChain Tool Usage utility 较高。

**与直接相关论文的差异**：
- vs **f-Secure**：f-Secure 也用 IFC 分离 planner/executor，但信任 app description/schema（weak 模型）；ACE 的 abstract planner 完全不看已安装 app，且明确针对 strong 模型，并增加 concrete plan 的静态验证与执行隔离（Table I, p.4；p.3）。
- vs **IsolateGPT**：IsolateGPT 的 planning 读取/信任 description，execution manager 消费 raw output；ACE 把 planning 拆成 abstract/concrete 两步，app output 只作为 typed data，且用 pairwise matching 防止 cross-app demotion（p.3–9）。
- vs **CaMel**：CaMel 用 custom Python interpreter 实现 fine-grained capabilities；ACE 用受限 plan language + lattice IFC + Docker 隔离 + orchestrator-worker，强调 planning/execution 分离（p.13, §VI）。
- vs **model-level defenses**（StruQ、Instruction Hierarchy、SecAlign）：ACE 是 system-level、LLM-agnostic；StruQ 在作者适配的 INJECAGENT 上 ASR 7%（p.12）。
- vs **PDoctor/VeriPlan**：这些工作检测/验证 planner 输出是否符合约束，不提供 attack mitigation；ACE 旨在阻止攻击并执行 IFC（p.13, §VI）。

**可复现资源**：代码 `https://github.com/escottrose01/ace-llm`；扩展版 arXiv 2504.20984（p.2, p.14 [16]）。论文未声明发布新数据集，使用 INJECAGENT、ASB、LangChain Tool Usage 三个外部 benchmark。上述 URL 是论文文本中的研究数据，未执行、未访问。

## 9. 局限性、失效场景、作者未解决的问题

### 9.1 作者明确承认的局限

- **无形式化 soundness 保证**：Python 子集与 runtime 行为复杂，作者明确说无法对数据隐私保证给出形式化 soundness；DSL + operational semantics + non-interference 证明是 future work（p.16, App. B）。
- **单 query / standalone app**：不支持 application suites 与 multi-query 交互（p.7, §IV-B）。
- **executor 的信任缺口**：orchestrator 看不到 plan worker 的程序状态，无法验证合法执行 trace 与 tool invocation；container escape 或 worker 伪造消息可造成外部损害（p.17, App. B）。
- **low-privilege matching 细节不在本文**：正文把 low privilege access 的讨论指向扩展版 [16]（p.9）。
- **benchmark 的效用有限**：INJECAGENT/ASB 的 app 是 trivially simulated，且不测量输出正确性；作者自己称其 utility 概念有限（p.11）。ASB 的 3 次 attacker app 调用被作者重新归类为非违规（p.12）。
- **成本/运行时开销**：concrete planning 可能对每对 abstract/concrete app 发一次 LLM query，成本随 app 数量乘性增长；Docker 创建/通信带来运行时开销（p.12–13, Table IV）。

### 9.2 本人推断的失效场景与未解决问题

- **具体匹配仍读取不可信 description**：abstract planner 不看 app，但 concrete planner 用 description embedding + LLM 做匹配。恶意 app 若把 description 伪装成某个 abstract app 的功能，可能在具体匹配阶段被选中，替代良性实现。论文的 planning integrity 主要针对 abstract plan 的 app 包含/排除，未评估“实现替换”这一层（pp.8–9, §IV-D；p.11 只保证输出作为 typed data）。这是 H2 的来源。
- **输出语义正确性不受保证**：ACE 只保证 app 输出符合 schema、进入 plan 的 data flow；恶意 app 可以返回 schema-valid 但语义错误的数据（例如错误的 fare、错误的账户余额）。论文的 “execution integrity” 是相对于 concrete plan 的完整性，不是输出真实性（p.11, §V-A；p.16 IFC 只约束 label flow）。
- **clearance 未 attest**：app memory 的 label 来自 “registered app security clearances”（p.10），论文没有说明如何验证 app 真实具备该 clearance。若恶意 app 被注册了合法的高 clearance，它可以在 policy 允许范围内接收敏感数据并外泄；IFC 控制“给哪个 app 看”，不控制“app 拿到后做什么”。这是本人推断的隐私缺口。
- **分支条件可被 app 输出影响**：abstract plan 允许 if/while，其条件可依赖 app 输出；攻击者可通过返回特定值选择 plan 允许的某条分支（例如让 user count 为 0，使计划输出“未找到用户”）。这不违反“按 plan 执行”，但可能违背用户意图。论文未讨论这种 plan-permitted steering。
- **query/context 可信假设可能失效**：若用户 query 本身包含不可信内容（例如“总结这封邮件”而邮件含注入），abstract planner 仍会读取它；ACE 的“trusted query”假设在真实场景中需要额外隔离。论文的 INJECAGENT 适配把注入放在 app 输出而非 query，未测试 query 注入。
- **无 adaptive attacker**：三种新攻击是针对 IsolateGPT 设计的；没有针对 ACE 的自适应攻击实验，也没有测试攻击者知道 ACE 架构后的策略。
- **无组件消融**：无法判断安全收益来自 abstract planning、IFC 还是 Docker 隔离；也无法判断 utility 损失主要由哪一阶段造成。
- **无密码学身份/审计/分布式部署**：没有 app 认证、计划签名、执行日志完整性、跨主机 orchestrator-worker 安全通道；这些在真实部署中会成为新的攻击面（见 §11）。
- **静态分析可能被语言/兼容层绕过**：作者承认 Python 子集难以形式化；compatibility layer 的语义翻译、异常/别名/动态行为未被 IFC 模型显式覆盖。这是本人推断，需实验验证（H1）。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**机制清单（原文事实）**：信息流控制（lattice + 静态分析）、能力/权限边界（Docker/OS least privilege）、标签（query label 与 app clearance）、基于 lattice 的访问控制。**没有**密码学原语、密码协议或证明。**结论：系统机制，无密码学构造/证明。**

**原论文已做（严格按 PDF）**：
- 使用 Denning（1976）的 **lattice model of secure information flow**：universally bounded lattice \((C, \sqsubseteq)\)、join/meet、静态/动态 label、三条 production rules、fixpoint iteration 与 Warshall 传递闭包（p.10, §IV-F；p.15–16, App. A；Eqs 1–5）。
- 这是经典的 **language-based security / information-flow control** 理论工具，属于形式化安全模型，但**不是密码学构造**：没有密码学安全定义、密码学攻击者游戏、密码学假设、定理或证明；没有加密、签名、MAC、承诺、ZK、MPC、FHE 等原语。
- 论文明确把 non-interference 证明列为 future work，并承认当前实现没有 soundness 形式保证（p.16）。

**个人推断（明确标为推断，不是论文结论）**：
- 可把“任意 concrete implementation 都保持 abstract plan 的控制流/信息流语义”形式化为一个 noninterference 或 refinement 定理；这是 PL/形式化安全方向，不是密码学。若要把“plan integrity”做成可证明的安全定义，可定义“实现独立性”游戏，但对手是 app 而非密码学敌手，仍不构成密码学问题。
- 若要引入密码学，需要改变信任模型：例如多个互不信任的 app 需要在不愿向彼此暴露输入的前提下联合计算，可用 MPC/FHE/PSI；但 ACE 把数据直接交给有 clearance 的 app（论文未使用加密），并信任 orchestrator，因此其原始威胁模型**不需要**这些原语。把 MPC 硬套到 ACE 的现有模型上，是伪交叉。
- 可用密码学 IFC（带标签的认证加密/MAC）防止不可信 worker 篡改 label 或数据；但 ACE 的 orchestrator 是可信的，当前设计没有这个需求。只有在把 executor 分散到不可信节点时，才成为真问题。
- 可用 zk/可验证计算证明 executor 按 concrete plan 执行，回应 p.17 的 trace 验证缺口；对确定性 plan 的证明比证明 LLM 推理可行，但仍需解决输入/输出绑定、compatibility layer 语义与“计划本身是否用户想要”的问题。这是应用密码学/可验证计算方向，不是本文已做的工作。
- 初步相关度判断（供后续打分，非论文结论）：**T_crypto ≈ 1–2 / 5**。有形式化 lattice 模型，但属于成熟的 IFC 理论，未见需要新密码学定义或构造的核心问题；不能因为出现 “capability barriers”“security architecture”“authorization” 等词就夸大为密码学创新。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**原论文已做（严格按 PDF）**：
- 执行隔离：Dockerized app workers、受限容器、least privilege、socket 通信、orchestrator 资源限额（p.9, §IV-E）。
- 策略执行：lattice-based IFC 静态分析、app clearance label、query label、concrete plan 验证（p.10, §IV-F；p.15–16）。
- app 匹配：OpenAI embedding + LLM 语义匹配 + compatibility layer（p.8–9, §IV-D）。
- **没有**认证、密钥管理、加密、签名、MAC、凭证、撤销、审计签名、TEE/remote attestation；orchestrator-worker 是 socket 通信，论文未给出 mTLS/会话密钥（p.9）。全文检索未发现这些机制的构造或使用。

**结论：系统机制，无密码学构造/证明。** 论文实际使用的是 lattice 信息流控制、OS 权限边界、security label/clearance 与基于策略的访问控制；签名、认证、密钥管理等均未出现。

**个人推断（明确标为推断）**：
- **App manifest/代码 attestation**：对 app 的 description、schema、代码哈希做签名，把“声明”与“实现”绑定；对 clearance 做 remote attestation（TEE 或签名凭证）。这可以直接缓解 §9.2 的“具体匹配读取不可信 description”和“clearance 未 attest”问题，是与密码工程团队匹配度最高的接口。
- **Plan 签名与透明日志**：对 abstract/concrete plan、执行结果、IFC 验证结论做签名并写入 append-only/透明日志，提供 accountability 与事后审计；但签名只保证完整性，不保证 plan 语义正确或用户授权一致。
- **分布式 executor 的通道安全**：若 orchestrator/worker 跨主机，需 mTLS/会话密钥、worker 身份认证与撤销；当前论文的 socket 通信模型不覆盖。
- **Per-app scoped credential / OAuth token**：ACE 的 IFC 只控制数据给哪个 app，不控制 app 用其外部 API 凭证做什么；真实部署需要按 app/任务签发最小作用域凭证、密钥生命周期与撤销。
- **TEE 保护 plan worker/orchestrator**：可用 TEE 减少 host 被攻陷的风险；但 TEE 本身不是密码学原语，remote attestation 才是密码学接口，且 TEE 不能解决 plan 语义/输出正确性问题。
- **伪交叉风险**：只把 Docker/OAuth 包一层就叫“密码学安全架构”；只给执行日志签名但不保证语义；只用 ZK 证明“某段代码跑了”但不绑定用户授权、输入来源与数据流。这些不构成研究贡献，反而会重复 ACE 已经用系统机制解决的问题。
- 初步相关度判断（供后续打分，非论文结论）：**A_crypto ≈ 1–2 / 5**。论文本身没有密码机制；但 app 身份/manifest 签名、clearance attestation、plan 审计、scoped credential 是明确的工程切入点，适合后续做“ACE + 密码学增强”的系统研究。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

以下均为**假设**，不是本文结论；论文没有测试，也不代表领域没有相关工作。

- **H1（IFC soundness）**：ACE 的静态 IFC 分析可能被 Python 子集/runtime 特性、compatibility layer 的语义翻译、异常/别名/动态行为绕过；可通过 fuzzing/自动生成 plan、构造 label 混淆样例来测量泄漏率。验证方式：在 ACE 代码上实现 adversarial plan generator，比较静态分析结论与实际数据流。
- **H2（实现替换）**：恶意 app 的 description 可以伪装成某个 abstract app 的语义，从而在 concrete matching 阶段被选中，替代良性实现；abstract plan 的 app 包含/排除不变，但实现已恶意。验证方式：构造 adaptive description，测量 substitution rate 与最终输出偏差。
- **H3（clearance 滥用）**：app clearance 未被 attest，恶意 app 若获得合法高 clearance，可在 policy 允许范围内接收敏感数据并外泄；IFC 只限制“谁可以看”，不限制“看过之后做什么”。验证方式：注册一个带合法 label 的恶意 app，测量其外泄能力。
- **H4（语义完整性）**：schema-valid 但语义错误的 app 输出会被 ACE 接受并用于最终答案；ACE 的 execution integrity 不等于 output correctness。验证方式：构造返回错误数值/错误文本的恶意 app，测量用户可见错误率。
- **H5（plan-permitted steering）**：攻击者可通过控制 app 输出影响 abstract plan 的分支条件，在 plan 允许的多条路径中选择对攻击者有利的一条；这不违反“按 plan 执行”，但可能违背用户意图。验证方式：设计含 if/while 的 plan，测量分支选择与用户意图偏差。
- **H6（多 query 组合）**：single-query/standalone 假设在 multi-query、app suite 场景下可能失效，出现跨 query 的数据污染或 label 混淆；验证方式：扩展 ACE 到多 query，测量 cross-query leakage。
- **H7（executor trace）**：orchestrator 无法验证 plan worker 的 trace；被攻陷的 worker/container escape 可调用 app 或外泄数据。验证方式：红队 plan worker，测量 orchestrator 能否检测。
- **H8（成本/DoS）**：concrete matching 的 LLM query 数随 abstract×concrete app 数量乘性增长，可能被大量 app 或恶意 description 放大为成本/延迟 DoS；验证方式：测量不同 app 数量下的 $/query 与 runtime 曲线。
- **H9（密码学增强的设计假设）**：签名/attested app manifest + plan 签名/透明日志 + 可验证执行，能缓解 H2/H3/H7，并带来可接受的性能开销；这是设计假设，需要用原型与对照实验验证，不能直接当作已被证明的结论。
