## 1. 150–300 字中文概述

本文提出 structured queries：把 LLM 输入拆成 prompt（应用开发者指令）与 data（不可信用户数据）两个通道，由可信前端用保留特殊 token 编码，并递归过滤数据中可能伪造分隔符的字符串；再用 structured instruction tuning 把 base（非指令微调）LLM 训练成"只服从 prompt 通道指令"的模型。作者在 Llama-7B 与 Mistral-7B 上对 15 种以上手工与优化型注入攻击评估：手工攻击 ASR 降至 0%（个别单元格 1–2%），TAP 97%→9%、GCG 97%→58%（Llama），AlpacaEval 效用基本不变；但对 GCG 仍不鲁棒，且只适用于程序化 API 调用场景。全文无密码学原语、无形式化安全定义或证明；其"分离"是解析与训练层机制，不是密码学认证。

## 2. 研究背景、现有方法不足、精确定义的问题

**背景（p.2–4, §1–§2）。** 作者把 prompt injection 放进经典注入漏洞谱系：早期电话 phreaking 用 2600 Hz 音调在语音通道伪造控制信号；SQL injection 源于数据库 API 只接受一条混合 control（SQL 命令）与 data（匹配关键字）的字符串；XSS 源于 HTML 单字符串混合标记与内容；command injection 源于 shell 把命令与参数放在同一字符串。每一次的根治方案都不是"过滤坏字符"，而是**严格分离 control 与 data**，例如 SQL prepared statements 把模板与参数变成两个 API 参数（p.4）。作者据此论证：LLM 的 API 是 unsafe-by-design，因为应用必须把 prompt 与 data 拼成一个字符串；应当改成 safe-by-design 的两通道 API。

**现有方法的不足（p.4–5, §2）。** 作者逐一批评：
- 在 prompt 里加"小心注入"提醒、加分隔符、加 in-context 示例等 test-time 防御，对最强攻击无效；
- Jatmo 通过任务特定微调把 ASR 降到 <1%，但每个任务都要重新微调一个模型，不能提供通用 LLM；
- 与本文最接近的同期工作 BIPIA（Yi et al.）虽然在 prompt 与 data 之间放特殊分隔符并微调，但没有前端过滤器、训练注入样本来自不同分布、训练集不含 clean 样本、特殊 token 嵌入随机初始化，导致安全性和效用都较差（p.13–14, §5.5）；
- 指令层级（instruction hierarchy，Wallace et al.）在本文之后出现，可视为 StruQ 的多级推广（system / user / tool output），并已被 OpenAI 部署到 GPT-4o mini（p.5, §2）。

**精确定义的问题（p.2–3, p.8, §1/§4.1）。** 如何构建一个支持 structured query 的 LLM 系统，同时满足三条约束：
1. **Security**：系统在任何情况下都不得执行 data 部分的指令；
2. **Utility**：能力与现有 LLM 接近；
3. **Feasible training**：不能从零训练大模型，必须能基于现有 base LLM 以可接受成本实现。

这是一个"接口 + 训练目标"的联合设计问题，而不是分类器/检测器问题。

## 3. Agent 系统模型（组件、交互流程、信任边界）

**本文严格说不是 Agent 系统**，而是单轮、无状态、无工具调用的 LLM-integrated application（p.4, §2；p.14, §6 明确说只保护通过 API/library 调用的程序化应用）。这一点对 Agent 安全项目很关键：文中没有工具调用、MCP、记忆、多轮对话、RAG 或多 Agent 通信。

**组件（p.8–9, §4.2–§4.3, Fig.2）：**
1. **应用开发者 prompt**：可信的任务指令（如 "Paraphrase the texts."）。
2. **用户/数据源 data**：不可信文本（简历、邮件、网页内容等）。
3. **Secure Front-End**：按硬编码模板把两者编码为特殊格式；对 data 递归过滤保留分隔符字符串；不含任何模型推理。
4. **Structured Instruction-Tuned LLM**：在特殊格式上微调过的 base LLM，只响应 prompt 通道的指令。
5. **输出**：普通文本响应。

**交互流程（p.9, Fig.2 已目视核对）：**
`prompt + data → Front-End 编码 → [MARK][INST][COLN] <prompt> [MARK][INPT][COLN] <data> [MARK][RESP][COLN] → LLM → output`。
前端还会删除 data 中的 `##`、`[MARK]`、`[INST]`、`[INPT]`、`[RESP]`、`[COLN]`，并循环到不动点。

**信任边界。** 模型提供者可信（提供 base LLM）、应用开发者可信（写 prompt）、前端可信且正确实现；**data 通道完全不可信**。攻击者被限制在 data 通道内，不能改 prompt、不能改格式、不能改模型或前端（p.6, §3.1）。论文没有画显式 trust-boundary 图，但 Fig.2 的模块边界与 §3.1 的文字共同定义了边界。

**与 Agent 系统的距离（本人判断）。** Agent 的工具输出、网页、检索文档在结构上正对应本文的 data 通道，因此该思路对 indirect prompt injection 有迁移价值；但 Agent 场景中"哪一段是 prompt、哪一段是 data"往往由框架动态拼接，且工具 Schema、系统提示、记忆会进入上下文，本文的单轮两通道假设不再自然成立（见第 9、12 节）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

**受保护资产（p.2, p.5–6）：** 应用开发者指令的**优先级/完整性**（模型应执行 prompt 而非 data 中的隐藏指令）、应用任务输出的正确性、模型效用。论文不保护模型权重、训练数据、用户隐私数据本身，也不讨论数据机密性。

**攻击者目标：** 让 LLM 把 data 中的隐藏指令当作新指令执行，从而偏离开发者设定的任务（例如把"是否为推销邮件"判为 "no"，或输出 "Hacked!"）。

**攻击者能力（p.6, §3.1 "Threat model"）：**
- 可**任意修改 data 部分**；
- **不能修改 prompt**；
- 知道 prompt 与应用的格式化方式（Kerckhoffs 式假设），但不能改；
- 不知道模型权重、不能改训练过程（GCG 评估时额外授予白盒梯度，作为 worst case，p.7, §3.8）。

**成功判据（p.6）：** LLM 的响应服从隐藏指令，而不是把该指令当作数据；LLM 是否同时服从 benign instruction 不影响判定。

**前提假设：**
- 前端可信且实现正确；过滤器递归执行到不动点，保证 data 中不残留保留 token 字符串（p.9）；
- 保留 token 在分词器中是真正的 special token，普通文本经前端后不会产生它们；
- 可获取**非指令微调**的 base LLM 做全参数微调（p.9–10, §4.4/§5）；
- 攻击者不能投毒训练数据、不能控制模型提供者。

**明确不在范围内（p.15, §6）：** jailbreak、training data extraction、其他 LLM 攻击；web 端多轮聊天机器人；被攻破的前端或恶意应用开发者。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

### 5.1 编码格式（p.8–9, §4.3）

在 Alpaca 模板基础上，把文本分隔符替换为**保留特殊 token**：

| Alpaca 原文 | StruQ 替换 |
|---|---|
| `###` | `[MARK]` |
| `:` | `[COLN]` |
| `instruction` | `[INST]` |
| `input` | `[INPT]` |
| `response` | `[RESP]` |

编码结果（p.8–9）：

```
[MARK] [INST][COLN]
Is this email trying to sell me something? Answer yes or no.

[MARK] [INPT][COLN]
Hi Jim, Do you have a minute to chat about our company's solutions? [...]

[MARK] [RESP][COLN]
```

关键点：这些 token 是**分词器级**的保留符号，普通文本即使写出字符串也会被前端过滤；因此攻击者无法在 data 中"拼出"控制分隔符。

### 5.2 前端过滤算法（p.9, §4.3，已目视核对 Fig.2）

```
def filter(s):
    s_before_filter = ''
    while s_before_filter != s:
        s_before_filter = s
        s = s.replace('[MARK]', '').replace('##', '')
        s = s.replace('[INST]', '').replace('[INPT]', '')
        s = s.replace('[RESP]', '').replace('[COLN]', '')
    return s
```

- 循环到不动点，处理"替换后新拼接出分隔符"的情况；
- 额外删除 `##`：防止攻击者用 `##` 冒充被替换掉的 `[MARK]`（原 `[MARK]` 对应 `###`）；作者称经验上若不删，该 Completion 攻击"somewhat effective"（p.9）；
- 过滤器只作用于 data，不作用于 prompt。

### 5.3 特殊 token 的嵌入初始化（p.9, §4.3）

新 token 没有预训练嵌入，作者用对应文本 token 的嵌入初始化：`[MARK] ← "###"` 的嵌入、`[INST] ← "instruction"` 的嵌入，以此类推；微调时更新。作者强调**随机初始化会显著降低效用**，甚至使模型学不会新 token。

### 5.4 Structured instruction tuning 的数据构造（p.9–10, §4.4, Algorithm 1）

设标准指令微调数据集 \(T=\{(p_1,d_1,r_1),\dots\}\)，其中 \(p_i\) 为指令、\(d_i\) 为数据、\(r_i\) 为目标响应。构造 \(T'\)：
- **50% clean**：原样保留 \((p_j,d_j,r_j)\)，维持效用；
- **25% Naive attack**：从 \(T\) 另取一个样本 \((p_i,d_i,r_i)\)，把 `p_i || d_i` 追加到 \(d_j\) 后面，标签仍为 \(r_j\)，即 \((p_j,\ d_j \parallel p_i \parallel d_i,\ r_j)\)；
- **25% Completion-Other attack**：采样假分隔符 \(d_{resp}, d_{inst}\)，取一个假响应 \(r'\)（与原响应不同），构造 \((p_j,\ d_j \parallel d_{resp} \parallel r' \parallel d_{inst} \parallel p_i \parallel d_i,\ r_j)\)。

若 \(d_j\) 为空则跳过（因为无 data 通道时注入无意义）。关键设计：训练时注入的指令与 prompt 指令**来自同一分布**，迫使模型学习"看位置"而不是"看内容"；这与 BIPIA 用不同分布注入样本形成对比（p.14, §5.5）。该过程不需要梯度优化或人工设计恶意样本，作者称比 BIPIA 更便宜（p.10, §4.4）。

**原文内部不一致（本人核对）：** §4.4 正文说 25% 的 Naive 样本会"assign it with another random training sample \((p_i,d_i,r_i)\)"，即注入指令来自**另一个样本**；但 Algorithm 1 第 6 行写的是 `T′[j][data] += T[j][instruction] + T[j][data]`，即**同一样本**的指令与数据。Completion-Other 分支（第 13 行）同样使用 `T[j]`。这不改变 50/25/25 的比例，但使"注入指令与 prompt 同分布"的具体实现描述存在歧义；复现时应以代码为准。

### 5.5 训练（p.10, §5）

- 模型：Llama-7B、Mistral-7B；
- 数据：cleaned Alpaca 指令微调集；
- 从 **base（非 instruction-tuned）** 模型开始全参数微调；
- 3 个 epoch；学习率 Llama \(2\times10^{-5}\)、Mistral \(2.5\times10^{-6}\)；
- 官方 Alpaca 模型与评测代码。

## 6. 安全属性与安全性论证

**声称的属性：** data 通道中的指令不会被执行；攻击者无法伪造控制分隔符；即使使用近似的假分隔符，模型也因特殊 token 与训练而忽略之。

**论证结构（两部分，均为经验性）：**
1. **架构/解析层**：前端保证 data 中不出现保留 token 字符串，故 data 无法进入控制通道。这一部分在"前端正确实现 + 过滤器可靠"的前提下是确定的。
2. **学习层**：structured instruction tuning 让模型学会"只服从 prompt 位置上的指令"。这是**统计性、经验性**的，不是不变量；GCG/TAP 的残余成功率即反例。

**没有形式化证明。** 全文没有安全定义、定理、归约或证明；"immune"（p.2 的愿景表述）与后文"not yet fully secure"（p.3、p.14–15）并存，应理解为目标而非已证性质。论文也没有给出"过滤器 + 模型"组合的端到端保证；安全性完全由第 7 节的 ASR 测量支撑。

**两个逻辑缺口（本人推断）：**
- 过滤器的可靠性只对**字面字符串**成立；分词器边界、Unicode 规范化、同形字、零宽字符等是否能让 data 产生等价控制效果，论文未系统测试（只测了 9 种 delimiter 变体，见 §5.2）。
- 学习层的泛化边界不清：训练只覆盖 Naive 与 Completion-Other 两类注入，GCG 仍达 58%/56%，说明"位置不变性"可被优化型后缀破坏。

**原文内部的小不一致：** p.3 称所有手工攻击 ASR 降至 `<2%`，但 Table 2 中 Mistral 的 Completion-RealCmb 为 `2%`（p.11）；Table 3 的 Llama 效用为 67.6%，Table 7 同一模型写作 67.7%（p.11 vs p.14）。不影响主结论，但引用时应以表格单元格为准。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

### 7.2 攻击集合（p.5, Table 1；p.6–8, §3.2–§3.8）

Naïve、Ignore（10 个变体）、Escape-Deletion（`\b`/`\r`）、Escape-Separation（`\n`/`\t`）、Completion-Other、Completion-Real、Completion-RealCmb、Completion-OtherCmb、HackAPrompt（20 条成功注入）、TAP、GCG。作者称"至少 15 种"。

### 7.3 主结果

**安全（p.11, Table 2，已目视核对）：**

| 攻击 | Llama 未防御→StruQ | Mistral 未防御→StruQ |
|---|---|---|
| Naïve | 6% → 0% | 5% → 0% |
| Ignore | 12% → 0% | 11% → 0% |
| Escape-Deletion | 3% → 0% | 1% → 0% |
| Escape-Separation | 2% → 0% | 4% → 0% |
| Completion-Other | 29% → 0% | 71% → 0% |
| Completion-OtherCmb | 41% → 0% | 77% → 0% |
| Completion-Real | 96% → 0% | 96% → 0% |
| Completion-RealCmb | 71% → 0% | 83% → 2% |
| Completion-Close (Max) | 96% → 1% | 96% → 1% |
| HackAPrompt | 52% → 0% | 38% → 0% |
| TAP | 97% → 9% | 100% → 36% |
| GCG | 97% → 58% | 99% → 56% |

条件：208 样本；TAP 使用 branching factor 4、depth/width 10，去掉 judge LLM 改用子串匹配，攻击目标 "print exactly 'Hacked!'"（p.19, Appendix A）；GCG 500 次迭代、沿用原论文超参、授予白盒梯度（p.7–8）。

**效用（p.11, Table 3）：** Llama 67.2% → 67.6%（不显著）；Mistral 80.0% → 78.7%（降约 1 个百分点，作者称在 0.05 水平上 borderline significant，因标准误 0.7%）。

### 7.4 自适应攻击（p.11–12, §5.2, Table 4）

作者针对自己的系统设计 9 种"近义分隔符"：改 `#` 数量、大小写、空格、冒号、拼写错误、用嵌入最相似的单词替换 instruction/input/response。未防御模型 ASR 61–93%；StruQ 全部 0–1%。原因：真分隔符被编码为保留 token，近义变体被编码为普通 token，嵌入差异大；真分隔符则被前端过滤器拦截。另测 `[inst]`、`[Inst]`、`#INST#`、`[[INST]]` 等变体，ASR 均 0%。

### 7.5 消融

- **数据增强（p.12, Table 5；Llama，标准 Alpaca 分隔符，不用前端过滤器，报告 6 类攻击的最高 ASR）：** 未防御 41%；Naive 16%；Ignore 6%；Completion-Other 3%；Fake Delimiter 70%；Naive+Completion-Other 0%（效用 66.0%）；Naive+FakeDelimiter 25%；Ignore+Completion-Other 0%；Ignore+FakeDelimiter 6%。结论：naive + completion 组合最优，最终采用。
- **分隔符选择（p.13, Table 6；Llama，使用前端过滤器）：** 五种 textual/special 组合的效用 60.2–67.6%，最高 ASR 均为 1%；全 special 组合效用 67.6%、ASR 1%，且作者称经验上更安全（p.13）。

### 7.6 与基线比较

- **Test-time 防御（p.13, §5.5；Llama，Completion-Real，未防御 96%）：** Reminder in Prompt 83%；Reminder after Data 39%；Delimiter Isolation 85%；In-Context Demonstration 48%；StruQ 0%。
- **BIPIA（p.14, Table 7，已目视核对）：** BIPIA 用 Vicuna-7B-v1.5，StruQ 用 Llama-7b。BIPIA 效用从 53.9% 降到 26.0%；StruQ 67.2%→67.7%。在 BIPIA 自己的 231 个测试样本上 BIPIA 尚可（Completion-RealCmb 7%），但在 StruQ 测试集上 Ignore 达 54%；GCG 对 BIPIA 达 100%。注：BIPIA 样本过长，单张 80GB GPU 无法跑 GCG（Table 7 脚注）。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

**贡献：**
1. 提出 **structured queries** 这一通用接口思想：把 prompt 与 data 变成两个通道（p.2–3, §1）。
2. 给出可实现的 StruQ 系统：保留特殊 token 的分隔符 + 递归过滤前端 + structured instruction tuning（p.8–10, §4）。
3. 首次在**方法设计与评估**中同时考虑 Completion 攻击（p.11, §5.1）。
4. 首次把 TAP/GCG 改造成 prompt injection 攻击并评估防御，指出优化型注入是最强威胁（p.11, §5.1；p.15, §6）。
5. 在 Llama/Mistral 上给出手工攻击近零 ASR、效用基本无损的结果（p.11, Tables 2–3）。

**与直接相关工作的差异：**
- **BIPIA**（同期）：BIPIA 无前端过滤器、训练注入来自不同分布、无 clean 样本、随机初始化特殊 token 嵌入；StruQ 在四点上都不同，并给出更好的安全性与效用（p.13–14, §5.5）。
- **Jatmo**：任务特定微调，每个任务一个模型；StruQ 是通用模型（p.5）。
- **Instruction hierarchy**：本文之后出现，支持 system/user/tool 多级；StruQ 只有 prompt/data 两级（p.5）。
- 与传统注入防御（prepared statements）的关系：作者明确把它作为设计类比，而不是把 SQL 注入防御直接搬来（p.4）。

**可复现资源：** 作者称代码已公开（原文为超链接 "here"，文本抽取未给出 URL，不能臆造）；使用公开的 Llama-7B、Mistral-7B、cleaned Alpaca、AlpacaEval、AlpacaFarm 以及 BIPIA 官方代码/数据（p.10, p.14）。论文未给出代码仓库的具体地址。

## 9. 局限性、失效场景、作者未解决的问题

**作者明确承认：**
- 只保护**程序化 API/library** 调用的应用；不适用于面向终端用户的多轮开放式聊天机器人，因为用户不会愿意标注哪段是指令、哪段是数据（p.14, §6）。
- 不防 jailbreak、数据抽取或其他 LLM 攻击（p.15）。
- **不是完全安全**：GCG 仍有 58%（Llama）/56%（Mistral）ASR；作者称这是重要开放问题（p.14–15）。
- 训练只覆盖 task-agnostic 的手工 Naive+Completion 注入，不能完全泛化到任务特定、资源密集的优化型注入（p.11–12, §5.1）。
- 优化型攻击代价高：TAP 约 100 次查询，GCG 每样本约 256k 次查询，比其它攻击高 >100 倍 GPU 小时（p.15）。

**本人补充的失效场景（推断）：**
- **过滤器会静默修改用户数据**：删除 `##` 与保留 token 字符串。对 Markdown、代码、数学文本等 `##` 有语义的任务，可能造成数据损坏；论文只用 AlpacaEval 测效用，未测这类任务。
- **单轮假设**：多轮对话中，上一轮输出可能进入下一轮上下文，通道边界由谁维护、历史消息算 prompt 还是 data，论文未定义。
- **Agent 工具输出**：工具返回值、网页、检索片段在 Agent 中都是 data，但框架通常把工具 Schema 与系统提示也拼进同一上下文；本文的两通道模型没有覆盖"动态 Schema"和"工具调用结果回灌"。
- **对 base 模型的依赖**：商业 API 往往只暴露 instruction-tuned/chat 模型，无法从 base 开始微调；这限制了实际部署。
- **规模与语言**：只测 7B 模型、208 个英文样本，非英语只测了注入句翻译；结论不能外推到更大模型或多语言应用。
- **前端信任**：若前端被绕过、配置错误或未对所有入口（如流式拼接、模板注入）统一过滤，保证失效；论文未做前端实现的安全性分析。
- **过滤器只处理字面量**：Unicode 同形字、NFKC 规范化、零宽字符、tokenizer 边界拼接等未系统评估。
- **无形式化保证**：安全结论完全依赖经验 ASR，无法给出可组合的保证。

**作者提出的未来方向：** 用访问控制/限流检测迭代攻击者（引 Glukhov et al.）；在初始层对 prompt 与 data 之间的 attention 做 masking；把 system prompt 纳入三级结构（p.15, §6）。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**结论先行：本文是纯非密码学防御，无密码学原语、无密码学假设、无形式化安全定义、无证明。** 它不使用密钥、签名、MAC、承诺、零知识、MPC、TEE 或任何密码协议。"structure/format separation" 是**解析层与训练层**的控制/数据分离，**不能**比作密码学认证、完整性保护或信道绑定；把保留 token 说成 "domain separation" 只是术语巧合，二者没有共同的安全模型。

按交接文档 §6.1 的五个问题逐条回答：

1. **保护什么对象、抵抗何种对手？** 保护"开发者指令优先于数据内容"这一行为完整性；对手是只能改 data 通道、知道格式但无法改 prompt/模型的前端外部攻击者。这是**语义/行为**资产，不是密钥或密文。
2. **是否需要密码学原语，而非普通访问控制？** 不需要。核心失败是模型无法从语义上区分"指令"与"数据"，这是自然语言理解与训练目标问题；没有密钥分发、敌手计算能力、可信第三方等密码学要素。即使加访问控制，也只能限制"谁能写 data"，不能限制"data 里写了什么"。
3. **适用的原语或理论工具？** 论文没有用任何原语。**（研究推断）** 可想到的相关工具只有"来源认证"：对 data 做签名/凭证以证明来源，对 prompt 做承诺以绑定开发者意图。但它们认证的是**来源**，不是**语义上的指令性**；模型仍可能把一段已签名的网页文本当指令执行。承诺也无法让模型在内部验证"这段文本不是指令"。
4. **能否形成严谨的威胁模型与证明义务？** 论文的威胁模型是清晰的（data-only 篡改、格式已知），但没有安全定义。**（研究推断）** 可以尝试定义"输出分布对 data 通道中的指令不敏感"的不可区分性/鲁棒性目标，并给出测量方法；但这是**机器学习鲁棒性**性质，没有密码学归约，也不存在"敌手优势可忽略"的计算假设。把它包装成密码学游戏会是伪形式化。
5. **哪些问题其实是自然语言意图理解误差，不是密码学能解决的？** 全部核心问题。判断"这句话是指令还是数据"依赖语义与上下文；过滤器只能处理固定字符串，GCG 后缀说明模型仍会被语义/优化技巧说服。密码学不能替模型做这个判断。

**若按项目 §6.1 量表打分（个人判断，仅供后续汇总）：\(T_{crypto}\) 约 0–1，倾向 0。** 理由：没有任何密码学对象或证明义务；唯一可类比的是"控制/数据分离"这一系统原则，而它属于传统系统安全（注入防御），不属于密码学。不应因出现 "separator/token/channel" 等词而加分。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**原论文已做：无。** 没有密钥管理、证书、签名、token 生命周期、TEE、审计日志或性能密码学实验；前端是纯字符串处理，模型是普通全参数微调。

**（研究推断，明确标为推断）可能的技术接口：**
- **数据来源认证**：在 Agent 中，工具输出/网页可用签名或内容凭证（如 C2PA 类 provenance）标注来源，前端把"已认证来源"与"未认证来源"分到不同 data 子通道。这只是**补充**：它能让模型/策略区分可信度，但不能替代"data 中的指令不执行"这一训练目标；而且验证签名的必须是前端，模型本身不验签。
- **能力/作用域令牌**：即使注入成功，若 Agent 的工具调用受 capability token 约束（只能读、不能转账），可降低后果。这是**纵深防御**，与 StruQ 的通道分离正交；本文没有工具调用，因而完全没有涉及。
- **审计与可追溯**：记录 data 通道的原始内容与过滤器删除的内容，用签名/Merkle 结构保证日志完整性。但日志完整性不等于"模型没有执行注入"，只能用于事后取证。

**伪交叉警告（不应作为研究贡献）：**
- 给 prompt 加 HMAC/数字签名：攻击者从不需要伪造 prompt，他们只提供 data；签名对"data 里的指令"无效。
- 对 data 做加密：加密只保护机密性，解密后模型仍会读其中的指令；且应用本来就需要读 data。
- 用 ZK 证明"data 中不含注入"：先不论 ZK 对自然语言命题不适用，"注入"本身没有形式化定义，证明目标空洞。
- 把"结构化查询"称为"密码学信道分离"：没有密钥、没有敌手模型、没有证明，属于术语包装。

**若按项目 §6.2 量表打分（个人判断）：\(A_{crypto}\) 约 0–1。** 没有可部署的密码协议、密钥生命周期或性能实验；与密码工程的真实接口仅限上述"来源认证/能力令牌/审计"的**外围补充**，且均需另行设计，不能归功于本文。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- **H1（过滤器绕过）**：前端只做字面字符串替换；可测试 Unicode 同形字、NFKC/NFKD 规范化、零宽字符、BPE 边界拼接能否在 data 中产生与保留 token 等价的控制效果。实验：固定 Llama-7B + StruQ 检查点，构造不改动字面 `[MARK]` 等字符串的变体，测 ASR 与过滤器命中率。失败判据：若所有变体 ASR 均 <1%，则字面过滤在该分词器上足够。
- **H2（Agent 工具通道迁移）**：把工具返回值包成 data 通道，在 ReAct/tool-calling Agent（如 AgentDojo 类环境）中测 StruQ 式微调对 indirect prompt injection 的 ASR；关键变量是多轮历史、工具 Schema 与系统提示是否破坏两通道边界。需要重新训练或适配模型，成本较高。
- **H3（安全定义与测量）**：把"data 通道指令不影响输出"形式化为可测量的分布性质（例如对成对样本的输出一致性/攻击成功率上界），比较 StruQ、BIPIA、instruction hierarchy 与未防御模型；这是测量/定义贡献，不是密码学证明。
- **H4（与来源认证组合）**：在 data 通道上叠加可验证来源标签，测试模型是否能在训练后条件化于"来源可信度"，以及签名验证放在前端时的端到端安全增益；需区分"来源可信"与"内容无害"。
- **H5（过滤器的数据完整性代价）**：构造 `##` 具有语义的任务（Markdown 标题、代码注释、表格），测量过滤造成的任务准确率下降；论文的 AlpacaEval 不覆盖此风险。
- **H6（无微调的通道分离）**：用 attention mask/架构改造在初始层阻断 prompt→data 的注意力，或采用 instruction hierarchy 的多级标签，比较其与全参数微调的安全/效用/成本；这可检验"必须微调"是否真是必要条件。

以上均为待验证假设；本笔记未做任何实验，不能表述为已被本文或领域证实。
