## 1. 150–300 字中文概述

本文是首个系统研究 LLM-based agent 资源管理安全的论文。作者按释放时机把 agent 资源分为 short-lived、long-lived、full-lifecycle 三类，对应单轮耗竭、同会话累积、跨会话永不释放三条 DoS 路径，并给出真实 CVE 案例。为自动发现此类漏洞，作者提出 AgentDoS：以 CodeQL 静态定位内存/磁盘 sink、判定生命周期并评估污点可控性与容量约束；再用 LLM 根据调用链和系统提示生成种子，以功能分、资源分和选择惩罚调度，用 Explorer/Exploiter 迭代变异，最后以 Web 界面无响应为 oracle。在 20 个开源 agent 上发现 36 个零日、15 个 CVE，精确率 100%、召回 94.7%。全文属程序分析与模糊测试工作，不含密码学原语或形式化证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- 背景：Agent 为保持自主性，会按自然语言指令执行下载、检索、解析等资源密集任务；开发者难以预判哪些中间资源后续还会用到，倾向保留上下文和中间文件，资源生命周期缺乏治理（p.2, Abstract；p.5, §2.3）。
- 直接后果：内存或磁盘被单次大请求、同会话多轮累积、跨会话持久文件耗尽，导致 agent 服务不可用。作者给出真实案例 CVE-2025-4\*\*90（p.4, §2.2, Fig.2）。
- 现有方法不足（p.2–3, §1；p.5, §2.2；p.14, §8）：
  1. 传统 DoS 检测主要针对 CPU（ReDoS、算法复杂度）或内存泄漏，不能覆盖 agent 的磁盘/内存语义型耗尽；
  2. 传统 fuzzer 依赖 bit-flip 等低层变异，无法生成“既激活特定工具、又诱导大资源消耗”的自然语言 prompt；AgentFuzz 虽能做功能语义 prompt，但只针对 taint-style 漏洞；
  3. 已有 LLM DoS 工作攻击的是推理阶段（生成长输出、增加延迟），不是 agent 实现层的资源生命周期；
  4. 没有工作对 agent 资源生命周期建模，导致跨轮/跨会话累积型漏洞被漏报。
- 精确定义的问题：给定 agent 的源代码与公开 Web 接口（grey-box），自动定位可控的内存/磁盘消耗点，判定其资源生命周期，生成并迭代自然语言 prompt，直到触发资源耗尽型 DoS，并输出可复现的 EXP（p.3, §1；p.6–7, §3.2；p.12, §6.3）。
- 注意：论文做的是**漏洞检测**，不是给 agent 部署防御；第 9 节的缓解建议是给开发者的运维建议（p.15）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- 典型流程（p.4, Fig.1）：用户在一个 chat session 中发出 prompt → agent 拼接 system prompt（含可用工具及描述）→ 调用 LLM → 解析 LLM 返回的 tool/action → 执行工具（如 download）→ 返回结果 → 用户可在同一 session 继续，或新建 session。
- 组件：第三方 LLM API（实验中为 GPT-4.1）、工具集合（Search、Download、Calculate、DBSearch 等）、chat session/上下文缓冲、workspace/磁盘、Web 框架路由（如 `@route.post("/chat")`）、session 创建/删除接口（p.4, Fig.2；p.8, §4.2.1）。
- 资源模型：内存资源包括可增长容器（list/set/dict）、HTML/XML 解析器（BeautifulSoup、html5lib）以及 HTTP 响应对象；磁盘资源主要是文件写入（`TextIOWrapper.write`、`aiofiles`）（p.7, §4.1.1；p.21, Table 5）。
- 生命周期模型（p.4, §2.1）：
  - **Short-lived**：单轮内分配、轮次结束由 GC 或显式释放；攻击者必须在单条 prompt 内耗尽。
  - **Long-lived**：跨同一 session 多轮保留，session 结束才释放；攻击者在同一 session 内反复交互累积。
  - **Full-lifecycle**：一旦分配永不释放，跨 session 仍存在；攻击者反复新建 session 累积。
- 信任边界：论文没有独立 trust-boundary 图。由 §2.4 可知，边界在 agent 的公开 prompt 输入接口：攻击者只能提交 prompt（以及让 agent 访问攻击者托管的外部 URL），agent 代码、工具实现、开发者与运行环境均假定可信（p.5, §2.4）。Session 删除逻辑是生命周期判定的关键边界：long-lived 资源应在此时释放，full-lifecycle 则不会（p.7–8, §4.1.2）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- 受保护资产：agent 服务的可用性、服务器内存与磁盘、其他正常用户的服务质量、开发者的运维成本与声誉（p.15, Ethical Considerations "Stakeholders"）。
- 攻击者目标：耗尽内存或磁盘，使 agent 无响应或无法处理正常请求；不窃取数据、不执行代码、不破坏完整性。
- 攻击者能力（p.5, §2.4）：
  - 远程、无特权，只能通过公开 Web 界面按正常方式提交 prompt；
  - 可反复创建新 session、在同一 session 内多轮交互（除非应用本身限制）；
  - 可让 agent 访问攻击者控制的外部资源（如 30 GB HTML、深层嵌套 HTML/XML），这是 AgentDoS 的 Exploiter 所模拟的能力（p.10, Prompt 4）；
  - 不需要 prompt injection、越狱或任何显式恶意指令；资源滥用请求可以看起来像正常任务（p.14, §9）。
- 前提假设（p.5, §2.4）：agent 与开发者均 benign；执行环境未被攻破；目标是提供 Web 服务的开源 agent；第三方 LLM 自带资源管理与隔离，因此 LLM 推理层 DoS 不在范围内（p.14, §8）。
- 不在威胁模型内：黑盒商业 agent（OpenAI GPTs、Coze）、内部人、供应链投毒、多租户隔离失效、CPU/GPU/token 成本攻击（p.15, Limitations）。
- 作者额外讨论的“attack re-delegation”（p.14, §9）：攻击者先把资源消耗到略低于上限，随后正常用户的合法请求轻易越限并触发故障，使故障看起来由正常用户造成。这是作者提出的规避/归因观察，**未做实验评估**。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

AgentDoS 是 directed grey-box fuzzing（DGF）框架，分两阶段（p.6, §3.2, Fig.3，已渲染核对）：

### 5.1 Vulnerable Operator Modeling（静态阶段）

1. **Candidate Locating**（p.7, §4.1.1）：用 CodeQL 定位内存/磁盘 sink。内存 sink 包括 Python 内建容器插入操作、BeautifulSoup/html5lib 解析、requests/urllib3/aiohttp/httpx 响应处理；磁盘 sink 包括 `TextIOWrapper.write`、`aiofiles.write`。若 sink 操作的是类成员变量，则回溯到其 caller 位置以获得更准确上下文（Fig.2 中 `self.memory.append` 归到 line 8）。从 sink 反向遍历调用图枚举调用链，抽取包含 sink 的函数代码片段；采用 LLMSmith 的规则增强 agent CFG 的精度与完整性。
2. **Lifecycle Identifying**（p.7–8, §4.1.2）：人工识别处理单轮 chat 的 API 入口与删除 session 的 API 入口，构造前向 CFG。
   - 内存：变量在同一函数内初始化（局部作用域）→ short-lived；被全局变量引用、且在 session 删除时被重新赋值 → long-lived；既非局部、session 删除也不重新赋值 → full-lifecycle。
   - 磁盘：写入后 CFG 中出现针对该路径的删除指令 → short-lived；session 终止时删除 → long-lived；永不删除 → full-lifecycle。
   - 静态无法判定时（如动态路径拼接）做人工动态验证。
3. **Exploitability Assessing**（p.8, §4.1.3, Table 1）：过程内污点分析，过滤不可控或被严格限制的 operator。
   - parser 类：任一函数参数可传播进 operator 即可疑；append 类：位于迭代次数受用户输入控制的循环中即可疑；long-lived/full-lifecycle 内存：只要用户输入可传播即保守视为可疑。
   - 磁盘：任一函数输入可影响写入数据即可疑。
   - 从 operator 反向分析 size 相关变量的条件检查；若检查限制 sink 执行，则视为存在 size limit。
   - 仅保留 `Controllable=True` 且 `Constraints=False` 的 operator，并记录 Table 1 的 8 个特征（Operator、Location、Type、Lifecycle、Snippet、Call Chain、Controllable、Constraints）。

### 5.2 Dynamic Fuzzing（动态阶段）

1. **Seed Generation**（p.8–9, §4.2.1, Prompt 1）：动态 hook 第三方 LLM 调用 API（如 OpenAI API），发送固定输入 "hi"，记录 API 参数并提取 system role 字段，得到完整 system prompt；只提取一次。随后把调用链与 system prompt 交给 LLM，采用 one-shot learning + Chain-of-Thought，生成功能特定（functionality-specific）的初始 prompt。
2. **Seed Scheduling**（p.9, §4.2.2, Eq.1–3）：
   - 功能分：`Fs = x^(-k) + Ls`（Eq.1），x 为执行轨迹到 sink callsite 的最短 CFG 距离，Ls 为 LLM-as-a-Judge 对 clarity/conciseness/relevance 的语义评分（Prompt 2）。
   - 资源分：short-lived 用执行期间峰值，`Rs = (mm − mi) / mt * 100`；long-lived/full-lifecycle 用单轮结束后的残留，`Rs = (me − mi) / mt * 100`（Eq.2）。mm 为执行中最大资源量，mi 为聊天前初始量，me 为 prompt 执行后的资源量，mt 为系统总资源量。
   - 选择分：`Ss = αFs + βRs − N`（Eq.3），N 为该 seed 已被选择的次数，用于避免过早收敛；实验中 k=1、α=β=0.5。
3. **Seed Mutation**（p.9–10, §4.2.3, Prompt 3/4）：基于 reflexion 的迭代变异，每个 seed 维护独立历史（新 prompt、推理、执行轨迹、反馈分数）。
   - **Explorer**：在 seed 尚未到达目标 sink 时使用，提供调用链、system prompt、历史 prompt、执行轨迹与功能分，引导 prompt 调用正确组件。
   - **Exploiter**：在 seed 已触发 sink 后使用，提供代码片段、历史 prompt 与资源分，引导 prompt 最大化资源消耗；可嵌入攻击者托管的外部 URL（30 GB HTML、深层嵌套 HTML/XML）。
4. **Lifecycle-aware dispatch**（p.7, §3.2；p.10, §5）：short-lived 与 full-lifecycle 用新 session 发送，long-lived 用持久 session 发送。
5. **Oracle**（p.10, §5）：对所有 sink callsite 插桩，持续观察 Web 界面可用性；若 agent 在执行 sink 时无响应，则标记为潜在 DoS。short-lived 输出单条 EXP prompt，long-lived/full-lifecycle 输出完整对话序列。

### 5.3 Implementation（p.10–11, §5）

- >1.5k 行 CodeQL 静态分析 + >5.4k 行 Python 动态 fuzzing/插桩；CodeQL 使用 `FunctionInvocation`、`BasicBlock`、`TaintTracking` API，结果导出 SARIF 再由 Python 解析。
- 动态侧 hook OpenAI API 提取 system prompt；用 Python `inspect` 获取栈帧以计算执行轨迹到 sink 的距离；用 `psutil` 实时监控系统资源。
- 每个 agent 只需人工识别 Web 框架装饰器（如 `@route.post`）对应的 API 入口、从 README 找到启动函数并插入插桩代码，通常 <10 分钟。

## 6. 安全属性与安全性论证

- 目标安全属性是**可用性（availability）**：agent 在恶意 prompt 下仍能正常响应，不因内存/磁盘耗尽而拒绝服务。论文没有把它写成形式化定义。
- **未提供形式化安全定义、定理或证明**；没有密码学证明，也没有对检测算法的最优性/完备性证明。检测是否成功由动态 oracle 经验判定（p.10, §5）。
- 经验论证分三层：
  1. 静态阶段用过程内污点分析 + 过近似（over-approximation）保证可疑点不被轻易漏掉，并用人工动态验证补足静态分析无法判定的生命周期（p.7–8, §4.1.2–4.1.3）。
  2. 生命周期识别在每类随机抽取 5% sink callsite，用 Python `weakref` 监控实际释放行为，报告 95.2% 准确率；错误主要来自 Python 静态分析无法解析间接调用（p.11, §6.2）。
  3. 动态阶段以 agent Web 界面无响应为 oracle；36 个报告全部人工复核为 true positive，精确率 100%；在 38 个漏洞的构造 benchmark 上召回 94.7%（p.12, §6.3–6.4）。
- 论证边界：这是“检测工具在 20 个 agent 上的经验有效性”，不是对任意 agent 的安全保证；20 分钟/20 MB 阈值可能漏掉慢速累积型漏洞（p.12, §6.3；p.15, §9）。
- **非密码学防御，无密码学原语/证明**：论文的机制全部是程序分析、模糊测试、LLM prompting 与 OS 资源监控；没有认证、授权、加密、签名、密钥管理或密码学假设。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

- **RQ**（p.11, §6.1）：RQ1 资源保留目的；RQ2 AgentDoS 有效性/效率；RQ3 与 SOTA 对比；RQ4 各组件贡献。
- **数据集**：20 个开源、提供 Web 服务的 LLM-based agent；按 "LLM Agent"/"Autonomous Agents" 关键词检索 GitHub，按 star 降序，验证 2025 年仍活跃维护，人工确认可作为 Web 服务运行；17/20 有 >10k stars（p.11, §6.1, Table 2）。代表：AutoGPT 176k、Dify 104k、LangFlow 81.4k、RagFlow 60.1k、Autogen 46.4k 等；总 LoC 覆盖 6.1k–150k。
- **环境**：被测 agent 与 AgentDoS 均用 GPT-4.1，temperature=0；agent 以默认配置部署在 Docker，资源按各 agent 最低要求分配，未明确时默认 4 GB RAM、10 GB disk、64-core Intel CPU（对齐 Dify 最低规格）；AgentDoS 在另一台 64-core/256 GB 机器运行（p.11, §6.1）。注意这些 Docker 配额是**测试环境约束**，不是防御机制。
- **RQ1（p.11–12, §6.2）**：静态阶段在 20 个 agent 上识别 2025 个潜在 vulnerable operator，short-lived 1566（77.3%）、long-lived 286（14.1%）、full-lifecycle 173（8.6%）；生命周期识别准确率 95.2%。对 5 个最知名 agent 的 148 个 callsite 花约 12 人时分析保留目的：long-lived 中 27.4% 存当前会话上下文、35.9% 存运行状态/日志、36.7% 用于初始化会话；full-lifecycle 中 37.9% 是下载后永不删除的文件、62.1% 是开发者运行日志。
- **RQ2（p.12, §6.3）**：发现 36 个零日，影响 16 个 agent（15 个 >10k stars），15 个已分配 CVE；精确率 100%。效率：119.08 CPU hours/20 agents，平均 5.95 h/agent；Seed Generation/Scheduling/Mutation 分别占 17.1%/14.2%/68.6%；平均 9.32M tokens/agent，按 2025-08 GPT-4.1 价格约 $44.3/agent。每个 sink callsite 限时 20 分钟；若 3 分钟内未触发或资源增量低于阈值则跳过（short-lived 单轮增量 <20 MB；其他生命周期 3 分钟累计 <20 MB）。
- **假阴性分析（p.12, §6.3）**：从 AgentDoS 未标记的 sink 中随机抽 103 个（5%）人工审查：95.15% 用户不可控；0.97% 受 LLM 上下文窗口限制；1.94% 输入规模导致现实不可行（如 RAGFlow 存 LLM 输出，正常输出约 2 KB，需 >24 小时）；1.94%（2 个）是真漏洞但被漏报，例如 SuperAGI 可用 `../../xxx` 路径穿越绕过“会话后删除工作目录”的限制。加上这 2 个构造出 38 个漏洞的 benchmark。
- **RQ3（p.12–13, §6.4, Table 3，已渲染核对）**：AgentFuzz 在全部 20 个 agent 上仅 3 TP、0 FP、35 FN，precision 100%、recall 7.9%；AgentDoS 36 TP、0 FP、2 FN，precision 100%、recall 94.7%，召回约 12 倍。AgentFuzz 的 35 个 FN 中，5 个因不做生命周期建模（总在新 session 发 prompt，无法累积 long-lived 资源），30 个因缺少资源消耗评估与语义变异（prompt 到达 sink 但资源不足）。
- **RQ4 消融（p.13, §6.5, Table 4，已渲染核对）**：w/o Generation 31 TP/7 FN，recall 81.6%；w/o Scheduling 25/13，65.7%；w/o Mutation 16/22，42.1%；完整 AgentDoS 36/2，94.7%。三个组件分别贡献约 13.1、29.0、52.6 个百分点召回。
- **案例（p.13–14, §7；p.21, Appendix B Fig.4–5）**：
  - Case I：L\*\*（>80k stars）short-lived 漏洞。`all_docs` 是局部变量，GC 在函数结束回收；但单条 prompt 可让 agent 对同一 30 GB 文件重复请求 1000 次，执行期间即耗尽内存。
  - Case II：L\*（>35k stars）long-lived 漏洞。每轮把 user input、LLM plan、tool output 追加到 `self.history`，session 结束才清空；默认 `history_len=0`，历史不发回 LLM，因此永远不会触发模型上下文上限，可无限增长。
- **无**：没有与其它 agent fuzzer 的对比（作者称 AgentFuzz 是唯一同类）、没有真实生产流量、没有多租户、没有防御部署评估、没有用户研究。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

- 贡献（p.3, §1）：
  1. 首个 LLM-based agent 资源管理安全的系统研究，给出资源耗尽的系统设计/实现根因；
  2. 设计并实现 AgentDoS，一个面向资源滥用型 DoS 的 directed grey-box fuzzer；
  3. 在 20 个真实 agent 上发现 36 个零日、15 个 CVE，验证实用性。
- 与最接近工作的差异：
  - **AgentFuzz [49]**：同样做 agent 动态漏洞检测，但只针对 taint-style，且总在新 session 发 prompt；AgentDoS 增加资源生命周期建模、资源消耗评分与语义变异（p.13, §6.4）。
  - **LLMSmith [50]**：提供 agent CFG/RCE 检测规则，AgentDoS 复用其规则但目标是资源耗尽而非 RCE（p.7, §4.1.1；p.13, §6.5）。
  - **Corba [86] / Breaking Agents [80]**：让 agent 执行重复/无关动作，属于行为层干扰；本文分析 agent 实现层的资源生命周期与耗尽（p.14, §8）。
  - **LLM DoS [38,43,76,83]**：攻击推理阶段（长输出/延迟），且第三方 LLM 通常有隔离；本文攻击 agent 实现层（p.14, §8）。
  - **传统 DoS 检测 [44–46,52–54,59,63,64,69,78]**：主要针对 CPU（ReDoS/算法复杂度），不覆盖 agent 的内存/磁盘语义型耗尽（p.5, §2.2；p.14, §8）。
- 可复现资源（p.16, Open Science）：20 个 agent 应用与 baseline 实现开放获取（Zenodo record 18242998）；AgentDoS 源码因伦理考虑仅对有资质、提交申请并通过审核的研究者开放（Zenodo record 18091114）。CVE 列表在 Appendix C（p.21, Table 6）。
- 伦理：所有漏洞按 CNA 时间线披露，应用名与 CVE 编号在正文中打码/匿名化（p.15–16）。

## 9. 局限性、失效场景、作者未解决的问题

- **需要源码**：AgentDoS 是 grey-box，无法直接用于黑盒商业 agent（OpenAI GPTs、Coze）；作者认为若能获得资源使用反馈（如响应延迟侧信道），方法可适配黑盒（p.15, §9 Limitations）。这是作者推断，未实现。
- **静态分析误差**：生命周期识别 95.2%，4.8% 错误主要来自 Python 间接调用/动态路径无法解析；需要人工动态验证（p.11, §6.2；p.7–8, §4.1.2）。
- **时间/阈值偏差**：每个 sink 20 分钟、3 分钟/20 MB 跳过阈值，可能漏掉慢速累积或需要长对话的漏洞；作者自己把 RAGFlow 的 24 小时案例归为“现实不可行”（p.12, §6.3）。
- **资源类型有限**：只覆盖内存与磁盘，不含 CPU、GPU、token/API 成本、网络带宽；只覆盖单 agent，不含 multi-agent 共享资源与跨租户影响（p.7, §4.1.1；p.15, §9）。
- **benchmark 无公共 ground truth**：38 个漏洞由 AgentDoS + AgentFuzz 检出加上 2 个人工发现的 FN 聚合而成，可能存在选择偏差（p.13, §6.4 "Benchmark Setup"）。
- **未评估防御**：第 9 节的 size limit、timeout、quota、dedup、监控告警只是建议；AutoGPT 的修复（100 MB/下载、1 GB/执行目录、任务后自动删除）是开发者已部署的措施，不是论文实验评估的防御（p.15, §9 "Mitigation"）。
- **未研究自适应攻击者**：攻击者知道检测器/配额后如何规避（如分片下载、慢速累积、路径穿越）只给出个别案例，没有系统评估（p.12, §6.3；p.14, §9）。
- **归因问题**：attack re-delegation 使 DoS 看起来由正常用户造成；论文只讨论，未提出检测或归因机制（p.14, §9）。
- **复现受限**：AgentDoS 源码 conditional release，完整复现需要申请与审核（p.16, Open Science）。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**结论：非密码学防御，无密码学原语/证明。** 论文没有使用或提出任何密码学原语、协议、密钥管理、认证/授权机制或形式化密码学证明。

**原论文实际使用的机制（全部为非密码学）**：
- 静态程序分析：CodeQL、CFG、过程内污点分析、调用链抽取、size 约束反向分析（p.7–8, §4.1）。
- 动态模糊测试：LLM 生成/变异 prompt、LLM-as-a-Judge、reflexion、seed 调度（p.8–10, §4.2）。
- 资源监控：`psutil` 采样内存/磁盘、`weakref` 验证生命周期、插桩 sink、Web 界面无响应 oracle（p.10–11, §5；p.11, §6.2）。
- 环境配额：Docker 4 GB RAM/10 GB disk 是**测试环境资源约束**；20 分钟/20 MB 是**fuzzing 效率启发式**，不是安全预算。第 9 节建议的 size limit/timeout/quota 是**运维层资源治理**，不是密码学访问控制（p.15, §9）。
- 因此，本文与理论密码学的直接技术连接为**零**；不能把资源配额、超时或限流称为密码学机制。

**个人推断（明确标为推断）**：
- DoS/可用性是 liveness 属性，标准密码学定义（IND-CPA、EUF-CMA 等）不覆盖。若要形式化，可构造“资源有界可用性”游戏：敌手在预算内提交自适应 prompt，挑战者维护内存/磁盘状态，优势定义为使服务不可用的概率；但本文没有这样做，且该游戏与密码学假设（计算困难性）关系不大，更接近系统安全的形式化。
- 密码学可以为资源治理提供**问责与可验证计量**，但不能替代配额执行：例如对每租户资源用量做签名审计日志、用 TEE 远程证明资源计量、用匿名凭证/rate-limit token 做隐私保护的准入控制。这些都是外部推断，本文未涉及、未评估。
- “attack re-delegation”（p.14）本质是**归因/问责**问题：客户端认证或签名请求可帮助定位消耗者，但不能阻止已认证客户端的资源耗尽；真正起作用的是配额、限流与隔离。把认证当作 DoS 防御是常见误区。
- 若要把 AgentDoS 的 oracle 变成可证明的检测器，需要定义“资源耗尽”的形式化谓词与检测器的 soundness/completeness；本文只有经验 oracle。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**结论：非密码学防御，无密码学原语/证明。** 论文的工程栈是 CodeQL + Python + OpenAI API + psutil + Docker + weakref，没有 TLS、OAuth、凭证、签名、加密存储、支付或密钥生命周期内容。

**原论文实际使用的机制**：
- 静态分析（CodeQL/SARIF）、动态插桩（Python `inspect`、`psutil`）、LLM API 调用、Docker 资源限制、Zenodo 制品发布（p.10–11, §5；p.16, Open Science）。
- 这些都不构成密码工程机制；Docker 配额是部署/测试配置，不是访问控制协议。

**个人推断（明确标为推断）**：
- 工程上更自然的互补方向是**资源层强制**：cgroups/容器配额、文件系统 quota、每工具/每会话预算、按内容哈希去重、TTL 清理。论文第 9 节已建议 dedup 与持续监控（p.15），但没有实现或评估。
- 密码工程可加入的增量是**可审计性**：对资源用量与配额变更做签名日志，便于事后归因 attack re-delegation；对跨组织 agent 调用，用签名的资源预算/收据证明“我已为这次调用付费/配额已扣减”。但签名只保证收据完整性，不能防止资源耗尽；强制执行仍在运行时计量与配额层。
- 若做多租户 agent 平台，可用匿名凭证 + 速率限制证明（rate-limiting credentials）在保护用户隐私的同时限制滥用；这是研究推断，本文没有涉及。
- 不要误读：论文的 `Constraints=True/False` 是静态分析中“是否存在 size 检查”的特征，不是密码学约束或访问控制策略。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- H1：生命周期感知的检测方法可推广到 CPU/GPU/token/API 成本等其它资源类型；需在相同 20-agent 数据集上验证检测率与误报，当前论文只覆盖内存/磁盘。
- H2：long-lived 与 full-lifecycle 资源的跨轮/跨会话累积是独立于单轮 size limit 的漏洞类；即使 agent 有 per-turn 限额，仍可能被同会话多轮或新建 session 绕过。可用论文的 Fig.2 案例与 AutoGPT 修复做对照实验。
- H3：把资源计量与配额执行下沉到工具/容器层（cgroups、FS quota、per-tool budget）能否在不破坏任务完成率的前提下阻止论文中的 36 个 PoC；这是防御评估，论文未做。
- H4：签名审计日志/TEE 计量能否可靠归因 attack re-delegation，并满足多租户隐私；需要定义威胁模型与性能开销，当前仅为推断。
- H5：黑盒场景下用响应延迟/资源侧信道替代 `psutil` 的检测可行性；论文只提出可能性（p.15），未验证噪声、校准与逃逸。
- H6：基于内容哈希的去重能否抵御“语义不同但内容近似”的大文件耗尽；论文建议 dedup（p.15），但未评估碰撞/绕过与存储开销。
- 以上均需在后续论文或复现实验中查证，当前仅为假设。
