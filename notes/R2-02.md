## 1. 150–300 字中文概述

AgentDojo 是一个面向工具调用型 LLM Agent 的动态安全评测环境。它以 4 个有状态应用（Workspace、Slack、Travel、Banking）、97 个用户任务和 27 个注入任务构造 629 个安全用例，并用环境状态上的确定性谓词而非另一个 LLM 来计算效用与攻击成功率。论文内置 4 种提示注入提示词与 4 类防御，评测 10 个模型。核心结果是：良性场景下最强模型也仅解决约 78% 的任务；GPT-4o 在 629 个用例、Important message 攻击下的 targeted ASR 为 47.69%，工具过滤防御可降至 6.84%，但该防御依赖“任务所需工具少于攻击所需工具”这一前提。论文的贡献是可持续扩展的评测框架与效用—安全权衡度量，不提出密码学机制、形式化安全定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- 背景：Agent 把 LLM 的文本推理与外部工具调用结合；LLM 缺少区分“指令”与“数据”的形式化机制，攻击者可在工具返回的第三方数据中植入指令，即间接提示注入（p.1–3, §1–2）。
- 现有 Agent benchmark 的不足：一类只测把指令转成单次函数调用（Gorilla、Berkeley Function Calling Leaderboard），一类测多轮任务但不含显式攻击（AgentBench、WebArena、WebShop）；ToolEmu 用 LLM 模拟工具环境并用 LLM 打分，作者指出这在提示注入场景下有问题，因为注入也可能劫持评测模型（p.2–3, §2）。
- 现有提示注入 benchmark 的不足：多集中于文档 QA、提示窃取或较简单的目标/规则劫持；InjecAgent 最接近，但只做单轮模拟，把一段对抗数据直接作为工具输出，不评估 Agent 的规划与多工具调用（p.3, §2）。
- 精确定义的问题：构建一个有状态、多工具、工具输出不可信的动态环境，用环境状态上的确定性检查同时度量 Agent 的任务效用与攻击者目标达成率，并允许后续加入新任务、攻击和防御；同时避免静态攻击集导致的防御过拟合（p.1, p.3–6, §3）。
- 作者对“为何要动态”的论证：对抗样本/越狱 benchmark 可用针对防御优化的攻击（AutoAttack、GCG），而现有提示注入攻击多为通用模板、不针对具体模型；此外很容易构造只挡住某一具体攻击的防御，因此需要自适应攻击评测（p.6, §3.3）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **Environment**：一个应用领域及其可用工具；论文实现 Workspace（邮件、日历、云盘）、Slack（消息、网页、文件）、Travel（航班、酒店、租车）、Banking（账户、转账）（p.3–5, §3.1；p.6, Table 1）。
- **Environment state**：由可变对象组成，例如 `WorkspaceEnvironment` 含 `inbox`、`calendar`、`cloud_drive`（p.4, Fig.3）。状态既是 Agent 读取的数据，也是工具写入的效果；初始数据为合成的良性 dummy data（p.4）。
- **Tools**：读写环境状态的函数，工具文档被放入 Agent 提示；工具输出以 YAML 格式化后喂给 LLM。§3.1 称共 74 个工具（p.4），但 Table 1 标题与数据卡写 70 个（p.6, p.24），Table 1 各行 24+11+28+11 实际为 74，存在内部不一致（见 §9）。
- **User task**：自然语言指令 + 确定性 `utility()` 二元函数 + 解题所需的 ground-truth 工具调用序列（p.4–5, Fig.5）。ground truth 用于把注入放到“确实会被查询”的工具输出位置（p.3–4, p.16, Appendix A）。
- **Injection task**：攻击者目标 `GOAL` + 确定性 `security()` 函数 + 实现攻击目标所需的 ground-truth 调用序列（p.5, p.16, Fig.10）。
- **Task suite**：某环境内 user tasks 与 injection tasks 的集合；对二者做笛卡尔积得到安全用例，user tasks 单独运行则得到良性效用用例（p.3, p.5, §3.1）。
- **Agent pipeline**：Agent 只需实现 `query(prompt, tools, env, messages, ...)`；防御可作为 pipeline 元素组合，例如 `ToolsExecutionLoop([ToolsExecutor(), PromptInjectionDetector(), llm])`（p.5, p.16, Fig.11–12）。
- **信任边界**：论文没有独立的 Threat Model 或 trust-boundary 图；Fig.1 与 §3.3 隐含的边界是：用户指令/系统提示可信，工具返回的第三方数据不可信且可承载注入，环境状态可被工具读写；攻击者不控制模型、工具实现或系统提示，只控制部分工具输出。Agent 在每个 episode 只处理一个用户任务，没有跨任务持久上下文（p.9 明确把这一点列为未覆盖场景）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：用户邮箱/日历/云盘中的私人数据、银行账户与资金、Slack 消息与网页内容、旅行预订及个人信息；代表性敏感目标是双重认证验证码（p.5–6, Table 1；p.16, Fig.10）。
- **攻击者目标**：让 Agent 执行恶意动作，包括把邮件/验证码外发、转账、预订最贵酒店、向同事发送钓鱼链接等；攻击是否成功由 `security()` 对环境前后状态的检查判定（p.5–6, §3.1/§3.4；p.16）。
- **攻击者能力**：控制工具输出中的注入占位符（placeholder），且这些占位符位于用户任务实际会查询的工具结果中；可假设知道用户名、模型名和工具 API 以定制注入；可用一组攻击中“任一对当前用例最有效”的 Max 攻击模拟自适应攻击者（p.3–6, §3.1/§3.3/§3.4；p.8, Table 2）。论文还测试注入在工具输出中的相对位置（p.8；p.21, Fig.21a）。
- **攻击者不能做**：不能直接改模型权重、系统提示、工具实现或环境初始状态；不能直接向 Agent 发消息（这是间接注入而非直接注入）；没有真实外部副作用，所有环境是模拟的。
- **前提假设**：文本模态、英文任务与提示、每个 episode 一个用户任务、环境状态检查是确定性的、注入长度/格式不受限制、没有多任务持久上下文、没有多模态输入（p.9–10, §5；p.25, F.5.2）。
- **威胁模型位置**：原文没有 “Threat Model” 小节；攻击者模型分散在 §3.3（攻击接口、先验知识、自适应攻击）与 §3.4（成功度量）中，p.6。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

本文没有新算法或密码协议，核心是评测环境的设计与度量：

1. **环境与任务构造**：4 个环境；每个环境定义状态 schema、工具集、用户任务与注入任务；任务包含自然语言提示、确定性检查函数和 ground-truth 调用序列（p.3–5, §3.1）。
2. **用例生成**：对每个环境的 user tasks 与 injection tasks 做笛卡尔积。由 Table 1 可算：Workspace 40×6=240，Slack 21×5=105，Travel 20×7=140，Banking 16×9=144，合计 **629** 个安全用例；用户任务合计 40+21+20+16=**97**，注入任务合计 6+5+7+9=**27**（p.6, Table 1；本人据表中数字计算）。
3. **注入占位机制**：环境状态中某些字段是攻击占位符；攻击函数接收 injection task，返回每个占位符对应的注入文本（p.3, p.6, p.16–17, Fig.13）。`get_injection_candidates` 利用 user task 的 ground-truth 调用序列，只把注入放进该任务会读取的工具输出中（p.16, Appendix A）。
4. **攻击接口**：新增攻击只需实现 `attack(user_task, injection_task) -> dict[placeholder, text]`；论文内置 Important message、TODO、Ignore previous instructions、InjecAgent 四种提示词，以及在这四者中按用例取最优的 Max（p.6, p.8, p.20, Fig.19/Table 4）。
5. **防御接口**：防御作为 Agent pipeline 元素插入；论文实现 Data delimiters、Prompt injection detector（ProtectAI 的 BERT/DeBERTa 分类器）、Prompt sandwiching（每次工具调用后重复用户指令）、Tool filter（先让 LLM 只选出任务所需工具）（p.8–9, §4.3；p.19, Fig.17–18）。
6. **度量**（p.6, §3.4）：
   - Benign Utility = 无攻击时正确解决的用户任务比例；
   - Utility Under Attack = 安全用例中既完成用户任务又无对抗副作用的比例；
   - Targeted ASR = 安全用例中攻击者目标达成的比例；
   - Untargeted ASR = 1 − Utility Under Attack；
   - 对攻击集合 {A1,…,An}，只要任一攻击成功即记该用例成功（Max 指标）。
7. **关键设计选择**：效用/安全检查是读取环境前后状态的确定性二元函数，而不是 LLM 评判器；作者明确以此避免“注入同时劫持评测模型”的评测污染（p.2, p.4）。

## 6. 安全属性与安全性论证

- **论文实际追求的属性**：（a）任务效用（benign utility）；（b）攻击下的效用保持（utility under attack / untargeted ASR）；（c）攻击者目标不可达成（1 − targeted ASR）。三者都是对固定用例集的经验比例，不是对任意攻击者的安全保证（p.6, §3.4）。
- **“形式化”的含义**：论文所说的 formal utility checks 指用代码在环境状态上做确定性判定（p.2, p.4），不是形式化安全定义、游戏、定理或证明。
- **无安全性证明**：NeurIPS checklist 明确将 theoretical results 标为 N/A（p.15）。全文没有定义攻击者模型的形式化能力、没有安全游戏、没有归约、没有密码学假设。
- **经验性论证**：安全结论来自 629 个用例上的 ASR 及 95% 置信区间（p.7, Fig.6；p.20, Tables 3–5）；作者也承认默认攻击/防御较简单，防御可能被自适应攻击绕过（p.8–10）。
- **结论边界**：即使某防御在 AgentDojo 上 ASR 很低，也只说明它在这 629 个用例和这组攻击下有效，不能推出对自适应攻击者的普遍安全性；数据卡甚至明确把“只用默认攻击评测防御”列为不适当用法（p.25, F.5.2）。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

- **模型**（p.6–7, §4）：闭源 Gemini 1.5 Flash/Pro、Claude 3 Sonnet/Opus、Claude 3.5 Sonnet、GPT-3.5 Turbo/GPT-4 Turbo/GPT-4o；开源 Llama 3 70B、Command R+。除 Llama 3 外均用官方 API；Claude 3/3.5 Sonnet 与 Llama 3 额外加专用工具调用提示（p.7；p.17–18, Fig.15–16）。
- **规模与条件**：每个 Agent 在完整 629 个安全用例、97 个用户任务上评测；攻击/防御消融主要用 GPT-4o，因为其良性效用最高；Claude Opus 因限流未深入分析（p.7, §4）。
- **基线攻击**：Important message（p.19, Fig.19a），即把恶意目标伪装成用户发来的“重要消息”，要求先完成恶意任务再完成原任务。
- **核心结果（Table 3, p.20；GPT-4o，629 用例，Important message）**：良性效用 69.00%（±3.61），攻击下效用 50.08%（±3.91），targeted ASR 47.69%（±3.90）。Claude 3.5 Sonnet：78.22%/51.19%/33.86%，在效用—鲁棒性权衡上最好；Command R+：25.44%/25.12%/0.95%。论文据此提出“能力越强越易被攻击”的 inverse scaling 现象（p.7, Fig.6a），但作者也指出低效用模型可能只是无力完成攻击目标。
- **效用损失**：多数模型在攻击下绝对效用下降 10%–25%（p.7, §4.1）。
- **分套件**：Slack 套件在 GPT-4o 上 ASR 达 92%，作者归因于攻击者控制了该套件很大比例的工具输出（p.7）；Fig.21b 的读数显示 Slack 约为 0.75，可作为该解释的量化旁证（p.21，本人读图）；Travel 的 injection task 6（同时订最贵酒店并外泄个人信息）成功率为 0%，因为模型通常只完成两个恶意子任务之一（p.7）。
- **攻击提示词消融（Table 4, p.20；GPT-4o）**：targeted ASR 为 TODO 3.66%、Ignore previous 5.41%、InjecAgent 5.72%、Important message 57.7%、Max 57.55%；untargeted 分别为 32.75%、33.23%、31.48%、49.9%、68.36%。Max 主要提升 untargeted 成功率，对 targeted 的均值提升不明显。
- **攻击者知识消融（Table 2, p.8；GPT-4o）**：占位符为“the model, the user”时 45.8%；猜错用户 23.2%（−22.6），猜错模型 23.7%（−22.1）；用户名正确 46.1%（+0.3），模型名正确 44.8%（−1.0），两者都正确 47.7%（+1.9）。即先验知识收益很小，猜错代价很大。
- **防御对比（Table 5, p.20；GPT-4o）**：无防御 benign 69.0%/targeted ASR 57.69%；Data delimiters 72.66%/41.65%；PI detector 41.49%/7.95%；Repeat prompt 85.53%/27.82%；Tool filter 73.13%/6.84%。PI detector 假阳性高、显著损害效用（p.9）。正文称 Tool filter 将 ASR 降至 7.5%，与表中 6.84% 略有出入（见 §9）。
- **Tool filter 的失效条件**（p.9）：当工具选择无法预先规划（后一步依赖前一步结果），或完成任务所需工具本身足以实施攻击时失效；后者占测试用例的 17%。多任务持久上下文下还可被“wait”式注入绕过。作者指出更复杂的 planner/isolated-agent 隔离仍无法防止“只篡改单个工具结果”的注入（如让某酒店总被选中）。
- **注入位置**（p.8；p.21, Fig.21a）：注入越靠近工具输出末尾越有效，GPT-4o 上平均最高约 70%。
- **DoS 对照**（p.20–21, Fig.20）：让模型停止/骂人/解 Captcha/发冒犯邮件/声称违法内容等 untargeted 攻击，效果不如带明确恶意目标的 targeted 攻击。
- **成本**（p.20, Appendix D）：GPT-4o 跑完 629 个安全用例约 US$35，97 个效用用例约 US$4。
- **统计**：95% 置信区间用 `statsmodels.stats.proportion.proportion_confint`（p.15, checklist）。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

- **贡献**：
  1. 首个（作者主张）有状态、多工具、动态对抗的 Agent 提示注入评测环境，含 4 个应用、97 个用户任务、27 个注入任务、629 个安全用例（p.1–6）。
  2. 用环境状态上的确定性检查替代 LLM 评判器，降低注入劫持评测的风险（p.2, p.4）。
  3. 可扩展的攻击/防御/任务接口，支持后续自适应攻击与新防御（p.6, p.16–17）。
  4. 对 10 个模型、4 种攻击提示词、4 类防御的系统评测与效用—安全权衡分析（p.6–9, p.20）。
- **与最接近工作的差异**：
  - InjecAgent：单轮、模拟、无规划；AgentDojo 要求 Agent 自行选择并串联多个工具，在有状态环境中完成原任务（p.3）。
  - ToolEmu：LLM 模拟环境与 LLM 打分；AgentDojo 用确定性状态检查，避免评测器被注入劫持（p.2–4）。
  - AgentBench/WebArena/WebShop：多轮但无显式攻击；AgentDojo 把攻击作为一等公民（p.2–3）。
  - 提示注入 benchmark（文档 QA、Tensor Trust、HackAPrompt）：任务更简单；AgentDojo 贴近真实 Agent 执行（p.3）。
- **可复现资源**：代码 MIT license，GitHub `ethz-spylab/agentdojo`，leaderboard `agentdojo.spylab.ai`；Zenodo DOI `10.5281/zenodo.12528188`；模型输出/对话以 JSON 发布，附复现全部图表的 Jupyter Notebook；数据集约 136 KB、合成数据（p.1, p.22–24）。

## 9. 局限性、失效场景、作者未解决的问题

- **攻击/防御仍简单**：默认攻击是固定提示词模板；Max 只是四种提示词按用例取最优，不是针对防御优化的自适应攻击；作者明确说更强攻击/防御是未来工作（p.8–10, §5）。
- **评测有效性**：数据卡明确警告，仅用默认攻击评测防御是不适当用法，必须尽力构造强自适应攻击（p.25, F.5.2）。
- **覆盖范围**：文本单模态、英文、单用户任务、无跨任务持久上下文、无真实外部副作用；作者列出多模态、注入长度/格式约束、自动化任务生成、更难任务等扩展方向（p.9–10, §5）。
- **隔离机制的固有缺口**：tool filter 在 17% 用例中无效；无法应对动态规划、多任务“wait”注入、只篡改单个工具结果的注入；planner/isolated-agent 方案也不能解决最后一类（p.9）。
- **防御副作用**：PI detector 假阳性显著降低效用（benign 41.49%）；delimiting 与 repeat prompt 对自适应攻击很可能无效，作者自己承认（p.8–9）。
- **数据与任务的人工性**：任务与检查函数手工设计，数据由作者/GPT-4o/Claude Opus 生成后人工检查；扩展成本高，可能存在作者偏差（p.4, p.9, p.24–26）。
- **内部数字不一致（本人核对，非作者自述）**：
  - 摘要称“LLM 解决少于 66% 任务、攻击对最强 Agent 成功率低于 25%”（p.1–2），但 Table 3 中 GPT-4o 良性效用 69.00%、targeted ASR 47.69%，Claude 3.5 Sonnet 78.22%/33.86%（p.20）。论文提到 Claude 3.5 Sonnet 是论文首版之后发布的，可能解释部分差异，但 GPT-4o 的数字仍与摘要不符，论文未说明口径。
  - 同名“Important message/无防御”条件下，Table 3 的 GPT-4o targeted ASR 为 47.69%，Table 4/Table 5 为 57.7%/57.69%（p.20）；具体提示词版本或用例子集可能不同，但论文未说明。
  - 工具总数：§3.1 写 74（p.4），Table 1 标题与数据卡写 70（p.6, p.24），而 Table 1 各行相加为 74。
  - Tool filter ASR：正文 7.5%（p.9），Table 5 为 6.84%（p.20）。
  - 引用这些数字时应以对应表格及其条件为准，不宜把摘要数字当作全表结论。
- **未解决问题**：效用与安全的权衡是否可判定；如何自动化生成可靠的任务与检查；如何评测自适应攻击；leaderboard 随模型版本漂移的可比性。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**原论文已做：无。** 本文是动态评测环境/benchmark，不含任何密码学构造、密码学假设、安全游戏、归约或证明；“security”指攻击者目标达成的经验比例，“formal”仅指环境状态上的确定性效用检查（p.2, p.4, p.6, p.15）。不能把“security benchmark”当作密码学形式化。

**个人推断（明确标为推断，不是论文内容）**：
- **把注入抵抗写成迹属性**：可把环境建模为状态转移系统，用户任务授权一组状态转移；安全性定义为“仅由不可信工具输出引起、且不在授权集合内的转移不发生”。这是授权/信息流性质，可用非干扰（non-interference）或迹谓词表述，不需要密钥；AgentDojo 的确定性 `utility()`/`security()` 可作为该定义的测试 oracle。但它仍不是密码学定义。
- **来源认证 vs 指令/数据混淆**：对工具输出做数字签名只能认证“谁产生/传输了这段数据”，不能认证“这段文本是数据而非指令”。以 AgentDojo 为试验台可验证一个反直觉假设：加签名很可能不降低语义注入的 ASR。这是可证伪的实验设计，不是论文结论。
- **能力令牌与工具过滤**：tool filter 本质是运行时授权（先缩小工具集合）。若用不可伪造、作用域受限的能力令牌实现，可把“LLM 自行选择工具”变成可审计的授权决策；但论文的 17% 失效用例说明难点在授权范围本身（任务所需工具足以作恶），而不在令牌不可伪造性。
- **可信执行/证明**：planner 与 executor 的隔离（论文引用的 Dual LLM、SecGPT，p.9）是架构隔离；若用 TEE/远程证明实例化，才进入密码工程范畴。论文未实现、未评测。
- **形式化的边界**：即使把 AgentDojo 的检查写成形式谓词，它刻画的是“在这组任务/工具/状态下是否越权”，不提供对任意自然语言攻击者的普遍保证；理论密码学的价值应放在授权、来源、隔离的可证明构造上，而不是给 ASR 数字套一个“安全定义”的外壳。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**原论文已做：无。** 论文使用的防御是提示分隔符、ML 分类器检测、重复用户提示、LLM 工具白名单（p.8–9, p.19）；没有认证、签名、加密、MAC、TEE、密钥管理、凭证或访问控制令牌。评测指标是效用与 ASR，不含密码学开销或密钥生命周期分析。

**个人推断（工程接口，均未在论文中实现）**：
- **工具清单/输出签名**：对工具描述与返回数据做签名和版本化，可防供应链篡改与来源伪造；但对“数据中夹带指令”无效。可作为 AgentDojo 的一个 defense pipeline 元素做消融，度量 ASR 与效用变化。
- **能力式工具授权**：按用户任务签发短期、作用域受限的 capability，运行时由工具网关强制；比 LLM 自行过滤更可审计。需要解决动态规划（无法预先确定工具集）与“必要工具即可作恶”的范围问题。
- **隔离执行与证明**：planner 只输出符号化计划，executor 在受限环境执行；若 executor 运行在 TEE 并提供 attestation，可把“工具实现未被篡改”变成可验证属性。这属于系统+密码工程，不是本文工作。
- **完整性审计**：对工具调用与环境状态变更做防篡改日志（hash chain/签名），便于事后归因；AgentDojo 的状态前后快照天然适合作为审计输入。
- **评测接口**：AgentDojo 可作为“密码机制是否影响效用/延迟”的实验床，但它本身不提供密码保证；任何“加了签名就安全”的主张都需要在同一 629 用例上做自适应攻击评测，而不能只报 clean ASR。
- **伪交叉风险**：仅给日志签名、仅把 OAuth/token 包进 Agent、仅用分类器过滤，若不解决指令/数据混淆与授权范围，不构成密码学贡献；本文的 tool filter 失效分析（p.9）已经说明“缩小工具集”不等于“权限不扩张”。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- **H1**：在 AgentDojo 中给所有工具输出加数字签名/来源证明，targeted ASR 不会显著下降（因为注入是语义指令而非来源伪造）；可在同一 629 用例、同一模型上做 A/B。此假设用于检验“签名能防提示注入”的常见误解。
- **H2**：用密码学能力令牌实现 per-task 工具授权，能在不调用 LLM 做工具选择的情况下复现 tool filter 的低 ASR（约 6.84%），但在论文指出的 17%“必要工具即可作恶”用例上同样失效；可度量授权范围而非令牌强度才是瓶颈。
- **H3**：针对每种防御构造自适应攻击（例如让注入指示模型忽略未来的用户提示、伪造分隔符、规避分类器），ASR 会显著高于论文的 Max（Max 仅覆盖 4 种固定提示词）；这是对论文防御结论的直接压力测试。
- **H4**：把 `utility()`/`security()` 的状态谓词提升为迹级授权规范，可形式化定义“未授权状态转移”，并在 629 用例上检查其表达力与误报/漏报；需验证该规范是否足以覆盖动态规划与多任务场景。
- **H5**：效用—安全 Pareto 排序随模型版本变化（论文已见 Claude 3.5 Sonnet 发布后的变化），leaderboard 的跨版本可比性需要版本固定与时间戳；可用重复评测验证。
- 以上均为待验证假设，不代表领域现状；需在后续论文与实验中查证。
