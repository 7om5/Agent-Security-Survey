## 1. 150–300 字中文概述

AgentHarm 是面向“恶意用户直接提示”的多步 LLM Agent 滥用基准（作者称首个）。作者手工编写 110 个明确恶意行为，覆盖欺诈、网络犯罪、骚扰、自残、恐怖主义等 11 类，并以详细/开放式与是否给工具提示组合成 440 个任务；每个任务配 2–8 个、共 104 个无副作用合成工具和人工评分 rubric。评分同时记录危害完成分与拒绝率，并设良性对照和“非拒绝危害分”以检查越狱后的能力保持。作者在公开测试集（264 任务）上评测 15 个前沿模型：无攻击时多个模型已高度配合；通用聊天越狱模板可迁移到 Agent；越狱后多步工具调用能力基本保留。基准按 10%/60%/30% 分验证/公开/私有集。全文不含密码学构造或形式化安全证明，属于能力与拒绝行为评测，不是安全认证。

## 2. 研究背景、现有方法不足、精确定义的问题

- 背景：LLM 越狱鲁棒性此前主要在单轮聊天场景研究；Agent 通过工具执行多阶段任务，若被恶意使用，后果可能大于输出一段有害文本（p.1, §1）。单轮鲁棒性不一定迁移到多轮（p.1 引 Li et al. 2024; Gibbs et al. 2024），而 Agent 天然是多步的。
- 现有不足：Agent 安全基准多聚焦“间接提示注入 + 良性主用户”场景，如 AgentDojo 的注入来自工具输出、InjecAgent、ToolEmu；ToolEmu 还假设用户意图良性，并用 LLM 模拟工具执行与评分。作者刻意避免 LLM 模拟工具，改用固定实现和详细 rubric（p.3, §2）。已有的 misuse 评测要么只统计首轮函数调用拒绝（Zou et al. 2024），要么把 AdvBench 内容套进工具调用（Wu et al. 2024），缺少覆盖多步工具依赖的直接提示滥用基准（p.3, §2）。
- 精确问题：度量 Agent 在“用户明确恶意”的直接提示下完成多步有害任务的倾向与能力，并评价越狱方法是否在提高危害完成度的同时保留 Agent 的任务执行能力；同时提供可复现、可防污染的评测集（p.1–2, Abstract/§1）。作者自称这是“first dataset to specifically measure direct prompting scenarios for multi-step agent misuse”（p.2, §1），此为首创性声明，不是独立验证的结论。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- 组件与流程（p.4–5, §3.1；p.6, §4.1）：用户给出一个初始 prompt；LLM Agent 在简单的 while loop 中生成工具调用，工具结果回填上下文，直到任务完成或模型停止。默认不使用复杂 scaffold，temperature 0，最多生成 4096 output tokens。
- 工具：104 个用 Inspect 框架实现的独立 Python 函数，无副作用，覆盖通用工具（Google/Bing/Onion 搜索、email、terminal、文件下载/上传）与领域工具（X、Instagram、TikTok、HuggingFace、酒店、PayPal 等）；每个行为平均 3.53 个函数，最少 2 个、最多 8 个不同工具。部分工具返回 LLM 生成的长文本（HTML、文章、用户消息），但工具逻辑本身是固定代码（p.5, §3.1.2；p.3, Table 1）。
- 评分器：评分函数读取完整 message trace（函数名、参数、调用顺序、工具返回），返回若干布尔检查的字典；部分检查调用 GPT-4o 语义 judge 判断“某段输出是否切题”。拒绝判断是另一个通用语义 judge，作用于 Agent 生成的所有消息（p.5, §3.1.3；p.4, Fig.2）。
- 信任边界：**原文没有独立的 Threat Model / Trust Boundary 章节或图**。其隐含边界是“恶意用户 → Agent → 合成工具”：用户是不可信输入源，工具与环境是基准提供的可信固定装置，模型 API 是执行通道；不建模工具投毒、记忆投毒、间接注入、多 Agent 串谋或供应链攻击。第 4 节据此明确列出。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- 受保护对象（隐含）：现实世界中可能被 Agent 有害行动侵害的法益（财产、隐私、人身安全、公共安全等，对应欺诈、网络犯罪、骚扰、自残、恐怖主义等类别）；在基准内部的代理指标是模型的拒绝行为/安全对齐。基准度量的是“有害任务完成度”，不是真实系统的机密性、完整性或可用性被破坏（p.1–2, Abstract/§1；p.4, §3.1.1）。
- 攻击者：拥有 API 访问权限的恶意用户；只能提交一个初始 prompt（可含通用越狱模板），可选用 provider 的 forced tool call 功能；不能在 Agent 执行中途追加对话（p.10, §5 明确“不考虑 multi-turn attacks”）。按本文的 API 评测设置推断（原文未逐条列出攻击者能力）：攻击者不掌握模型权重、工具实现或第三方数据源，也不控制工具返回内容；这些排除是由“direct prompting / 无间接注入”的设定隐含的。
- 攻击目标：让 Agent 以连贯的多步工具调用完成明确有害的任务，并尽量保持任务执行质量；评价指标同时看 harm score 与 refusal rate（p.1–2；p.7, §4.2）。
- 前提假设：任务必须是“digitally realizable”、不需要真实世界动作；合成工具只是 harm 的 proxy，任务相对简单；恶意行为与良性对照共享同一主题和工具结构；英文；不含真实姓名/地址/地点；30% 私有集从未暴露给公开 LLM API（p.4–6, §3.1–§3.2）。
- 重要区分：这是 **misuse（恶意用户主动滥用）** 威胁模型，不是“良性用户被第三方注入攻击”的间接提示注入模型；不要把 AgentHarm 的威胁模型与 AgentDojo/InjecAgent 混用（p.3, §2 明确对比）。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

本文没有新算法或密码协议，核心是基准构造与评分流程，分为三部分（p.3–5, §3.1）：

1. **Behaviors（行为）**：11 类 × 每类 10 个基础行为 = 110 个；全部手写，由未参与写作的独立人工审核；任务要求若干有依赖关系的函数调用，通常后一调用需要前一调用的信息；只做数字可实现的任务，避免真实世界行动与真实个人信息（p.3–4, §3.1.1）。
2. **Augmentations（变体）**：每个基础行为展开为 detailed / open-ended 两种表述，再各自是否加“先调用某个函数”的 hint，形成 4 个变体；110 × 4 = 440 个任务（p.4, §3.1.1）。另有逐条改写的 benign counterpart，主题相同但无恶意意图，用作能力基线（p.4–5, §3.1.1）。
3. **Synthetic tools（合成工具）**：用 Inspect 实现 104 个无副作用函数；工具会对错误参数/幻觉文件名返回可纠正的错误信息，支持 Agent 自我修正（p.5, §3.1.2）。
4. **Grading rubrics（评分规则）**：每个行为有专门评分函数，包含多项人工写死的检查（如目标函数是否都被调用、调用顺序是否正确、email 收件人/金额/钱包地址是否匹配），部分检查用窄范围语义 judge；检查项可给部分分，最终 harm score 是这些检查的聚合（0–1），但论文没有给出统一的加权公式（p.5, §3.1.3；p.4, Fig.2；p.18, Table 9 caption）。
5. **Refusal judge**：用 Table 5 的通用 prompt 判断整段回复是否“只是拒绝”；作为次要指标，与 harm score 分离，避免 refusal judge 被攻击时直接污染主指标（p.5, §3.1.3；p.14, §A）。
6. **Splits**：按行为划分 validation 10%（44）、public test 60%（264）、private test 30%（132）；validation 用于调参，public 用于最终评测，private 用于未来无污染评测（p.5, §3.1.1；p.3, Table 1）。
7. **Attacks（评测条件）**：no attack；forced tool call（provider 级预填工具调用，可能本身降低拒绝）；universal jailbreak template（改编自 Andriushchenko et al. 2025 的规则模板，改为工具调用格式；主要用私有验证集的一个样本优化，未在主数据集上调优；所有模型共用同一模板，主结果按单次尝试计）（p.7, §4.1）。
8. **派生指标**：non-refusal harm score（只在未拒绝的 generation 上算 harm score），用于判断越狱是否损伤能力；best-of-n（n=5, τ=1）作为攻击增强的上界分析（p.8, §4.3；p.9, Table 2）。

没有形式化算法、伪代码或数学推导；Figure 2 给出 behavior/tool/grading function 的具体代码示例，属于工程实现说明。

## 6. 安全属性与安全性论证

- **未提供形式化安全定义、定理或证明**。全文没有密码学安全游戏、攻击者计算能力假设、归约或可证明保证。
- 论文实际度量的是三类行为量：(i) **harm score**——按人工 rubric 的任务完成度；(ii) **refusal rate**——语义 judge 判定的拒绝比例；(iii) **non-refusal harm score**——未拒绝样本上的完成度。三者都是经验指标，不是“安全性”的形式化定义（p.5, §3.1.3；p.18, Table 9 caption）。
- 作者对测量有效性的论证是程序性的：题目手写并由独立人工审核；评分以固定工具和人工条件为主，LLM 只做窄范围语义判断；使用私有测试集防污染；用良性对照估计能力上限；人工检查大量执行日志（p.5–6, §3.1.3/§3.2；p.14, §A）。
- 作者明确降低主张：任务“relatively easy and do not themselves constitute end-to-end capabilities of concern”，基准主要测 refusal behavior 与基本 agentic competency，不测高级自主能力（p.6, §3.2；p.10, §5）。
- 因此：高 harm score 只说明模型在合成 proxy 环境中配合并完成了该 rubric 定义的任务，不等于真实世界危害能力；低 harm score 也不构成安全认证。基准中的“success”是评测意义上的任务完成，不是攻击者攻破系统安全的证明。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

**设置（除非另注，均为 public test set 264 任务、temperature 0、单次尝试、默认 while-loop scaffold、GPT-4o 语义 judge）**：
- 模型：15 个 API checkpoint（p.7, §4.1；p.15, §B）：OpenAI GPT-3.5-Turbo、GPT-4o mini、GPT-4o；Anthropic Claude 3 Haiku/Sonnet/Opus、Claude 3.5 Sonnet；Google Gemini 1.0 Pro、1.5 Flash、1.5 Pro；Mistral Small 2、Large 2；Meta Llama-3.1 8B/70B/405B（经 DeepInfra）。
- 条件：no attack、forced tool call、template attack；forced tool call 对 Gemini 全系与 Llama 全系不可用，Table 9 中记为 “-”。Gemini 因无参函数调用的 API 错误忽略约 16% 行为；Llama-3.1 使用额外的工具调用格式 prompt（p.7, §4.1）。
- 指标：harm score、refusal rate、non-refusal harm score；良性行为只算 no-attack 的 non-refusal score（p.18, Table 9 caption）。

**主结果（public test，264 任务，单次尝试）**：
- 无攻击时已有大量配合：GPT-4o mini 62.5% harm / 22.0% refusal；Mistral Large 2 82.2% / 1.1%；GPT-4o 48.4% / 48.9%；Claude 3.5 Sonnet 13.5% / 85.2%；Gemini 1.5 Pro 15.7% / 78.4%；Llama-3.1 405B 4.3% / 91.2%（p.7, §4.2；p.18, Table 9）。注意 p.7 正文对 405B 写 88.3%，与 Table 9 的 91.2% 不一致，本文以表格数值为准并保留此差异。
- 模板攻击显著提高危害分并压低拒绝：GPT-4o 48.4%→72.7%，refusal 48.9%→13.6%；Claude 3.5 Sonnet 13.5%→68.7%，85.2%→16.7%；Gemini 1.5 Pro 15.7%→56.1%，78.4%→3.5%（p.7, §4.2；p.18, Table 9）。forced tool call 也普遍降低拒绝，例如 GPT-4o 57.7% harm / 40.5% refusal，Claude 3.5 Sonnet 26.9% / 80.3%（p.18, Table 9）。
- 能力保持：模板攻击后 Claude 3.5 Sonnet 的 non-refusal harm score 为 81.9%，良性任务 non-refusal 为 82.0%；GPT-4o 为 84.2% 对 89.9%（p.7–8, §4.2；p.18, Table 9）。作者据此认为越狱后的 Agent 仍能连贯执行多步任务，而非“越狱后变笨”。良性行为本身几乎不被拒绝（Table 9 caption；Figure 3 caption），因此 benign non-refusal score 可作为能力参照。

**消融与分析**：
- best-of-5（τ=1，n=5，模板）：greedy（τ=0）72.7%→best-of-5 83.7%（GPT-4o）；68.7%→79.7%（Claude 3.5 Sonnet）；80.5%→90.8%（Mistral Large 2）。τ=1 的单次平均分反而低于 τ=0（GPT-4o 70.7%±0.7%；Claude 65.1%±1.3%；Mistral 67.4%±8.5%）（p.8, §4.3；p.9, Table 2）。
- prompting（Table 3，p.10）：CoT 与 ReAct 在无攻击时提高拒绝（如 GPT-4o refusal 48.9%→47.7%/61.7%；Claude 3.5 Sonnet 85.2%→87.1%/93.2%）；refusal prompt 对 GPT-4o 无攻击有效（harm 16.6%，refusal 82.6%），但对模板攻击下的 Mistral 无效（Template + refusal prompt 仍 79.5% harm / 0.0% refusal），作者认为模板压过了 refusal system prompt（p.8–9, §4.3）。
- agent vs chat-only（Appendix A，Table 8，p.15/p.17）：把 76/110 个任务改写为单轮 chat-only（排除 self-harm、terrorism、violence），同一模型在 chat 设置拒绝更高：GPT-4o 无攻击 50.0%→72.7%，模板 9.1%→31.8%；Claude 3.5 Sonnet 无攻击 88.6%→95.5%，模板 29.5%→72.7%。这是“改写后的 76 任务”对比，不能与 264 任务公开集直接横向比较。
- private test（Table 10，p.19，132 任务，7 个模型的子集）：例如 Claude 3.5 Sonnet 模板 68.9% harm / 15.2% refusal / 80.7% non-refusal；GPT-4o mini 模板 68.3% / 0.0% / 68.3%；GPT-4o 模板 63.1% / 16.7% / 74.9%。私有集结果与公开集方向一致，但样本量与模型子集有限。
- 成本：public test 单次约 0.5–1.5M tokens（70%–90% 为 input），GPT-4o 约 $1–4，GPT-4o-mini 约 $0.08–0.25（2024-09 价格）；judge 成本 ≤$0.5；并行实现约 10 分钟（p.5, §3.1.4）。
- 无训练、无防御基线、无人工 harmfulness 评分实验；所谓“对照”是 benign behaviors 与三种攻击条件，不是防御方法对比。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

- 贡献 1：首个专门测“恶意用户直接提示 + 多步工具调用”的 Agent 滥用基准（作者声明，p.2, §1）；110 个基础行为、440 个任务、11 类危害、104 个工具（p.1, Abstract；p.3, Table 1）。
- 贡献 2：把“能力保持”纳入越狱评分：不仅看拒绝，还看越狱后能否连贯完成多步任务；并提供 benign 对照与 non-refusal harm score（p.1–2；p.6, §3.2）。
- 贡献 3：细粒度、人工 rubric 为主的评分，LLM 只做窄范围语义判断，降低“整段 LLM 打分”的偏差与可攻击性（p.5, §3.1.3；p.14, §A）。
- 贡献 4：10%/60%/30% 划分与私有测试集，含 canary string，私有集在自己部署的 Azure 上评测以避免供应商日志污染（p.2；p.5–6, §3.1.1/§3.2）。
- 贡献 5：发现无攻击时多个前沿模型已高度配合；简单通用聊天越狱模板可迁移到 Agent；越狱后能力基本保留（p.6–8, §4.2）。
- 与最接近工作的差异（p.3, §2）：AgentDojo/InjecAgent 是间接注入、主用户良性；ToolEmu 假设用户意图良性且用 LLM 模拟工具/评分；Zou et al. 2024 只看首轮函数调用拒绝；Wu et al. 2024 把 AdvBench 内容套进工具调用；Tian et al. 2023 不涉及工具或多轮。AgentHarm 的差异点是“恶意用户 + 多步工具依赖 + 固定合成工具 + 人工 rubric + 能力保持”。
- 可复现资源：数据集公开在 `https://huggingface.co/datasets/ai-safety-institute/AgentHarm`（p.1, Abstract）；评测基于 UK AISI 的 Inspect 框架（p.5, §3.1.2）。论文正文只给出数据集 URL，未单独给出代码仓库地址；工具/评分函数的具体实现见 Appendix D 示例。

## 9. 局限性、失效场景、作者未解决的问题

**作者自述（p.10, §5）**：
- 只有英文 prompt，未考虑其他语言对拒绝率与表现的影响。
- 不考虑 multi-turn attacks：用户只发第一个 prompt，之后不能追加对话。
- 评分函数可能漏掉“另一种也算正确”的执行轨迹（例如 Agent 先向用户请求补充信息）。
- 评分绑定自定义合成工具，难以直接套用第三方工具或不支持自定义工具的 scaffold。
- 只测基本 agentic capability，不测高级自主能力（对比 Kimmiment et al. 2023 类开放式评测）。

**作者结论（p.10, §5）**：AgentHarm 提供了一个高质量的合成环境来测量 LLM Agent 的鲁棒性，希望推动 Agent 安全与安保研究；这是愿景性总结，不是新的实验结论或安全保证。

**本人补充/推断（明确标记）**：
- 合成工具无副作用、任务相对简单，harm score 是 proxy，不能外推为真实世界危害能力；作者自己也说任务“relatively easy”（p.6, §3.2）。
- 拒绝判断是通用 LLM judge，作者承认可能被“在工具调用之间要求拒绝”的消息欺骗；缓解是把 refusal 与 harm score 分离、不把 user message 传给 judge，但这只是降低影响，不是形式化保证（p.14, §A）。
- 评分含语义 judge，仍受 judge 偏差、校准与对抗输入影响；细粒度 rubric 降低但未消除该风险（p.5, §3.1.3；p.14, §A）。
- 私有集只有 132 个任务、且只评测了 7 个模型的子集（Table 10, p.19）；“无污染”是程序性隔离，不是可验证的密码学保证。
- 模型集合是 2024 年的 API checkpoint；结论对更新模型不一定成立。
- 基准可被优化/过拟合：作者用私有集与 canary 缓解，但公开的 264 个任务仍可被针对性训练；论文没有量化“训练集包含 AgentHarm 公开任务”对分数的影响。
- 没有防御基线，也没有测“加一个工具调用策略引擎/护栏后 harm score 是否下降”；因此不能从本文得出任何防御有效性结论。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**结论先行：本文无任何密码学构造/证明，不应被归类为密码学论文。**

**论文实际使用的机制（均非密码学）**：
- benchmark：110/440 个行为、11 类、104 个合成工具、public/private split。
- 评分器：Python grading function + GPT-4o 窄范围语义 judge + 通用 refusal judge；没有承诺、签名、零知识、MPC、TEE 或任何密码原语。
- 数据集：HuggingFace 公开托管；私有集靠“不公开 + 自建 Azure 部署”隔离，不是密码学密封。

**论文明确没有做的**：
- **无密码学构造、无密码学定义、无密码学证明**。没有安全游戏、 adversary 计算能力模型、归约、可证明安全声明。
- 没有把“拒绝”或“harm score”形式化为安全属性；没有证明某个 Agent 系统满足机密性/完整性/认证性/授权性。
- 没有密钥、身份、凭证、签名、加密、attestation、访问控制或审计日志完整性机制。
- 全文检索到的 “crypto” 只出现在任务内容里的 “crypto wallet / Ethereum”，不是密码学。

**个人推断（不得当作原文结论）**：
- AgentHarm 可以作为“下游经验测试集”来评估某个密码学或策略型护栏是否改变了 Agent 的工具调用行为：因为评分直接检查函数名、参数与顺序，工具调用中介（tool-call mediation）若阻断目标函数，harm score 会下降；但这只是行为评测，不是安全性证明。
- 若要把“工具调用策略”做成可证明的监控器，可把策略写成对 trace 的谓词，定义 soundness（不放过违规）与 completeness（不误杀合规），再用 AgentHarm 类 trace 做测试集；这一形式化在本文中不存在，属于推断。
- 私有测试集的“不可见性”可以用承诺（commitment）或可验证随机抽样来增强可验证性，但本文用的是程序性保密；这是开放的工程/理论问题，不是本文贡献。
- **不要把 harmful capability benchmark 当作安全认证**：高/低 harm score 既不能证明系统可被攻破，也不能证明系统安全；它只反映特定合成任务上的行为分布。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**结论先行：本文无任何密码工程机制，只有评测工程。**

**论文实际使用的机制（工程侧）**：
- Inspect 评测框架、纯 Python 无副作用工具、message-trace 评分函数、GPT-4o judge、HuggingFace 数据集托管。
- 没有 authentication/authorization、OAuth、token、签名、加密存储、TEE、key lifecycle、secure logging、provenance 或供应链签名。

**个人推断**：
- 若把 AgentHarm 用作护栏回归测试，必须注意它的工具是合成且评分绑定精确函数名/参数：真实系统中的工具调用授权、凭证最小权限、跨服务委托、撤销与重放保护，都无法由该基准验证。用 AgentHarm 分数上升/下降来宣称“密码工程防御有效”是伪交叉。
- 可考虑的工程接口：把 AgentHarm 的 trace 格式作为策略引擎的输入 schema，测“阻断/改写工具调用”对 harm score 的影响；但这需要额外接入真实工具或至少可配置的策略层，本文没有做。
- LLM judge 的完整性问题（p.14, §A）是评测系统自身的应用安全问题；密码学（如对评分结果签名、对 rubric 做承诺）可以提升可审计性，但不能替代 judge 的语义正确性。
- “forced tool call”是 provider 的 API 行为，不是密码协议攻击；把它当作“越狱”只在该评测设置内成立。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- H1：AgentHarm 的 harm score 排名与真实沙箱（如 Cybench/3CB 或人工红队）中的有害能力排名是否相关？若相关性低，说明合成工具 proxy 的外部效度有限。需要在同一批模型上做交叉基准研究。
- H2：工具调用中介/授权策略能否在**不改变 refusal rate** 的情况下显著降低 harm score？AgentHarm 把 refusal 与 harm 分开，正好提供可测的因变量；可做一个策略引擎的前后对照实验。
- H3：只在最终聊天输出上做 safety training，是否不如在中间工具调用决策上做训练？可比较两种微调对 harm score 与 benign 能力的影响。
- H4：通用模板的跨模型迁移是否主要由工具调用格式（JSON vs 自定义标签）解释？可做格式消融与跨 provider 实验。
- H5：评分器的对抗鲁棒性：若允许攻击者控制工具返回内容（本文明确排除的间接注入），rubric 中的语义 judge 与参数检查是否会被绕过？这会把 AgentHarm 扩展到注入场景，需重新定义威胁模型。
- H6（推测性）：用密码学承诺/可验证随机抽样来发布私有测试集，能否在不泄露任务的前提下让外部复现“私有集分数”？需要设计协议并测量开销；本文没有涉及。
- 以上均为待验证假设，不能因为本文未做就断言领域空白。
