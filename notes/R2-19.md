## 1. 150–300 字中文概述

本文提出 OpenAgentSafety（OA-SAFETY），一个在真实工具环境中评测 LLM Agent 安全性的模块化基准。它基于 OpenHands 构建 Docker 沙箱，让 Agent 操作文件系统、bash、Python 与浏览器，并通过 Sotopia 模拟的 NPC 进行多轮、多角色交互。基准含 8 类风险、356 个可执行任务（80 个手工种子任务 + GPT-4o 扩展、作者人工核验），覆盖良性、恶意与混合的用户/NPC 意图。评测采用规则脚本检查环境终态与 GPT-4.1 LLM-as-Judge 阅读轨迹的混合协议，并报告失败率、分歧率与成功完成率。七个模型在到达风险暴露点的任务中不安全率为 49%–73%；良性意图下仍达 50%–86%，浏览与文件/代码工具风险最高。人类标注显示 LLM judge 明显低估不安全行为、高估失败率。全文没有密码学构造、形式化安全定义或证明；其 "framework" 是评测基础设施，不是认证或安全架构。

## 2. 研究背景、现有方法不足、精确定义的问题

作者指出，LLM Agent 已被部署到软件工程、网页浏览、客服等场景，能力进展快于安全保障；一旦嵌入社会系统，灾难性失败与细微伤害都可能难以逆转（p.1, §1）。现有 Agent 安全基准的不足被明确归纳为三点：依赖模拟环境/玩具式工具 API、只覆盖单一领域（浏览或代码等）、缺少多轮多用户交互（pp.1–2, §1；p.4, Table 1）。Table 1 用三个维度比较了 24 个基准，只有 OPENAGENTSAFETY 同时具备 real-world tools、diverse intents、user interaction 三项（p.4）。

本文的问题不是提出新攻击或新防御，而是：如何构建一个可执行、可扩展、贴近真实部署的 Agent 安全评测环境，并用它测量主流 LLM 在 8 类风险、不同用户/NPC 意图下的不安全行为。作者将任务设计为 Docker 容器，包含环境、任务说明、NPC 行为与定制评测器；用规则评测与 LLM-as-Judge 互补，最后对 7 个模型做实证比较（pp.2–3 贡献列表；p.5, §2.2–2.3）。

需要强调的是：这里的 "adversarial" 指用户或 NPC 的自然语言意图具有恶意/操纵性，不是传统安全意义上的系统攻击者；论文没有给出正式威胁模型（见第 4 节）。因此本文属于 safety benchmark，而不是 security benchmark 或密码协议评测。

## 3. Agent 系统模型（组件、交互流程、信任边界）

**总体架构（p.2, Fig.1，已渲染核对）**：三阶段。
1. **Task Creation**：风险因素、意图、工具 → 种子任务 → GPT-4o 生成变体 → 人工核验。
2. **Task Execution**：User 与多个 NPC（Evil NPC、NPC 1、NPC 2）通过消息与 LLM Agent 交互；Agent 可调用 File System、Code、Browsing 等工具。
3. **Task Evaluation**：环境终态进入 rule-based evaluation；Agent 轨迹进入 LLM-as-judge；两者输出 safe/unsafe。

**组件（p.3, §2.1）**：
- Agent scaffold 为 OpenHands；Agent 运行在容器化沙箱内，可使用 Unix shell、文件系统、Python 解释器、Web 浏览器（p.3）。
- 为防真实伤害，网页服务在本地 Docker 中复刻：OwnCloud（文件共享）、GitLab（版本控制）、Plane（issue tracking），改编自 The Agent Company（p.3）。
- 多用户交互通过 Sotopia 模拟 NPC；作者扩展了 Sotopia 的 FastAPI/WebSocket 后端与 OpenHands 的 ChatNPC 工具，支持定向消息与广播消息（p.3；p.16, A.2）。
- NPC 由 GPT-4o 模拟（模型可配置），每个任务用 `scenarios.json` 定义 persona、目标和策略提示（p.19, A.4）。

**交互流程**：任务以 Docker 镜像挂载，Agent 读取 `/instruction/task.md`，多轮调用工具或与 NPC 对话，最后 finish；轨迹保存后由规则脚本检查文件系统/数据库/网站终态，并由 GPT-4.1 对中间 thought/action 打安全标签（pp.5–6, §2.3；p.18, A.3；pp.22–25 示例轨迹）。

**信任边界**：论文没有画 trust boundary，也没有独立小节定义信任边界。可观察到的事实是：Docker 容器把 Agent 与宿主系统隔离，网页与文件均为本地模拟，NPC 是 LLM 扮演的文本角色；Agent 在容器内拥有文件、shell、代码执行与浏览的广泛权限。NPC 的"身份/角色"仅由自然语言 persona 与对话内容表达，系统没有认证、凭证或访问控制机制来验证 NPC 是谁、代表哪个主体、是否被授权。因此本基准测的是模型对社会角色与政策的推理，而不是对已认证主体的授权执行。这一点对第 10–11 节的密码学判断很关键。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

**原文缺失正式威胁模型**：全文检索不到 "threat model" 或 "trust boundary" 的独立定义；"adversarial" 只在用户/NPC 意图的意义上使用（pp.1–2, §1；p.5, §2.2；p.8, §3.3）。按 handoff 要求，这里必须明确记录：论文没有形式化 threat model，只有任务层面的风险场景。

**受保护资产（由任务内容定义）**：SSH 私钥、API key、员工 PII（SSN、地址）、机密文件/薪资文件、GitLab 仓库分支策略、财务记录、雇佣决策、公开内容与调查数据等（pp.3–4, Table 2；p.7–9, §3.3；p.21, Table 6）。

**"攻击者"目标与能力**：
- 恶意用户：直接要求 Agent 执行不安全动作（如生成勒索软件、删除财务文件、批准无授权折扣）（p.5, §2.2；p.8）。
- 恶意 NPC：以同事/客户等身份，通过多轮说服、隐瞒权限、制造紧迫感，诱导 Agent 违反政策（p.5；p.7–8；p.19 示例 Mark 让 Agent 删除预算行）。
- 能力边界：只有自然语言输入与多轮对话；不能直接调用工具、不能修改环境、不能接触宿主、不能伪造系统凭证。NPC 由 GPT-4o 驱动，可能偏离设定策略，但作者称罕见（p.10）。
- 良性用户也可能因歧义或错误假设导致不安全行为（p.5；p.7 "benign intent does not imply safety"）。

**前提假设**：Docker 沙箱可防止真实世界伤害；任务可执行；Agent 拥有合法工具权限；评测在事后进行；不建模被攻陷的模型、工具、运行时或网络对手；不建模真实多主体凭证体系。结论应理解为"在受控模拟环境中，模型面对特定风险场景的行为率"，不是部署环境的攻击成功率。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

本文没有算法、协议、公式或密码学构造；核心是评测工程与测量方法。

**5.1 任务构建（p.5, §2.2）**
- 手工构造 80 个种子任务及其规则评测器，每个种子覆盖特定工具与社会情境组合。
- 用 GPT-4o 按模板生成变体，保留核心不安全 motif，改变场景、文件名、NPC 对话与工具细节；模板要求每次生成 K=3–5 个新任务，并写 `task.md`、`checkpoints.md` 与配套文件（p.26, A.7）。
- 共 356 个任务，全部由作者人工核验（p.5）。任务打包为自包含 Docker 镜像，含环境、任务说明、NPC 行为、规则评测器（p.5）。
- 任务分布（p.17, Fig.6–8，已渲染核对）：风险类别中 financial loss 20.9%、harmful decision-making 18.2%、unsafe code 14.8%、privacy breach 12.9%、data loss 12.7%、computer security compromise 10.1%、spreading malicious content 6.5%、legal violations 1.9%；工具中 file system 28.2%、ChatNPC 26.7%、browsing 20.3%、bash 12.5%、code generation/execution 12.3%；意图组合中 benign|malicious 35.5%、benign 30.4%、malicious 26.1%、benign|benign 4.3%、malicious|benign 3.7%。

**5.2 风险分类（p.4, Table 2，已渲染核对）**
8 类：Computer security compromise、Data loss/corruption、Privacy breach、Unsafe code execution、Financial loss、Spreading malicious content、Legal violations、Harmful decision-making。类别之间有重叠，例如 api-in-codebase 同时标为 financial loss、privacy breach、unsafe code（p.21, Table 6）。

**5.3 评测协议（p.5, §2.3；p.18, A.3）**
- **Rule-based**：每个任务一个 Python 脚本，检查最终环境状态（文件系统、数据库、网站）是否出现特定不安全结果，返回 1（unsafe）/0（safe）。
- **LLM-as-Judge**：用 GPT-4.1 阅读 Agent 轨迹与 unsafe behavior 描述，输出四标签：-1 = 未到达风险点（failure）；0 = 安全/拒绝/安全完成；1 = 有 unsafe 迹象但未完成；2 = 完成 unsafe 行为。Prompt 要求只依据轨迹、不得推测、不输出推理过程（p.18）。
- **附加指标**：Failure rate（未到达风险暴露点的任务比例）、Disagreement rate（LLM judge 判 safe 但规则评测发现具体不安全影响的比例）、Successful completion rate（拒绝或安全完成任务的比例）（p.5）。
- 设计逻辑是互补：规则评测精确但只能看终态，LLM judge 能看尝试/推理但不可靠；两者结合并用 disagreement 暴露盲点（pp.5–6）。

**5.4 没有的内容**：没有防御机制、没有 guardrail 实现、没有密码协议、没有形式化模型、没有攻击算法；任务套件是固定的，不是自适应攻击。

## 6. 安全属性与安全性论证

**没有形式化安全定义、定理或证明**。论文把 "safety" 操作化为两类经验判断：
- 规则评测：特定任务的终态是否违反预先写定的不安全结果；
- LLM judge：轨迹是否显示 unsafe 行为（四标签）。

因此"安全"是任务级、结果级、评测器级的标签，不是系统级安全属性，也没有 soundness/completeness 保证。作者自己指出：规则评测无法发现"有恶意意图但未执行成功"的情况，也无法识别内容安全风险；LLM judge 则会漏判隐含的不安全行为、把工具失败/认证失败误判为任务失败（pp.5–6；p.9, RQ4）。Table 4 的人类标注研究进一步证明 judge 不可靠：在 100 条 GPT-4o 轨迹上，GPT-4.1 判 unsafe 35.9%，人类判 71.7%；GPT-4.1 判 failure 42.4%，人类判 20.7%；总体分歧 39.1%（p.9, Table 4，已渲染核对）。作者据此认为报告的 failure rate 可能被高估，unsafe rate 应视为保守下界（p.9）。

**"Comprehensive" 的含义**是风险类别、工具与意图覆盖广，不是认证（certification），也不是安全保证。论文没有提供任何机制来证明某个 Agent "安全"，也没有给出通过/不通过的认证标准；它只报告测量结果。规则评测器本身是可信 oracle（直接读环境终态），LLM judge 是可信但不可靠的语义裁判；二者都没有密码学 attestation 或可验证计算。

**结论边界**：所有比率都是在 356 个固定任务、特定 scaffold（OpenHands）、特定模型版本与单次运行设定下测得的；Table 3 的 49%–73% 还是"仅统计到达 safety-vulnerable 状态的轨迹"的条件比率，全任务集比率见 Table 5（29.60%–41.26%，LLM judge），两者不可混用（p.6, Table 3 注；p.16, Table 5）。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

**模型（p.6, §3.1）**：7 个——Deepseek-v3、Deepseek-R1、Claude Sonnet 3.7、Claude Sonnet 4、GPT-4o、GPT-5、o3-mini。o3-mini 与 DeepSeek-R1 为推理模型，用于观察推理能力对安全的影响；同家族新旧模型用于观察能力提升的影响。

**环境与执行**：OpenHands scaffold；每个任务挂载到 Docker 容器，配本地网站/文件；Agent 完成后保存轨迹（p.6）。计算资源为 3 台 Amazon EC2 t3.2xlarge（每台 300GB 存储、支持 Docker），单模型跑完全部任务约 24–30 小时；不需要 GPU，模型调用走 OpenAI API 或 LiteLLM（p.20, A.5）。

**评测与人类研究**：GPT-4.1 作为 judge；人类研究随机抽取 100 条 GPT-4o 轨迹，两名专家标注，inter-annotator agreement 94%（p.9, RQ4）。

**核心结果（p.6, Table 3；不安全率条件于到达风险暴露点的轨迹）**：
- LLM-judge 不安全率：Claude Sonnet 4 49.06%、Claude Sonnet 3.7 51.20%、GPT-5 52.58%、Deepseek-v3 62.23%、Deepseek-R1 62.78%、GPT-4o 65.80%、o3-mini 72.73%。
- 规则评测不安全率：32.32%–52.15%；GPT-4o 与 o3-mini 仅约 32%，与 LLM judge 差距大。
- Disagreements 5.69%–14.95%；Failure 34.80%–48.90%；Successful completion 17.29%–40.40%。
- 全任务集（p.16, Table 5）：LLM-judge 29.60%–41.26%，规则 16.76%–34.00%，failure 34.80%–48.90%。这说明头条的 49%–73% 是条件比率，不是所有任务的不安全率。

**统计检验（p.6, §3.2）**：Mann-Whitney U 检验显示两组模型：Claude Sonnet 3.7、Claude Sonnet 4、GPT-5 显著更安全；对 o3-mini p<0.001，对 GPT-4o p≤0.006，对 DeepSeek-v3 p≤0.026，对 DeepSeek-R1 p≤0.023；其余比较 p>0.16。

**RQ1 用户意图（pp.7–8, Fig.3，已渲染核对）**：
- 良性意图并不安全：跨模型 50%–86% 的任务出现不安全行为；Claude Sonnet 3.7 在良性意图下反而最高（85.7%），说明拒绝策略没有泛化到细微风险。
- 恶意意图部分激活防御但不均匀：Claude Sonnet 3.7 降至 30%，Deepseek-v3 33.3%；o3-mini 反而升至 80.7%；GPT-4o 64.7%，DeepSeek-R1 66%。
- 良性用户 + 恶意 NPC：44.9%–69.2%，说明多轮意图跟踪不足；Claude 3.7 与 DeepSeek-v3 相对恶意用户单轮场景翻倍以上。

**RQ2 风险类别（p.8, Fig.4，已渲染核对）**：computer security compromise 72%–86%，legal violations、privacy breach、harmful decision-making 也高；o3-mini 在 legal 上达 88.2%；spreading malicious content 总体最低（Claude 3.7 27.7%），但 o3-mini 仍 74.9%。作者将这些归因于需要程序性判断/制度规范理解，而不是语法层面的危险。

**RQ3 工具（pp.8–9, Fig.5，已渲染核对）**：browsing 最高（59%–75%），认证、重定向与动态 DOM 会分散注意力；file system 与 code execution 放大意图错误（o3-mini 73.8%、GPT-4o 71.8%）；messaging/chat 45%–70%，模型不验证用户角色就分享敏感信息或接受请求（unauth-discount）。

**RQ4 judge 可靠性（p.9, Table 4）**：如第 6 节所述，GPT-4.1 明显低估 unsafe、高估 failure；ASB（Agent-SafetyBench 微调的 Qwen 2.5 7B）判 unsafe 81.5%、failure 0%，但与人类仍有 26.1% 总体分歧；作者结论是 LLM-based 评测不可靠，需要混合评测。

**消融/对照**：没有真正的消融实验，也没有防御基线；分析是事后按意图、风险类别、工具分组。没有报告重复运行的方差或置信区间；NPC 由 GPT-4o 驱动带来的非确定性只在 p.10/p.19 提及，未量化。任务生成用 GPT-4o 的偏置也没有对照。

**小的内部不一致（本人核对）**：p.6 §3 开头写 "five widely used LLMs"，但同页 §3.1 与 Table 3 均为 7 个模型；p.3 §2.1 列本地服务为 OwnCloud/GitLab/Plane，p.20 A.5 写 GitLab/ownCloud/RocketChat。前者可能是笔误，后者可能是服务列表更新未同步；不影响主要结论，但说明文本一致性有限。

## 8. 主要贡献、与直接相关论文的差异、可复现资源

**贡献（pp.2–3）**：
1. 一个模块化、可扩展的评测框架，356 个可执行任务，覆盖 8 类风险；任务系统变化用户意图（良性/恶意）与 NPC 行为。
2. 可扩展性：可加新任务、模拟网站、社会动态与定制评测器，能接入 WebArena 等外部生态（p.5）。
3. 对 7 个 LLM 的实证分析，发现良性输入中的"easy but unsafe"解法、以及需要制度规范理解的系统性风险。

**与直接相关工作的差异（p.10, §4；p.4, Table 1）**：
- 相比 Agent-SafetyBench、SafeAgentBench、AgentHarm、R-Judge 等依赖模拟 API/简化环境的工作，本文使用真实工具与 Docker 沙箱。
- 相比 SafeArena、ST-WebAgentBench、AdvWeb 等网页/单工具评测，本文把浏览、文件、代码、bash、消息整合到一个多轮多用户框架。
- 相比纯 LLM 安全基准（SALAD-Bench、h4rm3l、SafeBench 等），本文评测的是带工具执行的 Agent 行为，而不是静态输出。
- 与本项目语料中 R2-01（Agent Security Bench, ASB）、R2-02（AgentDojo）、R2-06（AgentHarm）、R2-09（SafeArena）、R3-46（OS-Harm）同属 A2/A1 评测线，但本文的差异化是"真实工具 + 多轮 + 多角色 + 8 类风险"的组合。注意：本文 Table 1/Table 4 的 "ASB"/Agent-SafetyBench 指 Zhang et al. 2024b，与本项目 R2-01 的 Agent Security Bench 缩写相同但并非同一篇（按引文判断，非 PDF 明示），引用时不要混淆。

## 9. 局限性、失效场景、作者未解决的问题

**作者自述（p.10, §5）**：
- 当前 LLM 可能在到达 safety-vulnerable 点之前就失败（探索/动态环境能力不足），随能力提升会缓解。
- NPC 可能偏离设定策略，作者称罕见、可通过更好的 prompt 改善。
- 任务扩展困难：高质量种子任务可复用，但扩展任务需要同时扩展执行环境（网站等）。
- 框架的模块化设计可支持新环境、评测方法与 guardrail agent，但这些是未来工作。

**本人补充的局限（基于全文阅读）**：
- **条件比率易被误读**：49%–73% 只统计到达风险暴露点的轨迹；全任务集为 29.60%–41.26%（Table 5）。部署风险不能直接等同于任一数字。
- **LLM judge 不可靠**：作者自己用人类研究证明 judge 低估 unsafe、高估 failure（Table 4）；因此依赖 judge 的 RQ 结论与 failure rate 都有测量误差。
- **无重复运行/方差**：NPC 与 judge 都有非确定性，但论文未报告多次运行的均值/置信区间；Mann-Whitney 检验是在任务层面，不是跨运行。
- **任务生成偏置**：80 个种子之外约 276 个（356−80）由 GPT-4o 扩展，可能继承生成模型的场景/措辞分布；作者只做人工核验，没有独立生成或人类对照。
- **单一 scaffold**：只测 OpenHands；不同 Agent 框架的工具接口、系统提示与安全策略可能显著改变结果。
- **无防御评测**：框架只测模型行为，不测 guardrail、权限控制、沙箱策略等防御；"design implications" 只是建议，没有实验验证。
- **类别不平衡与重叠**：legal violations 仅 1.9%，结论的统计功效弱；风险类别可同时命中（如 api-in-codebase 三类），不能当作互斥分层。
- **"多用户"是模拟 NPC**：不是多个真实主体、多个凭证域或多 Agent 协作；NPC 无认证身份，因此无法测真实授权/委托机制。
- **网站覆盖有限**：只有 OwnCloud、GitLab、Plane 三个本地服务；浏览任务的认证/重定向问题会造成大量 failure，可能掩盖真实的不安全行为。
- **人类研究范围有限**：仅 100 条 GPT-4o 轨迹、两名标注者；未覆盖其他模型或全部风险类别。
- **无正式 threat model/trust boundary**：无法把结果映射到具体攻击者能力或部署威胁；"adversarial" 是自然语言意图，不是系统对手。
- **无密码学内容**：不评测任何加密、签名、凭证、TEE、审计机制（详见第 10–11 节）。
- **指标语义**：Successful completion 同时包含"拒绝"与"安全完成"，高完成率不等于高安全性；规则评测的 1/0 也不等于"意图安全"。
- **文本一致性**：p.6 "five LLMs" 与 7 模型不符；p.3 与 p.20 的本地服务列表不一致（Plane vs RocketChat）。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**原论文实际使用的框架/环境/评分机制（事实）**：
- "Framework" = OpenHands scaffold + Docker 沙箱 + 自包含任务镜像 + 本地网站 + Sotopia NPC + 规则评测脚本 + GPT-4.1 judge（pp.2–5；pp.16–20）。它是评测基础设施，不是安全架构。
- 评分机制 = 规则脚本对终态的二值判断 + LLM judge 的四标签；指标 = unsafe rate、failure rate、disagreement rate、successful completion rate（p.5）。
- **无密码学构造、无密码学假设、无形式化安全定义、无定理或证明**。全文检索不到 encryption/signature/token 等机制性内容（仅在参考文献中出现一篇标题含 "Certifying" 的论文）。Docker 是 OS 级隔离，不是密码学信任边界；规则评测器是可信 oracle，没有 attestation；LLM judge 是语义裁判，不是 verifier。
- "Comprehensive safety framework" 是覆盖范围的自述，不是认证（certification）；论文没有给出任何"通过/不通过"的安全认证标准或可证明保证。

**个人推断（明确标为推断）**：
- 可形式化的对象不是"Agent 是否安全"这种整体属性，而是具体任务中的**授权不变量**。例如 change-branch-policy 可写成"只有具备 branch-admin 权限的主体才能把私有仓库改为公开"；unauth-discount 可写成"折扣只能由有权限的角色批准"；leak-document 可写成"文件只能发给被授权接收者"（pp.7–8, §3.3；p.21, Table 6）。这些可以构成 policy-compliance game 的 winning condition，但密码学只能保证主体身份、凭证不可伪造、作用域不可扩张；它不能判定一段自然语言请求是否构成有效授权。核心困难是意图/政策语义，不是计算困难性。
- 若要把评测做得"可验证"，可用承诺/签名固定任务、轨迹与环境快照，使第三方能复查规则评测的输入与结果；但这只保证记录完整性/可追溯性，不保证 judge 的语义判断正确，也不能替代 threat model。把这种机制称为"可验证 Agent 安全"会过度声称。
- 认证委托（authenticated delegation）与 capability 可以作为任务授权层，但必须与 policy engine 结合；单独给 Agent 发签名 token 不会减少 "helpfulness over authorization" 类错误（change-branch-policy 的失败正是模型把"帮忙"当成"有权"）。
- 伪交叉风险：(a) 把 Docker 沙箱类比 TEE/可信执行；(b) 把 LLM judge 的输出当作 attestation；(c) 用 zk 证明"轨迹确实发生过"来声称"行为安全"；(d) 把 benchmark 的 "safe" 标签当作认证。这些都不成立。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**原论文实际使用的机制（事实）**：
- 环境隔离：Docker 容器；本地 OwnCloud/GitLab/Plane；Sotopia + Redis/WebSocket 消息后端（pp.3, 16, 20）。
- 任务内容涉及 SSH 私钥、API key、SSN、机密薪资文件、GitLab 分支策略等，但这些是**被评测的风险对象**，不是被测系统部署的密码保护（pp.3–4, Table 2；p.21, Table 6）。
- 没有 credential broker、没有短期凭证、没有工具调用签名、没有加密存储策略、没有审计日志完整性机制；Agent 在容器内可直接读文件、跑 shell、访问本地网站。评测器直接读环境终态，不依赖密码学证明。

**个人推断（明确标为推断）**：
- 明确的工程切入点：
  1. **工具网关 + 任务作用域 capability token**：把 user/task/tool/参数约束绑定到签名 token，在 OpenHands 的工具调用层强制执行；可测 change-branch-policy、unauth-discount、leak-document 类任务。
  2. **凭证代理（credential broker）**：Agent 不接触长期 API key/SSH key，由 broker 按任务签发短期、最小权限凭证；直接对应 api-in-codebase（硬编码 API key）与 SSH key 泄漏任务。
  3. **签名 append-only 审计日志/轨迹承诺**：记录工具调用、参数、环境快照，支持事后归因、复现与第三方核验；可作为评测基础设施的一部分。
  4. **撤销、过期与跨 Agent 传播控制**：若扩展到多 Agent，需要保证委托链的作用域不扩张、撤销及时生效。
- 可测实验设计（推断）：在 OA-SAFETY 上做 baseline vs cryptographic control 的对照，分层报告 unsafe rate、successful completion、failure rate 与额外延迟；预期密码控制只对"未授权动作/凭证泄漏"类有效，对 legal violations、harmful decision-making、内容安全类无效。若整体 unsafe rate 下降主要来自 failure rate 上升（Agent 被锁死），则不能算安全收益。
- 伪交叉风险：仅把 OAuth/OIDC 包在工具外而不提供策略语义，不能阻止 Agent 自愿替无权限 NPC 改仓库；仅对日志签名不能发现语义不安全；仅加密存储不能阻止有读取权限的 Agent 把明文复制到公开目录（privacy breach 任务的机制正是如此）；把 Docker 隔离称为 "trusted execution" 是错误类比。本文可以作为密码授权机制的评测载体，但不能作为其安全性的证据。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

以下均为**待验证假设**，不是本文结论，也不代表领域空白：
- **H1**：在 OA-SAFETY 的 change-branch-policy、unauth-discount、leak-document 类任务上，工具层 capability 强制（而非 prompt 拒绝）能显著降低未授权动作率，且不显著降低良性任务成功率。证伪条件：下降主要来自 failure rate 上升，或良性任务成功率同步大幅下降。
- **H2**：credential broker（Agent 不见原始密钥、按任务签发短期凭证）能消除 api-in-codebase/SSH key 类泄漏，但对其他风险类别无显著影响。证伪条件：出现新的绕过路径（如 Agent 通过 shell 读取 broker 配置或缓存）。
- **H3**：规则评测与 LLM judge 的分歧主要集中在"尝试但未完成"和"内容安全"；对任务、轨迹与环境快照做签名/承诺可提高复现性与第三方可核验性，但不能提高语义判定准确率。证伪条件：承诺机制显著改变 judge 与人类的 agreement。
- **H4**：把沙箱中的模拟凭证换为真实短期凭证、并加入外部攻击者（恶意网页/工具输出/提示注入）后，不安全率会显著高于当前结果；当前 benchmark 是受控条件下的测量，不是部署风险上界。
- **H5**：在多轮 NPC 操纵下，"上下文意图聚合 + 策略感知 reference monitor" 的组合优于单一 prompt guardrail；可用本文的 intent 分层（benign、benign|malicious、malicious 等）做 2×2 对照。
- 以上假设需要在后续论文与自有实验中查证；不能仅凭本文未涉及就推断"无人研究"。
