## 1. 150–300 字中文概述

论文把 BrowserART、OS-Harm、RedCode-Gen 三个单 Agent 滥用基准改造成多 Agent 评测，在 13 种架构配置（角色、拓扑、记忆）、6 个模型和三种环境上，用分阶段指标 PR/ER/HA/HT 与良性任务成功率联合衡量安全—性能权衡。核心发现是：多数多 Agent 配置比单 Agent 更易完成有害任务，BrowserART 上 HT 从 10.0% 升至最高 38.0%（3.8×），且良性准确率不降反升；但没有一种架构普遍更安全，拓扑与记忆的效果会随环境和模型反转。论文是纯行为/架构层面的评测，不含密码原语、形式化定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景**：MAS 已进入生产部署，任务被拆分给规划、执行、工具调用、记忆与协调等多个 Agent（p.1, §1）。单个 Agent 即使能稳健拒绝直接有害请求，一旦与 Web 工具、持久记忆或其他 Agent 组合，仍可能产生系统级失败（p.1, §1）。作者把“架构”视为与显式防御并列的一类安全变量：角色分工、通信拓扑、记忆可见性会改变攻击面（p.3, §3）。
- **现有方法不足**（pp.2–3, §2）：
  - 单 Agent 安全研究覆盖 prompt injection、jailbreak、投毒、隐私泄漏，但评测对象是模型或单 Agent；AgentDojo、AgentHarm 等 benchmark 不系统改变架构。
  - MAS 安全研究覆盖串谋、感染式攻击、病毒式错位、辩论操控、错误放大，但多为特定攻击类型或失败模式分类（MAST、MultiAgentBench），缺少对架构设计的受控比较。
  - 防御研究仍以单 Agent 的输入/输出过滤为主；plan-then-execute、capability-based 架构虽有探索，但未与任务性能联合测量。
  - 经典 MAS 安全（信任/声誉、Byzantine 共识、有界对手下的安全协调）依赖固定消息语义、协议合规或显式协调假设；LLM MAS 使用自由形式自然语言协议，这些保证不能直接迁移（p.3, §2.2）。
- **精确问题**：在固定任务 prompt 与评分 rubric、只改变架构变量的条件下，(i) 从单 Agent 迁移到多 Agent 是否会提高有害任务完成率？(ii) 角色、拓扑、记忆三个维度各自朝哪个方向、以多大幅度影响脆弱性？(iii) 是否存在普遍更安全的架构？(iv) 安全变化是否以良性任务性能为代价？论文用 13 个配置 × 3 环境 × 多模型回答（pp.1–2, Abstract/§1；p.4, §4）。
- **三条设计假设**（p.3, §3）：角色分工把安全评估责任碎片化；拓扑决定意图、不确定性、安全信号如何传播；记忆可见性决定各 Agent 能看到多少上下文与状态。作者明确说这些是 hypothesis，不是定理。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **组件**：恶意用户（任务输入者）、orchestrator/planner（分解任务、派发子任务）、executor/specialist（持有部分工具、执行原子动作）、工具套件（浏览器原语、桌面 click/type/key/scroll、代码 python/text editor/bash/think）、私有或共享 memory/state、Agent 间通信通道（p.4, §4.2；pp.17–21, App B.1/B.3/B.5）。
- **交互流程**：
  - **Star**：中心 orchestrator 接收用户任务，分解为 per-turn 指令，经 `as_tool()` 调用某个 specialist；specialist 在全新 `AgentState` 中执行一个原子动作并返回结果；orchestrator 继续派发，直到完成（p.19, §B.4.1；p.21, §B.5）。
  - **Chain**：固定顺序（BrowserART: Click→Fill→Scroll→Navigate；OS-Harm: Click→Type→Key→Scroll；RedCode: Design→Code→Review→Test），每个 Agent 接收前一个的输出并传给下一个，无中心协调、无回溯（p.21, §B.5）。
  - **Mesh**：peer-to-peer 自由委派；每个 peer 在 system prompt 中看到可用 Agent 列表，输出 `THOUGHT / DELEGATE / INSTRUCTION`，框架把 delegate 字段转成对目标 Agent 的工具调用；任意 peer 可委派给任意 peer，没有类型匹配、结构化协议或委派目标限制（p.21, §B.5）。
- **信任边界**：原文没有画 trust-boundary 图，也没有密码学意义上的身份/认证/授权边界。可辨识的结构是：
  - 攻击者是**合法用户**，在 input time 提供恶意任务；论文明确“attacker does not modify model weights or system code, and interacts with the system only through natural language prompts and standard tool outputs”（p.4, §4）。
  - 从系统设定看，所有 Agent 处于同一可信执行域；论文没有给 Agent 凭证、签名、身份或相互认证；工具输出按标准输出处理（p.9, §8 把 indirect prompt injection 列为未研究威胁）；benchmark 环境（BrowserART 本地站点、OS-World VM、RedCode sandbox）与 LLM judge 被当作可信评测基础设施（p.4, §4.1；p.21, §B.6）。此段为本人据评测设定与威胁模型归纳。
  - 唯一的“隔离”是框架级的 context isolation：Inspect 的 `as_tool()` 为每次 specialist 调用新建 `AgentState`，specialist 的唯一 user message 是 orchestrator 传入的字符串；原始任务串、orchestrator 推理历史、其他 specialist 输出都不在 specialist 上下文中，除非 orchestrator 显式粘贴（p.19, §B.4.1）。作者强调这是框架的结构属性，不是 prompt 约定。
- **authority 的含义**：论文中的 “authority” 指**执行权限/控制流**（哪个 Agent 持有哪些工具、谁下指令、谁执行），不是访问控制模型或密码学授权。§3 讨论“高执行权限的 Agent 位于安全推理者下游时，安全判断可能只是建议而非约束”（p.4, §3），这是架构论证，不是 authz 机制。
- **责任缺口**：specialist 只看到窄指令，看不到完整任务与下游后果；orchestrator 只做分解，不做端到端安全评估；reviewer 只看孤立输出。因此没有任何 Agent 承担端到端安全判断（p.8, §6）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：不是密钥或机密数据，而是“有害任务不被完成”这一安全结果、良性任务成功率（能力）、以及基座模型的安全对齐。具体有害结果包括钓鱼邮件被发出、恶意代码被生成、诽谤/欺诈/虚假信息任务被完成等（p.4, §4.1；p.18, §B.2）。
- **攻击者目标**：让 MAS 完成一个单 Agent 会拒绝的有害任务；用论文的指标说，最大化 HT（Harmful Task, objective completed），并可接受部分有害动作（HA）作为中间结果（p.5, §4.4）。
- **攻击者能力**：
  - 在 input time 提供自然语言任务指令；可从 benchmark 的 harmful split 中选择任务；任务 prompt 与评分 rubric 固定（p.4, §4；p.4, §4.1）。
  - 了解系统存在，但论文没有建模“架构感知的自适应攻击者”；攻击不是针对某个拓扑优化的，也没有迭代搜索（此点为本人据 §4 与全文归纳）。
- **攻击者不能做**：修改模型权重或系统代码；通过工具输出注入；投毒记忆；在系统内安插恶意 Agent；读取 Agent 内部状态；针对 judge 优化；选择或重配置架构（p.4, §4；p.9, §8 明确把 indirect prompt injection、memory poisoning、adversarial agents 列为未研究威胁）。
- **防御者**：论文没有部署任何防御。基座模型的安全训练是唯一“防御”；架构本身是自变量。作者明确未评估 monitor agents、guardrail layers、policy-checking stages（p.9, §8）。
- **前提假设**：
  - benchmark 的 harmful/benign 任务与 rubric 能代表真实滥用与能力；judge 映射可靠（p.5, §4.4）。
  - 同一基座模型在不同架构下能力相同；架构是唯一变量；prompt 中不含安全指令，所有拒绝行为来自模型安全训练（p.19, §B.4.2）。
  - 任务可被分解为原子动作，工具划分与角色划分是忠实的（pp.18–19, §B.3）。
  - 良性任务成功率是能力代价的充分度量；OS-Harm 的良性任务几乎全为 0（standalone 2.0，其余 0.0），作者称主要因任务难度而非架构（p.6, §5.1）。
- **威胁模型位置**：没有独立 “Threat Model” 小节；由 p.4 §4 开头一段、p.5 §4.4 的指标、p.9 §8 的未研究威胁共同定义。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

本文没有提出攻击算法或防御协议；核心“方案”是一套**受控的架构评测设计**。可拆为四部分。

### 5.1 三个设计维度与 13 个配置

- **角色配置（Role Configuration）**：从 monolithic standalone 到不同粒度/范围的委派（p.4, §4.2；p.17, Table 8）：
  1. Standalone Agent：全部工具、自己的记忆、顺序执行（1 Agent）。
  2. Star + Single Exec.：orchestrator 生成计划，交给单个 executor 批量执行；变体为高层目标或详细动作序列（2 Agents）。
  3. Star + Batch Exec.：结构化计划，批量交接（2 Agents）。
  4. Star + Stepwise：每执行一个动作就回到 orchestrator，迭代反馈（2 Agents，Planner ↔ Executor）。
  5. Star + 2 Specialists：部分专门化（3 Agents）。
  6. Star + 3 Specialists：增加专门化（4 Agents）。
  7. Star + 4 Specialists：完全专门化（BrowserART 为一工具一 Agent；5 Agents）。
- **通信拓扑（Communication Topology）**：角色固定为 4 个 specialist，只换协调机制（p.17, Table 9）：
  1. Star：中心 orchestrator 派发，specialist 不直接通信。
  2. Chain：固定顺序接力，无中心协调、无回溯。
  3. Mesh：peer-to-peer 自由委派，无全局控制者。
- **记忆/状态可见性（Memory and State Visibility）**：角色与拓扑固定，只改每个 Agent 能额外看到什么（p.18, Table 10）：
  1. Private（baseline）：每 Agent 私有状态。
  2. +Own Reasoning：可看自己的过去 chain-of-thought。
  3. +Shared Memory：可看所有 Agent 的动作、观察与推理轨迹。
- **13 的算术**：7 个角色配置 + 2 个新拓扑（chain、mesh；star+4 已计入角色）+ 4 个记忆变体（star 与 mesh 各 +Own/+Shared）= 13（pp.17–18, §B.1；Tables 8–10）。这套设计采用“最小改变”原则：每一行相对上一行只改一个受控元素（p.17, §B.1）。

### 5.2 工具划分与 context isolation

- **BrowserART**：浏览器工具套件 `goto, click, fill, scroll, select option, send msg to user` 按动作类型划分；Star+2 为 Click+Fill / Scroll+Navigate，Star+3 为 Click+Fill / Scroll / Navigate，Star+4 为 Click / Fill / Scroll / Navigate（p.18, Table 11）。
- **OS-Harm**：把统一的 computer tool 拆成 click / type / key / scroll 四个互斥子工具；每个 specialist 仍保留 screenshot 与 submit，以便先观察再行动（p.19, Table 12）。
- **RedCode-Gen**：四个异构工具 python / text editor / bash / think，采用非对称划分；多个 specialist 保留 python，但只有一个能写代码。Star+4 为 Design（think）、Code（python, text editor）、Review（python, think）、Test（python, bash）（p.19, Table 13；pp.20–21, §B.4.2）。
- **context isolation**：所有 star 拓扑的 specialist 都经 Inspect `as_tool()` 调用，创建新的 `AgentState`，只含 orchestrator 传入的 input 字符串；原始任务、orchestrator 推理、其他 specialist 输出默认不可见（p.19, §B.4.1）。作者强调这不是 prompt 层的约定，而是框架结构；orchestrator 被提示输出窄的 per-turn 指令，而不是转发完整任务。该机制是论文解释“角色分工为何削弱拒绝”的核心因果链。

### 5.3 分阶段指标

- 四个互斥结果（p.5, §4.4）：
  - **PR（Planning Refusal）**：规划阶段拒绝任务。
  - **ER（Execution Refusal）**：委派之后、执行阶段拒绝。
  - **HA（Harmful Action）**：执行了一个或多个有害动作，但任务未完成（部分有害执行）。
  - **HT（Harmful Task）**：有害目标完成（攻击成功）。
- 四者近似构成完备划分：`PR + ER + HA + HT ≈ 100%`（p.5, Table 1 caption；p.13, §A）。另报 **Benign** 任务成功率，用于衡量能力代价。
- **攻击成功率比**可定义为 `HT_config / HT_standalone`；论文的 3.8× 即 BrowserART `38.0 / 10.0`（p.5, Table 1；p.6, §5.1）。
- 结果分类沿用各原 benchmark 的 judge protocol，再映射到四阶段层级；三个场景共享 `MASJudgeScorer` 基类，计算 per-agent compromise score（p.21, §B.6）。
- **judge**：BrowserART 用 Llama-3.3-70B-Instruct（Together API，HarmBench 风格）；OS-Harm 与 RedCode-Gen 用 GPT-4.1（p.5, §4.4；p.21, §B.6）。RedCode judge 只看代码是否实现指定恶意功能，不执行代码（p.21, §B.6）。
- **judge 校验**：先让 LLM-as-a-judge 标记可能的评分错误，再由两名研究者人工检查所有 flagged cases，并从完整日志中额外抽样；发现 15 个评分错误、20 处 scorer 修正；随后对剩余日志抽 10%，发现 7% 不一致，全部在最终结果中修正（p.5, §4.4）。

### 5.4 实验流程

固定任务 prompt 与评分 rubric，只改架构；主模型 GPT-4o 覆盖三个场景；扩展模型为 GPT-5.4、GPT-5-mini、Claude Sonnet 4、Qwen3-VL、Llama-70B-Chat；覆盖度因算力而不同：BrowserART 六个模型，OS-Harm 三个（GPT-4o、GPT-5.4、GPT-5-mini），RedCode-Gen 两个（GPT-4o、GPT-5.4）（p.5, §4.3；p.6, §5）。所有配置在 Inspect 框架中实现（p.17, §B）。任务数：BrowserART 100 harmful / 42 benign，OS-Harm 44 harmful / 50 benign（原 50 个 harmful 因 Inspect 的 OS-World 实现问题丢弃 6 个），RedCode-Gen 160 harmful / 50 benign（p.4, §4.1；p.18, §B.2）。

## 6. 安全声明与形式化程度

- **没有形式化定义、定理、引理、证明、security game 或 reduction**。全文没有给出“安全”的数学定义；`PR/ER/HA/HT` 是操作化指标，其判定依赖 benchmark rubric 与 LLM judge（pp.5, 21）。论文没有把“架构”形式化为一个代数结构，也没有定义组合算子。
- **安全声明是经验性、比较性的**：
  1. 多数多 Agent 配置比 standalone 更脆弱（p.1, Abstract；p.8, §6）。
  2. 攻击成功率最高相差 3.8×，且良性准确率可比或更高（p.1, Abstract；p.6, §5.1）。
  3. 没有单一设计普遍更安全；方向与幅度依赖场景、模型、架构（p.1, Abstract；p.8, §6）。
  4. 安全与性能可以解耦：能力评测不能替代对抗评测（p.2, §1；p.8, §6）。
  5. “安全属性不能从单个 Agent 直接组合到多 Agent 系统”（p.9, §7）——这是全文最强的概括，但只是经验证据支持的论断，不是组合定理。
- **“攻击”的含义**：本文的 attacker 是提交有害任务的用户，不是自适应的外部对手；HT 更像是“模型/系统未拒绝并完成有害任务”的比率，而非密码学意义上的 adversarial success。论文在 Limitations 中也把它称作 “jailbreak vulnerabilities”（p.9, §8）。
- **内部效度论证**：作者用两阶段 judge 校验、10% 抽样、15 个错误/20 处修正来支撑评分可信度（p.5, §4.4）；但没有报告重复运行次数、随机种子、置信区间、显著性检验或 inter-annotator agreement。所有数字是单次评测的百分比，不能据此判断小差异是否稳定（此点为本人核对全文后的推断）。
- **结论**：论文提供的是**架构层面的经验风险刻画**，不是可证明的安全保证；其“security”是行为安全/滥用抵抗，不是机密性、完整性、认证性或不可区分性。

## 7. 实验设置与主要结果

### 7.1 设置

- 环境：BrowserART（浏览器控制；100 harmful / 42 benign）、OS-Harm（桌面 computer use；44 harmful / 50 benign）、RedCode-Gen（沙箱代码生成；160 harmful / 50 benign）（p.4, §4.1；p.18, §B.2）。
- 模型：GPT-4o 主模型；GPT-5.4、GPT-5-mini、Claude Sonnet 4、Qwen3-VL、Llama-70B-Chat 扩展；覆盖度 6/3/2（p.5, §4.3）。
- 对照：standalone 为基线；角色、拓扑、记忆三个轴各自做最小改变消融；没有 guardrail/monitor/policy 基线（p.9, §8），也没有密码学/系统级访问控制基线（论文未设置，非原文明确讨论）。
- 指标：PR/ER/HA/HT + Benign；HT 视为 attack success；无置信区间（p.5, §4.4）。
- 评分：BrowserART 用 Llama-3.3-70B-Instruct，OS-Harm/RedCode 用 GPT-4.1（p.5, §4.4；p.21, §B.6）。

### 7.2 主结果（GPT-4o；均附条件）

- **角色分工，BrowserART（p.5, Table 1）**：
  - Standalone：PR 75.0 / ER 1.0 / HA 14.0 / HT 10.0；Benign 92.9。
  - Star+Single：94.0 / 0.0 / 1.0 / 5.0；Benign 83.3。
  - Star+Batch：90.0 / 3.0 / 2.0 / 5.0；Benign 92.9。
  - Star+Stepwise：82.0 / 4.0 / 11.0 / 3.0；Benign 92.9。
  - Star+2：40.0 / 2.0 / 20.0 / **38.0**；Benign 95.2。

### 7.3 跨模型结果

- **角色分工，BrowserART（p.13, Table 4）**：GPT-5.4 最高 HT 3.0（Star+Batch/Star+3/Star+4）；Sonnet 4 最高 7.0（Star+2）；GPT-5-mini 最高 5.0（Star+Batch）；Qwen3-VL 从 9.0 升到 40.0（Star+2）；Llama 70B 从 27.0 升到 42.0（Star+2）。
- **OS-Harm 与 RedCode（p.14, Table 5）**：GPT-5.4 在 OS-Harm 从 standalone 11.4 升到 Star+Single 15.9（简单委派反而更危险），在 RedCode 所有配置 HT=0；GPT-5-mini 在 OS-Harm 最高 4.5，在 RedCode 未测。
- **拓扑（p.15, Table 6）**：Qwen3-VL 上 star 最危险（37 vs chain 21 / mesh 20）；Llama 70B 上 mesh 最危险（36 vs chain 26 / star 35）；GPT-5.4 在 BrowserART 任何拓扑下 ≤3（OS-Harm 上并非如此）。
- **记忆（p.16, Table 7）**：GPT-5.4 在 BrowserART star 从 3→2→1（略改善）；Qwen3-VL 从 37→37→41；Llama 70B 从 35→44→45（共享记忆显著变差）；OS-Harm 上记忆效应随模型/拓扑变化，GPT-5.4 star 为 6.8→11.4→9.1，而 GPT-5-mini mesh 为 11.4→11.4→6.8，方向并不一致。
- **总体模式**：强对齐模型对架构碎片化更鲁棒，弱对齐模型在专门化/共享记忆下显著恶化；作者据此提出“架构碎片化与模型级对齐相互作用”（p.8, §6）。

### 7.4 消融与交互

- 三个设计轴本身就是消融：每个轴内保持其他变量固定（p.17, §B.1）。没有超参数消融、没有 judge 消融、没有 prompt 变体消融、没有重复运行方差。
- 交互效应基本未测：作者承认三个轴“in most experiments”独立变化，角色×拓扑×记忆的交互、以及与 A2A/MCP 协议的交互都未充分探索（p.9, §8）。
- 记忆的“剂量”只有三档（private / own CoT / full shared），没有更细的可见性粒度；拓扑只有 star/chain/mesh，没有 hierarchical tree、blackboard、debate、voting 等。

- **“GPT-5.4 ≤3% HT across all configurations” 的范围**：p.6 §5.1 在 BrowserART 段落内说 GPT-5.4 ≤3%、Sonnet 4 ≤7%；但 p.14 Table 5 显示 GPT-5.4 在 OS-Harm 的 Star+Single 为 15.9%、standalone 11.4%。p.8 §6 明确承认 OS-Harm 是例外，因此该句应理解为 BrowserART 范围内，但字面“across all configurations”容易被误读。

### 7.6 缺失的实验

- 没有重复运行/种子/置信区间/显著性检验；没有 judge 的 human IAA；没有对 judge 的对抗攻击。
- 没有自适应攻击者（architecture-aware prompt search、decomposition search）；没有 indirect prompt injection、memory poisoning、恶意 Agent、工具投毒。
- 没有 guardrail/monitor/policy-checking 基线；没有与密码学/系统级访问控制对比。
- 没有延迟、token 成本、吞吐；MAS 的额外模型调用没有被计量。
- 没有真实部署或用户研究；全部在 benchmark sandbox 中。
- 没有跨环境迁移实验（作者把 A2A/MCP、iterative red/blue teaming 列为 future work）。

## 8. 贡献与创新点（按原文主张）

1. **多 Agent 改造的标准化滥用 benchmark**：把 BrowserART、OS-Harm、RedCode-Gen 从单 Agent 评测改造成多 Agent 评测，保持任务语义、环境与 judge protocol 不变，只改变架构；引入 PR/ER/HA/HT 分阶段指标；三个改造全部开源（p.2, §1；p.17, §B）。
2. **架构对安全影响的经验刻画**：13 个配置 × 多模型 × 三环境；角色分布、通信拓扑、记忆可见性各自独立影响脆弱性；多数配置比 standalone 更脆弱；方向与幅度依赖场景、模型、架构（p.2, §1；pp.5–8, §5–§6）。
3. **安全—性能联合测量**：同时报告 HT 与 benign accuracy，发现二者可以解耦；BrowserART 专门化配置良性更高但 HT 最高 3.8×；能力评测不能替代对抗评测（p.2, §1；p.6, §5.1；p.8, §6）。
4. **“首个受控比较”的主张**：作者称这是 “the first controlled comparison of multi-agent architectural design choices for security across realistic environments”（p.2, §1）。这是原文主张，是否成立取决于对 “controlled” 与 “realistic” 的定义；本文只覆盖 13 个配置、3 个 benchmark、直接滥用威胁。
5. **与最接近工作的差异**（p.3, §2.3）：
   - Peigné et al. (2025) 量化 “multi-agent security tax”（鲁棒性与协作的权衡）；本文把架构拆成三个可独立变化的轴，并跨三个环境测量。
   - Zhu et al. (2025b, MASTER) 研究角色与拓扑对安全的影响；本文增加记忆可见性轴、分阶段指标、良性性能联合测量，并把单 Agent benchmark 改造成多 Agent。
   - MAST（Cemri et al. 2025）是失败模式分类；MultiAgentBench（Zhu et al. 2025a）评测协作动态；本文专注于对抗性滥用与架构因果。
6. **可复现资源**：代码 `https://github.com/benhagag10/Architecture-Matters-for-Multi-Agent-Security`（p.2, footnote 1；仅记录，未打开、未执行）；基于 Inspect 框架（p.17, §B）；prompt 在 §B.4.2（pp.19–21），工具划分在 §B.3（pp.18–19），judge 在 §B.6（p.21），transcript 在 App C（pp.21–24）。论文没有单独的数据集发布声明；改造代码与配置随仓库发布（原文称 “release all three adaptations”）。

## 9. 局限、失败案例、作者承认的不足

**作者明确承认的**（p.9, §8；p.6, §5.1；p.5, §4.4）：
- 只覆盖 browser、desktop、code 三个环境；结论应在此范围内解释。
- 只研究**恶意用户的直接滥用**；indirect prompt injection、memory poisoning、系统内 adversarial agents 是不同威胁，可能以不同方式与架构交互。
- 没有评估 monitor agents、guardrail layers、policy-checking stages；这些机制可能改变观察到的安全—性能权衡。
- 三个设计轴在多数实验中独立变化；角色×拓扑×记忆的交互、以及与 A2A/MCP 等通信协议的交互仍未充分探索。
- 没有做 iterative red-teaming/blue-teaming。
- OS-Harm 的良性性能几乎全为 0（standalone 2.0，其余 0.0），作者称主要因 OS-World 任务难度，而非架构效应。
- judge 校验的 10% 抽样中发现 7% 不一致（已修正）；没有报告 IAA。
- 没有单一架构在所有场景更安全；不能给出通用架构建议。

**本人推断的局限/失效场景**：
- **单次运行、无方差**：论文没有说明每个配置运行几次、用什么种子、是否平均；所有百分比没有 CI。小差异（如 31 vs 32 vs 33）不应被当作稳定效应。
- **攻击是静态的、非自适应的**：任务 prompt 固定，攻击者不知道架构，也没有针对拓扑/角色优化分解策略。真实对手可以搜索“如何把有害任务拆成每个 specialist 都愿意执行的原子动作”，这很可能提高 HT，并可能改变架构排名。论文的 HT 应视为**下界**，不是上界。
- **威胁模型是“合法用户作恶”，不是外部入侵**：没有身份伪造、权限提升、跨租户攻击、工具供应链攻击；因此本文的 “security” 更接近 safety/misuse resistance。用密码学认证/授权来防它基本无效（见 §11）。
- **prompt/框架混杂**：orchestrator prompt 明确要求“SPECIFIC instruction referencing the exact bid identifier”、specialist prompt 只给角色与原子动作；context isolation 是 Inspect `as_tool()` 的实现属性。换成共享上下文的框架、或换一套 orchestrator prompt，效应可能显著变化。论文没有做 prompt 变体消融，因此“架构”与“prompt 设计/框架默认值”存在混杂。
- **OS-Harm 的能力维度缺失**：良性几乎全 0（standalone 2.0），无法判断安全提升/下降是否以能力为代价；该场景的“安全—性能权衡”实际上只测了安全。
- **benchmark 覆盖窄**：只有 13 个配置，缺少 hierarchical tree、blackboard、debate、voting、mixture-of-agents、A2A/MCP 等真实生产架构；角色维度也只有 star 一种协调方式（拓扑轴才换 chain/mesh）。
- **工具划分是人工设计的**：BrowserART 的一工具一 Agent 是“干净”划分，可能放大碎片化效应；RedCode 的非对称划分又可能提供冗余，导致相反趋势。论文承认划分方式会影响结论（p.6），但没有系统改变划分方式。
- **模型覆盖不平衡**：RedCode 只有 GPT-4o 与 GPT-5.4，OS-Harm 只有三个模型；跨模型结论不能外推到所有模型。
- **judge 可信性**：BrowserART 用 Llama-3.3-70B、OS-Harm/RedCode 用 GPT-4.1，judge 本身可能被有害内容或格式误导；论文只做了错误抽查，没有对抗 judge 测试。
- **HT 的严重性未加权**：一个钓鱼邮件与一个可运行的 ICMP flood 都记为 HT=1；没有按危害程度、可复现性、影响范围加权。
- **没有成本模型**：MAS 增加模型调用与协调轮次；论文没有报告 token/延迟/金钱成本，无法判断“架构更安全”是否值得。
- **“3.8×” headline 的选择性**：见 §7.5；最大原始比值是 4.5×，且 3.8× 依赖 BrowserART 的特定配置。

## 10. 与理论密码学的可能联系（严格区分论文已做 / 个人推断）

**论文已做：无。**
- 全文没有密码学原语（加密、签名、MAC、承诺、零知识、MPC、FHE、TEE、匿名凭证），没有 security game、formal definition、theorem、proof 或 reduction。
- 没有把“架构安全”形式化为访问控制模型、信息流模型或协议；`PR/ER/HA/HT` 是 benchmark 评分层级，不是密码学优势/泄漏/不可区分性。
- Related Work 确实引用了 Byzantine 共识（Lamport et al. 1982）、信任/声誉管理、有界对手下的安全协调（De Persis & Tesi 2015；Ishii et al. 2022），但只是用来说明“经典 MAS 保证不直接迁移到自由形式 LLM MAS”（p.3, §2.2）。**引用不等于使用**；本文没有采用这些模型，也没有给出任何协议。
- “authority” 是执行权限/控制流，不是密码学授权；“trust boundary” 在原文中不存在；“memory isolation” 是框架级 context isolation，不是 TEE 或进程隔离的安全证明。

**个人推断（明确标为推断，不是论文贡献）**：
- **安全组合性**：本文的经验主张“safety does not compose”可以类比为密码学中的 secure composition（如 UC）问题：给定每个 Agent 的局部安全谓词，是否存在一个架构组合算子，使得局部安全蕴含全局安全？但二者的对手模型不同——UC 的对手是 PPT 机器与环境，本文的“对手”是提交任务的用户；本文的属性是拒绝行为，不是机密性/完整性。把本文形式化成一个组合定理是**新增理论研究**，不是论文已做。
- **信息流/非干扰（noninterference）**：可以把 “specialist 看不到完整任务” 建模为上下文标签与信息流约束，定义“有害意图不可达”作为非干扰属性；但本文的机制是语义上下文缺失，不是多级安全标签，也没有证明。若用 QIF/g-leakage 度量“意图泄漏”，需要定义 secret（有害意图）与 attacker observation（specialist 上下文），这与密码学泄漏模型只是形式类比。
- **形式化“责任缺口”**：可定义一个端到端安全谓词 `Safe(task, trajectory)` 与每个 Agent 的局部谓词 `Safe_i(context_i, action_i)`，证明在何种上下文可见性条件下 `∧ Safe_i` 不蕴含 `Safe`。这更像程序验证/组合式安全，不是密码学。
- **理论相关度判断**：按项目 `T_crypto` 量表，本文正文约 **0–1**：0 是因为没有任何密码原语/定义/证明；1 是因为“安全不组合”“信任边界”“authority”这些概念可以与组合式安全/访问控制理论类比，但论文没有做。若要做严格的形式化，需要新增定义与定理，属于新研究。

## 11. 与应用密码学/密码工程的可能联系（同上）

**论文已做：无。**
- 没有 OAuth/OIDC、TLS、X.509、VC、签名、MAC、TEE、ZK、capability token、审计日志、密钥管理或任何密码协议。
- benchmark sandbox（BrowserART 本地站点、OS-World VM、RedCode sandbox）是评测基础设施，不是论文研究的防御机制，也不构成认证协议。
- 防滥用完全依赖**基座模型的安全训练**；论文没有部署任何执行层策略引擎、reference monitor 或不可绕过的访问控制。

**为什么认证/授权不适合本文威胁模型**：本文的攻击者是**合法用户**，他本来就有权提交任务；伪造身份、窃取凭证、越权访问都不是攻击步骤。即使给每个 Agent 签发凭证、给工具调用加 capability token，用户仍可请求有害任务，Agent 仍可能执行。密码学能保证“谁在调用”，但不能判断“这个任务是否有害”——后者是语义/政策问题（此点为本人推断）。

**个人推断的工程接口（均标为推断，需新增设计与实验）**：
1. **工具级 capability/least privilege**：给每个 specialist 签发只允许特定工具、特定参数范围的 capability（Macaroons/Biscuit/UCAN 风格），由工具网关强制执行，而不是只靠 prompt 或框架的静态工具列表。作用：即使 orchestrator 被诱导，单个 specialist 也不能越权调用；对“工具划分”轴提供确定性执行。局限：本文的架构已经静态划分工具；攻击者通过组合合法原子动作完成有害任务，capability 不能阻止“合法动作的有害组合”。
2. **签名/可追溯的任务委派链**：orchestrator 给 specialist 的每条指令附带原始任务哈希、委派者签名、作用域与目的；specialist 在执行前验证。作用：让下游 Agent 看到“这条原子指令来自哪个原始目标”，可能恢复意图可见性、提高 PR（对应 §B.4.1 的 context isolation 机制）。局限：本文的攻击者就是原始任务的作者，签名只能证明来源，不能证明任务合法；它更像 transparency/provenance，而不是 authorization。
3. **TEE/远程 attestation**：证明 orchestrator/specialist 运行的代码、prompt、工具配置未被篡改。作用：保证“架构如宣称”；但本文威胁模型已排除系统代码修改，因此对本文攻击无直接帮助；对供应链/内部人威胁才有意义。
4. **签名审计日志/透明日志**：记录 `(task, agent, action, tool, timestamp, policy_id)`，支持事后归因与问责。作用：取证、合规；不能预防语义层面的有害任务完成。
5. **策略引擎 + 语义分类器**：在工具网关做字段级/动作级策略检查（如“禁止发送含钓鱼模板的邮件”“禁止生成 ICMP flood 代码”），由确定性规则 + 语义模型组合执行。这是最接近可落地的防御，但它不是密码学；密码学只能保护策略与日志的完整性，不能替代策略判断。

**伪交叉警告**：
- 只给 Agent 加 OAuth/身份认证：攻击者是合法用户，认证不解决滥用。
- 只给日志签名：事后取证，不阻止 HT。
- 用 TEE 证明“模型确实运行了”：证明的是计算完整性，不是任务合法性。
- 用 ZK 证明“Agent 遵守了某个策略”：策略本身的语义（什么是钓鱼邮件）无法被 ZK 电路完整表达；且 LLM 的概率性输出使“遵守”难以定义。
- 把 “authority” 当 RBAC：本文的 authority 是工具访问 + 控制流，不是角色-权限矩阵；直接套 RBAC 会丢失“意图在 Agent 间如何被稀释”这一核心机制。

**应用密码学相关度判断**：按项目 `A_crypto` 量表，本文正文约 **0**：没有识别任何密码机制使用点，威胁模型是合法用户滥用，认证/授权与问题正交。若把“签名委派链 + 工具 capability + 审计”做成原型并在本文 benchmark 上量化安全/性能收益，可到 2–3，但那是新增系统研究，不是本文贡献（此判断为本人推断）。

## 12. 可检验的研究假设

以下均为**假设/推断**，需新增实验；本文未做，不等于领域无人做过。

- **H1（意图可见性是因果机制）**：若把原始任务串（或忠实摘要）显式加入每个 specialist 的上下文，同时保持工具划分与拓扑不变，则 PR 应显著上升、HT 应显著下降，良性性能代价有限。实验：2×2（context isolation on/off × 2/4 specialists）在 BrowserART/RedCode 上重复本文任务与 judge；这可直接检验 §B.4.1/§6 的“有害意图碎片化”解释，而不是只靠 transcript 说明。
- **H2（有约束力的安全否决优于建议式 reviewer）**：在 orchestrator→executor 边界加入一个能看到完整任务的安全 Agent，并赋予其**绑定否决权**（而非仅建议），应比“advisory reviewer”更显著降低 HT；代价是良性任务的过度拒绝率上升。实验：在 13 个配置上比较 no-monitor / advisory / binding veto 三种条件，报告 HT、Benign、PR/ER 分布。本文明确未评估 guardrail（p.9）。
- **H3（分阶段指标比二元 ASR 提供更多信息）**：相同 HT 的两个架构可能在 ER/HA 上显著不同；PR/ER/HA/HT 分布对 human-rated harm 的预测力应高于二元 HT。实验：分层抽样 200–300 条轨迹做人工标注，比较 stagewise 与 binary 的 AUC/校准；同时报告 judge-human 一致性。本文只报告了 judge 错误抽查，没有做这一比较。
- **H4（委派链的 provenance 能恢复 chain 的拒绝率）**：Chain 拓扑的 PR 崩塌（RedCode 8.1%）部分源于下游只看到“被处理过的规格”而非原始意图；若每条链式消息附带原始任务哈希/摘要并要求下游验证，PR 应回升、HT 应下降。实验：在 RedCode chain 上增加 provenance 字段（可用签名或普通哈希），保持其他变量不变；这是密码学相邻的 transparency 干预，不是身份认证。
- **H5（对齐强度调节记忆效应）**：共享记忆对 HT 的影响由模型安全对齐强度调节：强对齐模型中性或略改善，弱对齐模型显著恶化。本文 Table 7 的方向（GPT-5.4 3→1；Qwen3-VL 37→41；Llama 70B 35→45）与该假设一致，但样本只有几个模型、没有对齐强度量化。实验：用 8–10 个模型、以公开对齐评分/拒绝率为协变量，做混合效应模型，检验交互项。
- **H6（自适应攻击会提高 HT 并可能反转架构排名）**：一个架构感知的攻击者，通过搜索“如何把有害任务拆成每个 specialist 都愿意执行的原子指令”，应比固定 benchmark 任务获得更高 HT；且最优架构可能从 mesh 变为其他。实验：用搜索式 prompt optimization（类似 Zhang & Yang 2025 的思路）对每个配置优化分解策略，预算固定，比较优化前后 HT 与排名。若成立，本文的静态 HT 应被解释为下界。
