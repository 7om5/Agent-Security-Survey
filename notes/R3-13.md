## 1. 150–300 字中文概述

本文是 ICML 2026 的立场论文，主张把可信 AI 要求嵌入 Model Context Protocol（MCP）这一 Agent–工具标准接口，使可信性从应用层的可选功能变为协议层的结构要求。作者以欧盟《可信 AI 伦理指南》的七项原则为透镜，逐项分析 MCP 及其生态的不足：人类监督被削弱且同意语义下放给 host；注册表信任不等于运行时安全；组合式工具链放大隐私、偏见与供应链风险；责任与审计难以归属。作者把改进建议归纳为五类干预点——风险自适应要求、元数据标准化、host 执行点、注册表治理、可持续性与公平性运营化——并提出 Server Cards、最小审计记录、补救接口、Eco Mode 等具体建议。全文是规范性/治理性论证，没有威胁模型、形式化属性、协议字段设计、实现或实验；其“trustworthy”是伦理与法律意义上的可信，不是密码学安全。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景**：MCP 由 Anthropic 提出，用于标准化语言模型与外部工具/上下文的交互，采用 host–client–server 架构（p.1–2, §0）。作者用临床支持系统举例：host 可从医院数据库取病历、检索医学文献、链接分析后向临床医生给出建议（p.1, §1）。这类组合式工作流带来强大的 Agent 能力，也把信任问题从单个模型扩展到工具、数据、注册表和供应链。
- **现有方法不足**（作者的核心动机）：
  1. 可信 AI 措施通常实现在应用层和组织层，导致采纳不一致、可被绕过；MCP 作为标准接口是“自然执行点”，协议层改进可传播到所有连接系统（p.1, Abstract/§1）。
  2. 现有 MCP 安全研究主要测量攻击面与攻击向量（如 Hou et al. 2025、Hasan et al. 2025、Narajala & Habler 2025、Guo et al. 2025），作者明确表示“we do not re-survey known attack vectors”，而是聚焦现有工作未覆盖的结构性缺口（p.3, §2）。
  3. 注册表只验证命名空间所有权与 schema 正确性，缺乏密码学或包级验证；注册表批准不保证运行时安全（p.3, §2）。
  4. 没有工具组合的认证框架，也没有协议级认证或信任评分方案；注册表主要依赖社区举报与下架（p.4–5, §2–§3）。
  5. 同意的语义与粒度完全委托给 host 实现，合规部署之间的用户知情程度差异很大（p.2–3, §1）。
- **精确定义的问题**：作者要回答三个问题：(a) 哪些可信 AI 要求可由协议本身支持，哪些需要 host 或注册表执行，哪些仍是开放研究/治理问题（p.2, §0）；(b) 在不破坏 MCP 轻量性的前提下，可以嵌入哪些具体改进（p.1–2, §1；p.9, §9）；(c) 七项原则之间如何相互影响、如何权衡（p.8–9, §8–§9）。论文的答案是“最小核心 + 可选 profiles + 五类干预点”。
- **注意**：Abstract 声称识别“三类东西”——fundamental shifts、critical challenges、strategic intervention points（p.1）。正文只把第三类（五类干预点）明确编码；前两类散落在各原则小节，没有独立章节或编号，见 §6/§9 的内部一致性问题。

## 3. Agent / MCP 系统模型（组件、交互流程、信任边界）

- **组件**（p.2, §0；Figure 1）：
  - **Host**：发起并编排工作流的 AI 应用，拥有工作流的全局视图，负责用户交互、同意界面、日志与（论文建议的）执行约束。
  - **Client**：协议组件，维护到 MCP server 的连接，中介请求与响应。
  - **Server**：暴露 tools、resources、prompts 等能力；可桥接数据库、文件系统与外部 API，因而能执行任意代码并直接访问系统资源（p.3, §2）。
  - **Registry**：发现面，验证命名空间所有权与 schema，提供信任信号；官方 registry 允许子注册表与客户端市场并存（p.3, p.6–7）。
  - **外部依赖/托管**：开源包、Cloudflare 等托管平台、异构工具的安全模型，均属于组合式供应链的一部分（p.4, §2）。
- **典型交互流程**（p.2, §0）：用户目标 → host 解释为任务 → 转成一个或多个协议级请求 → client 维持连接并转发 → 一个或多个 server 执行 → 结果返回 host，作为后续模型推理或用户输出的上下文。作者强调这是多步、双向、可迭代的循环，而不是一次性调用。
- **信任边界**（原文没有画出正式的 trust-boundary 图；Figure 1 是“原则—干预点”映射图，不是数据流图。以下为本人据 §0–§7 重构）：
  - **协议边界**：host/client 与 server 之间。host 被视为可信执行点，server 是外部能力提供者；但 server 可执行任意代码，边界实际上很薄（p.3–4）。
  - **注册表边界**：注册表批准/信任信号 vs 运行时行为。论文的核心判断是“registry-level trust does not guarantee runtime safety”（p.3）。
  - **组织/法律边界**：EU AI Act 的 provider/deployer 角色、GDPR 的 controller/processor 角色，与 MCP 的 host/client/server 技术角色并非一一对应（p.4, §3）。
  - **四层责任边界**：user、orchestration、agent、tool 四层存在“trustworthiness fragmentation”，且没有清晰映射到 EU AI Act 角色（p.4, §2）。
  - **生命周期边界**：创建/部署、运行、部署后维护三个阶段的安全与治理问题不同（p.3, §2）。
- **关键隐含假设**：host 是良性且有能力执行约束的；client 忠实中介；注册表至少能验证命名空间；用户能理解 consent；日志/审计可用。论文没有明确写出这些假设，也没有分析 host 被提示注入、被恶意应用控制或自身不可信的情形。这是本文系统模型最大的未言明边界（本人推断）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **论文没有独立的 Threat Model 小节**，也没有形式化的攻击者模型。它引用现有文献列举已知威胁（p.3–5, §2–§3），并把这些威胁放在“技术鲁棒性与安全”原则下讨论。以下资产/目标/能力是本人据原文威胁清单重构，不是作者的形式化定义。
- **资产**：
  - 用户个人数据与敏感属性（病历、金融、位置等，p.1 临床例子；p.4–5 隐私讨论）。
  - 凭证与系统访问权：server 可桥接数据库、文件系统、API，注册表批准后可直接执行代码（p.3）。
  - 工具输出、上下文与中间产物：跨工具组合会累积、复用、派生摘要（p.4–5）。
  - 用户意图与人类监督：意图在多步转换中退化， oversight 被交互速度淹没（p.2–3）。
  - 公平性/可访问性：受保护属性在组合工作流中被转发给无公平保障的工具（p.6）。
  - 计算/能源资源：多步工具调用与长上下文放大能耗（p.7–8）。
  - 生态信任：注册表排名、信任信号与发现面（p.6–7）。
- **攻击者目标**（据原文威胁清单归纳）：数据泄漏/外传；未授权动作；权限提升；供应链妥协；命名空间冒充与工具投毒；通过检索内容/工具输出注入指令；disinformation/媒体完整性破坏；偏见放大。成本/能源外部性在原文中属于治理问题，不是明确的对抗目标。
- **攻击者能力**（原文列举，未给预算或能力等级）：
  - 发布恶意或仿冒 server；利用 namespace typosquatting（p.3）。
  - 控制工具元数据/描述，实施 tool poisoning（p.3）。
  - 先通过审批、后改变行为，实施 rug pull（p.3）。
  - 通过检索内容、工具输出或中间产物嵌入恶意指令，实施 indirect prompt injection / command injection（p.3–4, p.7）。
  - 控制或入侵 server，使其成为数据外传通道；冒充 publisher（p.5, p.7）。
  - 利用工具组合产生单独测试时不出现的攻击面（p.4–5）。
- **不在论文威胁模型内的**（本人据全文推断）：网络层攻击者、恶意 host、恶意 client、模型权重后门、侧信道、多 Agent 合谋、物理访问、资源耗尽型 DoS（仅成本/能源被作为治理问题提及）。论文也没有给出攻击成功率、攻击成本、防御绕过条件等可检验指标。
- **前提假设**：MCP 保持轻量；host 会执行 consent 与 least-privilege；注册表会做基本命名空间/schema 校验；用户可以理解协议级 consent；日志可被生成和保留；法律角色可以映射到技术角色（p.2–4, p.9）。这些假设在论文中多为规范性期望，而非已验证事实。

## 5. 核心方案：作者提出的协议改进、架构、治理机制、关键步骤

论文不提出新的协议架构，而是在既有 host–client–server 架构内提出五类干预点（p.2, §0；p.9, §10）。其设计逻辑是“最小核心 + 可选 profiles”：默认保持 MCP 轻量，高风险/行业部署再启用更严格的要求（p.9, §9–§10）。

1. **[i] 风险自适应要求（risk-adaptive requirements）**：保持协议最小，但根据风险、领域、部署上下文调制保障触发条件；对高风险动作要求人类批准，对常规任务放行；用阈值监测 context/task drift，超过阈值才干预（p.2–3, §1；p.9, §10）。具体挂钩现有 MCP 原语：elicitation primitive 让用户重申意图，MCP Apps 让工具在对话中返回交互 UI，server 可声明 tool risk categories 与 required approval levels（p.3, §1）。
2. **[ii] 元数据标准化（metadata standardisation）**：引入可跨组合工作流持久化的机器可读信息，使下游能执行 consent、provenance 与 accountability（p.2, §0）。具体包括：
   - 更丰富的 provenance：source identifiers、timestamps、transformation steps；MCP 已有可选 `lastModified`，但更丰富的来源信息既未标准化也未强制（p.5, §3）。
   - 每工具调用标识、工具风险类别、purpose/usage constraints、治理元数据（声明角色、目的、司法辖区处理）（p.5, §3；p.9, §10）。
   - retention 元数据（配合 task TTL）与 storage limitation（p.5, §3）。
   - 公平性/可访问性元数据（alt-text、screen reader、bias testing、protected attribute handling）（p.6, §5）。
   - 能源/成本元数据（p.8, §6）。
   - “Sticky policies”：把目的与使用约束作为机器可读义务随数据跨组织边界传播，并在每次工具调用时验证（p.5, §3）。
3. **[iii] Host 作为执行点（host-layer enforcement）**：利用 host 对工作流的全局视图，执行 least-privilege scoping、audit logging、risk-based approval（p.2, §0；p.4, §3）。论文建议发布 reference host requirements，覆盖最小权限、风险自适应人工批准、结构化且隐私感知的审计轨迹、最小补救接口（p.9, §10）。
4. **[iv] 注册表治理（registry governance）**：把注册表视为塑造生态信任的治理界面，通过审核、身份验证、透明排名影响哪些 server 被发现、如何呈现、有哪些信任信号（p.2, §0；p.6–7, §4–§6）。具体建议：governance-by-design、透明可审计的排名标准、限制歧视性默认、可申诉的上架/下架程序（p.7, §6）；把 Server Cards 作为上架要求（p.6, §4）。
5. **[v] 可持续性与公平性运营化**：把环境影响、可访问性、公平性嵌入日常编排决策，作为可审计约束（p.2, §0；p.6, §5；p.8, §6）。具体是 Eco Mode：通过 MCP Sampling 的 `maxTokens` 设每请求 token 上限；用 `modelPreferences` 的 `costPriority` 等作为非约束提示；host 强制每工作流/每工具的调用预算与速率限制；采用限制性默认阈值；发布 publisher 提供的成本/能源元数据；提供可选的能效提示（p.8, §6）。
6. **跨切面的具体 artifact**：
   - **Server Cards**：注册表强制的上架材料，至少包含 publisher identity/contact、declared purpose、exposed tools、data access patterns、expected sensitive inputs/outputs、retention/sharing assumptions、security considerations、evaluation evidence（where available）、maintenance policy；作者说这超出当前 draft Server Card schema（主要面向发现与配置）（p.6, §4）。
   - **最小审计记录**：高风险部署记录 tool identity/version、authorisation context、inputs/outputs（适当可解释粒度）、policy constraints，并配合版本固定与 provenance（p.8, §7）。
   - **补救接口（redress interface）**：provenance metadata + host 生成的结构化 redress summary（明确 schema），可向用户呈现并供审计（p.8, §7）。
7. **没有给出的东西（关键）**：没有新的 MCP 消息类型、字段名、JSON schema、状态机、错误码、版本协商、一致性测试或参考实现；只引用了现有字段 `maxTokens`、`modelPreferences`、`costPriority`、`server.json`、`lastModified`、task TTL。因此这是**协议治理建议**，不是协议规范草案（本人推断，依据全文无 schema/字段定义）。

## 6. 安全/可信声明与形式化程度

- **定义层面**：论文给出了两个约定性定义：(a) host/client/server 的角色（p.2, §0，来自 MCP 规范）；(b) “trustworthy MCP” 指“protocol-level and ecosystem-level mechanisms that support trustworthy AI requirements across MCP-mediated workflows”（p.2, §0）。后者是**stipulative definition**，不是可操作的安全属性；没有给出判定条件、度量或反例定义。
- **分类层面**：五类干预点 [i]–[v] 是通过“iterative thematic clustering”得到的（p.1–2, §0），但没有说明编码者、样本、聚类可靠性或冲突消解，因此是**作者的概念分类**，不是可复现的系统综述方法。
- **论证层面**：主体是原则—不足—建议的规范性分析。典型论证结构是：“原则 P 要求 X；MCP 当前缺少 X 或把 X 委托给 host/registry；因此建议在协议/生态层加入机制 Y”。这类论证依赖对 MCP 规范的解读和对现有文献的引用，不是形式化证明。
- **经验层面**：论文引用了二手数据（1,899 个 server 中 7.2% 有漏洞；66% code smells、14.4% critical bugs、46% Python 依赖有漏洞；Hugging Face 89% 开发者孤立），但没有自己测量、复现或统计检验（p.3–4, p.6）。
- **形式化程度：无**。全文没有 theorem、lemma、proof、security game、adversary model、reduction、invariant、protocol state machine 或 conformance test。没有定义“安全”或“可信”的可判定属性；没有证明任何建议能阻止任何攻击。Figure 1 是概念示意图，不是形式模型。
- **“安全声明”的性质**：多数是结构性的否定判断，例如“registry approval does not ensure execution safety”（p.3–4）、“implementation quality as the sole defence mechanism”（p.3）、“MCP does not enforce these security principles at the protocol level”（p.3）。这些是有文献支撑的分析判断，但不是形式化定理，也不是本文的实验发现。
- **“可信”的范围**：七项原则包括 human agency、robustness/safety、privacy/data governance、transparency、fairness、societal/environmental well-being、accountability（p.1）。其中只有 robustness/safety 的一部分和 privacy 与经典安全重叠；fairness、sustainability、human oversight 不是密码学或传统安全属性。把“trustworthy”整体当作“security”会误读论文。
- **内部张力**：Abstract 说 MCP 架构“provides a foundation for trustworthiness”（p.1–2），但正文又说 MCP “reduces human-in-the-loop oversight by design”（p.2）、注册表批准不保证运行时安全（p.3）、“these advantages only materialise through careful implementation”（p.4）。结论把主张收窄为“pragmatic”：保持轻量 + 标准化负责任 AI 措施（p.9）。这说明作者自己也知道强主张站不住，但 Abstract 的措辞比结论更强。
- **“fundamental shifts”未兑现**：Abstract 承诺识别三类东西，但正文没有一节列出“shifts”。可重构为三条：(1) 信任对象从单模型/单工具转向组合与生态（p.4, p.9）；(2) 信任实施从应用/组织层转向协议层结构要求（p.1）；(3) 信任保证从注册表/部署时审批转向运行时与生命周期治理（p.3–5）。这三条是**本人据原文归纳**，不是作者明确编号的列表。

## 7. 实验或案例

- **没有实验**：全文没有 prototype、benchmark、用户研究、访谈、问卷、部署测量或消融。没有数据集、基线、指标、置信区间。没有 Table；唯一的图是 Figure 1（p.2）。
- **没有真正的案例研究**：论文中的“案例”都是说明性例子或类比，不是系统性的 case analysis：
  - 临床支持系统（p.1）：说明 Agent 可组合病历、文献与临床建议，但没有分析该场景的具体威胁或部署。
  - HTTP→HTTPS（并引 TLS/IPsec RFC，p.1）：用协议层安全演进类比 MCP 的可信性嵌入；引 RFC 2246、RFC 4301，但没有比较两者的威胁模型或治理结构。
  - Heartbleed/OpenSSL（p.4）：说明单个开源依赖漏洞可波及全球软件业，作为供应链脆弱性的类比。
  - Cloudflare 托管（p.4）：说明远程托管平台的级联故障/配置漂移风险。
  - App store 排名（p.7）：类比注册表的 gatekeeping 权力。
  - Hugging Face 89% 开发者孤立（p.6）：类比 MCP 生态的参与壁垒与集中化风险。
  - 新闻/媒体工作流（p.7）：说明 disinformation 与工作流操纵风险，但没有具体系统或数据。
- **二手经验数据**：1,899 个 server/7.2% 漏洞、66%/14.4%/46% 代码与依赖问题、89% 开发者孤立，均来自被引文献（Hasan et al. 2025；Ruohonen et al. 2021；Osborne et al. 2024），不是作者的第一手测量（p.3–4, p.6）。论文没有核验这些数字的抽样方法、时间窗口或生态代表性。
- **没有评估建议**：Server Cards、audit record、Eco Mode、registry governance 都没有原型或成本/收益分析；没有说明谁来实现、如何采用、如何验证合规。因此第 5 节的方案是**议程**，不是已验证的防御。

## 8. 贡献与创新点（按原文主张）

- **主张 1：把 MCP 定位为可信 AI 的协议级执行点**。理由是其标准接口地位、广泛采用与中介角色；协议层改进可传播到所有连接系统（p.1, Abstract/§1）。这是全文的核心立场。
- **主张 2：用欧盟《可信 AI 伦理指南》七原则系统分析 MCP**。逐项讨论 human agency、robustness/safety、privacy/data governance、transparency、fairness、societal/environmental well-being、accountability（pp.2–8, §1–§7），并声称这些原则与 OECD、UNESCO、NIST 框架共享，因此结论不限于欧盟（p.1）。
- **主张 3：识别三类东西**——fundamental shifts、critical challenges、strategic intervention points（p.1）。第三类明确落地为五类干预点；前两类散落各节（见 §6/§9）。
- **主张 4：五类干预点分类**：[i] 风险自适应、[ii] 元数据标准化、[iii] host 执行、[iv] 注册表治理、[v] 可持续性/公平性运营化；声称由“iterative thematic clustering”得出（p.1–2, §0；p.9, §10）。
- **主张 5：具体治理 artifact**：Server Cards、最小审计记录、redress interface、Eco Mode、reference host requirements、registry governance-by-design（pp.6–9）。
- **主张 6：跨原则的 cross-effects 与 alternative views**：承认原则之间会相互削弱/增强，存在隐私 vs 公平、透明度 vs 隐私、least privilege vs 多样性等权衡；承认协议本身不能保证可信（p.8–9, §8–§9）。
- **创新性评估（本人推断）**：相对于现有 MCP 安全文献（多聚焦攻击分类、工具投毒、供应链测量），本文的新意在于**把 MCP 从“攻击面”提升为“可信 AI 治理接口”**，并给出覆盖七原则的政策—工程议程。它不提出新的攻击、防御、协议或评测；其贡献是框架、分类与议程，而非可验证的技术机制。论文没有明确声称“first”，也没有与现有 MCP 安全综述逐条对比（无 Related Work 小节）。

## 9. 局限、失败案例、作者承认的不足

**作者明确承认/写出的**：
- “A protocol by itself cannot guarantee trustworthiness.”（p.9, §9）协议只能标准化共享技术钩子，使可信部署更容易一致实现。
- 替代观点：责任主要属于应用/部署层，由组织流程、行业监管、provider/deployer 义务执行；协议层机制可能增加复杂度与资源开销，开发者可能绕过；安全、透明、补救、可持续性要求高度依赖上下文，协议级强制可能过度约束低风险部署或保护不足高风险部署（p.9, §9）。
- 论文主张“最小核心 + 可选 profiles”，并同意比例原则（p.9, §9）。
- 某些挑战仍未解决，留待未来研究（p.2, §0）；Eco Mode 本身不解决环境问责，披露应被视为“claims rather than facts”；最优惩罚、审计概率与奖励结构仍是开放的机制设计问题（p.8, §6）。
- 论文明确区分哪些要求可由协议支持、哪些需要 host/registry、哪些仍是开放研究/治理问题（p.2, §0）。
- 没有独立的 Limitations 或 Ethics/Impact 小节；上述内容是分散的自我限定。

**本人推断的局限/失败场景**：
- **没有威胁模型**：没有形式化 adversary、能力等级、攻击预算、信任假设或成功条件；威胁清单是二手文献的汇总，不是本文的分析。无法据此证明任何机制的有效性。
- **host 被默认为可信执行点**：这是最大盲点。host 是 AI 应用，本身可能被提示注入、被恶意应用控制、或被用户误配置；论文没有分析“host 不可信/被攻破”时协议层机制是否仍有效。若 host 是攻击面，[iii] 的“host enforcement”就是把安全寄托在最可能被操纵的组件上。
- **“protocol-level”概念泛化**：五类中只有 [ii] 元数据标准化是真正的协议层改动；[iii] 是 host 实现要求，[iv] 是注册表治理，[v] 是编排策略，[i] 是部署配置。论文把它们统称为 protocol-level/ecosystem-level，模糊了“协议规范”与“生态惯例”的区别。没有 wire format、schema、版本协商或一致性测试，因此不是可实施的协议标准。
- **Server Cards 是自我声明，不可验证**：论文没有要求签名、attestation、可复现构建或第三方审计；只要求“registry enforced”上架。自我声明的 publisher identity、purpose、data access patterns 很容易被伪造或夸大；这与论文自己引用的 typosquatting、semantic deception、rug pull 风险直接冲突。没有说明注册表如何验证这些字段。
- **consent 不可执行**：论文承认同意语义下放给 host，但没有提出 consent receipt、可验证同意、撤回机制或用户可理解的摘要格式；“standardizing machine-readable disclosures of intent, scope, and impact”只是建议（p.3, §1），没有字段或验证方法。
- **审计的隐私悖论**：论文承认过细日志会泄露个人数据（p.5, p.8），但没有给出隐私保护日志的具体设计（如差分隐私、加密日志、访问控制、保留期限）。最小审计记录仍可能包含敏感输入/输出；“appropriately interpretable level”是未定义的。
- **法律角色映射未解决**：论文指出 GDPR controller/processor 与 MCP host/client/server 的映射非平凡（p.4, §3），但没有给出映射规则、责任分配或跨司法辖区方案；accountability 仍停留在“attribution signals + records”的建议。
- **注册表治理的可行性**：论文一方面说注册表批准不保证运行时安全（p.3），另一方面又把注册表当作治理界面（pp.6–7）。它没有分析开放协议下子注册表、客户端市场、镜像/私有部署如何绕过治理；也没有分析注册表运营者的激励、竞争与捕获风险。
- **没有优先级/成本收益/采用路径**：五类建议是并列的清单，没有说明先做什么、成本多少、谁来付费、如何衡量成功；没有对“轻量性”与“额外元数据/审计”的张力做定量分析。
- **可持续性建议边缘化**：Eco Mode 与 MCP 的核心安全/互操作目标关系较弱，容易被开发者忽略；论文自己说披露是 claims，不是 facts，削弱了该建议的可执行性。
- **二手数据可能过时/不可比**：1,899 个 server、7.2%、66%/14.4%/46% 来自不同文献、不同抽样时间与定义；论文没有讨论这些数字的生态代表性，也没有更新测量。
- **没有覆盖 prompt injection 防御**：论文把 indirect prompt injection 列为运行时威胁（p.3–4），但建议集中在元数据、审计、注册表治理，没有评估任何注入防御、模型层鲁棒性或工具输出隔离机制。
- **内部不一致/引用问题**：
  1. Abstract 承诺“fundamental shifts”，正文没有编号列表；只有结论中的“composition/ecosystem”与 §1 的“protocol-level shift”可勉强对应。
  2. “MCP 的核心机制是显式用户同意”（p.2–3）与“MCP 不在协议层强制执行安全原则”（p.3）存在措辞张力：同意是名义上的协议概念，实际由 host 实现。
  3. “MCP 提供日志机制”（p.8）与“日志不足”（p.4）需要区分“机制存在”与“没有强制内容/保留”；论文在 §7 说清了，但 §2 的表述较松。
  4. “MCP 架构提供可信基础”（p.1–2）与“MCP 设计上削弱人类监督”“实现质量是唯一防御”（p.2–3）之间的强/弱主张不一致；结论已收窄。
  5. 引用错误：p.1 把 UNESCO《人工智能伦理建议》标为 `(Zhu et al., 2025)`，但参考文献列表中唯一的 Zhu et al. 2025 是 Miniscope（least privilege framework），并非 UNESCO 文件；疑为引文错配。
  6. p.1/§1 使用 `(Commission, 2020)` 指代 Ethics Guidelines，但参考文献中 2020 条目是 ALTAI 评估清单，Guidelines 是 2019 条目；年份/条目使用不一致。
  7. 五类干预点声称由“iterative thematic clustering”得出，但没有方法细节（编码者、样本、一致性），不可复现。
  8. Abstract 的“any improvements to it automatically propagate to all systems using it”（p.1）过强：版本碎片、子注册表、客户端市场与 host 实现差异都会阻断传播；论文后文也承认 host/registry 执行差异（p.2–4）。AAIF 迁移、1,899 servers 等生态事实均为作者陈述或转引，未在本文中独立核验。

## 10. 与理论密码学的可能技术连接（区分原论文已做 / 个人推断）

**论文实际内容：无。**
- 全文没有安全定义、游戏、构造、定理、引理、证明、归约或密码学原语。没有 confidentiality/integrity 的形式化定义，没有 adversary model，没有不可区分性、模拟范式或复杂度假设。
- 唯一出现“cryptographic”的句子是 p.3 的否定性观察：“Registries validate namespace ownership and schema correctness but lack cryptographic or package-level validation mechanisms.” 这是指出缺口，不是提出密码机制。
- TLS（以及所引 RFC 4301 对应的 IPsec）仅在 p.1 作为 HTTP→HTTPS 的类比出现（引 RFC 2246、RFC 4301），用来说明“安全从应用层实现变成协议层要求”；论文没有设计 TLS 扩展、握手、证书或密钥管理。
- 论文的“trustworthy”是伦理/法律/治理概念，七项原则中 fairness、sustainability、human oversight 没有密码学对应；不能把“trust”直接映射为密码学信任。

**个人推断（明确标为推断，不是论文已做）**：
- 若要把“可信组合”形式化，可定义协议轨迹 `τ`、主体/工具/数据/目的的策略谓词 `Policy(host, server, tool, data, purpose)`，以及合规性属性“任何数据流都不违反 Policy”；再证明某个参考监视器/能力系统满足该属性。但论文没有做，而且其原则远超单一 confidentiality 属性。
- provenance/audit 可以用哈希链、数字签名、透明日志（Merkle tree）实现完整性；但这证明“记录未被篡改”，不证明“记录对应的行为是可信/公平/合规”。这是应用密码学，不是理论密码学，且论文未提出。
- 可用 QIF/g-leakage 度量“敏感数据经工具组合流向未授权方”的信息量；但论文的隐私问题是规范性的（目的是否兼容、同意是否有效），不是统计泄漏量；强行套用会丢失语义。
- 相关度判断：按项目 `T_crypto` 量表，本文约为 **0**；没有可归约的密码学定义、构造或定理。若把审计/来源的哈希链实现算作“理论联系”，那也只是工程完整性，不是本文贡献。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**论文实际内容：无（非密码学构造）。**
- 没有 OAuth/OIDC、TLS 握手、X.509/PKI、可验证凭证（VC/SD-JWT/BBS+）、数字签名/MAC、TEE/远程 attestation、ZK/MPC/FHE、密钥管理、capability token 或密码学审计日志。
- 逐项核对：
  - **OAuth/授权**：未出现。论文谈 least-privilege scoping 与 authorisation context，但没有 token 格式、scope 语法、颁发/验证流程或委托链。
  - **TLS/HTTPS**：仅 p.1 的历史类比；没有协议设计或部署建议。
  - **身份验证**：p.2 的 [iv] 提到 registry 的“identity verification”，p.7 提到“stronger publisher identity verification”；但没有说用 PKI、签名、VC 还是人工审核。
  - **attestation/TEE**：未出现。论文没有建议用远程 attestation 证明 server 行为或 host 完整性。
  - **签名/审计**：未出现。最小审计记录（p.8）只列字段，没有签名、哈希链、透明日志或存储完整性机制。
  - **VC/凭证**：未出现。Server Cards 是声明性文档，不是可验证凭证。
  - **sticky policies**：p.5 引用 Pearson & Casassa-Mont 2011 的“machine-readable obligations travel with data”，但论文把它当作元数据模板，没有讨论策略签名、策略引擎或密码 Enforcement。
  - **consent**：p.2–3 的 explicit user consent 是 UX/协议概念，不是密码学 consent receipt。
- 因此按项目 `A_crypto` 量表，本文约为 **0–1**：识别了“注册表缺乏密码学验证”这一缺口，但没有使用、设计或评估任何密码机制。不能因为出现 trust、security、identity verification、audit 就抬高相关度。

**个人推断的工程接口（均标为推断，需新增设计与实验）**：
1. **签名的 Server Cards / 发布者凭证**：由注册表或独立 CA 对 publisher identity、tool manifest、build hash 签名；host 在安装/调用前验证。作用：抵抗 typosquatting、publisher 冒充、rug pull 的一部分（至少能检测 manifest 变更）。局限：签名只保证“谁发布了什么”，不保证行为安全；恶意 publisher 可以签一个恶意 server；需要撤销、密钥轮换、透明日志。
2. **注册表透明日志**：用 Merkle tree/append-only log 记录 server 上架、下架、版本、信任信号；host 可验证 inclusion/consistency。作用：让“注册表是否悄悄下架/改排名”可审计。局限：不验证 server 行为；日志运营者仍可拒绝收录。
3. **可复现构建 + 远程 attestation**：server 发布可复现构建产物与 TEE attestation，host 验证运行代码与声明一致。作用：缓解 rug pull 与供应链篡改。局限：TEE 信任根、侧信道、生态系统采用成本；不能防止逻辑层恶意（如工具故意外传数据）。
4. **能力令牌/least-privilege token**：Macaroons/Biscuit/UCAN 风格 capability，带 tool、data、purpose、time、调用次数等 caveat，由 host 或 MCP gateway 强制执行。论文引用了 Miniscope（Zhu et al. 2025）作为 least-privilege 框架，但没有采用其机制。作用：把 [iii] 的 least-privilege 从建议变成可执行约束。局限：静态 scope 难以表达上下文相关的“目的兼容”；需要字段级 redaction 与策略语言。
5. **哈希链/签名审计记录**：对每次 tool call 记录 `(host, server, tool, version, auth_context, input/output hash, policy_id, timestamp)`，链式哈希 + 签名 + 透明日志。作用：取证与问责。局限：事后检测；日志隐私；哈希不隐藏内容；不能证明行为合规。
6. **隐私保护审计**：加密日志、访问控制、差分隐私摘要、保留期限；论文承认日志隐私风险（p.5, p.8）但没有设计。这是应用密码学/隐私工程的明确空白。

**伪交叉警告**：
- 给 MCP 加 OAuth 只解决“谁被授权调用”，不解决“调用是否可信/公平/符合目的”；论文的七原则远超授权。
- 给 Server Cards 签名只证明发布者身份，不证明卡片内容真实；恶意 publisher 可以签虚假声明。
- 给审计日志做哈希链只保证完整性，不保证日志记录了正确的语义，也不防止 host 故意不记录。
- 用 TEE 运行 host 只保护执行完整性，不防止模型被提示注入或输出恶意动作；TEE 不是语义过滤器。
- 把“trustworthy MCP”当成“加密 MCP”是范畴错误：论文的核心是治理、元数据、审计与责任，不是机密性协议。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

以下均为**假设/推断**，需查证外部文献；本文未做，不等于无人做过。

- **H1（风险自适应 host 执行降低未授权动作）**：若 host 按工具风险类别实施分级审批与 least-privilege scope，则高风险未授权工具调用率显著低于统一 consent 基线，且任务完成率不显著下降。实验：实现两个 MCP host 变体，在 100 个含高风险工具的工作流上红队测试；指标为未授权动作率、攻击成功率、任务完成率、审批次数/用户负担。
- **H2（可验证 Server Cards 降低恶意 server 选择）**：若注册表强制签名/可验证的 Server Cards（publisher、manifest、build hash），则用户/Agent 选择 typosquatted 或 rug-pull server 的比例显著低于自我声明卡片。实验：注册表模拟器 + 用户/Agent 选择任务；比较签名 vs 未签名、可验证 vs 不可验证；指标为恶意选择率、信任校准、安装转化率。
- **H3（持久 provenance/purpose 元数据降低跨工具数据复用）**：若每次工具调用携带并验证 purpose/usage constraints 与来源元数据，则组合工作流中的跨工具敏感数据复用/外传显著减少，且任务效用可接受。实验：instrumented MCP testbed，构造 50–100 个组合工作流；指标为敏感数据流数量、未授权复用率、任务成功率、元数据开销。
- **H4（标准化审计记录改善归因与补救）**：若高风险部署强制最小审计记录（tool identity/version、auth context、I/O、policy），则安全事件的平均归因时间与归因错误率显著低于无标准日志基线。实验：红队/桌面演练；指标为 time-to-attribution、根因正确率、日志隐私泄露量、存储成本。
- **H5（Eco Mode 预算降低能耗且不损任务）**：若 host 实施每工作流/每工具调用预算与限制性默认，则 token 消耗/能耗显著下降，任务成功率无显著下降。实验：Agent benchmark 上比较 Eco Mode on/off；指标为 tokens、工具调用次数、能耗估算、成功率、延迟。
- **H6（协议级 profiles 提高采纳一致性）**：若 MCP 提供 opt-in 高风险 profiles 与 reference host requirements，则不同 host 实现的合规一致性显著高于仅靠应用层指南。实验：开发者研究/部署审计；指标为 conformance rate、实现差异、开发者接受度、绕过率。
