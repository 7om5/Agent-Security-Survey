## 1. 150–300 字中文概述

论文研究间接提示注入下确定性信息流控制（IFC）防御的自主性收益。作者指出，IFC 在标签与策略正确时可按设计阻断攻击，但既有评测只看任务完成率（TCR），把确定性防御的代价（最高约 30% TCR 下降）与收益（减少人工审批）混在一起。为此提出 HITL load 与 TCR@k 两个自主性指标，并设计 PRUDENTIA：让规划器感知工具策略与上下文标签，用 plan 工具审慎决定何时展开不可信变量，并在逐调用审批之外提供“数据背书（endorsement）”这一更粗粒度的人机交互。系统在 FIDES 之上以提示/上下文工程实现，不修改 IFC 执行层。AgentDojo 上 o3-mini 的 TCR@0 从 FIDES 的 50.1% 提到 59.1%，o4-mini 的 HITL load 从 36.8 降到 19.2；WASP 上四个模型 ASR 均为 0、HITL load 为 0。全文是系统/PL 安全与评测工作，不含密码学原语、密码学定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景：间接提示注入（PIA）**。AI Agent 为完成任务从邮件、文件、网页等外部数据源读取内容；攻击者可在这些数据中嵌入指令，劫持 Agent 的行为，典型后果包括发布恶意补丁、泄露机密数据（p.1, §1）。Agent 越来越多被用于信息检索、浏览器与计算机操作（p.1），因此 PIA 的危害从“输出错误”升级为“执行有害动作”。
- **概率防御的不足**。模型对齐、防御性 system prompt、注入分类器等概率防御被广泛提出，但它们不提供强安全保证，面对自适应攻击仍然脆弱（p.1, §1）。作者在 p.10 进一步引用 Nasr et al. (2025)：StruQ 与 instruction hierarchy 的组合可被 100% ASR 绕过，另有 12 种概率防御可被类似绕过；因此本文不与概率防御做实验比较，只比较具有确定性保证的系统级防御。
- **确定性 IFC 防御的承诺与代价**。IFC 给所有数据附加完整性/机密性标签，标签随生成传播，工具调用前用策略检查标签；当数据标签正确、策略正确时，IFC 可以“by design”消除 PIA：不可信数据无法影响 consequential action，每个工具调用要么满足策略、要么被阻断并升级到人工审批（p.2, §1）。但确定性策略在良性场景也会限制合法动作，已有工作报告 AgentDojo 上最高约 30% 的任务完成率下降（p.2, §1）。
- **既有评测的缺口**。先前确定性防御工作用 TCR@0（文中常直接称为 TCR）与无防御的 TCR@∞ 对比，实际上是在“完全自主”与“无限人工干预”两个极端之间比较，能显示 utility loss，却不能量化确定性防御减少人工监督的收益（pp.4–5, §3）。作者认为真实 Agent（GitHub Copilot、OpenAI Codex、Anthropic Computer Use）默认对 consequential action 做 HITL 审批，因此“减少 HITL”本身是核心收益。
- **精确定义的问题**：(1) 如何定义并度量 IFC 防御带来的自主性？(2) 如何设计一个 IFC-aware 的规划器，把“策略合规”与“任务完成”同时作为显式目标，在不牺牲 TCR 的前提下减少 HITL？论文在 p.6 将其具体化为两个研究问题：IFC 如何影响自主性；PRUDENTIA 相对基线能把自主性提高多少。
- **范围限定**：论文只研究间接提示注入与确定性系统级防御；jailbreak、直接提示注入、tool poisoning、模型自身错误（幻觉/误解）不在安全保证范围内（p.10, §6）。这不是一篇“更聪明的注入分类器”论文，而是“如何让确定性防御在真实 HITL 工作流中更可用”的系统/评测论文。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **组件**（pp.2–3, §2；p.5, §4）：
  - **User**：提出任务，并在 HITL 环节做审批（approval）或背书（endorsement）。
  - **Planner LLM**：ReAct 风格的工具调用 Agent，负责规划、选择工具、决定是否展开变量、是否请求背书；在 PRUDENTIA 中还能看到工具描述里的策略标注。
  - **Tools**：执行实际动作（读邮件、查日历、转账、发帖、浏览器 click/type/goto 等）；工具实现被视为可信。
  - **IFC enforcement**：维护标签、传播标签、在工具调用前做策略检查；实现沿用 FIDES。
  - **Dual LLM 组件**：planner 与 quarantined LLM；不可信工具结果写入 variables，planner 只能看到变量标识符；quarantined LLM 在隔离环境中处理变量内容，其输出仍按不可信数据处理。
  - **External data sources**：邮件、文件、网页、GitLab issue、Reddit 帖子等；攻击者可以控制其内容。
  - **HITL approver**：人类用户；在策略检查失败时批准动作，或在展开变量时背书数据可信。
- **标签与策略模型**（p.3, §2）：
  - 标签格 `L` 是偏序集，任意两元素有上确界（join）`⊔`；新数据 `z` 由 `x,y` 派生时 `ℓ_z = ℓ_x ⊔ ℓ_y`，这是安全上的保守过近似。
  - 完整性格 `{T,U}`，`T ⊑ U`；由可信与不可信数据共同派生的数据为 `U ⊔ T = U`。机密性格 `{L,H}`，`L ⊑ H`；公开与秘密数据共同派生为 `L ⊔ H = H`；实验中使用用户集合的幂集 `P(U)` 作为更丰富的机密性格。
  - 工具调用写作 `f^ℓ[a_1^{ℓ_1},...,a_n^{ℓ_n}]`；策略 `π=(π_f, π⃗)`；调用满足策略当且仅当 `ℓ ⊑ π_f` 且对所有参数 `ℓ_i ⊑ π_i`。
  - **P-T（Trusted Action）**：`π_f=(T,⊤)`，每个需要可信的参数 `π_x=(T,⊤)`；只有决策发生在可信上下文时才允许调用。**P-F（Permitted Flow）**：对 `send(R,d)`，`π_d=(⊤,R)`，只有所有接收者都被允许读取 `d` 时才允许外发。非 consequential 调用总是允许；consequential 工具用 P-T，外发工具用 P-T 或 P-F，从而在可信上下文中允许“稳健的去分类”，否则阻止注入外泄。
- **交互流程**（pp.3–5, §2–§4）：
  1. 用户给出任务；planner 在可信上下文（初始为 HIGH INTEGRITY）中生成工具调用。
  2. 工具返回内容；若含不可信数据，内容被放入 variables，planner 的上下文不直接被污染。
  3. planner 可以用 quarantined LLM 对变量做受限查询；也可以选择展开变量（`expand_variables`），展开后上下文永久变为 LOW INTEGRITY；还可以请求用户背书（`ask_endorsement=True`），背书后变量内容被重新标记为 T，展开但不污染上下文。
  4. 每个 consequential 工具调用前做策略检查；通过则自动执行；不通过则进入 HITL 审批。审批通过后动作执行。
  5. PRUDENTIA 在展开前要求调用 `plan` 工具，写下为什么需要展开、后续要调用哪些工具、是否需要 HIGH INTEGRITY；这让 planner 在“展开导致上下文污点”与“背书/审批成本”之间做显式权衡（p.5, §4；p.28–29, App D.3）。
- **信任边界**：
  - 论文明确假设 **user、planner LLM、tool implementations 可信**；外部数据源可能含注入（p.3, §2；p.10, §6）。IFC 执行层、标签、策略也被视为可信基础设施（此点是本人据全文归纳；论文没有单独列 TCB 清单）。
  - **Quarantined LLM** 是可信实现，但它处理的是不可信数据；其输出仍作为不可信变量，不直接进入 planner 上下文。
  - **HITL 人类** 被视为可信的审批者：策略失败的调用需要人批准；背书更是一次“人把 U 数据升级为 T”的完整性去分类。论文承认人可能出错、会 confirmation fatigue，但没有把人建模为攻击者（p.9, §6）。
  - **Tool descriptions** 被视为可信，因此 tool poisoning 不在威胁模型内（p.10, §6）。
- **单 Agent 范围**：论文只考虑单个 planner + 工具 + 人类审批者；没有多 Agent 协作、Agent 间委托、跨组织信任链。WASP 是浏览器 Agent，AgentDojo 是 API/工具 Agent，二者都是单 Agent 环境。
- **WASP 的标签映射**：浏览器工具返回可访问性树（accessibility tree）的文本摘要；帖子/issue 等用户生成内容标为 untrusted，网站提供的按钮、textarea 等标为 trusted；不可信字段替换为 variables，agent 可展开（p.8, §5.2；pp.30–32, App E）。这把 IFC 的完整性标签落到可访问性树节点级别，是本文把 IFC 用于浏览器 Agent 的具体接口。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：
  - 用户数据的机密性：邮件、日历、银行账户、云盘文件、Slack 消息、GitLab/Reddit 内容等（p.6, §5.1；p.8, §5.2）。
  - 动作完整性：转账、发消息、发帖、修改文件、浏览器 click/type/goto 等 consequential action 不被注入劫持（p.3, §2；p.8, §5.2）。
  - 任务效用：TCR@∞ / TCR@k；以及人类注意力/审批负担（HITL load）。
- **攻击者目标**：通过间接提示注入，使 Agent 执行攻击者指定的 consequential action（例如把数据发到攻击者地址、修改账户邮箱、发布恶意内容），或至少让 Agent 偏离用户任务（WASP 的 ASR-intermediate 口径，p.8, §5.2）。
- **攻击者能力**：
  - 控制 Agent 会读取的外部数据内容：邮件正文、网页、GitLab issue、Reddit 帖子等；可嵌入指令、链接、紧迫性/权威性话术（p.1；p.8；p.30, App E 的注入示例）。
  - 在 WASP 中可通过网页文本直接嵌入目标，或诱导 Agent 点击 URL 中带目标的链接（p.8, §5.2）。
  - **不能**修改 user prompt、planner LLM、工具实现、标签、策略或 IFC 执行层；不能直接向可信上下文注入；不能投毒工具描述（tool poisoning 明确 out of scope）；不能做 jailbreak 或 direct prompt injection（p.10, §6）。
  - 论文没有建模：记忆投毒、供应链、侧信道、资源耗尽、合谋、多 Agent 攻击、对 HITL 界面的社会工程、对标签器的攻击。
- **防御者能力**：在 FIDES 之上改 planner 的提示与工具接口；可以给工具描述加策略标注；可以让 planner 选择背书/审批；不能修改 IFC enforcement（p.5, §4）。人类审批者可以批准策略失败的动作，或背书变量内容。
- **前提假设**（分散在 §2、§3、§6；论文没有独立 Threat Model 小节）：
  - 标签正确、策略正确；IFC 的“provable”保证以这两个条件为前提（p.2, §1）。
  - user/planner/tools 可信；外部数据源不可信（p.3, §2）。
  - 人类会认真审查 HITL 请求，并阻止来自注入的 consequential call（p.6, §5.1 明确写出这一假设）。
  - 良性任务可以在不违反策略的情况下完成；HITL load 只在良性轨迹上测量，且只统计成功完成的任务（p.4, §3）。
  - benchmark 的注入不会改变标签/策略/工具实现；攻击者只通过数据内容影响 Agent。
  - 没有对 HITL UI 的操纵攻击；论文把 UI 设计留作 future work（p.9, §6）。
  - 没有模型错误（幻觉/误解）的安全保证；论文只声称“security”，不声称 general safety（p.9, §6；p.10, §6）。

## 5. 核心方案：planning 模型、security/autonomy 目标、优化算法

### 5.1 形式化目标：自主性指标（pp.3–5, §3）

- 任务集合 `T={t_1,...,t_n}`；每个任务有用户 query、工具集合、初始环境状态、以及完成该任务的 trace 集合 `t_i ⊂ C*`（AgentDojo 提供特征函数）。planner `P` 概率性地生成 trace `P(t)=τ∈C*`；`τ∈t_i` 表示成功完成。
- 对 trace `τ`，`v(τ)` 是其中不满足 IFC 策略的工具调用数量：
  ```text
  v(τ) = |{ f^ℓ[a_1^{ℓ_1},...,a_k^{ℓ_k}] ∈ τ | ¬(ℓ ⊑ π_f ∧ ∀i. ℓ_i ⊑ π_i) }|
  ```
- **HITL load** = 所有成功完成任务的 `v(τ_i)` 之和（Eq.1）：
  ```text
  HITL load = Σ_{i∈[n], τ_i∈t_i} v(τ_i)
  ```
- **TCR@k** = 成功完成且 `v(τ_i) ≤ k` 的任务比例：
  ```text
  TCR@k = (1/n) · |{ i∈[n] | τ_i∈t_i ∧ v(τ_i) ≤ k }|
  ```
- `TCR@0` 表示完全自主（不允许任何策略违规）；`TCR@∞` 等价于 benchmark 的普通 TCR。论文的目标是让 planner 的 `TCR@k` 曲线尽量接近“all-knowing agent”的曲线；论文也指出 all-knowing agent 通常不能达到 `TCR@0=1`，因为动态工具结果的标签无法预先知道，所以 0 HITL 不是现实目标（p.4, §3）。但论文没有计算这个 oracle 曲线，也没有给出形式化的约束优化问题或求解算法。
- **关键口径**：HITL load 只在 **良性条件** 下、且只在 **成功完成的任务** 上统计；论文假设人会批准策略失败的调用（p.4, §3）。因此它不是攻击成功率，也不是“所有轨迹上的人工负担”；它是“良性任务中需要人工介入的策略违规次数”。

### 5.2 PRUDENTIA 的四个设计组件（p.5, §4）

1. **Policy and label awareness（策略/标签感知）**：工具描述中标注该工具是 consequential、egress 还是 always allowed（system prompt 中用 “ONLY HIGH INTEGRITY” 标签表达，p.25, App D.3）；planner 维护自己上下文的标签（HIGH/LOW INTEGRITY），从而能预测哪些调用会触发策略失败，并在规划时绕开，而不是事后被动处理（p.5）。
2. **Strategic variable expansion（策略性变量展开）**：通过 few-shot 示例教 planner 变量展开的后果；增加专用 `plan` 工具，要求 planner 在展开前显式说明“为什么必须展开、后续准备调用哪些工具、是否需要 HIGH INTEGRITY”，从而避免不必要的展开导致上下文过早污点（p.5；p.28–29, App D.3）。
3. **Endorsement vs. approval（背书 vs. 审批）**：展开变量时，planner 可以请求用户背书该变量内容；若用户背书，数据从 U 重新标记为 T，变量展开但不污染上下文，后续 P-T 调用无需逐次审批。论文的 10 项 TODO list 例子：背书整封邮件只需 1 次 HITL，而不背书地查看邮件会让上下文污点，之后 10 个 P-T 调用各需 1 次审批（p.5）。planner 还可以选择 `ask_endorsement=False`：上下文永久 LOW INTEGRITY，所有变量被自动展开；如果展开后最多只有一个 HIGH INTEGRITY 调用，这种“不背书、让它去审批”的策略可能更便宜（p.5；p.27–28, App D.3）。
4. **Declassification（去分类）被有意放弃**：去分类可以降低机密性标签，但“是否适合去分类”高度依赖情境；论文认为逐调用审批比 blanket declassification 更能捕捉情境，因此不提供该选项（p.5）。

### 5.3 实现方式与“优化”的含义

- 实现是 **context engineering**：把背书能力并入 `expand_variables`，增加 `plan` 工具，修改 system prompt；**不修改底层 IFC enforcement**（p.5, §4）。因此安全性仍由 FIDES 的标签传播与策略检查提供，PRUDENTIA 只改变 planner 的行为与 HITL 交互粒度。
- 论文所谓“optimizing agent planning”不是求解 POMDP、不是搜索、不是 RL、也不是训练；它是 **提示/工具接口层面的设计**，让 LLM planner 在任务完成与策略合规之间做更好的启发式权衡。论文没有报告任何训练、微调或策略搜索实验。
- 一个实现细节：不带背书的 `expand_variables` 被改成“展开所有变量”，因为一旦上下文污点，再隐藏其他变量没有自主性收益（p.6, §5）。
- **案例**（pp.14–15, App A）：workspace 任务 23（查 5 月 15 日三个 appointment 的描述 + 找 TechServices 密码重置链接）。planner 先用 `ifc_plan` 判断“展开后不需要 consequential 工具”，于是对日历描述调用 `expand_variables(ask_endorsement=False)`；随后搜索邮件、quarantined LLM 查询失败、再展开邮件正文，最终 0 次用户干预完成任务。这个例子说明“是否背书”是由后续计划决定的，而不是固定规则。

## 6. 安全声明与形式化程度（定义/定理/证明 vs 经验主张）

- **论文实际给出的形式化**：
  - 标签格、join 传播、工具调用策略满足性 `ℓ ⊑ π_f ∧ ∀i. ℓ_i ⊑ π_i`（p.3, §2）。
  - P-T / P-F 两类策略（p.3, §2）。
  - trace、`v(τ)`、HITL load、TCR@k 的定义（pp.3–4, §3）。
  - 这些是 **策略语义与度量定义**，不是密码学安全定义，也不是完整的非干扰（noninterference）定理。
- **“provable” 的来源与边界**：论文说 IFC 策略在“数据被正确标注、策略被正确指定”时“provably eliminate PIAs by design”（p.2, §1）。这个保证来自 FIDES/CaMeL/RTBAS 等既有 IFC 工作；本文没有给出新的定理、引理、证明或归约。PRUDENTIA 不修改 enforcement，因此作者主张它继承该保证（p.5）。
- **安全性的实际论证是条件性的**：
  - 需要 user、planner LLM、tools 可信（p.3；p.10）。
  - 需要标签正确、策略正确（p.2）。
  - 需要人类认真审查 HITL 请求，并阻止注入引发的 consequential call（p.6 明确写出这一 assumption）。
  - jailbreak、direct prompt injection、tool poisoning、模型幻觉/误解不在范围内（p.9–p.10）。
  - AgentDojo 上作者没有报告 ASR 表，而是说“by design, no attacks succeed in this setting due to strict policies, deterministic defenses, and our assumption that a human would review and stop consequential tool calls stemming from prompt injections”（p.6）。这是一个 **假设 + 设计论证**，不是实验测量。
- **经验安全结果**：WASP 上 PRUDENTIA 在 GPT-4o、o1、o3-mini、o4-mini 四个模型上 ASR 均为 0（p.8, Table 1）；但 WASP 任务全是 data-independent，不需要展开变量，因此这一结果主要验证“变量隐藏 + P-T 策略”在浏览器场景的效果，不验证背书机制在 data-dependent 任务上的安全性（p.2；p.9）。
- **背书是一个安全性关键的人为去分类**：用户背书把 U 数据升级为 T；如果用户被说服背书了含注入的邮件，后续 P-T 调用就可以在“可信”上下文中自动执行，IFC 不会再拦截。论文的威胁模型把 user 视为可信，因此不把它当作攻击；但论文自己承认 HITL 界面可能被攻击者操纵、confirmation fatigue 会导致用户草率批准（p.9）。这是“provable security”在真实人机系统中的最大缺口之一（本人推断，非作者原话）。
- **结论**：形式化程度 = **策略/度量定义 + 经验评测 + 继承式安全论证**；没有定理/证明/密码学归约。安全声明是“在标签/策略正确、TCB 可信、人类认真审批的前提下，IFC 阻断注入”；PRUDENTIA 本身不提供额外可证明保证，只提供更好的自主性。附录 A–E（pp.14–32）也没有定理/证明，只有案例、额外结果表、成本表、system prompt 和可访问性树示例。

## 7. 实验设置与主要结果（环境、基线、指标、关键数字、消融）

### 7.1 AgentDojo 设置

- **环境**：AgentDojo（Debenedetti et al., 2024），四个 suite：banking、messaging（Slack）、travel、workspace；攻击面来自邮件、文件、网页等外部数据（p.6, §5.1）。
- **策略**：沿用 Costa et al. (2025) 的 IFC 策略（P-T/P-F）；所有基线通过 Microsoft Foundry 调用 OpenAI 模型；主实验用 reasoning models o3-mini、o4-mini，附录加入 GPT-4o、GPT-5（p.6；p.16, Table 2）。
- **基线**：
  - **Basic**：无 IFC 的 ReAct Agent；但为了公平，给所有 consequential tool call 加 HITL 审批（类似 GitHub Copilot）。
  - **Basic-IFC**：Basic + IFC 标签/策略检查；只在策略失败时需要 HITL。
  - **FIDES**：SOTA IFC Agent，使用 Dual LLM、变量隐藏、quarantined LLM；planner 与信息抽取使用同一模型。
  - **PRUDENTIA**：在 FIDES 代码库上实现，加入策略/标签感知、`plan` 工具、背书/审批选择。
- **指标**：TCR@∞（benchmark utility）、HITL load（所有成功任务上的总干预次数）、TCR@0…TCR@4；每个实验重复 5 次，报告 mean ± std（p.6）。
- **安全口径**：作者假设在该设置下没有攻击成功，因为策略严格、防御确定、且人类会审查并阻止注入引发的 consequential call（p.6）。论文没有给出 AgentDojo 的 ASR 表。

### 7.2 AgentDojo 主要结果

- **IFC 本身提升自主性（o3-mini）**：Basic HITL load 48.2、TCR@∞ 62.5%；Basic-IFC HITL 32.4（1.5× 更低）、TCR 62.5%（相同）；FIDES HITL 18.8（比 Basic-IFC 低 1.7×）、TCR 64.3%（p.6–p.7；Table 2 p.16）。
- **TCR@0（完全自主）**：
  - o3-mini：PRUDENTIA 59.1% vs FIDES 50.1%、Basic-IFC 35.5%、Basic 24.3%；相对 FIDES +9.0 个百分点，相对 Basic-IFC +23.6 个百分点，相对 Basic +34.8 个百分点（p.7；Table 2 p.16）。
  - o4-mini：PRUDENTIA 59.4% vs FIDES 53.2%、Basic-IFC 42.5%、Basic 32.8%（Table 2 p.16）。
- **HITL load 与 TCR 的权衡**：
  - o4-mini：PRUDENTIA 73.2% TCR@∞、19.2 HITL；FIDES 75.7%、36.8 HITL（HITL 低 1.9×，但 TCR 低 2.5 个百分点）（p.7；Table 2 p.16）。
  - o3-mini：PRUDENTIA 69.8%、16.4 HITL；FIDES 64.3%、18.8 HITL；Basic 62.5%、48.2 HITL（p.7；Table 2 p.16）。
- **附录中的模型异质性（重要）**：
  - GPT-4o：PRUDENTIA 61.4% TCR@∞、23.8 HITL、42.5% TCR@0；FIDES 56.3%、7.8 HITL、50.3% TCR@0；Basic 72.2%、59.4 HITL、28.0% TCR@0（Table 2 p.16）。在 GPT-4o 上，PRUDENTIA 的 HITL load 高于 FIDES（23.8 vs 7.8），TCR@0 低于 FIDES（42.5 vs 50.3），且 TCR@∞ 低于 Basic（61.4 vs 72.2）。这是对“PRUDENTIA 一致优于基线”说法的反例。
  - GPT-5：PRUDENTIA 80.0% TCR@∞、7.3 HITL、72.7% TCR@0；FIDES 78.9%、41.3 HITL、57.1% TCR@0（Table 2 p.16）。在 GPT-5 上 PRUDENTIA 的 HITL 优势远大于正文声称的 1.9×（41.3/7.3≈5.7×），TCR@0 优势为 15.6 个百分点。
- **任务类型分析**（p.9；Fig.3 p.17）：按 Costa et al. 的分类，DI（data-independent）、DIQ（data-independent with quarantined LLM）、DD（data-dependent）。PRUDENTIA 在 DI 任务上通过避免不必要展开获得最高约 25% 的 TCR@0 提升（相对 FIDES）；在 DD 任务上通过背书/审批选择把 HITL load 降低最多约 2.5×（p.9）。Figure 3 显示 DD 任务的 TCR@0 差距最明显：o3-mini 上 PRUDENTIA 约 42% vs FIDES 约 12%（读图估计，精确值未在正文给出）。
- **WASP 设置**（p.8, §5.2）：21 个注入任务（12 GitLab、9 Reddit），2 个良性任务（发评论/点赞）；测试用例 48 个 GitLab + 36 个 Reddit；模型 GPT-4o、o1、o3-mini、o4-mini，其中 o1/o3-mini/o4-mini 使用 medium reasoning effort；攻击成功按 ASR-intermediate 计（即使未达攻击目标，只要让 Agent 偏离用户任务也算成功）；12 个浏览器工具，P-T 施加在 click、type、press、goto、tab_focus、go_back、go_forward；hover、scroll、new_tab、close_tab、stop 视为非 consequential，不施加策略。
- **WASP 结果**（p.8, Table 1）：
  - PRUDENTIA 在四个模型、GitLab/Reddit 上 ASR 全部为 0，HITL load 全部为 0；Basic 的 ASR 为 GitLab 14.6–29.2%、Reddit 36.1–61.1%。
  - TCR@∞ 提升示例：GPT-4o GitLab 64.60→75.00、Reddit 36.10→55.60；o1 GitLab 62.50→85.40、Reddit 47.20→50.00；o3-mini GitLab 72.90→72.90、Reddit 25.00→58.30；o4-mini GitLab 64.60→72.90、Reddit 36.10→63.90。
  - turns 与 Basic 接近：例如 GPT-4o GitLab 5.45→6.14、Reddit 8.62→8.45；o4-mini Reddit 8.38→8.13。
  - 因为 WASP 任务全是 data-independent，PRUDENTIA 不需要展开变量，0 HITL 是设计上的预期；作者也承认此时 PRUDENTIA 与 FIDES 表现相近，Basic-IFC 与 Basic 相近，因此省略了 FIDES/Basic-IFC 的冗余结果（p.9）。
- **成本/turn 开销**（pp.19–20, App C）：
  - GPT-4o banking：PRUDENTIA 平均 input tokens 22,577.69 vs FIDES 7,746.62（约 2.9×）；output tokens 535.45 vs 333.51（约 1.6×）；USD cents 3.859 vs 1.542（约 2.5×）。Travel：6.289 vs 3.277 cents（约 1.9×）（Tables 3, 5, 6 p.19）。
  - 输入 token 开销随模型/任务差异很大：o4-mini banking 上 PRUDENTIA 31,893.30 vs FIDES 5,367.80（约 5.9×）、Basic-IFC 792.39（约 40×）；Table 4 显示大部分 input tokens 命中缓存，作者称这带来成本/延迟节省，但缓存收益依赖部署（p.19）。
  - AgentDojo turns：o4-mini travel 12.280（PRUDENTIA） vs 7.950（FIDES） vs 6.520（Basic-IFC）；GPT-4o banking 6.200 vs 4.525（Table 7 p.20）。作者没有记录 wall-clock time；他们承认成本未优化，可用并行 plan、微调等方式降低（p.19–p.20）。
- **消融/组件分析**：论文没有传统超参消融；组件贡献通过任务类型分解与 Figure 3 展示（策略性变量展开、背书选择）。没有对 policy 标注错误、标签噪声、不同 HITL 预算曲线形状、模型规模等做消融。
- **统计**：AgentDojo 5 次重复，mean ± std；没有显著性检验，也没有置信区间。WASP 未说明重复次数，Table 1 只有平均值，没有 std。

### 7.3 原文内部数值/口径不一致（仅记录，不作为结论证据）

- **摘要 “up to 9%” 与 “up to 1.9×”**（p.2）与正文 o3-mini/o4-mini 的结果一致（o3-mini TCR@0 +9.0 个百分点；o4-mini HITL 36.8/19.2≈1.9×）；但附录 Table 2（p.16）的 GPT-5 行为 TCR@0 72.7 vs 57.1（+15.6 个百分点）、HITL 41.3 vs 7.3（≈5.7×）。若把 GPT-5 计入，“up to” 的数值不成立。本文在证据表中以分模型数值为准，不采用摘要的 “up to” 作为上界。
- **“23.6% higher / 34.8% higher”**（p.7）实际是百分点差：59.1−35.5=23.6 pp，59.1−24.3=34.8 pp；不是相对提升 23.6%/34.8%。原文措辞不严谨。
- **“Basic-IFC achieves 9.7% higher TCR@0 than Basic … FIDES achieves 10.7% higher TCR@0 than Basic-IFC”**（p.6）：这两个数字对应 o4-mini（42.5−32.8=9.7；53.2−42.5=10.7），但该段前文先讲 o3-mini（对应值为 35.5−24.3=11.2；50.1−35.5=14.6）。原文没有明确模型限定，读者容易误读。
- **“maintaining or improving TCR” / Finding 2 “equal or better task completion rates”**（p.7–p.8）：o4-mini 上 PRUDENTIA 73.2% < FIDES 75.7%；GPT-4o 上 PRUDENTIA 61.4% < Basic 72.2%。因此“equal or better”并非对所有基线/模型成立。
- **Finding 2 “consistently reduces HITL load compared to all baselines”**（p.8）：GPT-4o 上 PRUDENTIA 23.8 > FIDES 7.8，明确反例。一个可能原因是 HITL load 只统计成功任务，FIDES 在 GPT-4o 上 TCR 仅 56.3%，成功任务少，因而总 load 低；但这不影响“consistently”被 Table 2 反驳。
- **Finding 1 “Basic and FIDES … while maintaining the same task completion rates”**（p.7）：原文 Finding 1 写的是 “Basic and FIDES”，但 Basic 是非 IFC 基线，疑为 “Basic-IFC and FIDES” 的笔误；即便按 Basic-IFC 理解，Table 2 中 Basic-IFC 与 Basic 的 TCR 确实相同（同一模型 + IFC 不改任务能力），但 FIDES 在 GPT-4o 上 56.3% vs Basic 72.2%，并不相同；合并表述过宽。
- **Finding 1 的 “1.5−2.6×”**（p.7）：按 Table 2，o3-mini 的 Basic-IFC 1.49×、FIDES 2.56× 符合；o4-mini 的 1.40×、1.32× 与 GPT-5 的 1.29×、1.26× 都低于 1.5×；GPT-4o FIDES 的 59.4/7.8≈7.6× 高于 2.6×。因此 1.5−2.6× 不是跨全部模型/基线的统一范围。
- **WASP “similar number of turns” / “no additional overhead”**（p.8–p.9）：在 WASP 上确实接近；但 AgentDojo Table 7（p.20）显示 PRUDENTIA 的 turns 明显高于 FIDES/Basic-IFC（如 o4-mini travel 12.280 vs 7.950 vs 6.520），因此“无额外开销”只适用于 WASP 的 data-independent 场景。

## 8. 贡献与创新点（按原文主张）

1. **提出自主性指标**：HITL load 与 TCR@k，用 TCR@k 曲线刻画“安全约束下允许多少人工干预”的完整权衡，而不是只比较 TCR@0 与 TCR@∞ 两个极端（pp.2–5, §1/§3）。
2. **提出 PRUDENTIA 设计**：让 IFC Agent 的 planner 感知策略与标签；用 `plan` 工具做策略性变量展开；用 endorsement vs approval 的粗粒度 HITL 交互降低审批次数；有意放弃 declassification。实现只在提示/工具接口层，不改 IFC enforcement（pp.5–6, §4）。
3. **系统评测**：在 AgentDojo 与 WASP 上，与 Basic、Basic-IFC、FIDES 比较，报告 TCR、HITL load、TCR@k、turns、token/成本；WASP 上 0 ASR、0 HITL，AgentDojo 主实验（o3-mini/o4-mini）上更高的 TCR@0 与更低的 HITL load；附录 GPT-4o 行出现反例（pp.6–9, §5；pp.16–20, App B/C）。
4. **论点创新**：既有确定性防御工作把 HITL 当作“无限可用”的兜底，只用 TCR@0 衡量代价；本文主张“减少人工监督”才是确定性防御相对概率防御的关键收益，并据此重新设计 planner（pp.4–5, §3；p.10, §7）。
- **与直接相关工作的差异**：
  - FIDES（Costa et al., 2025）、CaMeL（Debenedetti et al., 2025）、RTBAS（Zhong et al., 2025）的 planner 对策略“无知”，只做事后阻断；PRUDENTIA 让 planner 在规划时主动绕开策略违规（p.5；p.10, §7）。
  - Kim et al. (2025) 也让用户授权不可信数据的使用；PRUDENTIA 的差异是让 planner 在 endorsement 与逐调用 approval 之间做成本选择，并用 `plan` 工具约束展开时机（p.10, §7；p.5, §4）。
  - f-secure（Wu et al., 2024）有形式模型与非妥协证明，但实际实现存在 implicit flow 问题；PRUDENTIA 不追求新证明，而是在 FIDES 的确定性执行之上优化自主性（p.10, §7）。
  - 概率防御（StruQ、instruction hierarchy、Spotlighting、Task Shield 等）不提供确定性保证，本文明确不与之比较（p.10, §6–§7）。
- **可复现资源**：论文承诺发表后开源代码（p.11, Reproducibility Statement），但没有给出 URL；system prompt 在 App D（pp.21–29），AgentDojo/WASP 是公开 benchmark；实验依赖 Microsoft Foundry 的闭源 OpenAI 模型，完全复现受模型版本与随机性影响；论文未声明单独发布数据集。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

### 9.1 作者明确写出/承认的

- **IFC 只保证 security，不保证 general safety**：确定性防御不能防止 LLM 幻觉、误解等非攻击性错误；因此 IFC 只能在安全目的上替代 HITL，不能在所有目的上替代（p.9, §6）。
- **HITL 界面设计未解决**：HITL 触发是确定性的、攻击者不能直接操纵触发条件，但审批/背书界面可能被攻击者操纵展示信息；作者把 UI 设计留作 future work，并建议用 IFC 标签与数据 provenance 帮助用户判断（p.9, §6）。
- **有意不做 declassification**：因为是否适合降低机密性标签高度依赖情境，逐调用审批更合适（p.5, §4）。
- **威胁模型范围窄**：jailbreak、direct prompt injection、tool poisoning 明确 out of scope；模型错误不在安全保证内（p.10, §6）。
- **不与概率防御比较**：因为概率防御没有保证；作者引用 Nasr et al. (2025) 的 100% 绕过结果作为理由（p.10, §6）。
- **成本未优化**：token/成本估计是粗略的，基于日志而非 API 响应；reasoning model 的 output token 没有完整日志；没有 wall-clock 时间；作者认为并行 plan、微调等可降低成本（pp.19–20, App C）。
- **WASP 的 0 HITL 是任务性质决定的**：WASP 全是 data-independent 任务，不需要展开变量；作者承认此时 PRUDENTIA 与 FIDES 相近，Basic-IFC 与 Basic 相近（p.2；p.9）。
- **AgentDojo 的安全是“by design”而非实测**：作者假设人类会审查并阻止注入引发的 consequential call（p.6）。
- **原文没有独立 Limitations 章节**：上述内容分散在 §5.2、§6 Discussion、App C；Ethics Statement 只有两句（没有直接负面社会影响；遵守 ICLR 伦理指南），LLM Usage Statement 说明用 LLM 助手检索相关工作与润色（p.11）。

### 9.2 本人推断的局限/失效场景

- **HITL load 的条件化偏差**：HITL load 只统计成功任务；一个防御如果失败更多任务，成功任务少，总 HITL load 可能反而更低。GPT-4o 上 FIDES 7.8 vs PRUDENTIA 23.8 就是例子：FIDES 的 TCR 只有 56.3%，PRUDENTIA 61.4%。因此跨方法比较 HITL load 必须同时看 TCR@k；论文的 “consistently reduces HITL” 在 GPT-4o 上不成立。可以改用“每成功任务 HITL load”或联合报告，但论文主表用总量。
- **没有 oracle/all-knowing 基线**：论文说目标是接近 all-knowing agent 的 TCR@k 曲线，但没有计算该曲线，也没有给出“最优自主性”的上界；因此无法判断 PRUDENTIA 离最优有多远，也无法判断剩余 HITL 是任务本质所需还是 planner 不够好。
- **没有人类用户研究**：HITL load 是干预次数，不是时间、认知负担或确认疲劳；论文引用 confirmation fatigue 文献，但没有测量真实用户在多轮审批/背书下的错误率、疲劳或信任。`endorsement` 的安全性完全依赖用户是否认真审查数据。
- **背书是安全链上的人为弱点**：用户背书把 U 数据升级为 T；如果注入内容被用户误判为良性，后续 P-T 调用会在“可信”上下文中自动执行，IFC 不再拦截。论文的威胁模型把 user 视为可信，因此没有建模“用户被社会工程”的攻击；也没有对 HITL 界面做红队测试。这是“provable security”与真实部署之间最大的缺口（本人推断）。
- **标签/策略正确性是强假设**：论文没有评估标签器错误、策略配置错误、策略冲突、策略过严/过松的影响。若工具输出被误标为 T，注入可进入 planner；若被误标为 U，utility/autonomy 下降。IFC 的保证是“garbage in, garbage out”。
- **AgentDojo 没有 ASR 实测**：作者说“by design”没有攻击成功，但没有报告攻击任务上的 ASR、没有做自适应攻击、没有测试攻击者针对 `plan`/endorsement 的诱导。WASP 的 0 ASR 不能外推到 AgentDojo 的 data-dependent 任务，因为 WASP 不需要展开变量。
- **WASP 只比较 Basic**：FIDES/Basic-IFC 的结果被省略；没有报告重复次数与方差；0 ASR/0 HITL 的说服力受任务类型限制（data-independent）。
- **成本/延迟可能抵消自主性收益**：GPT-4o 上 PRUDENTIA 的 USD 成本约为 FIDES 的 1.9–2.5×，但 o4-mini banking 的 input token 可达 FIDES 的约 5.9×；AgentDojo turns 也明显更多（o4-mini travel 12.28 vs 7.95）。论文没有做“每节省一次 HITL 需要多少 token/美元”的性价比分析。对于短任务，plan 工具与额外推理可能不划算。
- **统计显著性不足**：5 次重复、std 较大（如 GPT-4o PRUDENTIA HITL 23.8±9.8，Basic HITL 59.4±2.7），没有显著性检验；部分“1.5×/1.7×”差异可能落在噪声内。WASP 没有方差。
- **策略语言表达能力有限**：只有 P-T/P-F 两种工具级策略与用户集合的机密性格；没有目的限制、时间限制、字段级策略、用户自定义自然语言策略、撤销/同意。真实企业策略通常更复杂，`plan` 工具的“策略感知”可能无法覆盖。
- **单 Agent、短 horizon**：AgentDojo/WASP 任务通常 5–12 turns；没有长 horizon、多 Agent、跨组织委托、记忆/工具投毒、供应链攻击。PRUDENTIA 的 plan 工具在长任务中可能积累大量上下文，成本和错误率会上升。
- **“优化”不是算法优化**：没有形式化目标函数、没有搜索/学习、没有收敛性或最优性保证；本质上是一个 prompt/工具设计，效果依赖具体模型（GPT-4o 与 GPT-5 的差异就是证据）。

## 10. 与理论密码学的可能联系（严格；没有就写“无”）

**论文已做的部分：无。** 论文不使用任何密码原语或密码学机制（加密、签名、MAC、哈希承诺、零知识、MPC、FHE、TEE、匿名凭证、差分隐私等）；全文检索不到 crypt/encrypt/signature/homomorphic 等密码学术语。论文没有密码学安全定义、定理、证明或归约，也没有计算受限的密码学对手模型。其“provable security”指既有 IFC 工作在标签/策略正确时的系统级保证：不可信数据不能影响 consequential action；这是语言级信息流安全/访问控制的性质，不是密码学困难性假设下的归约。`security label`、`lattice`、`join`、`policy` 是 PL/系统安全概念；`⊔` 不是密钥派生，`ℓ ⊑ π` 不是 MAC 验证，P-T/P-F 不是密码协议。

**为什么不能把它当密码学**：
- 论文的对手是“能控制外部数据内容的注入者”，不是多项式时间算法；没有优势函数、不可区分性、模拟器、理想/现实世界。
- 安全边界是“user/planner/tools 可信 + 标签/策略正确 + 人类审批”，不是“密钥保密/计算困难”。
- 机密性标签 `{L,H}`/`P(U)` 是访问控制读权限的抽象，不是加密后的密文；数据在 Agent 上下文/变量中仍是明文（变量只是对 planner 隐藏，不是密码学隐藏）。
- “provable” 的证明对象是 IFC 执行机制（FIDES 等），本文没有重复证明，也没有证明 PRUDENTIA 的 prompt 设计保持该性质。

**个人推断的可能理论连接（明确标为推断，不是论文已做）**：
- **非干扰（noninterference）形式化**：可以把 IFC 的“低完整性输入不能影响高完整性输出”写成非干扰性质，并证明 PRUDENTIA 的规划/背书操作不破坏它；但背书本身是一次显式的人为完整性去分类，需要在定理里建模为可信的 declassification 事件。这属于 PL/语言级安全理论，不是密码学。
- **认证标签/来源**：如果标签由不可信组件生成，可以用签名/认证数据结构保护标签完整性；但本文假设标签由可信运行时分配，威胁模型不同。
- **密码学强制访问控制**：可以用 MAC/能力在工具边界强制执行策略；本文用进程内 reference monitor，不需要密码学。若运行时被攻破，密码学 MAC 也不能阻止已授权进程的恶意调用。
- **TEE/远程认证**：可以用 TEE 保护 planner/quarantined LLM 的执行与变量内容；本文没有服务方不可信的威胁模型，也没有性能/攻击实验。

**相关度判断**：按项目的理论密码学量表，本文正文约为 **0–1**：有形式化的策略/度量，但核心是系统/PL 安全，不需要密码学理论；若额外做非干扰证明或认证标签，才是新增的理论工作，不是论文贡献。

## 11. 与应用密码学/密码工程的可能联系（严格；没有就写“无”）

**论文已做的部分：无。** 论文没有 OAuth/OIDC、签名、加密、TEE、capability token、审计日志、密钥管理或任何密码协议。论文自身的授权机制是 IFC 策略检查：工具调用前比较标签与策略阈值；不是认证协议、不是访问令牌、不是密码学授权。FIDES 的变量隐藏是运行时数据封装，不是加密；quarantined LLM 是上下文隔离，不是 TEE 或密码学隔离。

**个人推断的工程接口（均标为推断，需新增设计与实验）**：
1. **签名的数据来源/标签凭证**：由邮件服务、浏览器或企业 IdP 对数据来源与敏感级别签发可验证凭证（如 SD-JWT/VC），运行时验证后再赋标签。作用：防止标签伪造/来源冒充，补充“标签由可信运行时分配”的假设。局限：本文的标签是运行时根据工具/数据流打的，不是数据源签发的；引入凭证会改变威胁模型与部署复杂度。
2. **对 quarantined LLM/planner 的远程认证与加密通道**：若隔离 LLM 或 planner 是远程服务，用 TLS + attestation 保护变量内容与模型完整性。作用：防止服务方/中间人读取变量。局限：本文假设本地可信执行；远程 attestation 不能防止模型本身被注入或输出错误。
3. **工具边界的能力令牌（capability）**：给每次工具调用签发带 recipient、tool、purpose、expiry 的 capability，由网关强制执行。作用：把 P-T/P-F 的策略检查从进程内移到可审计的执行点。局限：本文的 IFC 已经能在运行时检查标签；capability 需要额外的策略编译与密钥管理，且难以表达“同一封邮件里哪些字段可分享”的细粒度策略。
4. **HITL 审批/背书的抗钓鱼认证与审计**：对审批界面做来源认证、显示数据 provenance、记录审批人与时间戳，防止攻击者伪造审批或用户误点。作用：直接针对论文承认的“HITL 界面可能被操纵”风险。局限：这是人机交互与身份认证问题，不能替代 IFC；用户仍可能被内容说服。
5. **披露/审批的透明日志**：对每次 consequential call、策略失败、审批/背书做哈希链/签名日志，支持事后取证与合规审计。作用：问责与检测。局限：事后检测，不预防注入；日志完整性不等于策略正确性。

**伪交叉警告**：
- 加密静态数据/变量不能解决“planner 需要明文推理”的问题；变量对 planner 隐藏是上下文隔离，不是密码学保密。
- 签名工具输出只能证明“输出来自某工具”，不能证明内容无注入；注入内容可以是合法工具返回的恶意数据。
- ZK 证明“计划满足策略”需要把动态标签、工具语义、策略编译成电路，代价高且不覆盖自然语言/上下文歧义；本文的策略是简单的工具级标签，没必要用 ZK。
- 把 IFC 的“provable”说成密码学证明是错误类比；它没有计算假设、没有归约、没有密钥。
- 用 OAuth scope 替代 IFC 会丢失数据流标签传播（例如“由不可信邮件派生的计划”），无法表达 PRUDENTIA 的核心污点语义。

**相关度判断**：按项目量表，本文正文约为 **0–1**：没有识别或使用任何密码机制；若把“签名 provenance + capability 网关 + 审批审计”做成原型并量化安全/性能收益，可到 2–3，但那是新增系统研究，不是本文贡献（本人推断）。

## 12. 可检验的研究假设（3–6 条）

以下均为**假设/推断**，需外部实验或文献查证；本文未做，不等于无人做过。

- **H1（策略感知规划的自主性收益与模型相关）**：在相同 IFC 策略与 TCR 下，PRUDENTIA 的 HITL load 应低于策略无感知的 FIDES；但这一优势可能依赖模型能力与任务类型。实验：在 AgentDojo 四个 suite 上按模型分层，做配对 bootstrap/混合效应模型，检验 HITL 差异是否在控制 TCR 后仍显著；特别复现 GPT-4o 上 FIDES 7.8 vs PRUDENTIA 23.8 的反例。
- **H2（背书收益随展开后 consequential 调用数增长）**：设展开后需要 `m` 个 P-T 调用，背书策略相对逐调用审批节省的 HITL 应约为 `m−1`（在用户总是正确背书的前提下）。实验：构造 m=1,2,5,10,20 的任务，测 HITL load、TCR@k、用户错误率；若 m=1，背书不应优于审批（论文的 `ask_endorsement=False` 逻辑）。
- **H3（HITL load 的条件化偏差会改变方法排序）**：由于 HITL load 只统计成功任务，TCR 较低的方法可能获得更低的 load。实验：同时报告总 load、每成功任务 load、TCR@k，并在 TCR 匹配的子集上比较；预测 GPT-4o 上 FIDES 与 PRUDENTIA 的排序会随口径变化。
- **H4（针对背书/HITL 界面的自适应社会工程可绕过 IFC）**：如果攻击者能诱导用户背书含注入的邮件，后续 P-T 调用将在“可信”上下文自动执行。实验：用人类受试者或 LLM 模拟审批者，比较有无 provenance 展示、有无攻击者伪造的“可信来源”标记时的背书率与 ASR；这是对论文“provable security”边界的直接检验。
- **H5（标签/策略错误会线性破坏安全保证）**：IFC 的安全性以标签/策略正确为前提；注入标签噪声（把部分 U 标为 T、把 T 标为 U）与策略错误，测量 unsafe action 数与 HITL/TCR 变化。预测：少量“U→T”误标即可显著提高 ASR；这比优化 planner 更关键。
- **H6（成本归一化的自主性可能不利于 PRUDENTIA）**：PRUDENTIA 的美元成本约为 FIDES 的 1.9–2.5×（GPT-4o），input token 在 o4-mini banking 可达 5.9×；对短任务，节省的 HITL 可能不值这个成本。实验：定义 “HITL saved per USD/token”，在 AgentDojo/WASP 上按任务长度分层比较 PRUDENTIA vs FIDES vs Basic-IFC；预测短任务上 FIDES 更划算，长任务/多步依赖任务上 PRUDENTIA 更划算。
