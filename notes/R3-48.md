## 1. 150–300 字中文概述

本文主张把 Agent 安全作为系统安全问题处理：AI 模型必须视为不可信组件，安全不变量应在模型之外由系统层强制执行。作者认为以模型鲁棒性为中心的路线（对齐、注入分类器）无法给出可预测保证，转而从操作系统中提炼 TCB、安全策略、安全边界、reference monitor 等概念，以及最小权限、TCB 抗篡改、完全中介、安全信息流、人的薄弱环节五条原则。论文用 11 个真实攻击案例说明这些原则如何被违反，并提出三项研究议程：指令与数据分离、可验证的最小权限策略生成、信息流控制（IFC）。全文是立场与研究问题清单，不含形式化定义、定理、证明、实验或密码学机制；密码学仅作为系统安全类比出现。

## 2. 研究背景、现有方法不足、精确定义的问题

### 2.1 背景

- Agentic computing 被定义为“AI 模型使用各种工具完成用户以自然语言指定的任务”，运行在网站、应用与外部服务等复杂环境中，并暴露于可影响其行为的对抗输入（p.1, §1）。
- 论文的威胁模型是：攻击者控制 Agent 输入通道的某一部分（文档、工具输出等），目标是诱导非预期动作或窃取敏感数据（p.1, §1）。典型入口是间接提示注入：恶意网页、邮件、日历事件、桌面通知、Jira ticket、GitHub issue 等（pp.1, 5–6, 16–17）。
- 作者强调，即使没有外部攻击者，模型本身也是“不可靠组件”，在对抗或歧义输入下可能不可预测地行动（p.1, §1）。

### 2.2 现有方法为何不足

论文把主流路线概括为 **model robustness**：把模型当作安全的主要对象，用对齐技术使其直接抵抗对抗输入。作者给出两条经验性理由（p.1, §1）：

1. **经典对抗 ML 的历史**：计算机视觉时代反复证明攻击者可以绕过基于模型的防御（引 Athalye et al. 2018, [5]）。
2. **LLM 时代的同类现象**：攻击者“似乎总是成功”，且不需要显著增加攻击成本（引 Nasr et al. 2025 [36]、Pandya et al. 2025 [42]）。

作者进一步指出，现代 Agent 系统比视觉分类器复杂得多：LLM 只是“agent scaffolding、环境与工具”组成的更大系统的一部分，这恰好提供了引入系统安全技术的机会（p.1）。类比是：操作系统把进程视为不可信，Agent 系统也应把模型视为不可信，把安全属性表达并在系统层强制执行（p.1）。

### 2.3 精确定义的问题

论文没有给出单一的形式化问题陈述，而是把它拆成三个“gaps”/机制（p.1–2, §1）：

1. **指令与数据分离**：LLM 把可信指令与不可信数据混在同一 token 流中，缺少源级分离；需要一个确定性机制决定何时可以跟随新指令（p.2）。
2. **最小权限沙箱 + 可验证策略生成**：Agent 的任务是自然语言、动态、任务特定的，策略如何从 NL 可靠映射到形式语言，并随执行演化（p.2）。
3. **信息流控制（IFC）**：仅控制“能否访问”不够，还要约束信息在系统中的长程流动；LLM 混合所有输入，使标签传播与流分离困难（p.2）。

**注意结构性不整齐**：§1 说“three main gaps”，§2.1 却列出 **五条**原则（Least Privilege、TCB Tamper Resistance、Complete Mediation、Secure Information Flow、Human Weak Link），§5 又说“three main security mechanisms”。论文没有给出“五原则→三机制”的映射，且 TCB 抗篡改与人的薄弱环节在后三项机制中没有独立对应物（详见 §5、§9）。这是原文的结构性缺口，不是我的误读。

论文**没有独立的 Related Work 章节**；相关工作散见于 §3.2、§3.3 的行内引用与参考文献（pp.7–8, 10–14）。这与典型 SoK 不同，阅读时需自行重建其学术定位。

## 3. Agent 系统模型（组件、交互流程、信任边界）

### 3.1 组件

论文没有给出形式化的 Agent 架构图，但从正文与案例可重建出以下组件（pp.1–2, 4–6, 15–18）：

- **用户**：用自然语言给出任务；任务往往欠指定（underspecified），并会在执行中细化（p.5）。
- **Agent / LLM**：消费 system prompt、用户消息、工具输出与外部内容，生成工具调用或自然语言回复；是“untrusted component”（p.1）。
- **Agent scaffolding**：把模型接到工具、环境与通信通道上的运行时（p.1–2）。
- **工具**：shell、浏览器、API、UI、MCP server、Claude skills、OpenClaw ClawHub add-ons 等；动作空间开放，可在运行时组合（pp.5–7）。
- **环境**：网站、应用、外部服务、本地文件系统、网络（p.1）。
- **状态/记忆**：ChatGPT Memories、`settings.json`、`.env`、`localStorage` 中的 `userToken`、浏览器已认证会话等（pp.4, 15–17）。
- **不可信内容源**：文档、网页、邮件、日历事件、桌面通知、Jira ticket、GitHub issue、ANSI 输出等（pp.1, 5–6, 15–17）。

### 3.2 交互流程

可概括为：用户任务 → system/user prompt 进入模型上下文 → 模型生成工具调用 → 工具执行并返回输出 → 输出回到上下文 → 模型决定下一步动作，直到任务结束。关键点是：**外部内容可以在任意一步进入上下文**，而系统没有可靠的来源/provenance 标签，也没有分层抽象来区分“指令”与“数据”（pp.5–6）。Figure 2（p.17）用 ChatGPT Operator 案例画出了跨边界流程：恶意 GitHub issue → Operator 代理 → 已认证的 Gmail/网站会话 → 攻击者网页的 keylogger，最终 PII 外泄。

### 3.3 信任边界与 TCB 位置

论文借用经典安全架构（Figure 1, p.3）：**Untrusted System ↔ Security Boundary ↔ Trusted Computing Base（TCB）**，TCB 内含 **Reference Monitor**，Reference Monitor 解析 **Security Policy** 并对每个请求做批准/拒绝。TCB 被定义为“其完整性与机密性不受攻击者影响的代码与数据，即在攻击下仍应正确运行”（p.3）。

论文的规范性主张是：**模型应位于 TCB 之外**，安全不变量由确定性的系统代码强制执行。但现实 Agent 往往把模型放在 TCB 内：模型既制定策略又执行动作，于是 TCB 变成概率性的；用另一个 safety LLM 做 reference monitor 也不行，因为它是“unpredictably probabilistic reference monitor and TCB”（p.6）。这是全文最核心的信任边界论点。

**架构模型缺口**：论文没有说明在真实栈中边界应画在哪一层（OS 系统调用？浏览器？MCP gateway？工具运行时？），也没有给出 TCB 的分解与验证方法。它只给出抽象架构与案例，具体边界留给读者/后续工作（此点为本人推断）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

### 4.1 资产

从 11 个案例可归纳（pp.4, 15–18）：用户邮件与对话、PII、ChatGPT Memories、`.env` 中的 API keys、AWS credentials、`localStorage` 中的 `userToken`、本地文件系统、剪贴板、浏览器已认证会话、网络访问能力。资产既包括“数据”，也包括“能力/会话”（能代表用户行动）。

### 4.2 攻击者目标与能力

- **目标**：数据外传（DNS、图片 URL、ASCII smuggling、超链接、暴露端口、keylogger）、账户接管、任意命令执行/RCE、持久外传（SpAIware）。
- **能力**：控制 Agent 输入通道的一部分；托管恶意网页/文档/issue/ticket；构造编码载荷（base64 JavaScript、ANSI 转义序列、ASCII smuggling）；利用合法工具（`ping`/`nslookup`、`curl`、浏览器、剪贴板、`expose_port`）；控制攻击者服务器/域名；在部分案例中要求用户关闭防护（Cursor 的 Auto Run 或 Jira MCP 人工确认；p.16）。
- **不假设**：模型权重访问、训练期投毒、供应链植入**不是**核心威胁模型的一部分。训练数据投毒与对抗微调只在论文 §4 作为“ML 组合防御为何不可靠”的论据出现（p.9），不是论文主威胁模型；MCP/skills 供应链只在 p.5 提及，未展开分析。

### 4.3 威胁模型与前提假设

论文没有独立的 Threat Model 小节；威胁模型由 p.1 §1 的一句话与 p.2 的范围声明共同定义：

- **攻击者**：外部攻击者，控制部分输入通道；目标是诱导非预期动作或外传数据（p.1）。
- **模型**：不可信、不可靠，可能在对抗/歧义输入下失效（p.1）。
- **TCB**：应当是确定性的、抗篡改的；策略应当正确；reference monitor 应当完全中介（pp.3–4 的规范性原则）。
- **人**：可能是薄弱环节——用户误点权限提示、管理员配错策略、开发者写错 reference monitor（p.4）。
- **范围之外**：谄媚、幻觉、存在性风险、模型欺骗（scheming、evaluation awareness）属于 AI safety，不在本文范围（p.2）。

**形式化程度**：没有攻击者计算能力、先验知识、成功概率、攻击预算的形式化定义；这是一个**定性威胁模型**，用于案例归类而非可证明安全。

## 5. 核心方案：系统安全原则、执行层机制、11 个案例分析

### 5.1 五条系统安全原则（pp.3–4, §2.1）

| 原则 | 原文定义（压缩） | 在 Agent 中的含义 |
|---|---|---|
| Least Privilege（最小权限） | 组件/用户/进程只应获得完成任务所必需的权限，不多给；通常用沙箱隔离并从外部监控 | Agent 不应默认拥有全部 shell/文件/网络权限；工具参数应受限 |
| TCB Tamper Resistance（TCB 抗篡改） | TCB 应受保护，使攻击者无法劫持其功能；例如硬件 Cryptographic Root of Trust 验证并证明加载的 OS 正确 | 安全关键配置（如 `settings.json`）不可被 Agent 修改；TCB 本身需完整性保护 |
| Complete Mediation（完全中介） | 来自 Untrusted System 的每一个请求都必须由 reference monitor 对照策略验证，不能绕过 | 每一次工具调用/数据访问都要经过策略检查，不能只检查“发送邮件”而漏掉 `ping`/DNS |
| Secure Information Flow（安全信息流） | 敏感信息不得流向不可信区域，包括侧信道；策略须定义信息流向并在执行中动态强制 | 即使请求合法，响应也不能包含未授权秘密；需要 IFC 追踪数据传播 |
| Human Weak Link（人的薄弱环节） | 人会误判权限提示、配错策略、在 reference monitor 中引入 bug；架构必须考虑人的失败模式 | 不能把安全决策全推给用户；审批设计要避免疲劳与误点 |

### 5.2 三项执行层机制（pp.2, 6–8）

| 机制 | 论文主张 | 关键难点（原文承认） |
|---|---|---|
| （1）Provable separation of instructions and data | 类比 CPU 的 NX/W⊕X、SQL prepared statements 与 taint；在每一层强制指令/数据分离；模型级分离会被持续攻击者绕过，故需 defense-in-depth | 没有源级分离；即使显式分隔，攻击者仍能绕过 [26,36,42]；多模态使指令可藏在图像/视频/音频；分离可能过度限制 Agent 的适应性；分离也不能完全解决提示注入（工具参数仍可被污染） |
| （2）Least-privilege sandboxing with verifiable policy generation | 将 NL 策略翻译成形式策略，在沙箱中限制权限并用 reference monitor 确定性执行；翻译需带正确性保证 | 策略是自然语言、动态、任务特定；动作空间开放（运行时组合工具、任意 URL、无界操作序列）；“sensitive”“harmful”等谓词是语义的，超出形式策略语言表达力；NL→formal 翻译目前多交给未验证的 LLM |
| （3）Information flow control（IFC） | 给数据打标签，静态/动态追踪标签，按标签策略强制；补足“访问控制只是门禁”的不足 | LLM 混合多源输入，输出只能标为输入标签的并集 → **label explosion**；降级（declassification/endorsement）二十年未解；token 序列没有自然结构，标签粒度难定 |

**对机制（2）的精确化**：论文提出正确性判据是 **mutual entailment**——自然语言源 N 与形式策略 P 必须在部署的所有可达状态上对授权决定一致（p.7）。该判据“不可直接检查”，因为自然语言处处歧义；任何自动判定本身是概率性的。论文因此把它松弛为三个轴（pp.7–8）：

1. **Grounding**：N 与 P 的蕴含只在命名谓词与解释的“substrate”上才有意义；substrate 必须编码 Agent 的动作空间与“sensitive”“trusted site”等概念。
2. **Checkability**：即使 substrate 固定，蕴含检查仍是概率性的；问题是能否通过限制 N/P 的结构（策略片段、schema）使检查足够可靠，从而与确定性执行组合成有意义的端到端保证。
3. **Synthesis procedure**：N→P 翻译器必须给出 P 与 N 之间残余差异的可度量上界，并支持随任务演化的增量细化。

这三点是全文**最接近形式化**的部分，但仍是研究议程，不是定理。

**Table 1 的定量观察（本人据 p.5 PNG 逐格统计，非原文字句）**：11 行 × 5 列共 24 个勾选；**Secure Information Flow 出现在 11/11 行**，Least Privilege 6/11，Complete Mediation 3/11，TCB Tamper Resistance 2/11，Human Weak Link 2/11。这说明“安全信息流”是唯一贯穿全部案例的原则，也说明该原则的定义非常宽（几乎任何外传都算），用作诊断标签时区分度有限。

### 5.4 从案例到研究挑战

论文把开放问题集中为三节（§3.1–§3.3），此外还有贯穿性的 **semantic gap**（§2.3）：

- **指令/数据分离**：需要精确形式定义（引 Zverev et al. [72]）；需要可证明遵循该定义的 LLM（或确定性机制）；需要覆盖多模态；需要处理“合法地跟随数据中的新指令”的适应性需求；CFI 是“识别新指令后是否执行”的类比，但 Agent 没有等价策略（pp.6–7）。
- **可验证策略生成**：动作空间开放 + 策略语义化 + NL 歧义 → 只能走“翻译 + 概率性蕴含检查 + 残余差异上界”的路线；论文把 grounding、checkability、synthesis 三轴列为开放问题（pp.7–8）。
- **IFC**：标签传播只能取并集 → label explosion；降级（declassification/endorsement）长期未解；标签粒度缺少自然抽象层；论文提出软分布标签（QIF）、因果干预、机制可解释性三个方向（p.8）。
- **Semantic gap**：Agent 没有 OS 那样的 Hardware ⇔ Kernel ⇔ Process ⇔ Network 分层；它把高层 prompt 直接压成低层工具调用，策略表达层与执行层之间存在语义断层（p.6）。这是上述三个问题共同的根因。

## 8. 贡献与创新点（按原文主张）

原文明确列出三项贡献（p.2, §1 Contributions）：

1. **提炼核心原则**：基于作者们在 OS、网络、CPS、形式化方法、PL、对抗 ML 的多年经验，提炼 Agentic security 的基础原则。
2. **分析 11 个真实攻击**：展示这些攻击如何通过具体网络安全原则被理解、并在许多情况下被缓解。
3. **操作化原则**：讨论实现这些原则的具体安全机制；作者相信若在构建 Agent 时使用这些机制，“a large swath of attacks will be prevented by design”（p.2）。

**创新点评估（区分原文主张与本人判断）**：

- **框架层面**：把 Agent 安全从“模型鲁棒性”重新框定为“系统安全”，并用 TCB/reference monitor/security boundary 的经典架构来组织问题。这是本文最主要的贡献；但它是对 Saltzer & Schroeder [58] 与经典系统安全思想的移植，不是新原则的发明。
- **案例层面**：11 个案例的“攻击→原则→防御”映射是一个有用的教学/诊断工具；但映射是事后的，且 Table 1 与正文有若干不一致（§9.3）。
- **问题层面**：论文识别了三个 LLM 特有的障碍，具有分析价值：
  - **semantic gap**：Agent 缺少 OS 式分层，策略表达层与执行层断层（p.6）；
  - **probabilistic TCB**：LLM 作为 policy predictor/reference monitor 没有精确契约，无法证明其一致执行策略（p.6）；
  - **label explosion**：LLM 输出只能继承输入标签的并集，IFC 在 LLM 上退化为“全污染”（p.8）。
- **判据层面**：mutual entailment 作为 NL→formal policy 的正确性判据，以及 grounding/checkability/synthesis 三轴，是全文最接近“可操作研究纲领”的部分（pp.7–8）。
- **批评层面**：对“堆叠 ML 组件 = defense-in-depth”的反驳（p.9）——guard 模型与主模型共享统计失败模式，失败不独立——是对当前 guardrail 产业的重要警告。

**与直接相关工作的差异**（论文无 Related Work 章节，以下据行内引用重建）：

- 与 **model-robustness** 路线（对齐、对抗训练、StruQ [8]、SecAlign [10]、Instruction Hierarchy [68]）相比：本文认为这些是必要但不充分的，且无法给出可预测保证。
- 与 **确定性策略执行** 系统（Progent [61]、Debenedetti et al. "Defeating Prompt Injections by Design" [17]、ACE [29]、SAGA [65]、ceLLMate [32]、Costa et al. IFC [14]、Cedar [15]、Binder [19]、CAPSEM [22]、NeMo Guardrails [38]、Palumbo et al. [40]）相比：本文不是新系统，而是把这些工作组织成一个三机制议程，并指出 NL→formal 翻译这一缺口。
- 与 **NL→formal 翻译** 工作（ShieldAgent [12]、VeriGuard [34]、Progent [61]）相比：本文指出它们通常把翻译交给未验证的 LLM，缺少正确性保证；本文提出 mutual entailment 判据，但没有实现。
- 与 **IFC** 传统（Denning [18]、TaintDroid [20]、Tiwari et al. [66]、Sabelfeld & Sands [57]、QIF [35,63]）相比：本文把 IFC 扩展到 LLM，并指出 label propagation/explosion/downgrading/granularity 四个新问题。
- **无代码/无 artifact/无项目页**；论文是纯立场与议程。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

### 9.1 作者明确承认/写出的

- 指令/数据分离“if attainable”，且“unlikely to fully solve the prompt injection problem”，因为对抗数据仍可通过工具参数污染执行（pp.6–7）。
- 当前基于标签/分隔符的分离“cannot be enforced provably”，大多是 best-effort heuristics；黑盒/白盒提示注入都能绕过（p.7）。
- mutual entailment “not directly checkable”；任何自动蕴含判定都是概率性的；只能沿 grounding/checkability/synthesis 三轴松弛（pp.7–8）。
- IFC 在 LLM 上的标签传播是开放问题；输出只能标为输入标签并集，导致 label explosion；降级问题已开放近二十年（p.8）。
- Agent 缺少自然抽象层，存在 semantic gap；策略表达层与执行层不一致（pp.6, 8）。
- 在当前 Agent 中 TCB 是概率性的；安全 URL 集合无法实际枚举；因此输出清洗/人工批准只能提供不完整保证（p.16）。
- 每次导航都人工确认不是好机制，会把负担转嫁给可能缺乏专业性或耐心的用户（p.17）。
- 安全策略是动态、任务特定的；Agent 没有 app developer，权限必须从自然语言任务中动态预测（p.5）。
- 结论用 “we postulate” 而非 “we prove”：三项机制“将消除很大一部分攻击”，但需要解决所列挑战（p.9）。

### 9.2 本人推断的局限/失效场景

- **没有实现与测量**：全文没有原型、实验、开销数据。作者在 §4 为“系统方法太侵入、开销不可接受”的反对意见辩护，但没有给出任何性能/效用数据来支持“开销可接受”（p.9）。这使得“prevented by design”只是设计信念。
- **案例选择与事后归因**：11 个案例不是系统抽样；原则映射是事后进行的，任何外传都可被归为“安全信息流”违反（Table 1 中 11/11）。原则足够宽，因而难以证伪。
- **五原则与三机制不对齐**：TCB 抗篡改与人的薄弱环节没有独立机制；三机制也没有给出组合语义（如何叠加、谁先执行、冲突时谁优先）。"Defense-in-depth" 是口号，不是可组合的安全定理。
- **TCB 正确性被假定而非解决**：论文说 TCB 应确定性、抗篡改，但没有说明如何验证 reference monitor 本身；它只在 Human Weak Link 中提到“开发者可能引入 bug”（p.4）。一个确定性的 reference monitor 仍可能有 bug、策略解析错误、TOCTOU 问题。
- **策略翻译仍依赖不可信模型**：论文批评现有 NL→formal 方法“delegate to an unvalidated LLM call”（p.7），但它自己的路线仍需要一个翻译器 + 概率性蕴含检查；这等于把不可信性从执行层转移到翻译层，没有消除。论文没有给出翻译器的可信构造或误差上界。
- **IFC 在 LLM 上可能不可用**：label explosion 使“全污染”成为默认；软标签/QIF 需要攻击者先验与可计算的泄漏度量；因果干预成本高；机制可解释性尚不成熟。论文把这些列为方向，但没有证明它们能落地。
- **语义 gap 是根因，但论文的标题归因于“systems”**：三项机制的难点（什么是指令、什么是敏感、标签粒度）几乎都是语义判断，而不是系统机制。更准确的说法可能是：“执行架构是系统问题，语义判定仍是 AI 问题。”这是本文对项目最有价值的细微差别。
- **人类因素没有机制**：论文把 Human Weak Link 列为原则，但除“人工批准”外没有设计；而人工批准正是它自己批评的负担转移。没有审批疲劳、可用性、责任归属的分析。
- **范围缺口**：多 Agent 合谋/级联、MCP/skills 供应链、模型权重后门、侧信道、DoS/资源耗尽、经济攻击、隐私法规/合规都不在核心分析内；论文只在 p.5 提到 MCP/skills，在 p.9 提到投毒/对抗微调作为“ML 组合防御失败”的论据。
- **“real-world” 的边界**：部分案例依赖非默认配置（Cursor Auto Run、Jira MCP 人工确认关闭），部分依赖用户点击（Copilot 超链接、ClickFix）。这不否定案例真实性，但削弱“普遍代表性”。

1. **Table 1 与正文的勾选不一致**（以 p.5 PNG 为准）：
   - ChatGPT Long-Term Memory SpAIware：§2.2 明确列 TCB 抗篡改、最小权限、安全信息流三项；Table 1 只勾 TCB 抗篡改与安全信息流，漏了最小权限。

2. **“three gaps” vs “five principles” vs “three mechanisms”**：§1 说三个 gap，§2.1 列五条原则，§5 说三个机制；没有映射表，也没有说明为什么 TCB 抗篡改与人的薄弱环节没有对应机制。

7. **“all major systems implement a subset”**：p.2 说 "Today, all major systems implement a subset of these ideas"，没有给出证据或范围（OS/浏览器/数据库？Agent 算不算？）。这是修辞性概括。

## 10. 与理论密码学的可能联系（严格；没有就写“无”）

**论文本身：无。** 全文没有形式化密码学定义、安全游戏、定理、证明或 reduction；没有使用加密、签名、MAC、承诺、零知识、MPC、FHE、TEE、匿名凭证等任何密码原语。它的“security”是系统安全的规范性论证，不是密码学意义上的可证明安全。

### 10.1 论文实际提到的密码学内容（仅三处，且都是类比/例子）

1. **p.3, §2.1 TCB Tamper Resistance**：举例说 OS 由硬件 "Cryptographic Root of Trust" 保护，该 root of trust "verifies and attests that the Operating System being loaded is the correct one"。这是**经典 OS 的例子**，不是对 Agent 机制的提议，也没有展开 attestation 协议。
2. **p.5, §2.3**：提到 web 的 "Subresource Integrity" 确保第三方脚本未被修改——这是**哈希完整性**的工程类比，用于说明 Agent 缺少来源/完整性机制；论文没有提议在 Agent 中使用 SRI。
3. **p.6, §2.3**：说经典 TCB 的可预测性由两种方式保证：reference monitor 的确定性行为，或 "probabilistic bounds backed by hardness assumptions of cryptographic protocols"。这是全文**唯一直接提到密码学困难性假设**的句子，且是用来与 LLM 的“无保证概率性”作对比。

### 10.2 为什么这不是理论密码学

- **“Provable” 指形式化/系统保证，不是密码学证明**：p.2 的 "Provable separation of instructions and data" 指一种（尚未构造的）指令/数据分离性质；p.7 的 "verifiable policy generation" 指 NL→形式策略的 mutual entailment 检查。两者都不涉及计算困难性、密钥、敌手优势或 reduction。
- **“Attestation” 只出现在 OS 例子中**：论文没有提出 Agent TCB 的远程证明协议、测量启动、证书链或 TEE 方案。
- **“Verifiable” 不是密码学可验证性**：mutual entailment 是一个语义/形式化判据，作者明确说它不可直接检查、自动判定是概率性的；这不是签名/承诺/零知识意义上的 verifiable。
- **没有形式化敌手**：没有定义攻击者的计算能力、视图、优势、胜率；11 个案例是定性的，不是密码学游戏中的挑战者/敌手交互。

### 10.3 可精确定位的理论连接（以下均为本人推断，不是论文已做）

- **TCB 可预测性 vs 密码学困难性假设（p.6）**：这是最精确的接口。密码协议是概率性的，但可以在计算困难性假设下给出可忽略优势的界；LLM 作为 policy predictor/reference monitor 既没有确定性，也没有这样的界。一个理论研究可以把 Agent 系统建模为：不可信模型（可被任意 prompt 操控的 oracle）+ 确定性 reference monitor + 密码协议实现的 TCB；证明“在底层密码假设成立且策略正确的前提下，任何 PPT 攻击者都无法让系统违反策略”。但这类模型只能覆盖**策略已形式化**的部分，无法覆盖“sensitive/harmful”的语义判定。
- **指令/数据分离作为 noninterference**：可以把“数据不得影响控制流”写成语言级信息流性质（Denning 格模型 [18]、Sabelfeld & Sands [57] 的 declassification 框架），用类型系统/taint 分析证明。但这是**形式化方法/语言安全**，不是密码学；LLM 的 token 流没有类型结构，分离的执行机制仍待构造。
- **来源认证 vs 指令信任**：签名可以认证“这段内容来自哪个源”，但不能认证“这段内容应被当作指令执行”。论文 p.5 说 provenance 难以评估；密码学可以补前者，补不了后者。把“已签名”等同于“可信指令”是典型的 confused deputy。
- **IFC/QIF**：p.8 引用的 quantitative information flow [35,63] 是**信息论**的泄漏度量（g-leakage、min-entropy leakage），不是计算密码学。它可以在给定攻击者先验/增益函数下量化泄漏，但需要先验模型；对 LLM 的标签传播，它只能提供统计近似，不能提供密码学保证。
- **理论密码学相关度判断**：按项目 `T_crypto` 量表，本文正文约 **1**（只有概念类比：TCB 可预测性/密码困难性、attestation 例子；没有定义、定理、reduction）。若有人把上述 TCB+密码协议模型做成形式化定理，可到 2，但那是**新增理论研究**，不是本文贡献。

### 10.4 密码学不能解决本文的哪些核心问题

- **语义谓词**：什么是 “sensitive”、什么是 “harmful”、某个 recipient 是否有权知道某条信息——这些是上下文相关的语义判断，密码学原语不提供。
- **NL→formal 策略翻译**：密码学可以认证策略文件的完整性，但不能把自然语言意图翻译成形式策略；论文的 mutual entailment 检查本身是概率性的。
- **LLM 内部的标签传播**：密码学标签保护静态/传输中的数据；一旦数据进入模型，输出依赖所有输入，密码学无法追踪“哪条输入导致了哪条输出”。这是 label explosion 的本质。
- **人类因素**：审批疲劳、误点、策略配置错误，密码学不解决。

## 11. 与应用密码学的可能联系（严格；没有就写“无”）

**论文本身：无。** 论文没有使用 OAuth/OIDC、签名、MAC、加密、TEE、capability token、审计日志、密钥管理或任何密码协议。p.3 的 "Cryptographic Root of Trust" 是 OS 例子；p.5 的 "Subresource Integrity" 是 web 例子；p.6 的 "hardness assumptions" 是对比句。三者都不是对 Agent 的机制建议。

### 11.1 可落地的工程接口（以下均为本人推断，需新增设计与实验）

1. **TCB 的证明与隔离**：用 measured boot/remote attestation 证明 reference monitor、策略引擎与策略文件的完整性；用 TEE 把 reference monitor 与模型进程隔离；用签名策略包分发策略。对应论文的 TCB 抗篡改原则（p.3）。局限：TEE 侧信道、供应链信任、策略仍是外部输入。
2. **工具网关的 capability token**：在 MCP gateway / OS syscall 边界执行 macaroon、Biscuit、UCAN 风格的 capability；caveat 可绑定 task、resource、recipient、purpose、expiry；支持衰减（attenuation）与撤销。对应最小权限 + 完全中介（pp.3–4）。局限：capability 的 scope 是粗粒度的，难以表达“会议时间可分享但身份证号不可分享”的混合消息；需要字段级 redaction 与上下文谓词。
3. **来源/完整性认证**：对 MCP 响应、工具输出、skill 包、策略文件做签名；对网页内容尽量用 HTTPS/签名源；在 Agent 上下文中保留 origin 标签。对应 p.5 的 provenance 缺口。局限：大多数自然语言内容没有签名；签名只证明来源，不证明可信；攻击者也可以控制一个合法签名的源。
4. **安全关键配置的不可变/完整性保护**：对 `settings.json`、allowlist、策略文件做只读挂载、哈希锁定、签名校验；任何修改需人工批准。对应 Amp 案例的防御（p.17）与 SRI 类比（p.5）。
5. **可验证审计**：对每次工具调用/策略决定记录 `(principal, tool, args_digest, policy_id, decision, timestamp)`，用哈希链/签名/透明日志保证不可抵赖；支持事后取证与问责。局限：事后检测，不预防；日志完整性 ≠ 策略正确性。
6. **通道安全**：MCP/工具调用用 TLS/mTLS；远程模型/工具用认证通道。这是 baseline，不是充分防御。

### 11.2 密码学不能替代什么

- **不能替代策略语义**：capability 只能执行“谁可以对什么做什么”的形式化策略；无法判断“这条信息在这个上下文里是否敏感”。
- **不能替代指令/数据分离**：签名/加密不阻止模型把数据当指令；模型仍会在同一 token 流中处理两者。
- **不能替代 IFC 标签传播**：加密数据在模型解密/消费后仍是明文；密码学标签不能追踪模型内部的信息混合。
- **不能替代人类判断**：审批、策略配置、责任归属仍是组织/UX 问题。

### 11.3 伪交叉警告

- **给所有工具输出签名**：只证明来源，不证明“应跟随其中的指令”；攻击者控制合法源时无效。
- **加密 Agent 记忆/上下文**：模型需要解密后推理，明文仍进入上下文；加密只保护静态/传输，不阻止模型层泄漏。
- **ZK 证明“模型运行了某步”**：证明计算完整性，不证明策略合规；LLM 是概率性的，证明也不覆盖语义。
- **TEE 证明“模型是某个版本”**：只证明运行的是哪个模型，不证明该模型不会被注入；模型本身仍是不可信组件（这正是论文的立场）。
- **粗粒度 capability 替代所有策略**：会过度阻断合法任务，重蹈论文批评的“把负担转给用户”；真正的价值是“语义建议 + 可执行策略 + 可审计”的组合。

### 11.4 应用密码学相关度判断

按项目 `A_crypto` 量表，本文本身约 **0–1**：没有识别任何密码机制使用点，唯一的“信任根”是 OS 例子；若把上述 attestation + capability gateway + 签名策略/审计做成可运行原型，并量化安全/性能收益，可到 **2–3**，但这属于新增系统研究，不是本文贡献。

## 12. 可检验的研究假设（3–6 条）

以下均为**假设/推断**，需外部实验验证；本文未做，不等于领域无人做过。

- **H1（确定性执行层优于模型护栏）**：在相同 Agent 任务集上，把工具调用放到 deny-by-default 的最小权限网关后，面对自适应间接注入，未授权外传成功率显著低于纯模型 guardrail/分类器；代价是任务完成率与延迟。实验：2×2 设计（网关 on/off × 模型护栏 on/off），以论文 11 个案例为种子构造攻击变体，测 ASR、任务成功率、p50/p99 延迟。
- **H2（可验证策略生成减少过度授权）**：用“NL→形式策略 + mutual entailment 检查”的流水线，比直接让 LLM 生成策略或直接让 LLM 当 reference monitor 更少过度授权，且误拦率可控。实验：人工构造 50–100 个任务策略作为 ground truth，测策略偏差、拦截率、误拦率、效用。
- **H3（来源认证降低指令/数据混淆）**：对工具输出/MCP 响应/网页内容做签名或 origin 标签，能降低“把数据当指令”的间接注入成功率；但对使用合法通道的 confused deputy 无效。实验：按攻击类型分层（伪造来源 vs 合法源被滥用），比较签名 on/off 的 ASR。
- **H4（标签粒度决定 IFC 可用性）**：用 chat role（system/user/tool）或 web origin 作为标签粒度，比 token/变量级更可行，但会漏掉跨字段组合泄漏；软标签/QIF 可能减少 label explosion。实验：测泄漏检测 recall、过度阻断率、任务效用；比较 union-label、role-label、QIF 三种方案。
- **H5（异构执行具有超加性）**：沙箱 + capability + IFC 的组合，对自适应攻击的阻断率高于同数量的 ML guard 叠加，因为失败模式不相关（论文 p.9 的论点）。实验：构造独立屏障数 1/2/3 的配置，让自适应攻击者分别攻击，测“绕过所有屏障”的成功率与攻击成本。
- **H6（审批疲劳削弱人的防线）**：当审批提示超过一定数量/频率后，用户批准恶意动作的比例显著上升；这与 p.4 的 Human Weak Link 和 p.17 “不要每次导航都确认”直接相关。实验：用户研究，操纵审批次数（5/20/50 次），测批准率、误批率、任务完成时间。
