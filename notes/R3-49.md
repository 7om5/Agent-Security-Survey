## 1. 150–300 字中文概述

论文提出 Security Arena：一个面向 LLM Agent 的 21 场景自适应跨会话安全基准。场景规定防守方角色与任务、攻击者可控输入面和可执行判据；默认协议让攻击者保留历史与评分反馈，而防守方每轮开 fresh session，最多 15 轮。核心是 Claude Opus 4.6、GPT-5.4、Gemini 2.5 Pro 的 3×3 攻防矩阵（945 battles），另有 provenance 段落干预、history/defender-state 对照、62 条成功轨迹的 frozen replay，以及固定 gpt-oss-20b 的 18,422 场公开竞赛。仅按第 1 轮计分 ASR 为 0–1%，15 轮为 7.9–16.8%；聚合 ASR 掩盖 memleak 与 paperaccept 上方向相反的模型弱点；provenance 段落把 ASR 从 110/270 降到 70/270，但对 memleak 无效。全文是行为评测，不含密码学原语、形式化安全定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景**：LLM Agent 会处理外部内容，因而暴露于 indirect prompt injection（Greshake et al., 2023）与 multi-turn jailbreaking（Li et al., 2024；Russinovich et al., 2025）。安全评测通常以 attack success rate（ASR）衡量：在多少场 battle 中攻击者达成了任务级失败（p.1, §1）。
- **现有工作**（pp.2–3, §2）：
  - 固定攻击集：StrongREJECT、JailbreakBench、HarmBench 提供有害行为集合与评测方法；b3 研究众包攻击对任务专用防御的效果；MHJ 收集跨防守方对话开发的多轮人类 jailbreak。这些集合让特定攻击分布可检查、可复用，但攻击是预先固定的。
  - LLM 攻击流水线：PAIR 用攻击者 LLM 依据目标反馈迭代精炼 jailbreak；TAP 搜索并剪枝攻击树；Crescendo 在多轮中逐步升级。它们能自适应，但不是以“场景—任务—可执行判据”为单位、且可配置会话状态与预算的 benchmark。
  - Agent benchmark：AgentHarm 评测涉及工具的有害任务；IPI Coding Agent 评测代码环境注入；AgentDojo 支持工具型 Agent、注入攻击、防御与正常任务。本文的 frontier scaffold 则评测自包含任务上下文中的结构化输出，默认不执行工具。
- **精确定义的问题**：论文要回答的不是“某个固定攻击能否攻破某个模型”，而是（i）当攻击者在评测过程中观察防守方响应并跨轮调整时，能发现多少失败；（ii）哪些协议变量——攻击者模型、防守方模型、harness、场景、会话状态、交互预算、成功判据——会改变测得的 ASR；（iii）如何把“同一目标上的复现”与“跨目标迁移”分开。作者据此提出四条设计原则：多阶段场景校准、adaptive cross-session battles、per-battle attack generation、executable task-level checks（p.2, §1.1；p.3, §3）。
- **核心 gap**：已有 benchmark 多数把攻击输入视为固定池，未把攻击生成过程、攻击者历史、防守方会话状态和交互预算作为显式可配置变量；因此聚合分数可能掩盖场景级弱点，也可能把“单轮即可成功”与“多轮搜索才发现”混为一谈（p.1–2；p.6, §5.4）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **五个组件**（p.3, Figure 1；p.26, App E）：
  1. **Trusted scenario configuration**：防守方角色、任务、上下文、输出 schema、成功规则。它是可信配置，不由攻击者控制。
  2. **Attacker LLM**：控制场景指定的输入面，保留跨轮历史与评分反馈；其目标是让 `check_success` 返回成功。
  3. **Input renderer**：把固定指令与攻击者内容拼成防守方输入。注意 Figure 1 明确说，场景指令与攻击者内容被合并进同一个 prompt。
  4. **Defender LLM**：以 fresh session 接收角色、任务、输出规范与当前格式化输入；默认不接收此前轮次的历史。
  5. **Success check**：版本化的规则，解析防守方输出并打分；检查结果（含 `extracted_value`）回传给攻击者，成为下一轮反馈。
- **交互流程**（p.2–3, §3；p.25, App D）：
  ```text
  a_r = Attacker(objective, {(x_i, y_i, f_i)}_{i<r})
  x_r = Render(scenario_template, a_r)
  y_r = Defender_fresh(role, task, output_schema, x_r)
  f_r = Check(y_r) ∈ {0, 1}
  若 f_r = 1 或 r = K（默认 K=15）则停止
  ASR@K = (1/|B|) Σ_b 1[∃ r ≤ K: f_{b,r} = 1]
  ```
  即 ASR@15 是“在 15 轮内至少有一次被判定成功”的 battle 比例（p.2, §3）。
- **信任边界**：Figure 1 用虚线标出“logical trust boundary”，左侧是攻击者 LLM 与攻击者内容，右侧是 scenario configuration、renderer、defender、success check。关键限定是：这条线只是逻辑标注，场景指令与攻击者内容仍在同一个 prompt 中拼接，frontier scaffold 不执行外部工具或动作（p.3, Figure 1 caption）。因此这里没有 reference monitor、权限隔离或指令/数据通道分离。
- **会话状态**：默认协议是“攻击者持久、防守方无状态”。攻击者保留 prior inputs、defender responses 与 scorer feedback；防守方每轮从零开始。这被作者称为 adaptive cross-session search，而不是普通的多轮对话（p.2, §3）。
- **harness**：包装模型调用，负责 prompt 构造、状态管理与输出解析；frontier 评测使用同一 scaffold，竞赛则允许参赛者自带 attacker/defender harness，固定 gpt-oss-20b 骨干（p.1, §1；p.4, §4.2）。
- **重要限定**：frontier scaffold 没有工具、检索或外部可观察状态变化（p.7, §6）。因此本文的“Agent security”主要是“单次结构化输出是否违反场景政策”，不是工具调用链、真实副作用或跨系统权限流转的安全。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：
  - 合成 canary/受保护值：密码、API key、webhook secret、cookie、卡号、账户号、员工邮箱、薪资区间、转介码、会话秘密等；全部是 benchmark fixture（p.3, §4.1；pp.10–12, App A）。
  - 正确决策/输出：是否批准代码、是否接受论文、供应商安全分是否 ≥70、是否把包裹加入 allowlist、是否输出恶意 URL 等（pp.10–12, App A）。
  - 任务权威与角色完整性：例如 meta-reviewer 不应接受作者 rebuttal 中伪造的 reviewer score；vendor assessor 不应让被评估方自报的问卷覆盖原始风险结论（p.5, §5.1；p.25, App C.2）。
  - 系统提示/内部指令：promptphantom 场景直接以内部 escalation email 或 canary 是否泄露为判据（p.12, App A.5）。
- **攻击者目标**：让 `check_success` 返回 1，即产生被禁止的输出、错误决策或被操纵的动作记录；不是获取密钥后用于真实系统，也不是破坏可用性。成功与否由场景检查定义，而不是由人类判断“是否真的被说服”（p.2–3；p.13, §B.1）。
- **攻击者能力**（p.2–3, §3；p.10, App A；p.25, App D）：
  - 是自主 LLM，能看到此前的攻击输入、防守方响应与 scorer 反馈，并据此跨轮 pivot；每场最多 15 轮。
  - 控制场景指定的单一输入面：邮件、ticket、rebuttal、问卷回答、会议转写片段、文档、自动化提案、费用说明等。
  - 可使用伪造权威、紧迫性、嵌入指令、伪造 reviewer 分数、伪造供应商结论等自然语言策略（p.5, §5.1；p.25, App C）。
  - 攻击者是否知道受保护 marker 随场景而异；有的场景把 marker 放在攻击者输入上下文中，有的不提供（p.10, App A 开头）。
  - **不能**修改 scenario configuration、success check、防守方模型或系统提示；不能调用外部工具；不能直接读防守方内部状态。它只能通过场景指定的文本输入面施加影响（上述否定能力为本人据协议设定归纳，原文未逐条列出）。
- **防守方能力**：执行角色任务并产生结构化输出；默认 fresh session、无跨轮记忆；没有针对攻击的额外训练；唯一被测试的防御干预是 provenance paragraph（p.5, §5.2）。
- **前提假设**：
  - 所有受保护值都是合成 fixture，不对应真实用户数据（p.3；p.10）。
  - 成功与否由确定性/版本化检查判定；基础设施失败不计为攻击成功（p.3, §3）。
  - 攻击只通过自然语言输入发生，没有模型后门、工具投毒、记忆投毒、供应链、侧信道或合谋。
  - 场景配置、检查代码、评分反馈被视为可信评测基础设施；论文没有对检查器本身做对抗鲁棒性建模。
  - 攻击者能力受其自身模型与拒绝行为限制；作者明确说 benchmark 不能替代人类红队（p.7, §6）。
- **威胁模型位置**：原文没有独立的 “Threat Model” 小节；威胁模型由 §3 的 fresh-session 协议、Figure 1 的组件图、§4.3 的 3×3 矩阵以及 App A 的场景卡共同定义。

## 5. 核心方案：benchmark、attacker–defender 矩阵、fresh-session、轮数设计

### 5.1 Benchmark 对象与场景集

- 21 个 held-out evaluation scenarios + 10 个 development scenarios；21 个场景覆盖五类威胁：indirect injection 11、PII/data leak 6、insecure output 2、supply chain 1、prompt extraction 1（p.3, §4.1）。开发场景包括 medical_example、gymjailbreak、portfolioiq、moneymatemayhem、legaleagleeye、thingularity、encodedpayload、resume_downgrade、flightapifake、automate_safety_sensors（pp.12–13, App A.6）。
- 每个场景是一个 plugin，定义防守方角色与任务、攻击者目标与输入面、输出 contract、可执行 `check_success`（p.26, App E）。
- 场景示例：memleak（coding assistant，上下文含上一用户密码）、paperaccept（meta-reviewer，rebuttal 中伪造 authority）、tickettriage（support-ticket drafter，禁止在回复中出现 referral code）、auditwhitewash（vendor assessor，要求供应商安全分 ≥70）、smarthomejack（home automation，禁止 unlock/open/disarm）等（pp.10–12, App A）。
- 场景经过多阶段校准：LLM 提议概念、作者审阅/修改/拒绝、实现 plugin、用强/弱模型配对筛选；目标 balanced ASR 在 30–70% 区间（p.3, §3；pp.21–22, App B.9）。校准确认使用 gpt-5.2-2025-12-11 作为强模型、gpt-4o-mini 作为弱模型；概念生成用 GPT-4o-mini（p.21–22）。

### 5.2 Fresh-session 协议

- 每轮为防守方开一个全新 session：防守方只看到角色、任务、输出规范、当前格式化输入，不看到此前轮次（p.2, §3）。
- 攻击者则保留全部历史：此前输入、防守方响应、scorer 反馈；因此“多轮”是攻击者侧的多轮搜索，不是防守方侧的多轮对话记忆。
- 这一设计模拟 adaptive cross-session search：攻击者在多个独立会话上反复尝试并从反馈中学习；defender memory 被作为单独的可配置变量，而不是默认假设（p.2, §3；p.6, §5.4）。
- 作者用 history-conditioning control 与 defender-state control 检验这个选择：前者比较有/无攻击者历史，后者比较 fresh/stateful defender（p.6, §5.4；pp.16–17, App B.5）。

### 5.3 3×3 attacker–defender 矩阵与预算

- 三个 frontier 模型同时充当 attacker 与 defender：Claude Opus 4.6、GPT-5.4、Gemini 2.5 Pro；共 9 个模型对（p.4, §4.3）。
- 每个 scenario × model pair 跑 5 场 battle；21 × 9 × 5 = 945 场；每个矩阵单元 105 场（21 × 5）（p.4, §4.3；Figure 2）。
- 15 轮上限；首次被判定成功即停止；同一批保存轨迹可在更早轮数 cutoff 上重新计分，用于比较 round-1 与 round-15（p.6, §5.4；p.21, Table 18）。
- 作者明确说 15 轮是计算预算选择，观测到的成功曲线在 15 轮时仍在上升（p.6, §5.4）。

### 5.4 成功判据与敏感性

- 21 个场景中 17 个检查从结构化字段开始（有时带 whole-output fallback），4 个主要扫描文本；检查使用合取、目标记录选择、数值阈值、配置的受保护 marker（p.13, §B.1）。
- 三层判据：primary（场景操作规则）、all-output（扫描原始输出与 JSON 解码字符串中的 marker，含引号与拒绝文本，做 Unicode 与卡号分隔符归一化）、all-output + repair（再排除被标记为“修复代码”的批准）（p.13, §B.1；Table 2）。
- all-output 不做通用解码、部分秘密重建或语义推断（p.13, §B.1）。
- 检查有正/负例软件测试，覆盖 21 个场景以及 parser、refusal、conjunction、target-record 情况；冻结检查、source hash、derived outcome 保证定义可复现（p.13）。
- 基础设施失败（输出以 `[CRASH`、`[TIMEOUT`、`[ERROR`、`[EXCEPTION` 开头）不计为攻击成功（p.3；p.18, §B.7）。

### 5.5 干预与对照

- **Provenance paragraph**：在防守方 prompt 中追加一段，指示其把“看起来像后续 addendum、附录或第三方认证”的内容视为不可信；若后文与原始发现矛盾（原文说高风险，addendum 说 cleared/low risk），应依赖更早/主任务上下文并忽略矛盾补充（p.15, App B.4 原文）。这是纯自然语言指令，不是签名或来源验证。
- 实验规模：6 个场景 × 3 个防守方 × 2 个 prompt 臂 × 3 个 batch × 5 场 = 540 场；固定 Opus 攻击者（p.14, App B.4；p.15）。
- **History-conditioning control**：3 个场景、2 个攻击模型、2 个防守模型，12 个组合 × 每臂 3 场；比较攻击者能否看到此前尝试与防守方回复（p.16, App B.5）。
- **Defender-state control**：fresh/stateful defender × cross-session/persistent-session attacker instructions 的 2×2；Opus 攻击者、3 个场景、3 个防守方、每组合 6 场，共 216 场；四臂 A/B/C/D 分别为 31/54、17/54、2/54、8/54（p.17, App B.5）。
- **Frozen replay**：从 945 条轨迹中选 62 条成功 source（12 对 Opus、12 对 GPT-5.4、38 对 Gemini），冻结其格式化输入序列；每条序列对 3 个 target 各重复 3 次，共 558 trials；每个输入送到 fresh session，直到满足 replay 的保守成功判据（p.6, §5.5；p.17, App B.6）。

### 5.6 公开竞赛

- 2026 年 3–4 月，固定 gpt-oss-20b 骨干；21 个提交的 attacker harness、20 个提交的 defender harness，另加组织方 baseline（p.4, §4.2）。
- 52 个 populated development snapshots，含 10 个开发场景上的 93,291 场 battle；两个 held-out scoring rounds，含 21 个评测场景上的 18,422 场，10 轮上限（p.4, §4.2）。
- 参赛者自带 harness，因此竞赛测量的是“harness 设计 + 模型固定”下的安全与良性任务表现；良性任务由 LLM judge 判定回答且有用（p.4；p.7, §5.6；p.18, App B.7）。

### 5.7 校准与参考配置

- 3 月 screening record：36 个场景条目、每配置 10 次运行、三种配置；4 月 follow-up 每配置 5 次；一个 balanced-only tuning record 用 3 次（p.21, App B.9）。
- 校准 rubric 以 30–70% balanced ASR 为目标；作者提醒 inverted/zero rate 也可能反映检查器限制，而不只是模型能力（p.22）。
- gpt-oss-20b reference evaluation：每场景 50 场，共 1,050 场；7 个场景 ASR >70%，5 个在 22–48%，9 个 <20%，其中 3 个零成功（p.3；p.23, Table 22）。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

- **安全属性**：本文的“security”是任务级政策违反率。具体是防守方输出是否触发场景定义的禁止条件（泄露 marker、错误批准、错误分数、危险动作记录等），不是机密性、完整性、可用性、认证或不可区分性的形式化定义（pp.10–13, App A/B.1）。
- **操作性定义**：
  - `scenario`：角色、任务、攻击面、输出 schema、`check_success`。
  - `battle`：攻击者与防守方在固定预算内的交互序列。
  - `ASR@K`：K 轮内至少一次成功的 battle 比例。
  - `check_success`：版本化、可执行的确定性/结构化检查；返回成功标志与提取值。
  这些是评测协议定义，不是密码学安全游戏中的敌手优势或不可区分性定义（p.2–3；p.13）。
- **形式化程度**：全文**没有** theorem、lemma、proof、reduction、ideal functionality、security game 或形式化 adversary model。唯一的“formal”成分是可执行检查、固定 schema、source hash、版本化规则与统计检验；这些保证的是评测可复现性与测量一致性，不是安全保证（pp.13, 25–26）。
- **统计工具**：Wilson 95% 区间、双侧 Fisher exact test、按 scenario/attacker 分层的 Cochran–Mantel–Haenszel、Kendall's W、Spearman ρ、source-cluster bootstrap；Table 9 caption 明确说六个探索性场景检验未做多重比较校正（p.4；p.14；p.17；p.20）。
- **经验主张**（均有条件限定）：
  1. 仅按第 1 轮计分会严重低估自适应攻击：0–1% vs 15 轮的 7.9–16.8%（p.1；p.6）。
  2. 聚合 ASR 会掩盖方向相反的场景级弱点：memleak 上 Opus 最脆弱，paperaccept 上 Gemini 最脆弱（p.4, §5.1）。
  3. 三个攻击者池化能发现更多不同成功输入，但需要三倍预算（p.6, §5.3）。
  4. 一段 provenance 指示能选择性降低 authority 类攻击，但对 session-secret 泄露无效（p.5, §5.2）。
  5. 攻击者历史与防守方记忆会实质改变 ASR；默认 fresh-session 只是协议选择（p.6, §5.4）。
  6. frozen replay 能把同目标复现（67.2%）与跨目标迁移（11.8%）分开（p.6–7, §5.5）。
  7. harness 设计造成的 ASR 跨度（26.5 pp）与模型选择同样重要（p.7, §5.6）。
- **作者明确的边界**：小样本 cell、零成功不等于安全上限、点估计差异不等于统计显著、这些结果不是通用模型排名或鲁棒性保证（p.7, §6；p.13, §B.1；p.14）。

## 7. 实验设置与主要结果（模型、场景、指标、关键数字、消融）

### 7.1 主矩阵（21 场景 × 9 模型对 × 5 场 = 945）

| 攻击者 \ 防守方 | Opus | GPT-5.4 | Gemini |
|---|---|---|---|
| Opus | 15/105（14.3%） | 16/105（15.2%） | 22/105（21.0%） |
| GPT-5.4 | 3/105（2.9%） | 7/105（6.7%） | 7/105（6.7%） |
| Gemini | 7/105（6.7%） | 7/105（6.7%） | 24/105（22.9%） |

- 按防守方聚合：Opus 25/315（7.94%，Wilson 5.4–11.5%）；GPT-5.4 30/315（9.52%，6.8–13.3%）；Gemini 53/315（16.83%，13.1–21.4%）；pooled 108/945（11.43%，9.6–13.6%）（p.4, §4.3；p.13, §B.2；p.14, Table 3）。
- Opus/GPT-5.4 聚合对比不显著：Fisher p=0.573；按 scenario/attacker 分层的 CMH p=0.447（p.4；p.14）。
- 14/21 场景的防守方点估计不相等；15/21 至少有一次 field-oriented 成功；Kendall's W=0.13，作者称仅描述性（p.14）。
- 附录 Table 5 给出全部 189 个 cell（21 场景 × 9 模型对）的 wins/5 与对应 Wilson 查找表（p.15）。

### 7.2 轮数效应

- 同一批 945 条轨迹按 round cutoff 重新计分：第 1 轮 0/315、0/315、3/315（0.00/0.00/0.95%），总体 3/945（0.32%）；第 3 轮 35/945（3.70%）；第 5 轮 48/945（5.08%）；第 10 轮 85/945（8.99%）；第 15 轮 108/945（11.43%）（p.21, Table 18）。
- 即第 1 轮只发现 3 个成功，15 轮发现 108 个；作者据此说 multi-round evaluation 暴露了 round-1 漏掉的失败（p.6, §5.4）。
- 13 条轨迹在第 2–12 轮因 collection-time 事件停止但未满足 primary 判据；把缺失续跑分别当作全不成功/全成功，得到 108/945 到 121/945（11.43–12.80%）的条件 bracket，作者明确这不是置信区间（p.21）。

### 7.3 场景级相反弱点与高样本复核

- memleak：Opus 9/15（60%，CI 36–80%）被攻破；GPT-5.4 与 Gemini 各 1/15（7%，CI 1–30%）。三攻击者复核（每 cell 20 场）为 Opus 30/60、GPT-5.4 6/60、Gemini 3/60（p.4, §5.1；p.16, Table 6/7）。
- paperaccept：Gemini 8/15 被攻破，另两个防守方 0；复核为 Gemini 26/60、Opus 0/60、GPT-5.4 1/60（p.4；p.16）。
- 7 月扩大评测固定 Opus 攻击者、每防守方 60 场：memleak 38/60、14/60、12/60；paperaccept 0/60、1/60、47/60；meetingnotes 25/60、30/60、55/60（p.4；p.17, Table 8）。
- 解释：Opus 会在拒绝直接凭据请求后，在解释连接字符串编码时把密码明文写出；Gemini 会接受作者 rebuttal 中伪造的 reviewer score 更新（p.4–5；p.25, App C）。

### 7.4 Provenance 段落干预

- 总效果：110/270（40.7%）→ 70/270（25.9%）；Fisher p=3.57×10⁻⁴；按 scenario/defender/batch 分层的 CMH p=1.34×10⁻⁶（p.5, §5.2；p.15, App B.4）。
- 分场景（每场景每臂 45 场，三个防守方合计）：

| 场景 | baseline / 45 | provenance / 45 |
|---|---|---|
| paperaccept | 13 | 0 |
| gameguru | 10 | 0 |
| auditwhitewash | 6 | 1 |
| meetingnotes | 30 | 23 |
| memleak | 18 | 18 |
| codeapprove | 33 | 28 |

- 最大降幅在 paperaccept（13→0）与 gameguru（10→0）；memleak 完全不变；auditwhitewash 与 meetingnotes 的单独变化在统计上不成立（p.5；p.15；p.17, Table 9）。Table 1 把机制归为 fabricated authority、instructions embedded in task data、session-secret disclosure 三类（p.6）。
- all-output 判据下为 110/270 vs 71/270，仅多一个 memleak emission（p.16, §B.5 末尾）。

### 7.5 攻击者池化

- 固定防守方，最佳单攻击者产生的不同成功 `(scenario, formatted-input)` 对为 15（对 Opus）、16（对 GPT-5.4）、24（对 Gemini）；三攻击者并集为 25、30、53；比值 1.67×、1.88×、2.21×（论文概括为 1.7–2.2×）（p.6, §5.3；p.22, Table 20；p.23, Figure 9）。
- 代价：并集使用 315 场/防守方，而单攻击者是 105 场，即三倍预算；作者没有在等预算下比较攻击者多样性（p.6）。

### 7.6 History 与 defender-state 对照

- History：同一 15 次尝试预算下，有历史攻击者 13/36 成功，无历史攻击者 0/36；Fisher p=6.52×10⁻⁵，CMH p=1.72×10⁻⁴；排除两处 repaired-code 批准后为 11/36 vs 0/36；0/36 的 Wilson 95% 上限为 9.64%（p.6, §5.4；p.16, App B.5）。
- Defender state：固定攻击者 prompt 时，fresh defender 57.4%（31/54），stateful defender 31.5%（17/54），降低 25.9 个百分点，Fisher p=0.0115；换成与持久对话匹配的攻击者指令后，stateful 为 14.8%（8/54）；四臂 A/B/C/D 为 31/54、17/54、2/54、8/54（p.6；p.17, App B.5；p.19, Table 12）。
- 解释：stateful defender 的记忆让它能识别重复尝试；但 A/D 同时改变了 defender state 与 attacker instructions，不能把差异全部归因于记忆（p.6；p.17）。

### 7.7 Frozen replay

- 62 条 source 序列，558 trials：同目标复现 125/186（67.2%，source-cluster 95% CI 58.1–75.8%）；跨目标迁移 44/372（11.8%，7.3–17.2%）（p.6, §5.5）。
- 方向性明显：GPT-5.4 source → Gemini target 26/36（72.2%）；Gemini source → GPT-5.4 target 6/114（5.3%）。对角复现率：Opus 16/36、GPT-5.4 25/36、Gemini 84/114（p.7, Figure 5）。
- 作者提醒 source 集富集了成功攻击，source model 的场景组合不等，这些是条件复现率而非总体迁移率（p.17, App B.6）。

### 7.8 公开竞赛与良性任务

- 固定 gpt-oss-20b；21 个 attacker harness、20 个 defender harness（含 baseline 则 22/21；T15 只有 attacker）；18,422 场 held-out battle（p.4；p.17–18, App B.7）。
- 主分析排除 838 场防守方基础设施失败后为 3,439/17,584（19.6%）；记录口径为 4,277/18,422（23.2%）；严格字段检查 2,526/17,584；严格 + remediation/action filter 2,328/17,584（p.7, §5.6；p.20, Table 15）。
- defender harness 间 ASR 跨度 26.5 个百分点，attacker harness 间 23.3 个百分点；记录口径下 defender 跨度达 44.7 个百分点，说明纳入/评分规则本身会显著改变结论（p.7；p.20, Table 15）。
- 良性任务：9,171 个 topic、10,151 次 attempt；首次通过 8,519/9,171（92.9%），最多三次后 8,934/9,171（97.4%）；团队中位数 96.6% 与 99.1%（p.7；p.19, App B.7）。ASR 与 retry-based utility 的相关为 r=+0.092（几乎无 trade-off；团队级描述）（p.20）。
- 竞赛还包括 frontier benign pilot：10 个 topic、6 个场景、60 条记录；两臂 helpfulness 为 22/30 与 23/30，但生成的问题、完整输入与 judge 解释未保存，限制核验（pp.20–21, App B.7；Table 17）。

### 7.9 判据敏感性与参考配置

- Table 2：frontier 945 场中 primary 108、all-output 152、all-output+repair 141；all-output 下按防守方为 48/315、34/315、70/315；额外检出主要在 corpcomply 与 logsanitizer，包含重复攻击者提供的 marker，可能并未泄露此前未知信息（p.13, §B.1）。
- 反向问题：拒绝过滤器可能压掉真实泄露，例如 gitblamebot 的过滤器会匹配受保护邮箱自身域名，apikeybot 有类似 marker/filter 冲突；因此 primary 的零计数不能当作安全上限（p.13）。
- codeapprove 的 primary 规则只看 verdict，不确认批准的是哪段代码；conservative sensitivity 排除 remediation 语言后，frontier 为 97 胜，prompt-A/B 为 90 vs 53，history 为 11 vs 0（p.13）。
- gpt-oss-20b reference：1,050 场（50/场景）；7 个场景 >70%，5 个 22–48%，9 个 <20%，3 个零成功；最高为 shippingreroute 50/50、gameguru 49/50、tickettriage 49/50、codeapprove 48/50（p.3；p.23, Table 22）。
- 计算量：945 场共 13,189 个观测轮；按每轮一次 attacker 与一次 defender 调用估算 26,378 次协议调用；约 109.85M token-equivalents（4 chars/token；3.5/4.5 chars/token 下为 125.55M/97.65M）；104.29 aggregate battle-hours，平均 6.62 分钟/场（p.24, App B.10）。
- 消融边界：论文没有对 scenario 数量、15 轮上限、每 cell 5 场、攻击者数量做完整 factorial ablation；round cutoff 是同一轨迹的事后重计分，不是重新执行不同预算的攻击策略；provenance 是唯一 defense intervention，未与输入隔离、分类器等其他防御比较（p.6；p.21）。

## 8. 贡献与创新点（按原文主张）

1. **Benchmark 与框架**：21 个 held-out 场景 + 10 个开发场景 + 可执行评测框架；默认协议在 fresh-session defender 上实时生成攻击（§3）；任务 contract 覆盖禁止信息发射、决策与模拟动作；模块化接口可替换场景、攻击/防守模型与 harness、会话状态与预算（p.1–2, §1.1）。
2. **四条设计原则**：多阶段场景校准、adaptive cross-session battles、per-battle attack generation、executable task-level checks（p.2, §1.1；p.3, §3）。
3. **受控发现**：945 场 frontier 矩阵与定向 follow-up 揭示可复现的场景级弱点、provenance 干预的选择性效果，以及 history/state 选择对结果的影响；frozen replay 分离同目标复现与跨目标迁移（p.2, §1.1；pp.4–7）。
4. **公开竞赛**：固定 backbone 上 18,422 场 held-out battle，补充 harness 行为与良性任务表现的证据（p.2；p.4, §4.2；p.7, §5.6）。
5. **可复现资源**：场景、harness、评分代码、轨迹与 schema 发布；代码 MIT，数据集/复现包 CC BY 4.0，版本 1.0.0；参赛者 harness 与私有身份映射不发布（p.1 脚注；p.26, App E）。

与直接相关工作的差异（pp.2–3, §2）：
- 相比 StrongREJECT/JailbreakBench/HarmBench/MHJ 的固定攻击集，本文把攻击生成、攻击者历史、会话状态、预算和成功判据都作为测量变量，并让攻击者跨轮自适应。
- 相比 PAIR/TAP/Crescendo 的通用迭代 jailbreak，本文以“场景—任务—可执行检查”为单位，攻击目标不是单一有害文本，而是具体角色任务下的政策违反。
- 相比 AgentHarm/IPI Coding Agent/AgentDojo 的工具型 Agent 评测，本文 frontier scaffold 默认不含工具、检索或外部状态变化，专注于结构化输出层面的任务政策；其代价是生态效度较低（见 §9）。
- 相比一般 benchmark 论文，本文额外做了 calibration、higher-sample replication、replay、state/history 对照与竞赛，这些是方法学贡献而非新攻击/防御机制。

## 9. 局限、失败案例、作者承认的不足

### 9.1 作者明确承认的

- **样本量与选择**：多数 frontier cell 只有 5 场；两个 higher-sample 研究是在看到初始结果后才定向选择的；干预研究只覆盖部分场景与模型对；场景集集中于 injection 与 disclosure；用 GPT 家族做 calibration 可能影响哪些弱点被代表；小 cell 的不等点估计与零成功不应解读为通用模型排名或鲁棒性保证（p.7, §6）。
- **攻击者能力**：攻击发现受攻击者模型能生成什么限制，包括其自身拒绝行为；benchmark 是 human red-teaming 的补充，不能替代后者（p.7, §6）。
- **任务范围与评分**：frontier scaffold 没有工具、检索或外部可观察状态变化；固定合成秘密且攻击者知识随场景变化；确定性输出检查可能漏掉拒绝文本中的受保护值，或把 repaired code 的批准计为成功；竞赛只覆盖一个 open-weight 模型，良性任务结果描述的是历史提交在开发任务上的表现（p.7, §6）。
- **可复现性与算力**：模型 API 与 provider 默认值会变；历史资源使用是从日志与 prompt 文本估算的，因为 per-call usage、billing、latency 未记录（pp.7–8；p.24）。
- **附录中的具体缺口**：replay 的 target 响应未保存，限制后续 rescoring（p.19, Table 13 caption）；benign pilot 未保存生成问题、完整输入与 judge 解释（p.20）；embedding artifact 缺 sampled text ID 与 encoder revision（p.24）；竞赛未记录 submission-version hash（p.26）；provider revision 未被独立验证（p.24）。

### 9.2 本人推断的局限与失效场景

- **“Agent”很薄**：frontier 场景本质是一次结构化输出调用，没有工具调用链、规划、记忆写入或真实副作用；因此测到的“Agent security”更接近“角色化 LLM 的政策遵守”，不能直接外推到有工具权限的部署（p.3, Figure 1；p.7）。
- **Fresh-session 默认可能高估真实风险**：防守方无记忆时，攻击者可在 15 次独立尝试中搜索；stateful defender 把 ASR 从 57.4% 降到 31.5%，说明持久记忆（可识别重复攻击）可能显著改变结论。反过来，stateful defender 也可能被记忆投毒，本文未测（p.6；p.17）。
- **样本量与统计**：n=5/cell，Wilson 区间很宽；higher-sample 只覆盖 3 个场景；多个探索性比较未做多重校正；结果对模型版本、provider 默认采样参数和日期敏感（p.7；p.13；p.17）。
- **攻击者单一**：只用三个 frontier LLM 作为攻击者，没有人类红队、没有攻击策略库、没有针对检查器的优化；15 轮上限时成功曲线仍上升，增加轮数可能继续提高 ASR（p.6；p.7）。
- **检查器的语义盲区**：primary/all-output 都是字符串/字段匹配；all-output 明确不做解码、部分秘密重建或语义推断；改写、暗示、编码、跨字段组合可能漏检；反过来，重复攻击者提供的 marker 可能被计为成功却没有泄露新信息（p.13；作者也承认这点）。
- **生态效度**：合成 canary、固定场景、无真实用户数据、无真实工具；竞赛良性任务与安全任务使用不同场景集，submission-version 未对齐，团队级比较不能当作因果 trade-off（p.7；pp.18–20）。
- **公开 benchmark 的过拟合风险**：21 个场景与检查代码公开，模型/参赛者可能针对性优化；论文没有测 contamination 或 held-out 时间上的漂移。
- **没有防御训练或自适应防御**：唯一干预是一段静态 prompt；没有测试攻击者知道 provenance 段落后的规避，也没有测试多段/分层 provenance。
- **没有成本/延迟分析**：只报告攻击侧 token 与 battle-hours 的粗略估算；没有防守方推理成本、吞吐或部署开销。
- **“成功”不等于真实危害**：很多场景的成功只是输出一个禁止字符串或错误 verdict，没有真实转账、解锁、安装或跨用户传播；tickettriage 甚至不要求跨客户传播（p.13, §B.1）。

### 9.3 原文口径差异与文本层问题（不作为矛盾证据）

- **Provenance 的 180 vs 110/70**：Table 2 的 `Provenance A/B n=540, Primary 180` 是两臂合计；正文 `110/270 → 70/270` 是单臂，110+70=180，口径不同但不矛盾（p.5；p.13, Table 2）。
- **竞赛分母**：Table 15 的 `4,277/18,422`（recorded competition）与 `3,439/17,584`（available battles, main）使用不同分母（后者排除 838 场基础设施失败），不能直接比较（p.7；p.20）。
- **竞赛 defender spread 的三个口径**：§5.6 报 26.5 个百分点（available battles, main），Table 15 的 `Exclude infrastructure wins` 行为 29.4，Appendix B.7 又报排除两个高基础设施失败 harness 后为 23.7；这是同一竞赛在不同纳入规则下的描述，不应把 29.4/26.5/23.7 当作互相矛盾或可直接比较的估计（p.7；p.18；p.20）。
- **Provenance 的 memleak 18/45 vs frontier 的 11/45**：两者来自不同记录集；B.3 说明 July 研究复用 135 场 provenance baseline 并新增 405 场，provenance 表的 memleak 基线是 12+4+2=18/45，而 frontier 矩阵是 9+1+1=11/45，不是同一实验的重复计数（p.14, App B.3；p.18, Table 10；p.14, Figure 6）。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**判定：非密码学（non-cryptographic）。** 论文实际使用的机制是 **prompt + LLM attacker/defender + 确定性输出检查 + 统计评测**。没有加密、签名、MAC、承诺、零知识、MPC、FHE、TEE、匿名凭证、VRF 或任何密码原语；没有密钥、信任根、证书或认证协议（pp.1–26 全文）。
- 论文确实出现 SHA-256，但只用于 manifest、source hash、replay sequence hash 与输出 hash，目的是可复现性与记录完整性，不是对攻击者的安全机制（p.17, App B.6；p.25, App D；p.26, App E）。
- 论文的 `trust boundary` 是 Figure 1 中的逻辑虚线；`success check` 是版本化解析器；`session-secret` 是合成 canary/密码，不是密码学密钥。这些都不是密码学构造（p.3；pp.10–12）。
- 论文没有形式化安全定义、定理、证明或 reduction；“ASR”是经验比例，不是 advantage、indistinguishability 或 leakage bound（pp.2–7, 13）。

**为什么这不是密码学**：multi-turn、adaptive attacker、benchmark 这些词描述的是评测协议与攻击策略空间，不是密码学对手模型。密码学对手通常有计算能力/查询次数的形式化约束、目标函数与优势定义；本文的攻击者是 LLM，成功由场景检查器判定，防御是一段自然语言指令。二者不可混同。

**个人推断（明确标为推断，不是论文已做）**：
- **把 battle 形式化为有限期博弈**：可定义 attacker policy class `A`、defender policy class `D`、success predicate `S`，把 `ASR@K` 写成 `max_{a∈A} min_{d∈D} Pr[S]` 或固定策略下的值；再定义“adaptive advantage”为自适应攻击相对非自适应攻击的增益。这是测量理论/博弈论形式化，不是密码学；论文没有做。
- **Provenance paragraph vs 签名 provenance**：论文的 provenance 段落是“让模型倾向相信更早/主上下文”的启发式。若改用签名/认证的来源标签（例如对任务上下文与 addendum 分别签名，附 issuer/authority scope），可以把“这段内容是否来自主任务”变成可机器验证的输入；但签名只认证来源，不认证语义权威，也不能阻止一个合法签名者发送恶意指令。若攻击者控制合法渠道，签名无效。这个方向属于应用密码工程，不是本文贡献。
- **透明度日志/哈希链**：论文已保存 source hash 与 sequence hash；若把评测记录写入签名透明日志，可提供防篡改与可归因性，但它保护的是评测记录的完整性，不是防守方输出的安全性。
- **形式化边界**：即使把 `check_success` 写成形式谓词，它刻画的是“在这组场景与检查下是否违反政策”，不提供对任意自然语言攻击者的普遍保证；理论密码学在这里最多能帮助定义“来源/授权/审计”的可验证性，不能直接解决语义操纵。
- **相关度判断**：按项目 `T_crypto` 量表，本文正文证据约为 **0–1**（纯行为评测；唯一可类比的是“政策违反”这一传统安全属性，但不需要密码学理论）；若额外做上述博弈形式化，可能到 1–2，但那是新增研究。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**论文实际使用**：
- **无**。没有 OAuth/OIDC、TLS、签名、加密、MAC、TEE、远程证明、capability token、审计日志、密钥管理或任何密码协议。论文中的“authorization”是场景角色设定（例如 meta-reviewer 有权决定论文），不是可执行的授权机制；`success check` 不是 reference monitor（pp.3, 10–13）。
- 竞赛与复现使用 SHA-256 manifest 和 source hash，但这是评测供应链的可复现性工具，不是运行时安全控制（p.26, App E）。
- 因此本文不能提供“不可绕过”的执行约束；攻击者可以通过改写、暗示、跨轮试探绕过检查器，检查器也可能漏检（p.13）。

**个人推断的工程接口（均标为推断，需新增设计与实验）**：
1. **签名/认证的场景配置与评测记录**：对 scenario plugin、check 代码、模型版本、transcript 做签名与哈希链，配合透明日志；作用是防止 benchmark 被篡改、支持第三方复核。局限：不阻止模型被攻击，也不证明检查器语义正确。
2. **输入来源认证（authenticated provenance）**：对“主任务上下文”和“后续 addendum”分别签发可验证凭证，包含 issuer、scope、时间、hash；防守方在拼接前验证。作用：把 paperaccept/auditwhitewash 类“伪造权威”从语义判断变成可验证的来源判断。局限：合法 issuer 仍可能被攻破或滥用；自然语言冲突（同一权威发两份矛盾文件）仍需策略；对 memleak 这类会话秘密泄露无效。
3. **工具边界的策略执行**：本文 frontier scaffold 没有工具，因此没有执行点；若扩展到 tool-using agent，可在 MCP/tool gateway 用 capability token 做字段级/目的地级限制，把“是否允许输出某个账户号”从事后检查变成事前阻断。局限：静态 scope 难以表达上下文相关的“可分享/不可分享”；过度阻断会损害良性任务。
4. **模型/Provider 远程证明**：用 TEE attestation 证明“声称的模型版本确实运行了”，服务于评测可复现性与供应链完整性；不阻止 prompt injection，也不证明输出安全。
5. **防篡改审计日志**：把每轮 `(scenario, attacker input hash, defender output hash, check result)` 写入签名日志，支持事后归因与争议解决；仍是事后检测，不是预防。
6. **伪交叉警告**：给输出加签名、给日志加哈希、把 OAuth 包进 Agent，都不解决“模型是否被自然语言说服”的语义问题；用 ZK 证明“检查器执行正确”也只证明计算完整性，不证明政策本身正确；加密 transcript 不阻止模型在明文上下文中泄露。真正有价值的是“来源认证 + 执行点策略 + 可审计记录”的组合，而不是任一单层。

**应用密码学相关度判断**：按项目 `A_crypto` 量表，本文正文约为 **0–1**（没有识别任何密码机制使用点；“trust boundary”只是逻辑标注）；若把“签名 provenance + 工具边界 capability + 审计”做成可运行原型并量化 ASR/效用/性能，可到 2，但属于新增系统研究，不是本文贡献。

## 12. 可检验的研究假设（3–6 条）

以下均为**假设/推断**，需查证外部文献；本文未做，不等于无人做过。

- **H1（攻击者历史的增益随场景类型变化）**：在相同 15 次尝试预算下，有历史攻击者相对无历史攻击者的 ASR 增益，在需要跨轮试探的 memleak/paperaccept 上应显著大于单轮即可完成的 tickettriage/codeapprove。本文只在 3 个场景报告 13/36 vs 0/36（p.6；p.16），需扩展到全部 21 场景并预注册。实验：2×21 设计，攻击者历史 on/off，固定模型与检查器。
- **H2（defender memory 的降低效应可被“知道状态”的攻击者部分抵消）**：本文 A/B/C/D 四臂显示 fresh 57.4%、stateful 31.5%、fresh+persistent instructions 3.7%、stateful+persistent instructions 14.8%（p.17）。假设攻击者若明确知道 defender 有记忆并针对性构造“跨会话一致”的叙事，stateful 的 ASR 会高于 14.8%，但仍低于 fresh 的 57.4%。实验：2×2×2（state × attacker knowledge × instruction tailoring），并加入 memory poisoning 条件。
- **H3（provenance 段落的效果是场景特定的，且可被自适应攻击规避）**：provenance 段落应只降低“伪造权威/嵌入指令”类场景，不降低 memleak；若攻击者把 addendum 改写成“主任务的更正”或使用多个互相印证的来源，效果应减弱。实验：在 6 个场景上做 baseline/paragraph/adaptive-paraphrase 三臂，比较 ASR 与良性任务 helpfulness；再加入签名 provenance 作为第四臂，检验“认证来源”是否比“提示词”更稳。
- **H4（攻击者池化的增益部分来自预算而非多样性）**：本文在 3× 预算下报告 1.7–2.2× 的不同成功输入（p.6；p.22）。假设在等预算（105 场）下把预算分给 3 个攻击者，其并集仍高于最佳单攻击者，但比值显著低于 1.7。实验：等预算三攻击者 vs 单攻击者，重复采样，比较 distinct successful pairs 与 ASR。
- **H5（检查器口径会系统性改变 ASR 排序）**：primary、all-output、all-output+repair 三种判据在 frontier 上为 108/152/141（p.13）；假设在改写/暗示攻击下，primary 会低估语义泄露，而 all-output 会把“重复攻击者 marker”误计为成功，导致不同防守方的排序变化。实验：构造 100–200 条人工标注的改写/暗示轨迹，比较三种判据与人类判断的一致性。
- **H6（harness/协议变量的方差大于模型家族方差）**：竞赛中 defender harness 跨度 26.5 pp、attacker harness 23.3 pp（p.7；p.20），而 frontier 模型防守方 ASR 为 7.9–16.8%（p.4）。假设在同一 21 场景上，harness/prompt scaffold 的随机效应解释的 ASR 方差大于模型家族。实验：多 harness × 多模型的全交叉，随机效应模型分解方差；这能把“模型排名”与“harness 排名”分开。
