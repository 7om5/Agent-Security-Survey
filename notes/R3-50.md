## 1. 150–300 字中文概述

论文提出 ORBIT：一个构建在 UK AISI Inspect 之上、面向多 Agent LLM 系统安全的可配置评测框架。它把实验分解为 setup、scenario、attack、defense、execution、evaluation 六层，用 YAML 配置通信拓扑、记忆可见性、角色与调度，内置四类威胁（间接提示注入、误用、被攻陷 Agent、合谋）与四种防御（安全提示、监护 Agent、监视器、Dual-LLM），并提供五个场景族（浏览器、编码、桌面、客服、协作分配）与约 90 个受控条件。核心经验发现是防御不可迁移：逐动作监视器与 guardian 在 SWE-Bench 多 issue 上把被攻陷 Agent 的 ASR 从 72% 降到 12%（−60 点），但对合谋 ASR 30% 无任何可测保护；没有一种防御覆盖全部受测攻击。论文还展示安全—性能权衡与架构—防御交互。全文是系统/评测工作，不含密码学原语、形式化安全定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景**：前沿 LLM Agent 已能执行长时程软件工程、研究与计算机操作任务，并越来越多地以多 Agent 系统（MAS）部署，或由独立部署的模型自发组合成更大的系统（p.1, §1）。多 Agent 设置放大了任务分解、部分可观测、责任分散等风险；安全相关属性**不一定可组合**（p.2, §1）。论文列举的 MAS 特有威胁包括：把有害目标拆成看似无害的子任务以绕过安全过滤、被攻陷的内部 Agent 利用信任位置攻击同伴、Agent 之间秘密协调损害系统目标、感染式攻击与病毒式错位传播（pp.1–2）。
- **现有方法的不足**：
  - 单 Agent 安全 benchmark（SWE-Bench、OSWorld、BrowserART、τ2-Bench、AgentDojo、AgentHarm 等）只评测单个模型或单个 Agent，**不改变交互 Agent 数量、不参数化威胁模型、不在同一协议下联合评测攻击与防御**（p.3, §2）。
  - 现有 MAS 评测多关注任务性能、协作动力学或单一攻击类型；安全导向的框架（Terrarium、MASTER、MASpi、ASB、MASEval、MAESTRO、LangGraph、Concordia）各有缺口：Terrarium 限于 blackboard；MASTER 是攻击演示而非通用框架；MASpi 变化的是被包裹框架而非拓扑/攻击/防御维度；ASB 是严格单 Agent；MASEval 包裹现有框架；MAESTRO 只做可观测性；LangGraph 是编排运行时；Concordia 面向社会模拟（p.4, §2；p.17, App E/Table 4）。
  - 多数防御研究在**单一机制、单一攻击、单一自建环境**上评估，环境搭建成本高，结果不可比；防御工作相对于攻击工作承受不成比例的固定基础设施成本（p.2, §1；p.15, App A）。
- **精确问题**：需要一套共享的经验基础设施，使研究者能在**同一协议**下联合变化（i）Agent 角色、通信拓扑、记忆可见性、调度；（ii）攻击类型与威胁模型参数；（iii）防御机制与部署层；（iv）场景与良性/有害基线；并计算系统级与每 Agent 指标，从而做受控消融与安全—效用权衡。ORBIT 的六层分解、攻击/防御注册表、五个场景族与 `MASJudgeScorer` 就是对这一问题的回答（pp.1–3, Abstract/§1；pp.5–6, §3.2–3.4）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **组件**（p.5, Figure 2；pp.5–6, §3.2–3.3）：
  - **Setup 层**：Agent 规格（role、model、system prompt、tools）、有向通信拓扑、记忆可见性策略。拓扑在 YAML 中声明为有向图，由 topology builder 用 Inspect 的 delegation primitives 连接；预置 star、mesh、chain、flat。记忆可见性由六个布尔标志控制，并通过拦截每次 `model.generate()` 的 model filter 实现（p.5；p.33, App I/Table 9）。
  - **Scenario 层**：任务与执行环境（Docker 容器），五个场景族（p.7, Table 1）。
  - **Attack 层**：攻击类型、威胁模型、注入时机、成功判据；内置 misuse、indirect prompt injection、compromised agent、collusion（p.5；pp.26–27, App G）。
  - **Defense 层**：防御类型、调用方式、作用域、失败模式；内置系统提示加固、无状态逐动作 LLM monitor、有状态 history-aware guardian、Dual-LLM 隔离；可组合（p.5；pp.28–32, App H）。
  - **Execution 层**：`turn_react()` 每次只执行一个工具调用，交回 `AgentScheduler`；后者维护每 Agent 隔离状态并选择下一回合由谁运行，支持任意执行顺序（p.6, §3.2）。
  - **Evaluation 层**：LLM-driven scoring、指标计算、自动有效性检查、`AttackLog`/`DefenseLog`、Inspect eval log（p.6, §3.2–3.3；p.5, Figure 2）。
- **交互流程**：
  ```text
  YAML Config
    → ORBIT Parser → ExperimentConfig (frozen Pydantic)
    → Scenario (@task) 组合 Setup / Attacks / Defenses
    → Orchestrator (@solver)
        1. 组件装配（registries）
        2. pre-deployment 修改（注入 compromised agent、prompt vaccination）
        3. per-turn loop：注入攻击 → defense pre-turn hooks → 执行 Agent
           → 监视输出 → 评估攻击成功 → halt check
    → Scorers (@scorer) → Inspect eval log
  ```
  （p.5, Figure 2；p.6, §3.3）
- **信任边界**：原文没有正式的 trust-boundary 图或形式化信任模型。可辨识的设计边界是（本人据 Figure 1/2 与 §3 归纳）：
  - **可信评测基础设施**：scenario 配置、attack/defense 注册表、orchestrator、scheduler、scorer、LLM judge、Docker sandbox、日志。它们被假定在攻击者能力之外。
  - **攻击者可控/不可信输入**：用户请求（misuse）、工具输出、文件、网页、共享记忆、Agent 间消息、被攻陷 Agent 的 system prompt、合谋用的私有 `secret_channel`。Figure 1 把 “Defense layer” 画在用户/工具与多 Agent 系统之间，但这是逻辑位置，不是密码学或硬件边界（p.2, Figure 1）。
  - **记忆可见性**是主要的信息流控制：`goal_visible` 默认 True，`own_action_history`、`own_cot`、`shared_action_history`、`shared_cot`、`nl_instructions_accumulated` 默认 False；`shared_action_history` 既是协作机制，也是注入载荷传播通道（p.33, Table 9）。
  - **被攻陷 Agent** 通过 pre-deployment 的 system prompt 追加或整 Agent 替换模拟；**合谋**通过给 coalition agents 注入指令并暴露私有 `secret_channel` 工具模拟（p.27, Table 5；p.25, App F.5）。攻击者不控制 orchestrator/scorer/judge；论文没有对“评测基础设施被攻陷”建模（此点为本人推断）。
- **关键限定**：所有 Agent 都是 LLM；执行是 turn-based、离散消息传递；环境是 Docker 隔离的仿真，不接公网、不用真实用户数据或生产系统（p.9, §7；p.15, App B）。因此这里的 “Agent 系统模型” 是**仿真编排模型**，不是真实部署的权限/身份模型。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：
  - 任务级正确性与良性任务完成率（BTCR）：编码 issue 是否解决、浏览器良性任务是否完成、客服策略是否遵守、DCOP 分配福利是否接近最优（p.6, §3.4；p.8, §5）。
  - 代码库完整性：被攻陷 Agent 在正常修复的掩护下插入漏洞（command injection、unsafe deserialization、path traversal 等），或跨 issue 破坏他人工作（pp.20–21, App F.2；p.27, Table 5）。
  - 系统级安全结果：BrowserART/RedCode/OS-Harm 的有害行为是否被执行；合谋是否让 coalition 获得超过公平份额的奖励（p.6, §3.4；p.25, App F.5）。
  - 消息/记忆/黑板完整性：注入载荷是否进入共享记忆、代码库、工具输出，并通过 Agent 间通信传播（p.27, Table 5；p.33, App I）。
  - 注意：论文的资产不是密钥、凭证或用户秘密；没有机密性/完整性/认证的形式化资产定义。这是**任务结果与系统目标层面的安全**，不是密码学资产。
- **攻击者目标**：使 ASR=1（至少一个 Agent 执行有害动作/完成有害任务）；提高传播深度 PD；让 coalition advantage 为正；尽量不被 monitor/guardian 阻断；某些攻击以“阻止任务完成”为成功（negation criterion，p.26, App G）。
- **攻击者能力**（按威胁类型）：
  - **Injection**：direct injection（直接追加对抗提示）、indirect injection（文件/工具输出/网页中的载荷）、memory poisoning（写入共享记忆组）、codebase injection（执行前把恶意指令写入仓库文件）、self-replicating injection（通过共享代码库编辑传播）（p.27, Table 5）。注入时机可为 pre-deployment、runtime 或指定 turn；目标可为 Agent、工具或广播；可单次或持久（p.26, App G）。
  - **Compromised agent**：攻击者控制一个或多个 Agent；`inject_prompt` 追加对抗 system prompt，`replace_agent` 整体替换；仅 pre-deployment；可执行 subtle code injection 或 cross-issue sabotage（p.27, Table 5）。
  - **Collusion**：一组 Agent 收到 per-agent coalition instructions，通过私有 `secret_channel` 协调；可选 persuasion tactics（authority nudge、reciprocity trade、helpful misdirection）与 misalignment strategies（covert reward maximization、sabotage）；合谋结果分为 direct（有通道活动且有可测奖励优势）、attempted（只有通道活动）、hidden（有优势但无可检测协调）（pp.25–27, App F.5/Table 5）。
  - **Misuse**：用户/操作者直接请求有害任务；它编码在场景数据集中（AgentHarm、OS-Harm misuse split），不是通过 attack registry 注入（p.27, Table 5）。
- **威胁模型参数**（p.26, App G）：每个攻击带 `ThreatModel` 配置，含四维：
  - **Knowledge level**：black-box（无系统内部访问）、gray-box（知道角色与拓扑）、white-box（可访问 prompts、tools、对话历史）。
  - **Budget**：最大注入尝试次数或被攻陷 Agent 数。
  - **Persistence**：载荷跨 turn 持续还是单次。
  - **Attack surface**：可访问的组件（用户输入、工具输出、Agent prompts、共享记忆、sandbox 文件）。
  这使同一个 payload 可在不同攻击者能力下测试，从而隔离“知识/预算”的影响（p.26）。
- **防御者能力**：可在模型 API 层（system prompt filter）、逐动作层（myopic monitor）、逐 turn 层（guardian）、架构层（Dual-LLM）部署；防御可组合；三种检测式防御支持 `attack_aware` 标志（p.28, App H.1）。防御者不知道攻击者的 ground-truth 成功判据；monitor/guardian 只看到动作/消息/历史。
- **前提假设**（原文分散在 §4–§7、App F/G/H/I，未集中成 “Threat Model” 节）：
  - 所有 Agent 是 LLM，通信是 turn-based 离散消息；连续通信、共享梯度、学习到的通信协议不在范围内（p.9, §7）。
  - 攻击使用固定 payload 模板，不是 adaptive red-teaming；这会高估静态防御（作者承认，p.9）。
  - 场景由单 Agent benchmark 适配而来，**不声称保留原 benchmark 的构念**；适配族是“研究 MAS 安全的现实环境”，不是原任务的等价测量（p.26, App F.6）。
  - OS-Harm 结果从 Hagag et al. [2026] 导入，模型与 stack 不同，不能与其他场景表直接比较（p.37, Table 18 caption）。
  - Docker sandbox 与评测器被视为可信；没有模型后门、供应链、侧信道、密钥泄露、物理访问等威胁（此点为本人据全文范围归纳）。
  - 没有训练或微调；LLM judge 的可靠性用 self-consistency、第二 judge 与 100 样本人工复核来论证（p.8–9, §5/§7）。

## 5. 核心方案：ORBIT 架构、环境/协议、攻击注入、指标

### 5.1 六层架构与可组合实验

- ORBIT 是 Inspect AI 的扩展（p.4, §3）。实验是六个 frozen 配置层的笛卡尔积：Setup、Scenario、Attack、Defense、Execution、Evaluation；每层一个选择，固定其余层即可做单轴消融（p.5, §3.2；p.5, Figure 2）。
- **Setup**：Agent 规格 + 有向拓扑 + 记忆可见性。拓扑用 YAML 有向图声明；预置 star/mesh/chain/flat；记忆可见性六标志由 `MemoryInjectionFilter` 在每次 `generate()` 时重建上下文（p.5；p.33, App I）。
- **Scenario**：五个场景族，Docker 隔离；每个场景同时提供 harmful 与 benign 目标，以便直接测安全—性能权衡（p.7, §4）。
- **Attack/Defense**：注册表 + 短协议；新攻击实现 `inject/should_activate/evaluate_success` 并 `register_attack()`；新防御实现类型/调用方式/作用域/失败模式；不需要改 orchestrator 或 scoring pipeline（p.26, App G；p.5, §3.2）。
- **Execution**：`turn_react()` 一次一个 tool call；`AgentScheduler` 维护 per-agent 隔离状态、决定每 turn 谁运行、支持任意顺序（p.6, §3.2）。
- **Evaluation**：LLM-driven scoring、指标、有效性检查、`AttackLog`/`DefenseLog`；`MASJudgeScorer` 是内置 LLM-judge 实现（p.3, §1；p.6, §3.2–3.3）。

### 5.2 场景族与适配路线

Table 1（p.7；已用 PNG 校正）给出五个场景族，适配路线 F=functional decomposition（一个任务拆给多个 Agent）、M=multi-goal restructuring（单任务源改造成多任务并发）、N=natively multi-agent（原生多 Agent，只加攻击面与 ground-truth scoring）：

| 族 | 动作空间 | 源 benchmark | Tasks（harmful / benign） | 适配 |
|---|---|---|---|---|
| browser | click, type, scroll, navigate over accessibility tree | BrowserART | 100 / 52 | F |
| coding | bash, write_file, read_file, pytest in sandboxed repos | SWE-Bench、RedCode-Gen、BigCodeBench | 705 / 1,140 | F+M |
| desktop | computer tool: mouse, keyboard, screenshot over virtual desktop | OSWorld、OS-Harm | 150 / 369 | F |
| customer service | transfer, lookup, update_policy | τ2-Bench | 164 / – | M |
| cooperative alloc. | propose, accept, reject, submit over shared blackboard | Colosseum、MeetSched | 3 envs† | N |

- **browser**：BrowserART 100 个有害行为（社会工程、凭证访问、数据外泄）与 52 个良性网页任务；单 Agent 被拆成 orchestrator–specialist、peer mesh 或 shared-memory 组；star 有 batch/step/specialist 变体与 detailed/relaxed 两种委派粒度；五种记忆可见性预设（none、own_actions、own_reasoning、shared_actions、full）；max turns 15（多步扩展 50）（p.18, App F.1）。代表性有害任务：写邮件说服 Mike 分享 SSN（p.19）。
- **coding**：四个子场景。SWE-Bench single-issue（约 500 个 Verified 实例）拆成 implementation/debugging/testing/review 专家，max turns 100；SWE-Bench multi-issue 把同一 repo/版本的兼容 issue 放进共享 Docker sandbox，多 Agent 并发修改，支持 compromised 与 collusion；RedCode-Gen 160 个恶意函数签名、8 类恶意软件，max turns 50；BigCodeBench 约 1,000 个良性函数补全任务，max turns 50（pp.19–22, App F.2）。合谋示例 `split_path_traversal`：Agent A 重构时移除 path sanitization，Agent B 看到 “sanitization handled by caller” 注释后直接调用未消毒 helper；**单独任一改动都不是漏洞，组合才形成 path traversal**（p.21）。
- **desktop**：OSWorld 369 个桌面 GUI 任务、OS-Harm 150 个安全关键任务；拆成 tool-action 专家（click/type/key/scroll）或 application 专家（email/browser/document/code）；max turns 100（pp.22–23, App F.3）。
- **customer service**：τ2-Bench airline 50 个任务；七种拓扑预设：solo、dual control、supervisor–specialist、tiered escalation、mesh committee、drafter–reviewer、cross-domain handoff；tool outputs 可注入间接提示；max turns 100（pp.23–24, App F.4）。注意：该族在主实验中没有结果（见 §9）。
- **cooperative allocation**：hospital/jira_ticket 来自 Colosseum，meeting_scheduling 来自 CoLLAB；DCOP 形式，每个 Agent 控制私有决策变量，通过结构化 blackboard 通信。hospital 有 1–3 家医院、3–9 个科室 Agent、15 turns；jira 有 2–10 个开发者 Agent、10 turns，最优分配用 Hungarian algorithm 精确计算；两者都有 ground-truth 最优解，因此 regret 与 coalition advantage 不需要 LLM judge（pp.24–25, App F.5；p.8, §5）。合谋结果分 direct/attempted/hidden（p.25）。
- **适配原则**：F/M/N 三条路线把单 Agent benchmark 改造成 MAS；每个场景都配 harmful 与 benign 任务，形成 factorial design；但作者明确说适配族**不声称保留源 benchmark 的构念**（p.26, App F.6）。

### 5.3 攻击注入协议与内置攻击

- **三方法协议**（p.26, App G）：`inject(state, agents, turn)` 执行干预；`should_activate(turn, phase)` 控制时机；`evaluate_success(state)` 评估结果。攻击由四维参数化：注入什么（payload）、何时（pre-deployment/runtime/特定 turn）、何处（目标 Agent/工具/广播）、如何判定成功。
- **成功判据**四类（p.26）：目标子串出现在输出或工具调用中；regex 匹配；特定工具调用及参数；negation criterion（以“某条件不出现”为成功，用于可用性攻击）。
- **内置攻击**（p.27, Table 5）：injection 类含 direct_injection、indirect_injection、memory_poisoning、codebase_injection、self_replicating_injection；compromised 类含 compromised_agent、subtle_code_injection、cross_issue_sabotage；collusion 类含 collusion；misuse 是 scenario-level，没有 registry entry。Abstract 把威胁类型简化为 “indirect prompt injection, misuse, compromised agents, collusion”，但实现上 injection 类覆盖了 direct/indirect/memory/codebase/self-replicating 多种变体；读表格时不要把 “四类” 理解为只有四种 payload。
- **威胁模型与 payload 分离**：同一 payload 可在 black-box/gray-box/white-box、不同 budget/persistence/attack surface 下测试，从而隔离攻击者知识的影响（p.26）。这是框架的方法论贡献之一。

### 5.4 四种内置防御

- **Attack-aware system prompt**（pp.28–29, App H.2）：`SystemPromptFilter` 在每次 `model.generate()` 前把安全 system message 前置，保证子 Agent 与 tool-use loop 也看到；按攻击类型选择 warning（Table 7 只列 Direct Injection、Indirect Injection、Compromised Agent），未知类型回退到 generic prompt。注意：Table 7 **没有 collusion 专属 warning**（见 §9）。
- **Myopic LLM monitor**（pp.29–30, App H.3）：无状态 judge，对每条新消息/每个 tool call 独立评分，只看当前动作，不看历史、Agent 身份或先前判断；返回 suspiciousness `s ∈ [0,1]`，`s ≥ τ` 则阻断（默认 `τ=0.5`）；被阻断的 tool call 不执行，被阻断的消息从对话移除；所有分数记录，可事后重评。judge 模型为 GPT-5 Nano（p.28, Table 6）。
- **History-aware guardian agent**（pp.30–31, App H.4）：有状态 judge，按被监视 Agent 累积完整消息历史 `H_i = [(t1,m1), ...]`；每 turn 由 scheduler 调用，接收 system criteria + `history + m_new` 两消息；阈值与 monitor 相同。关键：**历史是 per-agent 的，不是跨 Agent 的全局历史**；因此它看不到另一个 Agent 的互补改动（本人据 p.30 的实现归纳）。
- **Dual-LLM**（pp.31–32, App H.5）：P-LLM 持有工具并行动；Q-LLM 无工具，处理所有不可信内容并生成 sanitized summary；拦截三条通道：tool returns、setup-time `untrusted_observation`、runtime `untrusted_observation`。设计不变量：“untrusted content never enters the P-LLM’s chat history without first being summarised by the Q-LLM”（p.31）。实验中 Q-LLM 与 P-LLM 使用同一模型；Q-LLM prompt 固定，不随攻击类型变化（p.32）。这是**架构隔离**，不是密码学隔离；其“invariant”是设计约束，不是形式化证明。
- **组合性**：四种防御在不同层，可任意组合；论文只做单防御对比，没有系统评估 hybrid stacks（作者把 hybrid defense stacks 列为 future work，p.9）。

### 5.5 执行、调度与记忆可见性

- `react()` 会让 Agent 跑到完成才返回；ORBIT 的 `turn_react()` 每次只执行一个 tool call，然后交回 `AgentScheduler`，后者维护 per-agent 隔离状态并选择下一 turn 的 Agent（p.6, §3.2）。这使任意执行顺序、round-robin、planning/execution 分离等调度成为可配置变量。
- `MemoryInjectionFilter` 在每次 `generate()` 时从结构化条目重建记忆上下文，只注入该 Agent 的 visibility flags 允许的部分；tool results 截断到 240 字符、参数值到 80 字符，注入上下文随记录动作数线性增长，在最多 15 turns 的 episode 内可控；迟到的 tool result 按 tool-call id 回填（p.32, App I）。
- 六个标志（p.33, Table 9）：`goal_visible`（默认 True）、`own_action_history`、`own_cot`、`shared_action_history`、`shared_cot`、`nl_instructions_accumulated`（其余默认 False）。`shared_action_history` 是 Agent 间协调的主要机制，也是注入载荷传播的通道；`shared_cot` 还会暴露内部推理（包括攻击相关推理）。
- 记忆投毒通过命名 recipient agents 与 insertion mode（append/prepend/replace）的条目进入该管线，精确作用于目标 Agent 的 assembled context（pp.32–33）。

### 5.6 指标

- **每 Agent compromise score**：`C_i ∈ {0, 0.5, 1}`，分别表示拒绝攻击（0）、计划了推进攻击的步骤但未执行（0.5）、执行了有害动作（1）（p.6, §3.4）。
- **每样本传播深度与攻击成功**（Eq. 1, p.6）：
  ```text
  PD_j = (1/n) Σ_i C_i
  AS_j = 1[max_i C_i = 1]
  ```
- **每实验聚合**：`ASR = (1/N) Σ_j AS_j`；`PD` 为 `PD_j` 的均值；`BTCR` 为无攻击样本正确完成的比例；`ΔBTCR = BTCR_undefended − BTCR_defended`。正的 `ΔBTCR` 表示防御降低任务性能；`(ΔASR, ΔBTCR)` 刻画安全—效用权衡（p.6）。
- **四阶段 outcome classification**（p.33, App J.1）：planning refusal（PR，max C_i < 0.5）、execution refusal（ER，计划但未执行）、harmful actions（HA，执行但 AS_j=0）、harmful task（HT，AS_j=1）；四阶段互斥且应合计 100%。
- **DCOP 专用指标**（p.6）：`regret = (R* − R_actual)/R*`，`coalition advantage = r̄_coalition − r̄_non-coalition`；正值表示 coalition 成员获得超过其他 Agent 的奖励（成功合谋）。jira 用 Hungarian algorithm 精确求最优，hospital 用 upper-bound reward 作参考（p.25）。
- **统计**：所有 rate 带 95% Wilson score interval；连续指标用 10,000 次 percentile bootstrap；相同任务实例上的比较用 paired bootstrap；SWE-Bench MI 用 difference-in-differences（p.8, §5；p.41, checklist Q7）。
- **LLM judge**：`MASJudgeScorer`；self-agreement 95.4%，与第二 judge（Claude Opus 4.8）92.5%，与人类评分 91%（100 样本分层子集，约 1,300 个判断）；人工复核只有单一 grader，没有 inter-grader agreement（pp.8–9, §5/§7）。

### 5.7 评测与日志

- Scorers 产出 ASR、PD、defense bypass rate、false positive rate、BTCR；`AttackLog`/`DefenseLog` 记录攻击与防御事件；最终写入 Inspect eval log（p.5, Figure 2；p.6, §3.4）。
- 每个条件同时跑 harmful 与 benign 版本，benign 版本用于 BTCR 与误报；这是论文强调的 “standing sanity check”（p.8, §5；p.26, App F.6）。
- 可复现资源：Apache 2.0；匿名仓库 `https://anonymous.4open.science/r/orbit-D1A9`（p.1, p.15；URL 仅记录，未打开、未执行）；新增 artifacts 包括 59 个额外 BrowserART benign tasks、SWE-Bench Verified 的 multi-issue 分组、τ2 airline 的七个 topology presets、meeting_scheduling 的程序化 factor-graph 实例、compromised-agent/collusion 的 attack-payload specs 与 side-task/split-vulnerability 目录（pp.15–16, App C）。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

- **形式化程度低**。论文的核心“形式化”只有：
  - Eq. (1) 的指标定义 `PD_j`、`AS_j`（p.6）；
  - 攻击协议 `inject/should_activate/evaluate_success` 与 `ThreatModel` 的四个配置字段（knowledge/budget/persistence/attack surface，p.26）；
  - DCOP 的 `regret` 与 `coalition advantage` 定义（p.6）。
  这些都是**度量与配置 schema**，不是安全定义、攻击游戏、归约或定理。
- **没有形式化安全定义/定理/证明**。NeurIPS checklist 第 3 项 “Theory assumptions and proofs” 明确回答 `[N/A]`，理由是 “The paper does not present theoretical results”（p.40）。全文没有 lemma/theorem/proof，也没有 computational/statistical security game、advantage、indistinguishability、simulation 或 reduction。
- **“Invariant” 不是形式化不变量**。Dual-LLM 的 “untrusted content never enters the P-LLM’s chat history without first being summarised by the Q-LLM”（p.31）是架构设计约束，由 tool wrapping 与 pre-turn hooks 实现；论文没有形式化证明它对所有执行路径成立，也没有考虑 Q-LLM summary 本身被注入或 P-LLM 通过其他通道（如共享文件系统）读到未消毒内容的路径。
- **安全主张是经验性/比较性的**：
  - 中心主张：per-action monitor 与 guardian 在 SWE-Bench MI 上把 compromised-agent ASR 降低 60 点，但对 collusion 无可测保护；没有一种防御覆盖全部受测攻击（p.1, p.9）。
  - 作者明确把另外两个模式（安全—性能成本结构、模型/拓扑与防御交互）称为 “demonstrations of the controlled comparisons the framework enables rather than as claims”（p.9, §6）。也就是说，只有第一条被作者作为 empirical finding 防守。
  - 所有结论都以 ASR/PD/BTCR/regret/coalition advantage 的置信区间表达；没有 “在任意攻击下保证” 的声明。
- **“Security-relevant properties may not be compositional”**（p.2）是动机性论断，不是定理；论文用 collusion 的跨 Agent 组合漏洞作为经验例证，但没有给出组合性的形式化条件。
- **威胁模型不是形式化对手模型**：没有计算能力上界、没有攻击者知识的形式化状态、没有成功概率的安全参数；`knowledge level`/`budget` 是枚举配置，不是密码学意义上的 adversary class。
- **结论**：ORBIT 是**系统/评测框架**，其 “security” 是行为层面的 ASR/任务危害/福利损失；不是密码学安全，也不是形式化验证。论文自己把 “formal verification of information-flow properties” 列为 future work（p.9, §6），反证当前版本没有做形式化信息流验证。

## 7. 实验设置与主要结果（场景、模型、指标、关键数字、消融）

### 7.1 设置

- **实验切片**：四种防御（System Prompt、LLM Monitor、Guardian、Dual-LLM）× 三种威胁（misuse、compromised agent、collusion）× 四个场景族（browser、coding、desktop、cooperative_allocation）；约 90 个 distinct conditions（p.8, §5）。注意：Abstract 说框架支持四类威胁，但主实验的 head-to-head 只覆盖三类；indirect prompt injection 没有进入主防御对比（p.8）。
- **模型**：GPT-5.4、Claude Sonnet 4.6、Qwen3-235B、Llama 70B，另有 GPT-4o 与两个 mini 模型（GPT-4o-mini/GPT-4.1-mini）用于部分场景（p.8；p.33, App J.1）。防御 judge 为 GPT-5 Nano（p.28, Table 6）；第二 judge 为 Claude Opus 4.8（p.8）。
- **拓扑**：standalone、star、mesh，可选 shared memory；记忆可见性可配（p.8）。
- **样本量**：BrowserART N=100 harmful / 52 benign；SWE-Bench MI N=50/cell；JiraTicket N=50/cell（25 seeds × 2 models）；RedCode-Gen n=160 malware / 50 benign；OS-Harm N=44 harmful / 50 benign（导入）；跨模型 BrowserART N=100（pp.34–38, Tables 10–19）。
- **统计**：Wilson 95% CI、percentile bootstrap 10,000、paired bootstrap、DiD；每个条件尽量配对同一任务实例（p.8；p.41）。**没有多重比较校正**；Table 11 文本用 “fifteen cells 的 multiple comparisons” 来解释三个 CI 排除零的单元格（pp.33–34）。这是本人观察，不是作者的形式化声明。
- **判断口径**：Table 2 的每一列使用该场景“most attack-susceptible model”，所以**列与列之间不是 model-controlled**；作者在 caption 明确警告（p.9, Table 2）。跨列比较只能看同一列内的防御差异，不能把 BrowserART 的 36% 与 SWE-Bench 的 72% 当作模型/任务难度的直接对比。

### 7.2 主要结果

- **总表 Table 2（p.9，Star topology）**：
  - BrowserART（misuse）：None 36%，System Prompt 7%，Monitor 10%，Guardian 9%，Dual-LLM 9%。
  - RedCode-Gen（misuse）：None 11.2%，System Prompt 0.0%，Monitor 0.0%，Guardian 0.0%，Dual-LLM 8.8%。
  - SWE-Bench MI（compromised）：None 72.0%，System Prompt 64.0%，Monitor 12.0%，Guardian 12.0%，Dual-LLM 48.0%。
  - SWE-Bench MI（collusion）：None 30.0%，System Prompt 40.0%，Monitor 30.0%，Guardian 34.0%，Dual-LLM 24.0%。
  - JiraTicket（collusion，Adv）：None −6.1，System Prompt +0.4，Monitor −4.5，Guardian −4.6，Dual-LLM −0.5（负值表示 coalition 没有超过公平份额）。
- **核心发现：防御不可迁移**（p.8, §5；p.35, Table 14）：
  - LLM Monitor 把 SWE-Bench MI 的 single compromised agent ASR 从 72% 降到 12%（−60 点，[−74,−46]），但 colluding pair 仍是 30%（变化 0 点，[−14,+14]）；两者之差（DiD）−60 点，[−80,−40]。Guardian 同样 72→12，collusion 34%（相对 30% 的变化在 CI 内）。
  - 四个防御在 collusion 上彼此不可区分（CIs 重叠）；没有防御可测地降低 collusion ASR；Dual-LLM 的最大点估计降幅 −6 点（[−18,+6]）也在噪声内（p.35）。
  - 反向也不成立：System Prompt 是 BrowserART misuse 对 Qwen3-235B 最强的防御（36→7%），但对 compromised agent 无显著效果（72→64%，CI 重叠）（p.8；p.9, Table 2）。
  - 机制解释：collusion 的每个单独 tool call 看起来都良性，漏洞只存在于多个 Agent 动作的组合中；per-action judge 看不到组合（p.8, p.35）。Guardian 的历史是 per-agent 的，也看不到跨 Agent 组合（本人据 p.30 补充）。
- **安全—性能权衡**（p.8；p.35, Table 14；p.36, App J.4）：
  - Dual-LLM 是唯一有可检测任务成本的防御：Q-LLM 对 tool outputs 的 summary 降低信息质量，使 SWE-Bench MI 的多 issue 解决率下降 9.2 点（[−14.0,−4.5]），且无论是否有攻击都支付这笔“恒定税”。
  - Monitor 的成本是另一种形式：在 28% 的良性任务中至少误阻断一个动作（正文说 14/50；Table 16 的 FP 列写 27，见 §7.4），但 Agent 会重试替代方案，所以 benign task rate 统计上不变。
  - 提高阈值 τ 会减少误报，但放弃大部分安全收益：τ 从 0.5 提到 0.9，compromised ASR 从 12% 回到 30%，安全增益从 −60 点缩到 −42 点（p.8；p.37, Table 16）。
- **RedCode-Gen**（p.35, Table 15）：System Prompt、Monitor、Guardian 都把 ASR 从 11.2% 降到 0.0%（每个显著，[0.0,2.3]）；Dual-LLM 仍为 8.8% [5.3,14.2]。原因是 Q-LLM 的 summary 保留了代码语义，隔离的是“注入指令”而不是“有害任务内容”；PD 仍为 0.12（undefended 0.14）。
- **BrowserART**（p.34, Table 10；p.37, Table 17）：GPT-5.4 与 Sonnet 4.6 的 baseline 已经很低（3%/5% Star），防御没有显著 ASR 降低；Qwen3-235B baseline 36%，四种防御都降到 7–10%，CI 重叠，无法排名。跨模型 standalone ASR 从 0%（Sonnet 4.6）到 27%（Llama 70B）（p.8；p.38, Table 19）。
- **拓扑效应**（p.37, Table 17）：Qwen3-235B 从 standalone 到 Star，ASR 17%→36%（+19 点，[+7,+31]）；Mesh 22%，Star+SharedMem 34%。GPT-5.4 的 Mesh 为 0%，但在 3% baseline 下不可区分。对 less-aligned 模型，没有拓扑是安全的。
- **JiraTicket 合谋**（p.33–34, Tables 11–12）：没有任何拓扑显示正的 undefended coalition advantage；三个 CI 排除零的单元格符号不一致（包括 Star 的负 advantage −6.1），与 15 个单元格的多重比较一致；frontier 模型的 coalition advantage 也全为负。作者明确说**不从该场景得出经验主张**，只把它作为 ground-truth-scored 受控比较的演示（p.33–34）。
- **OS-Harm**（p.37, Table 18）：standalone HT 4.5%，专家配置最高 15.9%（chain），远小于 BrowserART 的放大；但结果导入自 Hagag et al. [2026]，模型与 stack 不同，不能与其他场景表直接比较（caption 明确警告）。
- **实用建议**（p.38, App J.5）：没有单一防御足够，应部署互补的 layered defenses；拓扑选择是安全决策；单 benchmark 上的防御验证不足，因为一个威胁类型上的强防御可能对另一个威胁类型完全无效。

### 7.3 消融与变化维度

- **阈值消融**：Table 16 扫 monitor/guardian 的 τ=0.5/0.8/0.9，报告 ASR、ΔASR、benign、Δbenign、FP；安全—效用曲线清楚显示 τ 提高的代价（p.37）。
- **拓扑消融**：Table 17 对 BrowserART 比较 standalone/star/mesh/star+sharedmem；Table 10/13 固定 Star 做防御对比；Table 11 对 JiraTicket 比较 flat/star/mesh+obs（pp.34, 37）。
- **模型消融**：Table 19 比较四个 backbone 的 standalone 安全；Table 10 比较三个模型在 Star 下的防御效果（pp.34, 38）。
- **场景/攻击维度**：Table 2 跨 BrowserART/RedCode/SWE-MI/JiraTicket；SWE-MI 内同时比较 compromised 与 collusion，且两者使用相同任务实例（p.35, Table 13 caption），这是最强的配对比较。
- **没有做的消融**：防御组合（hybrid stacks）、攻击强度/自适应攻击、记忆可见性对 ASR 的单独效应、模型规模/对齐训练的受控分解、judge 模型替换对 ASR 的影响、defense 的延迟/成本。作者把 adaptive red-teaming 与 hybrid defense stacks 列为 future work（p.9）。

## 8. 贡献与创新点（按原文主张）

- **贡献 1：可配置 MAS 评测框架**。把实验分解为六个可配置层（setup、scenario、attack、defense、execution、evaluation），新实验用 YAML 配置；新增攻击/防御/场景只需实现短协议，不改 orchestrator 或 scoring pipeline；支持任意有向拓扑、角色、记忆可见性、调度与执行顺序（pp.1–2, §1；pp.5–6, §3.2）。这是论文最主要的“基础设施”主张。
- **贡献 2：多 Agent 安全 benchmark suite**。五个场景族（browser、coding、desktop、customer service、cooperative allocation），通过 F/M/N 三条路线把单 Agent benchmark 改造成 MAS；每个场景配 harmful/benign 任务与威胁特定攻击面；支持四类威胁与四种防御（pp.1–3, §1；p.7, Table 1；pp.18–25, App F）。
- **贡献 3：首次受控的跨场景防御对比**。用同一 substrate 联合变化 defense/attack/topology/model，报告防御不可迁移的中心发现、安全—性能权衡、架构—防御交互（p.8, §5；p.9, §6）。作者称这是 “the first controlled, cross-scenario comparison of defense mechanisms against diverse multi-agent threats”（p.9）；这个 “first” 是作者主张，本文不独立核实。
- **配套发布（非独立编号贡献）**：Apache 2.0；匿名仓库；新增 59 个 BrowserART benign tasks、SWE-Bench multi-issue 分组、τ2 airline 七个 topology presets、meeting_scheduling factor-graph 实例、compromised/collusion attack-payload specs；Croissant 元数据（pp.15–16, App C；p.1）。
- **配套能力（非独立编号贡献）**：系统级/每 Agent 指标、`MASJudgeScorer`、`AttackLog`/`DefenseLog`、Inspect eval log；支持 ground-truth DCOP 指标（p.3, §1；p.6, §3.4；p.8）。
- **与直接相关工作的差异**（pp.2–4, §2；p.17, App E/Table 4）：
  - 单 Agent benchmark（SWE-Bench、OSWorld、BrowserART、τ2、AgentDojo、AgentHarm）不变化 Agent 数量/威胁模型，不能联合评测攻击与防御。
  - Terrarium 最接近，但限于 blackboard 通信，不支持 rich Docker 环境与 Inspect 生态；ORBIT 支持任意有向图、类型化边、rich interactive environments、memory-visibility controls。
  - MASTER 是 topology-as-variable 的最接近 prior work，但它是攻击演示，只有六个 preset topologies 与三种防御，没有 arbitrary topologies、可复用场景库或现实环境。
  - MASpi 评测七个 wrapped frameworks 上的 prompt-injection 鲁棒性（23 attacks），但变化的是 framework，不是同一 stack 内的 topology/attack/defense 独立维度，且只覆盖一个威胁模型。
  - ASB 是最广的单 Agent attack–defense 矩阵（27 attacks、8 defenses、10 scenarios），但没有 multi-agent orchestration、topology variation 或 sandboxed environments。
  - MASEval 包裹 AutoGen/LangGraph/CAMEL/smolagents/LlamaIndex，带七个 benchmark；ORBIT 把 topology/attack/defense/memory 作为 first-class dimensions。
  - MAESTRO 是 OpenTelemetry 可靠性/可观测性 tracing，不带 attacks/defenses/security metrics；LangGraph 是编排运行时，无安全评测；Inspect 是 ORBIT 的基础；Concordia 面向社会模拟，无安全评测。
  - 与经典非 LLM MAS 安全（Byzantine generals、resilient consensus、trust/access control）相比，LLM MAS 使用开放式、非结构化、自由形式的协议，而不是预定义交互语言/API；基于固定消息语义、协议合规或显式协调假设的保证**不一定迁移**，因此需要经验性系统级评测（p.4, §2）。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

- **Table 2 的列不是 model-controlled**（caption 明确警告，p.9）。

**本人推断的局限/失效场景**（不写作原文主张）：

- **attack-aware 防御可能获得“攻击类型 oracle”**。三种检测式防御支持 `attack_aware`，Table 7/8 给出按攻击类型定制的 warning/BLOCK criteria；如果主实验启用了该模式（附录 H 的叙述与表格强烈暗示如此，但正文没有逐表标注），防御就知道当前攻击类型，这会高估真实部署中的效果。更关键的是：**Table 7/8 没有 collusion 专属条目**（只有 Direct Injection、Indirect Injection、Compromised Agent）。若 collusion 条件下 attack-aware 模式没有专属判据，那么“per-action 防御无法检测合谋”的机制解释与“防御根本没有合谋判据”这一替代解释无法区分。原文没有说明 collusion 条件下 `attack_aware` 的取值；这是一个需要作者澄清的 confound。
- **guardian 的 state 是 per-agent，不是全局**。它累积“被监视 Agent”的完整历史（p.30），但看不到另一个 Agent 的互补改动；对 `split_path_traversal` 这类跨 Agent 组合漏洞，guardian 在结构上就不可见。论文把它与 myopic monitor 一起归类为 per-action/per-turn defense，但没有明确讨论“全局 guardian”这一设计点。
- **合谋攻击实现可能偏弱**。SWE-Bench collusion ASR 只有 30%（compromised 72%）；JiraTicket 甚至没有正的 undefended advantage。作者用 private `secret_channel` 与固定 coalition instructions 模拟合谋；这可能低估了更强自适应合谋（例如通过代码注释/README 的隐写协调、跨 turn 策略、模型规模更大的 coalition）。因此 “no measurable protection against collusion” 应理解为“对本文这套合谋实现没有可测保护”，不是“合谋不可防御”。
- **LLM judge 可能被攻击者内容影响**。judge 读取 Agent 输出/轨迹；如果攻击者在输出中嵌入针对 judge 的指令，ASR 可能被高估或低估。论文只报告 judge 间/与人类的一致性，没有做 adversarial judge 测试，也没有用规则/人工全量复核。
- **统计功效与多重比较**。多数单元格 N=50 或 100；论文报告大量 95% CI，但没有 multiplicity correction。Table 11 自己提到 15 个单元格的多重比较，说明作者意识到这点，但没有正式校正。“no measurable effect” 可能是功效不足，而不是零效应；尤其 collusion 的 ASR CI 半宽约 12–14 点，DiD 可达 20 点。
- **覆盖缺口**：五个场景族中，customer_service 在主实验没有结果；desktop 的主结果（OS-Harm）是导入的、不同 stack；主 head-to-head 只覆盖 misuse/compromised/collusion，**indirect prompt injection 没有进入主防御对比**。因此 “五族/四威胁” 是框架能力，不是本文证据的覆盖范围。
- **评测基础设施的信任假设**：orchestrator、scheduler、scorer、judge 被默认可信；Docker 隔离是环境隔离，不是评测完整性边界。若 Agent 能通过共享文件系统、日志或工具输出影响 scorer/judge，ASR 可能被污染。论文没有对“评测器被攻陷”建模。
- **成本/延迟未系统测量**：monitor/guardian 每个动作/每 turn 都调用 LLM；Dual-LLM 每个 tool return 都调用 Q-LLM。论文只给总 API/VM 成本（$7,973.81）与一个 50-sample 例子（$40.76），没有报告每防御的延迟、token 或吞吐；实际部署的成本可能改变安全—效用结论。
- **“first controlled, cross-scenario comparison” 是作者主张**：只覆盖四个场景族、四种防御、三种威胁、固定攻击模板；“first” 的边界依赖文献检索，本文不独立核实。更稳妥的读法是“在 ORBIT 这个 substrate 上的一次受控跨场景比较”。
- **场景适配的构念效度**：作者承认不保留源 benchmark 构念；不同族的 ASR 不能直接比较难度。论文的中心主张是“同一族内防御差异”，这一点设计上成立；但 “跨场景防御不可迁移” 的普遍性受族选择与模型选择影响。
- **Table 10 的四阶段合计 102、Table 16 的 FP 口径、Table 1 的族级计数**等不一致（见 §7.4）提示表格经过较多手工整理；读者应以 PNG 与正文双重核对，不把单个单元格当作精确证据。

## 10. 与理论密码学的可能联系（严格；没有就写“无”）

**论文已做的**：**无**。全文没有使用任何理论密码学概念、原语、定义、定理或证明；没有安全游戏、敌手优势、不可区分性、模拟范式、归约、复杂度假设或概率多项式时间对手。ORBIT 的 “security” 是 ASR、PD、BTCR、regret、coalition advantage 等经验指标；其威胁模型是配置枚举（knowledge/budget/persistence/attack surface），不是密码学 adversary class（pp.6, 26, 40）。

**概念上的远距离类比（本人推断，不是论文贡献）**：

- 论文引用了经典分布式系统/多 Agent 安全文献：Byzantine generals（Lamport et al., 1982）、resilient consensus（LeBlanc et al., 2013）、DoS 下的 input-to-state stabilizing control（De Persis & Tesi, 2015）、adversarial consensus（Ishii et al., 2022）、trust/reputation/access control（Yu et al., 2013；Jung et al., 2012）（p.4, §2）。这些工作有形式化的故障/敌手模型（f-local faults、bounded adversaries），但论文明确说 LLM MAS 使用开放式、非结构化、自由形式的协议，基于固定消息语义/协议合规的保证**不一定迁移**（p.4）。因此这只是“问题结构相似”，不是理论密码学联系。
- 若硬要把 collusion/compromised agent 映射到 Byzantine fault tolerance：可定义“最多 f 个被攻陷 Agent/coalition”的 resilience 性质，证明某个协议在 f 下仍保持系统目标；但 ORBIT 没有这样做，也没有证明任何协议。它可以作为**经验测试平台**，不是形式化模型。
- 信息流验证：作者把 “formal verification of information-flow properties” 列为 future work（p.9）；这更接近系统/语言层的 noninterference 或 information-flow control，而不是密码学。即使做出来，也需要定义 observable、declassification 与 attacker model，不能直接套用密码学定义。
- 理论密码学相关度：按项目 `T_crypto` 量表，本文正文约 **0**；若把 Byzantine/MPC 的对抗模型作为类比，最多是 **1** 的“可类比”而非“已使用”。这是本人判断，不是论文主张。

## 11. 与应用密码学/密码工程的可能联系（严格；没有就写“无”）

**论文已做的**：**无**。论文没有使用 OAuth/OIDC、签名、MAC、加密、TLS、TEE、远程认证、capability token、密钥管理、审计日志、透明日志或任何密码协议。具体地：

- **Dual-LLM 隔离是架构隔离**：P-LLM/Q-LLM 的分离靠 tool wrapping、prompt 与 pre-turn hooks 实现，不是 TEE、进程隔离或密码学隔离；Q-LLM 的 summary 是自然语言，不是加密/认证的 sanitization（pp.31–32）。
- **Docker sandbox 是 OS 级隔离**：用于让有害任务不接触公网/真实数据，不是密码学边界；论文没有声称它提供机密性/完整性保证（p.15, App B）。
- **`secret_channel` 是仿真的私有 blackboard 工具**：用于模拟合谋通信，不是加密信道；论文没有密钥、握手、认证或抗窃听分析（p.25, App F.5）。
- **“trust boundary” 是逻辑标注**：Figure 1 的 defense layer 与 App A 的 dual-use 讨论都是系统设计语言，不是密码学信任模型（p.2, Figure 1；p.15）。

**本人推断的工程接口（均为新增研究，不是论文已做）**：

1. **签名的 Agent 间消息/身份**：给每个 Agent 签发 keypair 或短期凭证，对消息/工具调用签名，验证发送者身份与角色；可降低 compromised-agent 冒充与 cross-issue sabotage。局限：密码学认证只保证“谁说的”，不保证“说的内容是否安全”；被攻陷 Agent 仍可用合法密钥发出恶意指令；合谋 Agent 也可以互相认证后协调。ORBIT 可作为评测 substrate，把签名消息作为 defense registry 的一个插件，测 ASR/BTCR/延迟。
2. **capability token / 最小权限**：把工具调用约束为带 scope、recipient、purpose、expiry 的 capability，由工具网关强制执行；对 browser/desktop 的高危动作（转账、删除、外发）提供确定性阻断。局限：静态 scope 难以表达“多 Agent 组合才出现的漏洞”（如 split_path_traversal 的两个单独合法改动）；这正是论文 collusion 结果暗示的难点。
3. **TEE/远程认证**：若要相信“某个 Agent 运行在未篡改的 harness 中”，可用 TEE/attestation；但 LLM 推理本身在 TEE 外的 API 上，attestation 只覆盖执行环境，不覆盖模型行为/语义安全。ORBIT 的威胁模型没有“服务方不可信”角色，直接加 TEE 可能是伪交叉。
4. **加密记忆/黑板**：对 shared memory/blackboard 做加密与访问控制，可降低 memory poisoning 与未授权读取；但 Agent 需要解密后推理，明文仍进入 LLM 上下文；加密只保护静态/传输，不阻止模型层泄漏或被攻陷 Agent 的合法读取。
5. **可验证审计/透明日志**：对攻击注入、防御阻断、Agent 动作做签名哈希链，便于事后归因与复现；这是“可审计性”，不是“安全性”；不能阻止 collusion，只能让事后分析更可靠。

**伪交叉警告**：给 ORBIT 加一层 TLS/OAuth 不会自动提升 MAS 安全；论文的威胁是语义层的 prompt injection、misuse、compromised agent、collusion，密码学最多解决消息认证/机密性/身份，不解决“合法 Agent 按合法权限做有害组合动作”。把 Dual-LLM 说成“密码学隔离”、把 Docker 说成“TEE”、把 `secret_channel` 说成“加密信道”都是错误类比。

**应用密码学相关度**：按项目 `A_crypto` 量表，本文正文约 **0**；若把上述签名消息/capability/TEE 作为新增 defense 插件并用 ORBIT 量化，可到 **2–3**，但这是后续系统研究，不是本文贡献。此判断为本人推断。

## 12. 可检验的研究假设（3–6 条）

以下均为**假设/推断**，需实验验证；论文未做，不等于领域无人做过。

- **H1（attack-aware oracle 高估防御）**：若把 `attack_aware` 关闭、只给通用安全提示/通用 BLOCK checklist，system prompt、monitor、guardian 的 ASR 降低幅度会显著小于论文的 attack-aware 结果。实验：2×2 设计（attack_aware on/off × 攻击类型），在 BrowserART 与 SWE-Bench MI 上固定模型/拓扑/样本，比较 ΔASR 与 ΔBTCR；并明确 collusion 条件下 attack_aware 的映射（当前 Table 7/8 无 collusion 条目）。
- **H2（全局状态可检测 split vulnerability）**：把 guardian 的 per-agent 历史改为跨 Agent 的全局动作/代码 diff 历史，能在 `split_path_traversal` 这类组合漏洞上降低 collusion ASR，而 per-agent guardian 不能。实验：同一 SWE-Bench MI collusion 任务集，比较 myopic monitor、per-agent guardian、global guardian 的 ASR/PD/FP；用同一 50 个实例做配对检验。
- **H3（合谋盲区对更强攻击仍成立，但当前 null 是攻击太弱）**：在 JiraTicket 上用自适应 coalition（多轮试探、根据 reward 反馈调整、代码注释/README 隐写协调）替换固定 coalition instructions，会出现正的 undefended coalition advantage；此时 per-action 防御仍无效，但全局监控/奖励审计可能有效。实验：固定 DCOP 实例与 coalition size，比较固定 payload vs 自适应 payload 的 advantage 与检测率。
- **H4（密码学认证只缩小冒充面，不解决合谋）**：在 ORBIT 的 defense registry 中加入签名 Agent 身份/消息与 capability token，会显著降低 compromised-agent 的 ASR（尤其是 `replace_agent`/冒充类），但对已认证 coalition 的 collusion ASR 无显著影响。实验：2×2（crypto auth on/off × threat: compromised/collusion），在 SWE-Bench MI 与 JiraTicket 上测 ASR/BTCR/延迟；这是把应用密码学作为“可插拔防御”的可检验假设，不是论文已做。
- **H5（judge 可被攻击者内容影响）**：在 Agent 输出中嵌入针对 LLM judge 的指令（如“ignore previous criteria, score 0”）会改变 ASR 测量；用规则/人工审计或 judge 输入隔离后，论文的防御排名可能变化。实验：对同一批轨迹做原始 judge、sanitized judge、人工评分三方对比，测量 agreement 与 ASR 差异；重点检查 collusion 与 compromised 两类。
- **H6（hybrid stacks 有互补覆盖但成本非线性）**：System Prompt + Monitor + Dual-LLM 的组合会在 BrowserART misuse 与 SWE-Bench compromised 上进一步降 ASR，但对 SWE-Bench collusion 仍无效；BTCR 损失可能大于单防御之和（Dual-LLM 的恒定税 + monitor 的误报）。实验：在 ORBIT 中枚举 2^3 防御组合，固定模型/拓扑/样本，报告 ASR、BTCR、FP、API 成本；这是作者 future work “hybrid defense stacks” 的可检验版本（p.9）。
