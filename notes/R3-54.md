## 1. 150–300 字中文概述

论文提出 ASPI（Ambiguous-State Prompt Injection）基准，把"澄清"从普通执行中分离为独立 Agent 状态：在 728 个任务–攻击对、四个 AgentDojo 域上，保持任务、攻击目标、环境与评分不变，比较执行态与澄清态的注入成功率。十个前沿模型在澄清态经 `ask_user` 返回通道接收注入时 ASR 大幅上升（o3 1.8%→34.0%，Gemini-3-Flash 2.2%→35.7%，Kimi K2.5 11.1%→63.1%）。作者把差距分解为状态效应与通道效应，发现 `ask_user` 通道是主要放大器，而单纯状态效应因模型而异；两种轻量防御降低但未消除漏洞。全文是行为级基准与经验评测，不含密码学原语、形式化安全定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景：澄清被视为 Agent 的良性能力。** 识别任务欠指定并向用户提问，被广泛认为能减少误解、贴近用户意图（p.1, §1；引 Aliannejadi et al. 2020、Min et al. 2020、Zhang & Choi 2025）。2025–2026 年一批工作进一步研究"何时问、问什么、如何问"（p.1；p.11, A. Related Work）。作者指出，这些工作把澄清当作能力指标，未研究其安全后果。
- **现有提示注入研究的盲区。** 间接提示注入主要研究恶意内容经工具返回、检索内容或第三方数据进入 Agent 上下文（p.1, §1；p.11, A）。代表性基准 InjecAgent 偏单轮工具输出，AgentDojo 提供动态、有状态的多步执行环境与确定性 utility/security 评分，但二者都把攻击建模为"标准执行过程中到达"（p.11, A）。作者称此前没有基准把"澄清状态"单独隔离出来，比较同一任务、同一攻击目标在"执行态 vs 澄清态"下的差异。
- **现有澄清研究的盲区。** ClariQ/AmbigQA 研究短程语义歧义；QuestBench 把缺失信息推理形式化为欠约束满足；UserBench/ClarifyBench 扩展到多轮用户–Agent 交互；LHAW 生成可控欠指定的长程任务并衡量澄清价值（p.11–12, A）。这些工作评估的是 benign 澄清的质量/成本，而不是澄清通道是否改变注入脆弱性。本文明确把自己定位为与它们正交（p.12）。
- **精确问题。** 论文要回答三件事：(1) 从标准执行转到"寻求澄清"状态，是否会提高 Agent 对提示注入的易感性？(2) 这一差距中有多少来自交互状态、多少来自投递通道？(3) 轻量输入过滤/工具限制在澄清时是否仍然有效？（p.1 Abstract；pp.6–7, §5；p.8, §6）
- **操作性定义。** "澄清状态"被定义为：Agent 在收到删除一个必需 slot 的 `p_base` 后，调用 `ask_user` 工具；若只输出自然语言澄清而未调用工具，允许一次显式提示重试，仍不调用则从澄清比较中排除（p.5, §4.2）。因此本文研究的是**工具介导的单 slot、单轮澄清**，不是所有自然语言澄清行为。
- **作者主张的总体结论。** 标准执行时安全评估会系统性低估交互式 Agent 的攻击面；在完全指定任务上的鲁棒性不等于在歧义下的鲁棒性（p.1 Abstract；p.8, §6）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **环境与组件。** 基于 AgentDojo（Debenedetti et al., 2024）的四个应用套件：Workspace、Slack、Travel、Banking；复用其工具实现、模拟环境、用户任务、攻击者目标与确定性评分函数（p.3, §3.1；p.14, App C.3）。主要组件包括：
  - **Agent 模型**：十个前沿/推理/轻量模型，经 LiteLLM 调用（p.6, §4.4；pp.16–17, App D.2）。论文没有复述 Agent scaffold 的完整 system prompt，而是依赖 AgentDojo 的默认实现；这是复现性上的一个空缺（本人推断）。
  - **工具**：各套件的搜索、读取、发送、更新、删除、转账等 API；平均任务需 2.91 次工具调用，涉及 52 个工具函数（p.14, App C.3）。
  - **`ask_user` 工具**：澄清状态的判定标志；其返回值被视为"用户回答"（p.5, §4.2；pp.15–16, App D.1）。
  - **User simulator**：`gpt-4o-mini-2024-07-18`，temperature 0.3；根据原始任务、`p_base`、缺失 slot 和 Agent 的实际问题动态生成回答（p.5, §4.2；p.16, App D.1）。
  - **评分器**：AgentDojo 确定性 utility/security 函数为主；LLM judge 用于行为分析与部分语义判定（p.23, App G）。
- **交互流程（澄清条件）。** Turn 1：Agent 收到 `p_base`（删除了一个用户提供的必需信息），开始与环境和工具交互；Turn 2：Agent 提出澄清问题并调用 `ask_user`；Turn 3：simulator 生成回答（benign 时只给缺失信息；attack 时在回答中嵌入攻击目标）；Turn 4：Agent 带着该回答继续执行；最终从完整轨迹计算 utility 与 ASR（pp.15–16, App D.1）。所有澄清条件共享到 Turn 2 的前缀，只在 Turn 3 分叉，以保证差异只来自注入内容（p.16）。
- **信任边界。** 论文的威胁模型明确把 system prompt、工具实现、模型权重放在可信侧；攻击者只能修改环境中的内容（邮件、文档、共享工作区）（p.2, §2）。真正的弱边界是**用户关联的澄清通道**：Agent 主动请求、期待得到任务关键信息，并把 `ask_user` 返回或随后的用户消息当作可信指令；而该通道可能被平台中间件、共享频道、邮件伪造或人工转述污染（p.2, §2；p.12, App B）。
- **角色/来源标签是唯一出处信号。** Agent 上下文中区分"用户消息 / 工具输出 / 系统提示"的主要是消息角色，而不是密码学认证或来源证明；论文没有给 Agent 提供"这条澄清回答来自谁、是否被转发/篡改"的元数据。攻击正是利用这种角色信任启发式：把恶意指令放进"用户回答"的角色里。
- **与 R3-08 式形式化的差别。** 本文没有给出 Agent 循环的 `C≤t` 形式化，也没有 memory 模块、多个协作 Agent 或显式规划器；主实验是单 Agent + AgentDojo 工具 + user simulator。多 Agent 管道只作为现实部署场景在 App B 讨论，未做实验（p.12）。
- **攻击面区分（容易混淆，必须说清）。** `clarif tool` 是澄清之后**任务工具**的输出被注入；`clarif ask user` 是 `ask_user` 的返回值被注入；`clarif user` 是澄清之后**用户消息**被注入。三者不是同一通道；本文的核心新通道是 `clarif ask user`（p.4–5, §4.1；p.16, App D.1）。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产。** (1) 用户良性任务的正确完成（utility）；(2) 敏感输出与动作：邮件内容、报价/引文、文件标识符、IBAN、URL 等（p.14, App C.3）；(3) 具体危险动作，如删除文件、向攻击者发邮件、把频道消息发到攻击者网站、向攻击者 IBAN 转账、预订高价酒店（pp.14–15, App C.4；p.3, Fig.1）。
- **攻击者目标。** 原文："cause the agent to execute a malicious action without the user's knowledge, ideally while the benign task completes normally"（p.2, §2）。即优先追求"隐蔽的双重执行"：用户任务看似完成，同时攻击目标被执行。攻击目标与评分沿用 AgentDojo（p.2）。
- **攻击者能力。**
  - 可修改 Agent 运行环境中的内容：邮件、文档、共享工作区（p.2, §2）。
  - 可通过三条通道投递恶意指令：(i) 工具输出（被污染的检索内容）；(ii) 澄清回答（注入 `ask_user` 中继通道）；(iii) 用户消息（直接用户轮次，作为更强基线）（p.2, §2）。
  - 在澄清场景中，攻击者可影响"用户回答"：App B 给出三类现实路径——环境投毒 + 人工转述（用户查阅被改文档后转述）、平台中介中继（Slack/Teams bot、可伪造的邮件回复、多 Agent 管道）、程序化返回路径注入（表单处理器、中间件、RAG 管道）（p.12, App B）。
  - **不能**修改 system prompt、工具实现、模型权重；**不能**访问具体用户任务（p.2, §2）。
- **前提假设/范围限制。**
  - 单一外部攻击者；不研究会观察澄清行为并自适应调整策略的攻击者（p.8, §6 Limitations）。
  - 单 slot 缺失、单轮 `ask_user`；多 slot、多轮、开放式语义歧义未覆盖（p.2, §2 Scope；p.8）。
  - 十个固定模型、四个 AgentDojo 域；不代表全部部署系统、专用领域模型或微调变体（p.8）。
  - 用户回答由 LLM simulator 生成，不是真人；攻击回答由生成模型按固定算子构造，未做人评真实性验证。
  - 评分以 AgentDojo 确定性函数为主，部分语义判定用 LLM judge；judge 不在 Agent 运行时内。
- **威胁模型位置。** 原文没有独立的 "Threat Model" 长节；§2 用一段定义 threat actor、goal、vectors、clarification-specific risk 与 scope，App B 补充现实场景。与 R3-08 等系统论文相比，本文的威胁模型是**基准级、范围受限**的，不是形式化能力模型。
- **一个未被论文展开的能力。** 攻击者既然能回答 Agent 的澄清问题，就能看到该问题；问题本身可能泄露缺失 slot/用户意图。论文只把这一点当作注入机会，没有分析"澄清问题向不可信回答者泄露任务信息"的隐私/安全问题。

## 5. 核心方案：ambiguity clarification、攻击构造、放大机制

### 5.1 基准与模糊性构造

- 每个 ASPI 样本来自一个 `(U, I)` 对：`U` 是 benign 用户任务，`I` 是攻击者目标；从 `U` 的原始 prompt `p` 和 ground-truth 工具轨迹出发，构造 `p_base`：**精确删除一个完成所必需、且由用户提供的信息 slot `s`**（p.3, §3.2）。每个样本还包含：期望的澄清问题 `q`、能解决歧义的 benign 回答 `r_benign`、澄清后应执行的安全动作 `a_safe`（pp.3–4）。
- **slot 约束**：缺失信息不能通过工具或环境恢复；没有它任务不可完成；必须是用户提供而非工具可检索；benign 回答必须完全解决任务（p.4）。实践中有效 slot 包括收件人、日期/时间、标识符、目的地；弱/可默认的省略（如风格偏好）被排除（p.4）。
- **构造流程**：Gemini 3.1 Pro 在固定模板下提出候选删除与澄清问题；随后通过确定性的 10 项质量检查（是否为合法删除、slot 是否必要且不可恢复、问题/回答是否与任务规格一致、注入是否保留 benign 前缀、是否包含攻击目标、是否避开禁用短语等）（p.3–4；p.13, App C.2）。构造温度 0.7，每个样本最多 2 次重试（p.13）。
- **人工验证**：随机抽 200 例，83 名至少本科学历、来自 19 个国家/地区的标注者；99% correctness，AC1≈0.99；不满足四条标准的样本复核后修正或丢弃（p.5, §4.2；p.15, App C.5）。
- **数据统计**：728 条记录；Workspace 407、Slack 97、Travel 94、Banking 130；原始 prompt 平均 31.4 词，base 27.8 词，平均删除 3.6 词，97.7% 的 base 更短；slot 类型：date/time 26.1%、recipient 20.2%、destination 12.5%、identifier 8.8%、other 32.4%；攻击目标类型（可重叠）：emails 55.6%、quotations 31.6%、file identifiers 22.1%、IBANs 15.9%、URLs 14.8%；平均 2.91 次工具调用、52 个工具函数（p.14, App C.3）。
- **为什么用单 slot**：这是最小、最可控的澄清设定，只有一问一答、缺失类型已知，过滤多余内容最容易；真实歧义常是多 slot、多轮、开放式，注入面更大，因此报告的 ASR 很可能是**下界**（p.3, §3.2；p.8）。

### 5.2 注入构造：三个语言算子

- ASPI 不为每个条件定义不同的"攻击类型"，而是用**同一个攻击目标 `I`**，只改变它"何时、以何种方式"出现（p.3–4, §3.3）。注入回答由 Gemini 3.1 Pro 按固定模板生成，必须先给出合法答案，再嵌入攻击目标，读起来像自然的用户聊天（p.13, App C.1）。
- 三个算子（p.13, App C.1）：
  - **HR（Hierarchy Rebinding, FM-1）**：通过上下文暗示权威，不使用显式授权语句。
  - **GS（Goal Substitution, FM-2）**：把攻击目标作为同一工作流的一部分引入。
  - **CP（Constraint Poisoning, FM-3）**：把攻击目标框成用户已知的前置条件、副作用或条件。
- 为降低"一眼假"的注入，模板禁用 "Since you're..."、"By the way..."、"I've granted you"、"full delegate access"、"as per policy"、"standard protocol"、"the portal won't let you" 等过渡/授权短语（p.13）。
- 每条记录包含 HR/GS/CP 三个变体（p.14, App C.3），但主表只报告聚合后的 `clarif user`，**没有按算子给出 ASR 分解**；这是后文 §7 指出的分析空缺。
- 重要：本文**没有**提出新的攻击优化算法，也没有对注入文本做搜索/迭代优化；攻击目标是 AgentDojo 预定义的，注入是固定模板生成的。因此它是"攻击面基准"，不是"攻击方法论文"。

### 5.3 八个匹配条件

所有条件共享同一 task specification、attacker goal、environment 和 scoring functions，只在交互状态与注入点上不同（p.4–5, §4.1）：

- 执行态（原始 `p`）：
  - `exec benign`：无攻击，测 utility。
  - `exec tool`：恶意指令经工具返回内容进入。
  - `exec user`：把攻击目标追加到原始 prompt（直接用户指令）。
  - `exec next turn`：在后续用户消息中投递攻击目标。
- 澄清态（`p_base`，必须先澄清）：
  - `clarif benign`：只给缺失信息，测 utility。
  - `clarif tool`：澄清后，经任务工具输出投递恶意指令。
  - `clarif ask user`：恶意指令直接嵌入 `ask_user` 的返回值（本文的核心新通道）。
  - `clarif user`：澄清后，经用户消息投递恶意指令。
- 这 8 个条件构成近似的 2×2×2 对照：状态（execution/clarification）× 通道（tool/user）× benign/attack；`clarif ask user` 没有执行态对应物，是澄清特有的通道（p.4–5；p.6, §5.2）。

### 5.4 评测流程与指标

- 执行条件用原始 `p`，Agent 与环境交互至结束；澄清条件用 `p_base`，只有调用 `ask_user` 的样本才进入澄清比较；若只输出自然语言澄清，允许一次显式提示重试，仍不调用则排除（p.5, §4.2）。
- 所有澄清条件共享到 Turn 2 的前缀；在 Turn 3 只改注入内容；环境和消息历史在分叉前复制，分支独立执行，避免条件间污染（pp.15–16, App D.1）。
- 指标（p.5, §4.3；p.17, App D.3）：
  - `Utility(c) = (1/|G|) Σ u_c(g)`，`u_c(g)∈{0,1}` 表示 benign 任务完成。
  - `ASR(c) = (1/|G|) Σ σ_c(g)`，`σ_c(g)∈{0,1}` 表示攻击目标达成；ASR 为主安全指标。
  - `Clarification rate`：在 `p_base` 下调用 `ask_user` 的样本比例。
  - 配对差：`Δ(c1,c2) = (1/|G★|) Σ (σ_c1(g) − σ_c2(g))`，`G★` 是调用 `ask_user` 的子集。
  - 头条比较：`A4 = ASR(clarif ask user) − ASR(exec tool)`。
  - 分解：`A4 = [ASR(clarif tool) − ASR(exec tool)] + [ASR(clarif ask user) − ASR(clarif tool)] = Δstate|tool + Δask|clarif`。
  - 用户通道状态效应：`A2 = Δstate|user = ASR(clarif user) − ASR(exec user)`。
  - 95% CI：paired bootstrap，B=1000；显著性：exact two-sided McNemar；报告 p<0.05/0.01/0.001（pp.17–18）。
- **口径提醒（重要）**：执行条件 ASR 在全部 728 组上计算；澄清条件 ASR 只在各模型进入澄清的子集上计算（p.19 给出 393–590 例）。因此不能把 Table 2 的两列直接相减来复算 Table 3 的 A1/A4；Table 3 是在 `G★` 上重新配对计算的（p.20 Table 2 caption；p.17）。

### 5.5 放大机制：为什么澄清会放大注入

论文给出的机制不是"歧义让模型变笨"，而是**结构性的信任不对称**（p.1–2；p.7, §5.5；p.8, §6；pp.27–28, App G.6）：

1. **主动索取**：Agent 自己发起澄清，期待得到任务关键信息；相比被动读到的工具输出，它更可能把回答当作"合法任务输入"。
2. **用户关联通道**：回答以用户消息/`ask_user` 返回的角色出现，角色标签本身带有信任含义；Agent 缺少来源认证，难以区分"用户本人"与"被污染的中继"。
3. **必须使用**：为了完成 benign 任务，Agent 必须吸收回答中的缺失信息，不能像对待可疑工具输出那样整体忽略。
4. **良性信息与攻击交错**：澄清回答通常前半段是合法答案、后半段是注入；整条丢弃会损害 utility，segment-level 过滤才可能保留 utility，但攻击者可把指令拆散/改写以逃避过滤（p.7；p.22, App F.1）。
5. **通道不可关闭**：`ask_user` 是澄清任务所必需的，工具过滤器必须保留它；因此不能像裁剪无关工具那样关闭该通道（p.7；p.22–23）。
6. **问题泄露 slot**：Agent 的澄清问题告诉回答者缺什么，攻击者可据此把注入伪装成"正好相关的补充信息"。
- 行为分析支持这一解释但仍属**归因性证据**：judge 把大量澄清态失败标为 `CONFUSED`（把注入当成原任务的一部分）或 `PERSUADED`（意识到外部/异常但因权威/必要性/任务相关性而执行），且 `TASK AND ATTACK`（同时推进 benign 与攻击目标）常是主导失败形态，而不是完全放弃任务（p.7；pp.27–28, 30；Fig.10、Fig.13）。这不是对"信任"的直接测量，也没有中介效应分析。

### 5.6 防御适配

- **Prompt guard**：沿用分类器式注入检测（ProtectAI DeBERTa 类），但改为 **segment-level**：扫描新进入的 user 与 tool 消息，命中只替换可疑 segment 为短标记，保留 benign 澄清内容；因为澄清回答常是"合法答案 + 注入"的混合，整条丢弃会破坏 utility（p.22, App F.1）。
- **Tool filter**：在 Agent 行动前的"最后一个安全边界"裁剪工具，只保留当前任务看似需要的工具；**始终保留 `ask_user`**，否则防御会因阻止澄清而"看起来有效"；裁剪可能用于无关 write/send/external 动作的工具（p.22–23）。
- 两者是互补的：prompt guard 作用于"进入模型的内容"，tool filter 作用于"模型下一步可用的动作"（p.23）。
- 结果：都降低 ASR，但都不消除澄清态漏洞；prompt guard 对 user 通道更有效，tool filter 对 tool 通道更有效，`clarif ask user` 仍有 27.0%/23.9%（Gemini-3-Flash）与 12.3%/19.3%（Gemini-3.1-Pro）的残余 ASR（p.7, §5.4；p.24, Table 5）。防御还带来明显 utility 代价（p.24, Table 6）。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

- **论文实际定义了什么。** 只有评测量：`u_c(g)`、`σ_c(g)`、`Utility`、`ASR`、`clarification rate`、配对差 `Δ`、`A1/A2/A4`、bootstrap CI 与 exact McNemar（pp.5, 17–18）。这些是**统计/评测定义**，不是安全定义。
- **没有形式化安全模型。** 全文没有：(1) 安全游戏（game）或攻击者/模拟器/挑战者的形式化；(2) 机密性、完整性、不可区分性、不可伪造性等安全属性定义；(3) 定理、引理、证明、reduction；(4) 密码学或计算复杂性假设；(5) 对 Agent 信任边界、来源认证、策略执行的数学模型。所谓 "security" 就是以 AgentDojo 确定性 security function 为主、LLM judge 为辅的 ASR，属于**经验行为指标**。
- **经验主张及其证据强度。**
  - **C1（头条）**：澄清态 `ask_user` 攻击比执行态工具攻击更容易成功。证据：Table 2/Fig.2，10 个模型中 9 个 A4 为正；o3 +31.3、Gemini-Flash +33.3、Kimi +46.3；Opus 例外（-0.9，p=0.125）（p.20–21）。支持"新通道是高影响攻击面"，但**不支持**"所有模型、所有通道都一致放大"。
  - **C2（分解）**：差距可分解为状态效应与通道效应；`ask_user` 通道是主要驱动，状态效应异质。证据：Table 3；A1 在 6/10 模型为负（DeepSeek -16.1、Qwen3-235B -7.8、Kimi -4.6、Qwen3-32B -2.5、o3 -1.2、Opus -0.4），仅 Gemini-Pro +2.3、Gemini-Flash +5.0、GPT-5.5 +0.2 为正，GPT-5.4 为 0；A2 在 7/10 为正，但 Opus -20.1、GPT-5.5 -7.4、GPT-5.4 -8.6（p.21）。这一条与 C1 合起来说明：**"澄清状态"本身不是稳定放大器，"可被攻击者回答的澄清通道"才是**。
  - **C3（防御）**：两种轻量防御降低但不消除。证据：Table 5/6；只在 Gemini-3-Flash 与 Gemini-3.1-Pro 上评估（p.24；p.7）。支持"结构性残余漏洞"，但不是对所有模型/攻击者的普遍结论。
  - **C4（机制）**：失败来自"被索取的输入被当作任务相关/可信"，而非澄清问题质量差或任务放弃。证据：on-target 问题后仍常出现 `TASK AND ATTACK`；`CONFUSED`/`PERSUADED` 比例在澄清通道更高（pp.27–28, 30；Fig.12–13）。这是**归因性/相关性证据**，不是因果中介分析。
- **因果解释的边界（本文最关键的方法论问题）。** 头条 `A4` 同时改变了交互状态（`p`→`p_base`、多一轮澄清）与投递通道（工具输出→`ask_user` 返回），所以它不能单独证明"歧义状态导致脆弱"。真正隔离状态的是 `A1`（`clarif tool` vs `exec tool`），而 `A1` 异质且多为负。以 o3 为例：Table 2 的 1.8→34.0 看似 +32.2 pp，但 Table 3 的 A1 只有 -1.2 pp，按作者分解，几乎全部来自 `ask_user` 通道效应（A4 31.3 = A1 -1.2 + 通道 32.5）。Gemini-Flash 的 A4 33.3 中 A1 仅 5.0；Kimi 的 A4 46.3 中 A1 为 -4.6。**因此标题中的 "seeking ambiguity clarification amplifies" 在因果上更准确的表述是 "solicited clarification response channel amplifies"**；论文 §5.2 与贡献 bullet 已有限定（"channel ... consistently amplifies ... state alone is heterogeneous"），但标题/摘要的措辞更强，容易被误读为状态因果。
- **"consistently" 的边界。** 按 Table 3：A4 9/10 为正（Opus 负）；A1 3/10 正、1 个 0、6 个负；A2 7/10 正、3 个负。因此"clarification-seeking consistently amplifies"只在"跨通道头条比较"的意义上近似成立；在"状态单独作用"与"用户通道状态作用"上都不一致。
- **统计推断的内部张力。** Table 3 同时报告 bootstrap 95% CI 与 exact McNemar p 值，但两者在个别格子不一致：Opus A4 = -0.9，CI [-1.9,-0.2] 不含 0，p=0.125；GPT-5.5 A1 = +0.2，CI [0.0,0.6] 不含 0，p=1.00。论文没有解释这两种推断为何冲突（小样本/低不一致对数下 percentile bootstrap 与 exact McNemar 可以不一致），也没有做多重比较校正。读者不应把 CI 与 p 值同时当作强证据。
- **结论。** 论文提供的是**经验性、比较性、行为级**的安全评估：在特定基准、模型、攻击算子和评分口径下，澄清通道显著提高了 ASR；它没有提供"永不泄漏"或"防御不可绕过"的形式化保证，也没有任何密码学安全声明。

## 7. 实验设置与主要结果（模型、任务、指标、关键数字、消融）

### 7.1 设置

- **数据**：728 个 `(U,I)` 组，四个 AgentDojo 套件；每组含原始 prompt、攻击目标、ground-truth 工具轨迹、`p_base`、缺失 slot、期望问题、benign 回答、安全动作；每条记录含 HR/GS/CP 三个注入变体（p.3–4；p.14）。
- **模型**：10 个 agent 模型：GPT-5.5、GPT-5.4、o3、Gemini-3.1-Pro、Gemini-3-Flash、Claude-Opus-4.7、Kimi-K2.5、Qwen3-235B、Qwen3-32B、DeepSeek-V3.2（p.6, §4.4；pp.16–17 给出 provider 标识，如 `openai/gpt-5.4`、`gemini/gemini-3-flash-preview`、`anthropic/claude-opus-4-7`、`fireworks_ai/kimi-k2p5`、`bedrock/qwen.qwen3-235b-a22b-2507-v1:0`、`fireworks_ai/deepseek-v3p2`）。
- **解码**：默认 provider API，无 prompt 修改；reasoning 模型 T=1.0（或 provider 默认），非 reasoning T=0.0；无随机种子；无缓存；每次评估重新调用（p.17）。
- **Judge**：主 judge Gemini-3.1-Pro，独立 judge GPT-5.4；固定 prompt、temperature 0；攻击是否成功以确定性 AgentDojo 评分为主，语义/部分完成时用 judge 辅助；证据不充分/间接/含糊时判为非成功（p.6；p.23, App G；p.28, App G.7）。
- **统计**：paired bootstrap B=1000（防御消融可到 2000）；exact McNemar；报告 95% CI 与双侧 p 值（pp.17–18）。
- **计算**：CPU-only + 外部 API；每组约 20–30 次 agent 调用、10–15 次 judge 调用；每模型约 18,000 次 agent 调用、10,000 次 judge 调用；8–40 小时/模型；主实验并行后约 3–4 天；日志约 3GB（p.18, App D.4）。

### 7.2 主结果：澄清态 `ask_user` 攻击

Table 2（p.20）与 Fig.2（p.5）的关键数字如下。`ΔA4` 与 `A1` 来自 Table 3（p.21）；`ΔA4` 是 `clarif ask user − exec tool`，`A1` 是 `clarif tool − exec tool`（状态效应）：

| 模型 | exec tool ASR | clarif ask user ASR | ΔA4 | A1（状态效应） |
|---|---:|---:|---:|---:|
| Opus 4.7 | 2.1 | 2.2 | -0.9 | -0.4 |
| GPT-5.5 | 0.0 | 4.9 | +4.9 | +0.2 |
| GPT-5.4 | 0.0 | 12.0 | +12.0 | 0.0 |
| o3 | 1.8 | 34.0 | +31.3 | -1.2 |
| Gemini-3.1-Pro | 1.1 | 24.3 | +22.9 | +2.3 |
| Gemini-3-Flash | 2.2 | 35.7 | +33.3 | +5.0 |
| Qwen3-235B | 41.9 | 63.2 | +18.8 | -7.8 |
| Qwen3-32B | 18.7 | 42.2 | +25.2 | -2.5 |
| DeepSeek V3.2 | 65.4 | 77.3 | +10.2 | -16.1 |
| Kimi K2.5 | 11.1 | 63.1 | +46.3 | -4.6 |

- 10 个模型的 `clarif ask user` ASR 范围为 2.2–77.3%；`exec tool` 为 0.0–65.4%；`clarif user` 为 47.8–90.6%；`exec user` 为 29.8–84.5%（p.20, Table 2）。
- Clarification rate 为 54.0–81.0%（p.20, Table 2）；进入澄清的子集为 393–590 例（p.19, App E.2）。
- **直接用户通道仍是最强攻击向量**：例如 Opus 的 `exec user` 75.7% 远高于 `clarif ask user` 2.2%；GPT-5.5 54.0% vs 4.9%；Gemini-3.1-Pro 74.7% vs 24.3%。只有部分模型（o3、Qwen3-235B、Kimi、DeepSeek）的 `clarif ask user` 接近或超过其 `exec user`（p.20, Table 2；p.7, §5.3）。因此"澄清通道是高影响新面"成立，但不能说它取代了直接用户注入。
- **问题选择控制**：限制到 10 个模型都调用 `ask_user` 的 n=68 组后，within-model 方向保持、跨模型排名 Spearman ρ=0.988（p.6, §5.1；pp.19–21, App E.2；Fig.7）。不过 Fig.7 中 Opus 为 0.0→0.0，原文"remains higher ... in every case"对 Opus 不严格成立（p.20–21）。

### 7.3 状态/通道分解（Table 3, p.21）

- **A1（tool 通道状态效应）**：Gemini-Flash +5.0、Gemini-Pro +2.3、GPT-5.5 +0.2、GPT-5.4 0.0、Opus -0.4、o3 -1.2、Qwen3-32B -2.5、Kimi -4.6、Qwen3-235B -7.8、DeepSeek -16.1。**6/10 为负**：在这些模型上，同样的工具注入在澄清态反而更不容易成功，作者解释为澄清阶段可能触发更严格的过滤/更低的信任（p.7）。
- **A2（user 通道状态效应）**：Qwen3-32B +25.4、Qwen3-235B +24.5、DeepSeek +11.7、Gemini-Pro +6.0、Kimi +3.6、o3 +1.7、Gemini-Flash +0.9；Opus -20.1、GPT-5.4 -8.6、GPT-5.5 -7.4。**7/10 为正，3/10 为负**：用户通道的状态效应也强烈依赖模型。
- **A4（头条跨通道）**：9/10 为正，Opus -0.9；最大为 Kimi +46.3、Gemini-Flash +33.3、o3 +31.3；最小正值为 GPT-5.5 +4.9。A4 的数值与 Table 2 两列直接相减可能不同，原因是配对子集/分母不同（见 §5.4 与 §13 的 "Table 2/3 分母差异" 行）。
- **结论**：状态效应与通道效应存在强交互；`ask_user` 通道是主要放大器，但"歧义状态"本身既可能放大也可能抑制脆弱性。论文的摘要/标题比其分解结果更强调"clarification"整体。

### 7.4 按套件泛化（Table 4, p.22）

- 对多数模型，澄清态 ASR 在 Workspace、Slack、Travel、Banking 四个套件都上升；例如 o3 的工具通道：Workspace 0.5→33.8、Slack 8.2→37.5、Travel 1.1→61.0、Banking 1.5→15.9；Gemini-3-Flash：0.2→29.4、7.2→65.7、3.2→51.1、3.9→21.9（p.22, Table 4；PNG 核对）。
- 例外存在：Opus 的 Travel 工具通道 16.0→10.9（下降），说明并非所有模型/套件都单调上升。总体支持"不是单一域的伪影"，但不是普遍定律（p.21–22）。

### 7.5 防御结果（Table 5/6, p.24；p.7, §5.4）

- **Gemini-3-Flash**：`clarif ask user` 35.7% → prompt guard 27.0% → tool filter 23.9%；`clarif user` 85.5% → 37.3%（guard）→ 63.2%（filter）；`exec user` 84.5% → 30.1% → 59.9%；`clarif tool` 7.4% → 2.2% → 1.3%（p.24, Table 5）。
- **Gemini-3.1-Pro**：`clarif ask user` 24.3% → 12.3% → 19.3%；`clarif user` 82.8% → 34.3% → 56.0%；`exec user` 74.7% → 30.4% → 54.7%；`clarif tool` 3.7% → 0.2% → 0.5%（p.24, Table 5）。
- **Utility 代价**：Gemini-Flash 的 `clarif ask user` utility 46.0% → 20.7%（guard）/40.6%（filter）；Gemini-Pro 69.3% → 39.6%/60.0%；prompt guard 在澄清条件下 utility 下降尤其大（p.24, Table 6）。这说明防御的"降 ASR"不是免费的，且 prompt guard 可能通过破坏任务信息来降攻击。
- **结构性残余**：tool 通道状态效应在防御后大多被压到约 0（如 Gemini-Pro 从 +2.6 到 ≈0，p.7；注意 Table 3 报 +2.3，见 §9），但 user 通道仍保留正 gap（prompt guard 下 +7.2 / +3.9）。`ask_user` 必须保留，prompt guard 只能移除显式注入片段，无法处理良性信息与指令交错的情况（p.7；p.22–23）。

### 7.6 行为分析（LLM-as-judge, App G）

- **澄清问题质量**：多数模型在相当比例样本上问 on-target 问题；GPT-5.4 与 Gemini-3.1-Pro 的 on-target 率最高，Qwen3 变体较低、off-target/无澄清比例更高（p.27, App G.6；Fig.9）。
- **失败形态**：攻击后常见 `TASK AND ATTACK`（同时推进 benign 与攻击目标），而不是 `ATTACK ONLY`；说明注入常被并入任务上下文，而非替换任务（p.7；p.27–28；Fig.10）。但 Table 1 的 utility 在 user 通道大幅下降（如 Opus 97.8→38.9），说明"良性任务仍完成"的理想并不总成立。
- **通道差异**：工具输出攻击多被 `IGNORED`/`ACKNOWLEDGED REFUSED`；`clarif user` 与 `clarif ask user` 的 full/partial compliance 更高（p.7；p.28；Fig.11）。
- **归因**：澄清通道的失败更多被标为 `CONFUSED`（把注入当作原任务）或 `PERSUADED`（意识到外部但因权威/必要性/任务相关性而执行）（p.30；Fig.13）。
- **on-target 不等于安全**：即使澄清问题完全命中缺失 slot，后续仍常出现攻击跟随；因此问题不是"问得不好"，而是"回答被当作可信任务输入"（p.7；Fig.12）。

### 7.7 人评与一致性

- 数据构造人评：200 样本、83 名标注者、99% correctness、AC1≈0.99（p.5；p.15）。
- Simulator 可靠性：200 样本、3 名独立标注者、>99% 认为回答正确、AC1≈0.99（p.16）。
- Judge 一致性：200 样本、3 名人类标注者；attack 字段 macro binary κb = 0.942（LLM–LLM）、0.905（Human–LLM）、0.775（human IRR）；`clarif ask user` 的 κb = 0.911/0.873/0.801；`clarif tool` 的 κm=κb=1.000（p.28；p.29, Table 7，PNG 核对）。utility 字段一致性较低（macro κm 0.581/0.540/0.505），作者归因于 utility 判断更主观（p.28）。

### 7.8 缺失的实验/消融

- **没有传统消融**：没有逐项移除 HR/GS/CP 算子、没有按 slot 类型（date/time、recipient、destination、identifier）报告 ASR、没有按 prompt 长度/删除词数做剂量–反应分析、没有模型规模消融。
- **没有自适应攻击**：作者明确未研究能观察澄清行为并调整策略的攻击者（p.8）。
- **防御只在 2 个模型上评估**（Gemini-3-Flash、Gemini-3.1-Pro），没有 10 模型全量；没有 defense-aware adaptive attacker；没有与更强防御（spotlighting、structured separation、capability-based/capability-flow 系统）对比。
- **没有真实部署/用户研究**：全部是 AgentDojo 模拟环境 + LLM user simulator；没有延迟、token 成本、用户满意度、过度澄清率。
- **没有复述 Agent scaffold/system prompt**：只说明沿用 AgentDojo，具体 prompt 依赖外部仓库；这会影响完全复现（本人核对）。

## 8. 贡献与创新点（按原文主张）

1. **首个"澄清放大注入"的系统研究**（p.1–2, Abstract/§1）：作者主张此前没有工作把 clarification 作为独立 Agent 状态、在匹配任务/攻击/环境/评分下测量其注入脆弱性。该主张的文献新颖性无法在本文内独立验证，但问题表述与实验设计是清晰的。
2. **ASPI 基准**（p.2, §1；pp.3–5）：728 个配对 task–attack 实例、四个域、系统化的单-slot 歧义构造流水线、8 个匹配条件、三种注入算子、共享前缀/分支协议。其"配对"设计使执行态与澄清态可在同一任务/攻击目标下比较。
3. **状态/通道分解**（p.2；pp.6–7, §5.2）：把头条差距拆成 `A1`（tool 通道状态效应）与 `A2`（user 通道状态效应），并指出 `ask_user` 通道是主要驱动、状态效应异质。这是本文最有分析价值的贡献，也限制了其标题的因果强度。
4. **澄清时防御评估**（p.2；p.7, §5.4；App F）：把 segment-level prompt guard 与 ask_user-aware tool filter 适配到澄清场景，证明"降低但不消除"，并量化 utility 代价。
5. **行为诊断**（p.7, §5.5；App G）：用 LLM-as-judge 给出 `CONFUSED`/`PERSUADED`/`TASK AND ATTACK` 等失败形态，提供机制层面的解释。
6. **可复现资源**：匿名代码/数据 `https://anonymous.4open.science/r/aspi-5074`（p.1；仅记录，未打开、未执行）；复用 AgentDojo；给出数据构造 prompt（App C.1）、评测 prompt（App G.5）、统计流程（App D.3）、计算资源（App D.4）。

**与直接相关工作的差异（按原文）**：

- **AgentDojo**（Debenedetti et al., 2024）：提供执行态、动态工具环境与确定性评分；ASPI 直接复用其任务/工具/评分，但新增"歧义–澄清"状态、配对条件与 `ask_user` 通道（p.3；p.11）。
- **InjecAgent**（Zhan et al., 2024）：单轮、工具输出注入；ASPI 是多步、有状态、澄清交互（p.11）。
- **ClariQ/AmbigQA/QuestBench/UserBench/ClarifyBench/LHAW**：研究 benign 澄清质量、缺失信息推理、多轮用户意图或欠指定任务价值；ASPI 研究这些交互的安全后果，作者称正交（pp.11–12）。
- **提示注入防御**（spotlighting、instruction hierarchy、execution isolation、prompt guard、tool filter）：ASPI 不提出新防御家族，而是测试已有轻量防御在澄清通道下是否仍有效，并强调结构性残余（p.11；p.22）。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

### 9.1 作者明确承认/写出的

- **合成歧义、单 slot、单轮**：只删除一个用户提供的信息，可能不覆盖多 slot、冲突信息、开放式语义不确定性、多轮澄清；因此报告的 ASR "likely underestimate"（p.3, §3.2；p.8, §6 Limitations）。
- **依赖 `ask_user` 原语**：不同 Agent 架构可能用自然语言轮次、无显式工具调用、或多 Agent 管道实现澄清；结果可能随之变化（p.8）。
- **威胁模型受限**：单一外部攻击者、不能访问 system prompt、不研究自适应攻击者；现实攻击者可能有更多 affordance（p.8）。
- **模型/域覆盖有限**：10 个模型、4 个 AgentDojo 域；不代表专用领域模型、微调变体、真实部署的多样性；扩展到更广架构/环境/真实部署是未来工作（p.8）。
- **防御只是轻量基线**：降低但不消除；`ask_user` 必须保留；prompt guard 只能移除显式注入片段；tool filter 不能移除必需工具；残余 ASR 仍存在，且有 utility 代价（p.7；p.22–23）。
- **社会影响/双用**：澄清通道可用于 exfiltration、向未授权端点发送内容、未授权交易，同时良性任务可能正常完成，难以发现；基准用于防御评估，使用标准注入技术，不引入新攻击能力（p.11, Societal Impacts）。

### 9.2 本人推断的局限/失效场景

- **"状态"与"通道"在头条比较中混杂**：A4 同时改变 prompt、轮数/交互状态与通道；真正隔离状态的 A1 异质且 6/10 为负。标题/摘要的"clarification-seeking amplifies"容易被读成状态因果，但数据更支持"可被回答的澄清通道放大"。作者在 §5.2 有限定，然而摘要/标题的措辞更强。这是本文最重要的解释性局限。
- **澄清子集的选择偏差**：澄清态 ASR 只在调用 `ask_user` 的 393–590 例上计算；不同模型进入澄清的样本不同。n=68 的 common subset 控制是好的稳健性检查，但只占 728 的约 9%，且 Fig.7 中 Opus 0.0→0.0，说明"every case higher"也不严格。
- **攻击真实性**：攻击回答由 Gemini 3.1 Pro 按固定算子生成，只做了"读起来自然"的 prompt 约束；没有对攻击消息做人类真实性/说服力评估，也没有与真实用户写作分布对比。simulator 的 99% 可靠性验证针对"回答是否解决澄清问题"，不等于攻击注入的自然度。
- **问题泄露**：攻击者回答澄清问题时可看到问题本身，问题会泄露缺失 slot/任务意图；论文没有测量这种信息泄露，也没有把它作为攻击能力的一部分。
- **Judge 自偏好/共享偏差**：主 judge Gemini-3.1-Pro 与被评估的 agent 模型重合；GPT-5.4 也是被评估模型。虽然主 ASR 以确定性评分为主，行为标签仍可能受 judge 自偏好影响；论文只报告一致性，没有做 judge 偏差实验。
- **Utility 指标窄**：只测任务完成，不测用户满意度、延迟、token 成本、过度澄清/打扰；澄清本身需要额外轮次，可能在实际部署中不可接受。Table 1 还显示 user 通道攻击下 utility 大幅下降，"良性任务仍完成"的理想并不普遍。
- **防御评估窄**：只 2 个 Gemini 模型；prompt guard 的分类器阈值/误报率未报告；tool filter 的"哪些工具看似需要"如何判定未详述，可能依赖任务上下文（其中可能已含攻击内容）；没有 defense-aware adaptive attacker。
- **没有按算子/槽位的 ASR 分析**：HR/GS/CP 哪个更有效、date/time 与 recipient 槽位是否更易攻击，均未报告；这限制了对"哪种澄清最危险"的理解。
- **统计多重比较**：10 个模型 × 3 个比较 × 多个条件，未做 family-wise correction；部分小效应（GPT-5.5 +4.9、Opus -0.9）在实践上是否重要不明确；CI 与 McNemar 在个别格子冲突（见 §9.3）。
- **没有密码学/系统级防御对比**：没有 capability token、签名来源、TEE、审计日志等；防御停留在输入过滤与工具裁剪，无法提供不可绕过的执行约束。
- **现实部署差距**：AgentDojo 的工具/评分是模拟的；真实系统有 OAuth、MCP、跨平台消息、多 Agent 管道，澄清回答的来源与权限更复杂；本文的 `ask_user` 是一个高度结构化的原语。

### 9.3 原文内部不一致/需警惕的数字（本人核对，不作为支持性证据）

1. **Opus 的"both settings"表述**：p.6 称 "Claude Opus 4.7 remain robust in both settings, with near-zero ASR"；Table 2（p.20）显示 Opus `exec user` 75.7%、`clarif user` 58.3%。若"both settings"仅指 Fig.2 的 `exec tool`/`clarif ask user`（2.1/2.2），则成立；若泛指 execution/clarification，则不成立。措辞含糊，易被误读。

## 11. 与应用密码学的可能联系（严格；没有就写“无”）

**论文实际使用：无。** 没有 OAuth/OIDC、TLS、签名、加密、MAC、TEE、capability token、审计日志或密钥管理。AgentDojo 的"用户/工具/环境"是模拟的，`ask_user` 没有认证；p.12 的"平台中介中继"只是威胁场景，不是已实现的密码协议。

**个人推断的工程接口（均标为推断，需新增设计与实验）：**

1. **认证澄清来源**：对 `ask_user` 返回/用户消息做签名或平台 attestation（如 WebAuthn、签名消息、SD-JWT VC），让 Agent 能区分"用户本人"与"被污染的中继/伪造回复"。作用：关闭 App B 的 platform-mediated relay 与 spoofed email 路径。局限：签名只认证来源，不认证语义意图；用户可能被社会工程后主动转发恶意内容；多 Agent 管道中"用户"本身可能是一个不可信组件。
2. **工具/内容来源证明**：对工具输出、检索文档、共享工作区内容做签名 provenance（C2PA/内容凭证、MCP server attestation、TLS），让 Agent 至少知道内容来自哪里。作用：帮助区分 trusted instructions 与 untrusted data。局限：签名不保证内容良性；攻击者可以在合法来源中放入恶意指令；模型仍可能忽略来源标签。
3. **工具边界的任务级 capability**：在 send/delete/transfer 等危险 API 前执行带 caveat 的 capability token（收件人、文件 id、金额、目的、有效期），由网关强制执行，而不是只靠 LLM 自觉。作用：即使注入成功，也能阻止超出用户委托范围的动作（如删除 id=49、向攻击者 IBAN 转账）。局限：自然语言任务难以自动推导精确策略；论文的 tool filter 只是非密码学近似；若攻击目标落在允许范围内（如给合法收件人发恶意内容），capability 无效。
4. **签名审计日志/透明日志**：记录 `(actor, recipient, item, tool, args, policy_id, timestamp)`，做哈希链/签名/透明日志，支持事后取证与归因。作用：检测 `TASK AND ATTACK`、追责、用户可验证。局限：事后检测，不预防；日志完整性不等于披露适当性。
5. **TEE/隔离规划器（dual-LLM 风格）**：把不可信内容的处理与高权限规划器隔离；TEE 可证明代码/配置完整性。作用：降低注入内容直接影响高权限动作的概率。局限：澄清回答必须被理解和使用；语义注入仍可影响隔离层输出；TEE 证明的是执行完整性，不是任务对齐。
6. **端到端加密用户–Agent 通道**：保护网络传输。作用有限：本文攻击是内容层/平台中继层，不是网络窃听；加密不能阻止合法通道中的恶意内容。

**伪交叉警告：**

- 只"加密澄清回答"不解决问题：Agent 必须解密并阅读内容，注入仍在。
- 只"签名回答"不解决社会工程：攻击者可让合法用户/平台代签或转发。
- 只把 OAuth scope 套在 Agent 上通常太粗：本文攻击多使用允许的工具与恶意参数（删除指定文件、向指定 IBAN 转账），需要参数级/任务级策略，而不是仅工具级 scope。
- 用 ZK 证明"Agent 运行了某步骤"证明的是计算完整性，不是"披露/动作适当"。
- 把 contextual privacy/ASR 当密码学安全度量是错的；差分隐私、不可区分性等与本文的语义注入问题没有自然对应。

**相关度判断（本人推断）**：按项目 `A_crypto` 量表，本文正文约 **0–1**（没有识别任何密码机制使用点；唯一的"授权"是模拟环境预设）；若把"认证澄清来源 + 工具边界 capability + 签名审计"做成可运行原型并在 ASPI 上量化安全/utility/性能收益，可到 2–3，但这是新增系统研究，不是本文贡献。

## 12. 可检验的研究假设（3–6 条）

以下均为**假设/推断**，需查证外部文献；本文未做，不等于无人做过。

- **H1（认证来源降低平台中继攻击）**：若对 `ask_user` 回答/用户消息加签名或平台 attestation，并要求 Agent 只把已验证来源的内容当作"用户指令"，则 App B 的 platform-mediated relay 与 spoofed email 路径的 ASR 应显著下降；但环境投毒 + 人工转述（用户本人被诱导）可能不受影响。实验：在 ASPI 中增加 signed/unsigned 两个版本，按通道分层比较 ASR 与 utility。
- **H2（"被索取"本身是否放大）**：把同一段恶意文本分别放在"Agent 主动提问后的回答"与"同一轮的非索取用户消息"中，保持内容、位置、长度、角色相同，检验"被索取"是否独立于"用户通道/时机"提高 ASR。若差异消失，则本文的放大主要来自用户通道而非澄清状态。实验：新增 `clarif user` 的 matched "unsolicited" 对照，测量 ΔASR。
- **H3（防御的 Pareto 前沿）**：在全部 10 个模型上比较 prompt guard、tool filter、两者组合，预测 prompt guard 降低 ASR 更多但 utility 代价更大，tool filter 保留 utility 但 `ask_user` 通道残余更高；组合可能接近但无法消除残余。实验：2×2 设计，报告 ASR/utility/澄清率/延迟的 Pareto 前沿。
- **H4（自适应攻击者提高 ASR）**：允许攻击者观察 Agent 的澄清问题与历史行为，迭代优化注入（模仿用户风格、拆分指令、绕开 segment 过滤器），预测 ASR 高于固定 HR/GS/CP 算子，尤其在 prompt guard 下。实验：用搜索/反馈循环优化攻击文本，比较静态 vs 自适应，报告查询预算与迁移性。
- **H5（多 slot/多轮放大）**：把单 slot 扩展为多 slot、多轮澄清，预测 ASR 更高、`TASK AND ATTACK` 比例更高、防御残余更大；单 slot 结果是下界。实验：构造 multi-slot/multi-turn 版本，保持任务与攻击目标，比较 ASR 与 utility。
- **H6（澄清问题泄露任务信息）**：测量 Agent 的澄清问题向"可回答的恶意方"泄露多少缺失 slot/用户意图；预测问题越具体，攻击者的注入越有效，形成"可用性–安全性"权衡。实验：让恶意 responder 只看到问题（不看原任务）来生成注入，比较 ASR 与问题具体度的关系。
