## 1. 150–300 字中文概述

论文把多 Agent 轨迹失败分析从“事后归因”改写为“在线审计”：审计器在轨迹展开的每一步只观察前缀 τ0:k，输出 CONTINUE 或 ALARM，并在报警时给出最早的决定性错误步 k̂ 与责任 Agent â。作者构建 AFTRAJ-2K（2,272 条 Coding/Math/Agentic 轨迹，含严格筛选的安全轨迹与多 LLM judge 标注的失败轨迹），并用 Qwen2.5-7B-Instruct 做 coarse-to-fine 训练：先用相邻安全/不安全前缀对做 BPPO 边界对齐，再用 what/where/who 三轴奖励的 GRPO 锐化步级定位。在 AFTRAJ-2K 上 Exact-F1 66.44、ASS 0.59；在 Who&When 上 Step-Acc 57.69、Agent-Acc 73.08、ASS 1.62。全文是可靠性监控与经验评测，不含密码学原语、形式化安全定义或证明。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景**：LLM 多 Agent 系统被用于长程任务（软件、数学、Web/QA），每一步都以上一步输出为条件；一个 decisive error（如错误工具调用、错误中间推理）会被下游 Agent 接受并级联为整条轨迹失败（p.1, §1）。部署后还会触发工具调用、文件写入、外部 API 等不可逆副作用（p.1；p.9 Impact Statement）。
- **现有方法及不足**：现有工作几乎都做 **post-hoc failure attribution**：在轨迹已经失败后，输入完整 τ 与 Ω(τ)=0，输出单个 (k̂, â)。Who&When（Zhang et al. 2025c）、AgenTracer（Zhang et al. 2025b）训练/提示模型在事后定位 decisive step；AgentDebug（Zhu et al. 2025）分析完整轨迹并给纠正反馈（pp.2–3, §1/§2；pp.18–19, App C）。其三点结构性缺陷是：(i) 全 hindsight，能看到未来步与终局标签；(ii) 单次输出；(iii) 预测发生在失败已materialize之后，没有干预窗口（p.3, §2）。
- **数据缺口**：在线审计需要 (i) 失败轨迹的逐步 ground truth (k*, a*)，(ii) 经过验证的安全轨迹以提供每个前缀的正监督，(iii) 跨异构 MAS 框架与任务域的覆盖。Who&When 只有失败轨迹、没有安全轨迹；ATBench 有安全/不安全但偏安全任务且只有轨迹级标签（p.3, §3.1）。直接把 post-hoc 模型逐前缀重跑是 ill-posed，因为它们训练时假设已经观察到 Ω(τ)=0（p.3, §2）。
- **精确定义的问题**：学习一个在线审计器 `f_online(τ0:k) ∈ {CONTINUE} ∪ {ALARM} × {0,…,k} × N`，在每个前缀只凭可见窗口判断是否已出现 decisive error；若已出现，必须在**该错误发生的步**报警并给出责任 Agent，而不能等到事后（p.3, Def. 2.2）。这带来两个耦合要求：① 可靠区分仍安全的前缀与已越过 decisive error 的前缀；② 在错误发生的当步 commit，而不是 hindsight 定位（p.2, §1）。
- **重要限定（本人判断）**：标题中的“early failure prediction”容易被理解为“预测未来会不会失败”；但定义与实验实际做的是**对已经 commit 的 decisive error 做最早可观察前缀上的检测与定位**，没有预测未来失败概率、失败时间或风险分数。所谓“early”是相对于“轨迹结束后的 post-hoc 归因”，不是“错误发生之前”。Stage 1 的“risk-anticipation prior”也只是表示层面的先验，不是概率预测。这个语义差别影响 §6 与 §10 的判定。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **轨迹模型**（p.2, §2, Eq. 1）：`M = (S, N, π_sys, Ψ, Ω)`；S 为系统状态，N 为有限 Agent 角色集合（Planner、WebAgent、CodeWriter 等），π_sys 为给定当前状态产生下一 turn 的系统策略，Ψ 为状态更新函数，Ω: T → {0,1} 为轨迹终局成功/失败判定。观测轨迹为 `τ = (t0,…,tN−1)`，`ti = (role_i, action_i, content_i)`，其中 role_i ∈ N，content_i 是该动作产生的可观测内容。
- **三类具体 MAS 模板**（p.16, App B.3.1）：
  - Coding：AutoGen Swarm，两个角色 CodeWriter 与 CodeTester，按需 handoff，终止哨兵 `FINAL_VERIFIED_TESTS_PASSED`；任务为 HumanEval+ 与 MBPP+。
  - Math：同一 AutoGen Swarm 模板，MathSolver 与 Verifier，终止哨兵 `ANSWER_VERIFIED`；任务为 MATH-500。
  - Agentic：Smolagents，CodeAgent Manager 把 web search 与 Wikipedia retrieval 委托给 ToolCallingAgent `search_agent`；任务为 GAIA 与 HotpotQA；GAIA 附件按文本解析、图片 base64、音频 Whisper 转写后注入 prompt。
  - 所有子基准统一使用 GPT-5.4-mini backbone、greedy decoding、每任务最多 40 步（p.16）。
- **交互流程**：turn-based；角色可 handoff；Manager 规划并委托，search_agent 返回检索结果，Manager 汇总并 final；Math/Coding 由 Verifier/CodeTester 独立复核并输出哨兵。审计器不参与执行，只读前缀并给 verdict（p.3, §2；p.16）。
- **审计器的位置**：外部进程，"runs alongside" 被审计的 MAS；不修改 agents、tools 或 inter-agent protocol，把系统当 black box（p.18, App C；p.28, App G）。每个前缀独立调用，系统 prompt 与 incremental-view user prompt 对所有 baseline 一致（p.17, App B.3.3）。
- **信任边界**：原文**没有独立的 trust-boundary 图或威胁模型**。可辨识的边界是：审计器被视为独立、可信的观察者；被审计 Agent 被视为**合作但会犯错**，不是恶意对手；轨迹文本（包括工具返回）是审计器的输入，但原文没有把它当作不可信数据。角色 `role_i` 只是轨迹中的字符串，没有身份认证；因此“who”轴的归属在对抗环境下可被伪造（此点为本人推断）。数据构造使用的 GPT-5.4-mini/5.4 judge、评测标签、审计器本身都被默认可信。
- **“safe”的语义**：p.4 脚注 1 明确说明，本文的 safe 指“成功完成且不含任何一步的纠正会改变结果”，**区别于 RLHF 文献中的 safety/alignment 用法**。这是理解全文安全属性的关键：这里的 “unsafe” 是任务失败轨迹，不是有害/违规/被攻击轨迹。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：任务正确性/终局 Ω；轨迹完整性（不被 silent error 污染）；干预窗口（在 tk+1 commit 之前 halt 的机会）；计算与外部工具资源（避免继续消耗，p.2）；以及部署方的运行信任。论文没有把“用户数据/密钥/权限”列为资产。
- **攻击者**：**没有**。本文不是攻击论文，也没有对抗性威胁模型。它研究的是“合作但会犯错的 Agent 产生一个 decisive error 并级联”的**可靠性失败模型**（p.1–2）。没有恶意 Agent、恶意工具、外部攻击者、投毒、后门、共谋、侧信道或资源耗尽模型。
- **如果强行套用安全威胁模型（本人推断，不是原文）**：可以把“产生 decisive error 的 Agent”视为故障源，把“希望轨迹失败/被误判”的一方视为对手；但原文没有给出对手目标、能力、预算、知识或成功判据。Broader Impact 只把 adaptive evasion 列为部署风险（“agents whose training signals overlap with auditing signals could attempt to mask decisive errors behind auditor-friendly prefixes”，p.29），没有实验。
- **防御者能力**：训练一个 7B 外部审计器；可在每个前缀查询；可设置 CONTINUE/ALARM 阈值（但论文固定 FAR≤20%、Step-Acc≥50% 的 deployable region，p.20）；不修改被审计系统。审计器可读完整前缀（含工具返回与 Agent 推理文本），但不能读未来步、终局标签或 oracle correction。
- **前提假设**（分散在 §2、§3.1、App B.3、App H）：
  - decisive error 存在、可定义、可标注；存在一个 admissible correction 与 downstream rollout 使 Ω 翻转为 1（Def. 2.1）。
  - 每条失败轨迹以**最早** decisive error 为监督目标；成功轨迹在每个前缀都是 SAFE（p.3–4）。
  - Agent 的失败是“自然/可注入”的，不是对抗性优化出来的；工具与框架行为可复现。
  - 轨迹级 train/test split 按 family 分组，safe 轨迹及其注入变体在同一 partition，防止泄漏（p.6；p.15 Table 3 caption）。
  - LLM judge（GPT-5.4）能可靠标注 (k*, a*)；多 judge 投票可替代人工 ground truth（p.5；p.16）。
  - 评测环境是 benchmark 沙箱，不产生真实世界副作用（p.9 Impact Statement；p.29 Broader Impact）。
- **威胁模型位置**：原文没有 “Threat Model” 小节；只有 §2 的问题形式化、§3.1 的数据构造、App B.3 的实现细节与 App H 的限制。若在笔记/论文中引用，应写“无对抗威胁模型，仅有非对抗 failure model”。

## 5. 核心方案：online audit、早期预测、特征/模型、训练

### 5.1 任务与输出

- 审计器在每个前缀 `τ0:k` 输出：`CONTINUE`，或 `ALARM` 加预测的 decisive step `k̂ ∈ {0,…,k}` 与责任 Agent `â ∈ N`（p.3, Def. 2.2）。SAFE verdict 时 `k̂=SAFE`、`â` 与 `reason` 为 null（p.5–6）。
- 推理时严格 step-by-step incremental walk：每个前缀都查询，greedy decoding；第一个带可解析 step index 的 ALARM 记为预测步；所有轨迹都走完整长度以暴露 false alarm（p.6, §4.1；p.17, App B.3.3）。
- 输出格式为两段式 `<think>…</think><answer>{JSON}</answer>`，JSON 含 `answer`（step int 或 "SAFE"）、`agent`、`reason`（p.22–24, App E）。

### 5.2 AFTRAJ-2K 数据构造（pp.3–5, §3.1；pp.13–16, App B）

1. **收集**：在 AutoGen/MetaGPT/Smolagents 上跑 Math/Coding/Agentic 任务，得到 `D_succ` 与 `D_fail`（Eq. 5）。
2. **安全轨迹筛选**：三个二值谓词 `F = {outcome, integrity, coherence}`（Eq. 6）。`φ_outcome` 用 sympy 符号等价（Math）、GAIA 官方 scorer（GAIA）、保守人名/地名归一化（HotpotQA）、子进程测试 15 s 超时（Coding）；`φ_integrity` 拒绝工具错误、序列化失败、空预测、环境受限终止；`φ_coherence` 用 GPT-5.4 judge 检查每 turn 是否对齐声明的 sub-goal（p.4；p.16）。只有全部通过才进入 `D_safe`，并在每个前缀标 `(SAFE, ∅)`。
3. **constructive stream（注入失败）**：从 `D_safe` 采样注入步 `k_inj ∈ {1,…,|τ|−2}` 与 fault category c，生成错误 turn 后 re-roll 系统；若 Ω(τ̃)=0 且目标 turn 确实被改，则接受，标签 `(k*, a*) = (k_inj, a_kinj)`（p.4–5, Eq. 7；p.16）。fault catalog：Math 4 类（computation_slip、premature_finalization、verification_shortcut、verdict_misread）；Coding 3 类（code_bug、verification_skip、verdict_misread）；Agentic 包括 tool_injection、prompt_injection、verification_shortcut、solver_premature_verdict、verifier_text_shortcut、final_verdict_override。实现有 turn-rewriting（短程 Math/Coding）与 live-replay（工具增强 Agentic）两种模式（p.16）。
4. **diagnostic stream（自然失败定位）**：对 `D_fail` 用 propose-and-verify：P=5 个 proposer 调用给出候选 `(k_cand, a_cand)`，V=3 个 verifier 按四个二值标准 `(s_exists, s_substantive, s_decisive, s_earliest)` 复核；候选的 strict-support 计数（四个标准同时成立的 verifier 数）达到 `⌊V/2⌋+1 = 2` 才接纳；每个轨迹取 strict-support 最高者，平局用 verifier confidence 打破；proposer/verifier 均为 GPT-5.4、温度 0.2（p.5, Eq. 8；p.16）。最终 `D_unsafe = D_fail_inj ∪ D_fail_nat`。
5. **规模**：2,272 family-level 轨迹；safe 1,158、unsafe 1,114；train 1,940、test 332；Coding 608（safe 361/unsafe 247，train 517/test 91，平均 10.0 turns）、Math 792（395/397，676/116，16.2 turns）、Agentic 872（402/470，747/125，8.4 turns），总体平均 11.5 turns（p.13–15, Table 3）。另有 Who&When 外部基准 127 个 MAS（p.14, App B.1）。

### 5.3 Stage 1：Failure-Boundary Alignment（BPPO）

- 对每个 unsafe `(τ, k*, a*)` 构造两个只差一个 turn 的边界对：pre-boundary `τ0:k*−1` 的最优 verdict 是 CONTINUE；post-boundary `τ0:k*` 的最优 verdict 是 ALARM(k*, a*)（p.5, §3.2）。两者形式相似但要求逻辑相反的 verdict，用来隔离 “failure boundary” 这一显著信号。
- 用 base policy 采样 chosen/rejected responses，按解析出的 verdict 分类；数据按 prompt 位置分为 `D_BS` 与 `D_BE` 两个子集联合优化（p.5, Eq. 9）：
  `L_BPPO(π_θ; π_ref) = − Σ_{c∈{BS,BE}} E_{(x,v*,v)~D_c}[ log σ(β Δ_θ(x,v*,v)) ]`，
  其中 `Δ_θ(x,v*,v) = log π_θ(v*|x)/π_ref(v*|x) − log π_θ(v|x)/π_ref(v|x)` 是 implicit-reward margin。联合最小化迫使 π_θ 在 decisive step 处翻转 verdict，得到 `π_θ1` 作为 Stage 2 初始化。
- 规模/超参：1,902 boundary pairs；β=0.1；lr 5×10⁻⁷；3 epochs；effective batch 16（1×16 grad-accum）；8-bit AdamW；cosine + 50-step warmup；max prompt 8,192；bfloat16；gradient checkpointing；2×H200 FSDP（p.6, §4.1；p.17, Table 4）。

### 5.4 Stage 2：Three-Axis Verdict Sharpening（GRPO）

- 每个 rollout 产生结构化 verdict `ŷ = (k̂, â, r̂)`；对 SAFE verdict，`k̂=SAFE`，`â,r̂=null`（p.5–6）。
- 三轴奖励（p.6, Eq. 10–11）：
  - **what（结构）**：二值格式门 `G(ŷ) ∈ {0,1}`，检查 schema、JSON well-formedness、content grounding。
  - **where（时序）**：`r_step(k̂,k*) = exp(−(k̂−k*)²/(2σ_step²))`，以 ground-truth step 为中心的高斯。
  - **who（因果）**：`r_agent(â,a*)`，角色完全匹配给满分，不匹配给部分分。
  - 组合：`R(ŷ,y*) = G(ŷ)·R_content(ŷ,y*) − η_G·1(1−G(ŷ))`；`R_content` 对正确 SAFE 给 +1，对正确 ALARM 给 `w_s r_step + w_a r_agent`（w_s+w_a=1），对跨类错误给 −1。类对称 ±1 防止 class-bias drift；格式违规的软惩罚保留早期梯度。
- GRPO 目标（p.6, Eq. 12）：`L_GRPO(θ) = −E[min(ρ_{j,t}(θ)A_j, clip(ρ_{j,t}(θ),1−ε,1+ε)A_j) + β_KL D̂_KL(π_θ‖π_θ1)]`；token-level importance ratio；reference policy 锚定在 Stage 1 checkpoint `π_θ1`（不是 base），使 KL 把策略拉回 risk-anticipation prior；KL 用 low-variance k3 estimator。
- 规模/超参：1,940 prompts × G=8 rollouts；lr 1×10⁻⁶；8 epochs；effective batch 32；β_KL=10⁻³；max prompt 8,192、max response 4,096；verl + vLLM，rollout T=1.0/top-p=1.0，validation greedy T=0.1；2×H200（p.6；p.17, Table 4）。
- **设计理由（App G, p.28）**：外部审计器优于 Agent 自反思，理由包括 generator-verifier asymmetry、自反思继承同一 posterior/blind spots、自反思与主任务竞争导致 over-correction/oscillation、外部审计器可热插拔/独立校准/避免 monitor signal 反馈造成 obfuscated reward hacking；经验锚点是同 backbone 的 Reflexion-7B 只有 23.38 Exact-F1/3.17 ASS，而本文 66.44/0.59（2.84×/5.4×）。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

- **形式化对象**：论文给出了轨迹模型（Eq. 1）、decisive error 的反事实定义（Def. 2.1, Eq. 2）、online auditor 的函数签名（Def. 2.2, Eq. 4），以及 Exact-F1/ASS 的指标定义（Eq. 13–14）。这些是**机器学习/序列决策问题的形式化**，不是安全定义。
- **没有的形式化**：全文没有 theorem、lemma、proof、reduction、security game、adversary model、advantage 定义、soundness/completeness 定义或校准保证。没有证明“审计器不会漏报/误报”，也没有证明“报警后系统一定可恢复”。所有效果都是经验指标。
- **“安全”主张的实际内容**：论文主张的是**可靠性/部署监控**效果：在 AFTRAJ-2K 上 Exact-F1 66.44、ASS 0.59；比最强 proprietary baseline DeepSeek-V4-Pro（46.56/1.77）高 19.88 分、ASS 紧 3×；在 Who&When 上 Step-Acc 57.69、Agent-Acc 73.08、ASS 1.62（p.7, Tables 1–2）。这些是 empirical claims，不是 security guarantee。
- **“safe/unsafe” 的语义**：p.4 脚注明确 safe 是“成功且无任何一步的纠正会改变结果”，不是 safety/alignment。因此论文的 “unsafe trajectory” 是**失败轨迹**，不是有害/被攻击轨迹；“auditor” 是 failure detector，不是 security monitor。把本文的 “safety” 直接映射到 Agent Security 的 adversarial safety 会误读。
- **干预主张的边界**：论文反复说 ALARM 创造 “intervention window”（p.3, p.8, p.9, p.29），但**没有实现干预**（halt/rollback/repair），也没有闭环实验测量“报警后失败是否被阻止、损害是否降低”。它只预测错误步；预测 ≠ 预防。这是 §9 的核心限制。
- **形式化程度评级（本人判断）**：中等偏低的 ML 形式化（定义 + 目标函数 + 指标），无安全证明。可复现性依赖 GPT-5.4 系列闭源模型与 2×H200，非完全可复现。

## 8. 贡献与创新点（按原文主张）

1. **问题重构**：提出 online auditing，把 agentic failure analysis 从“完成后归因”改为“部署时逐前缀 continue-or-alarm”；审计器不看未来步、工具响应或终局，必须在错误 commit 的当步报警（p.1–3, Abstract/§1/§2）。这是概念层面的主要贡献。
2. **数据集**：AFTRAJ-2K，2,272 条 family-level 轨迹，覆盖 Coding/Math/Agentic；安全轨迹经三谓词严格筛选，失败轨迹经 constructive injection 或 diagnostic propose-and-verify 获得步级 `(k*, a*)` 标注；同时提供 safe 与 unsafe 两类监督，填补 Who&When 只有失败轨迹、ATBench 只有轨迹级标签的缺口（p.3, §3.1；pp.13–16）。
3. **训练 recipe**：coarse-to-fine。Stage 1 用 adjacent safe/unsafe boundary pairs 做 BPPO，先学 failure boundary 的 risk-anticipation prior；Stage 2 用 what/where/who 三轴奖励的 GRPO，把 prior 锐化为步级定位；KL 锚定 Stage 1 checkpoint 而非 base（p.5–6, §3.2）。
4. **经验结果**：在 AFTRAJ-2K 上 66.44 Exact-F1、0.59 ASS，超过 GPT-4.1、DeepSeek-V4-Pro 等 proprietary judges 与同 backbone 的 post-hoc AgentDebug-7B；在 Who&When 上 Step-Acc 57.69、Agent-Acc 73.08、ASS 1.62；并给出 FAR/Step-Acc 部署 trade-off 与 per-call 成本（p.7；p.20–21）。
5. **设计论证**：App G 系统论证“外部审计器 vs Agent 自反思”，用同 backbone 的 Reflexion-7B 做经验锚点（23.38/3.17 vs 66.44/0.59），把性能差归因于 audit paradigm 而非模型规模（p.28）。

**与直接相关工作的差异**：Who&When 是 post-hoc benchmark，只有失败轨迹；AgenTracer 用 counterfactual replay/fault injection 训练 tracer，但仍在完整轨迹上；AgentDebug 看完整轨迹并给纠正反馈，在线协议下 Exact-F1 只有 9.63；runtime monitoring 线（Kale et al. 2025、Baker et al. 2025、SHADE-Arena）多是 trajectory-level 或 sabotage 检测，本文是 per-step structured verdict +  curated decisive-error supervision；step-level critic 线（PRM800K、Math-Shepherd、ProcessBench）输出 scalar score，本文输出 `(label, step, agent)` 三元组并直接作为 deployment monitor（pp.18–19, App C）。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

**作者明确承认的**：
- 在线协议要求每个前缀都查询，相对 one-shot post-hoc 有持续的 operational dependency；为了可 colocate 才保持 7B；不做 per-step instrumentation 的部署不在 scope（p.28–29, App H）。
- 域覆盖仍限于 Coding/Math/Agentic（web/QA）；long-horizon embodied agents 与 open-ended scientific discovery 未覆盖，是 failure-attribution 领域的共同开放问题（p.29）。
- Broader Impact 承认两类负效应：deployment-time auditor 会激励 evasion、形成 generative agents 与 runtime monitors 的 arms race；false alarm / missed detection 在 distribution shift 下有下游代价。建议与 post-hoc attribution audits、provenance logs 组合，暴露 calibrated alarm confidence，不要把 verdict 当 hard kill switch，安全关键场景加 human-in-the-loop（p.9；p.29）。
- 没有独立的主文 Limitations 章节；限制集中在 App H 与 Broader Impact。

**本人推断的局限/失效场景**：
- **没有对抗威胁模型**：全文没有 attacker、攻击实验、自适应 evasion 评估。Broader Impact 只把 evasion 写成风险，没有测。若用于安全场景，攻击者可优化“auditor-friendly prefix”（把错误拆成多步、用看似合理的推理包装、在工具返回中注入让审计器困惑的内容），论文的 Exact-F1/FAR 不构成鲁棒性证据。
- **没有闭环干预**：论文只预测 decisive step，没有实现 halt/rollback/repair，也没有测量“报警后任务是否被救回、损害是否降低”。所谓 intervention window 是概念性的；false alarm 的成本（中断 safe 轨迹）与 missed detection 的成本没有 end-to-end 度量。
- **标签的可信性**：diagnostic stream 的 `(k*, a*)` 由 GPT-5.4 proposer/verifier 以 2-of-3 产生，没有人工 IAA、没有人工抽检、没有执行式 counterfactual 验证；constructive stream 的 fault 由 GPT-5.4-mini 生成、judge 由 GPT-5.4 判定，存在同家族模型的循环偏差。Definition 2.1 的反事实“存在 correction 使 Ω=1”在自然失败轨迹上不可计算，标签只是近似。
- **safe 筛选是代理**：`φ_outcome/φ_integrity/φ_coherence` 并不直接验证“没有任何一步的纠正会改变结果”；被下游恢复的 silent error 仍可能留在 D_safe，从而给审计器错误的 CONTINUE 正监督（p.4 自己提到这个风险，但三谓词并不能完全排除）。
- **单一 decisive error 假设**：Def. 2.1 只取最早一步；真实失败常有多因、多错误、错误相互掩盖。标“最早”在 LLM judge 之间也可能有分歧（论文用 2-of-3 掩盖了分歧）。
- **指标脆弱**：Exact-F1 要求 step 完全匹配，off-by-one 即算错；Agentic 域只有 48.70，说明边界模糊时定位仍难。ASS 只在 U_det 上平均，少报警的模型会获得虚低 ASS（Stage 2 alone 在 Math/Coding 的 0.03/0.17 就是例证，p.20 作者也承认它“raises very few alarms but places them precisely”）。
- **无统计推断**：没有 CI、seed 方差、显著性检验；test 只有 332 families（FAR 的 4/169 说明 safe test 子集更小）。Table 1/2 的小数点差异（如 66.44 vs 66.4）不能支撑细粒度排名。
- **Case study 与正文不一致**：p.8 正文说 Fig. 5 的 decisive error “commits at Step 3, where the search_agent returns the wrong town Horwich”，但 Fig. 5 中 search_agent 返回 Horwich 是 **Step 5**，AgentForesight 也返回 Step 5；Step 3 是 Manager 的 “Target attribute: nearby former mill town”。同一段又说 “AgentForesight-7B alone returns Step 5”，因此 “Step 3” 很可能是笔误。该不一致不影响主表，但说明定性分析需以图为准。
- **Table 1 caption 的口径问题**：caption 说 “AgentDebug-7B detects zero unsafe trajectories with no step-shift samples to average”，但表中 AgentDebug 在 Coding 有 28.57 Exact-F1、ASS 4.05；只有 Math 是 0.00/—。因此 “zero unsafe trajectories” 应理解为“在 Math 上零检出”，不是全数据集零检出。引用时需限定域。
- **Eq. 8 阈值措辞**：公式用 `≥ ⌊V/2⌋+1`，正文 p.5/p.16 写 “exceeds the majority threshold ⌊V/2⌋+1 = 2”；V=3 时 “exceeds 2” 字面是 ≥3，与公式的 ≥2 冲突。应以公式为准。
- **“early prediction” 的过度表述**：见 §2；论文没有 forecast horizon、失败概率、time-to-failure，只有“已 commit 错误的最早检测”。标题的 “prediction” 会误导读者以为可以提前预知尚未发生的失败。
- **审计器自身的攻击面**：审计器读取完整前缀（含工具返回、Agent 推理文本）。若工具输出含间接 prompt injection，审计器可能被诱导输出 SAFE 或错误 step；论文没有测。角色名只是字符串，who 轴可被伪造；没有身份认证/签名。
- **效率口径**：1.03 s/call × 平均 11.5 turns ≈ 12 s/trajectory；40 步上限时约 41 s；论文没有报告端到端吞吐、并发、显存、长轨迹的排队延迟。4.73 s/call（RTX 4500 Ada）只出现在正文，未进 Table 7。
- **可复现性**：依赖 GPT-5.4-mini（数据生成）与 GPT-5.4（judge）、DeepSeek-V4 系列等 2026 年闭源模型；代码只在 supplementary，未给公开 repo（p.13 只说 “include our source code in the submitted supplementary materials”）；AFTRAJ-2K 未声明独立下载地址。完全复现受 API 版本与随机性影响。

## 10. 与理论密码学的可能联系（严格；没有就写“无”）

**无。**

- 论文没有使用任何密码原语：没有加密、签名、MAC、承诺、零知识、MPC、FHE、TEE、匿名凭证、哈希链或密钥管理。
- 论文没有密码学意义上的形式化安全定义：没有 adversary、security game、advantage、indistinguishability、soundness/completeness、reduction 或 theorem/proof。Def. 2.1/2.2 是轨迹与在线决策的数学定义，不是安全定义。
- 这里的 “audit” 是 ML/oversight 意义上的 runtime monitoring，不是 cryptographic audit（可验证计算、attestation、transparency log、proof of execution）。这里的 “decisive error” 是任务正确性意义上的反事实错误，不是密钥/明文/完整性被破坏。
- 若要做理论连接，需要新增研究：把“审计器 + 可能作恶的 Agent”建模为带部分可观测的序贯博弈，定义 detection soundness/completeness 或 evasion advantage，并证明某个 monitor 的保证。但这属于安全博弈/序贯检测理论，不是密码学；而且核心对象是自然语言语义错误，密码学的代数工具不能直接处理。该段为本人推断，不是论文内容。
- 特别警告：不要因为标题含 “auditing” 就把它归为“可验证审计/密码审计”；也不要把它与 “proof of inference”“zkML” 类比——本文没有证明任何计算。

## 11. 与应用密码学/密码工程的可能联系（严格；没有就写“无”）

**论文实际使用：无。** 没有 OAuth/OIDC、签名、加密、TEE、远程 attestation、capability token、Merkle/透明日志、密钥管理或任何密码协议。p.16 的 “GAIA 附件 base64/Whisper” 只是数据处理，不是密码机制；p.17 的 API 调用是普通 HTTPS 客户端，不是论文贡献。

**个人推断的工程接口（均需新增设计与实验，不是论文已做）**：
1. **防篡改审计日志**：对每次 verdict 记录 `(trajectory_hash, prefix_hash, k̂, â, model_version, threshold, timestamp)`，用哈希链/签名/append-only transparency log 保存。作用：事后可验证“审计器当时看到了什么、报了什么”，支持取证与问责。局限：只证明日志完整性，不证明 verdict 正确；审计器本身可能错。
2. **轨迹来源认证**：对每个 turn 的 `(role, action, content)` 与工具返回做签名/attestation，绑定 Agent 身份与执行环境。作用：让 “who” 轴的 `â` 可信，防止一个 Agent 伪造另一个角色的 turn；当前 role 只是字符串。局限：语义错误仍可能由合法身份的 Agent 产生；签名不判断内容对错。
3. **审计器运行时 attestation**：用 TEE/远程 attestation 证明部署的是声称的 7B 模型、prompt、阈值与代码。作用：防止运营方偷偷换弱审计器或改阈值。局限：证明的是 code identity，不是检测质量；模型权重/提示的语义等价性仍难验证。
4. **轨迹与日志的机密性**：轨迹可能含用户数据、代码、检索内容；静态/传输加密、TEE 内推理、字段级 redaction。作用：避免审计日志成为新的泄漏面。局限：审计器需要明文前缀才能推理；加密不阻止模型层泄漏。
5. **报警/干预的授权**：对 halt/rollback 命令做签名与权限控制（谁有权停哪条轨迹、是否需要双人审批），把 “auditor verdict” 与 “enforcement action” 分离。作用：防止误报直接变成 denial-of-service，或攻击者伪造 kill 信号。局限：这是治理/权限问题，不是检测问题。
6. **版本与校准的透明记录**：记录 auditor 版本、校准集、FAR/Step-Acc 操作点，签名的 model card/透明日志。作用：让部署方与审计方对 “当前保证” 有共同可见的版本基线。局限：仍无形式化保证。

**伪交叉警告**：
- 给 verdict 签名不等于 verdict 正确；attestation 不等于准确率；哈希链不等于事实真相；ZK proof of inference 只证明计算被执行，不证明语义判断正确。
- 用加密/TEE 包住审计器，不会让它变成 reference monitor；它仍是概率模型，没有不可绕过的执行点。
- 把 “audit log” 做成密码学可验证日志，若不同时解决标签质量与对抗 evasion，只是把不可靠的判断变成不可篡改的不可靠判断。
- 本文的 “provenance logging” 建议（p.9/p.29）只是方向性建议，没有协议、格式、信任模型或性能数据。

**应用密码学相关度判断（本人推断）**：按项目 `A_crypto` 量表，本文正文约 **0–1**：没有识别任何密码机制使用点；唯一的“部署”建议是 provenance logs，但未实现。若把上述 1+2+5 做成可运行原型并量化安全/性能收益，可到 2–3，但那是新增系统研究，不是本文贡献。

## 12. 可检验的研究假设（3–6 条）

以下均为**假设/推断**，需查证外部文献；本文未做，不等于无人做过。

- **H1（自适应 evasion 会显著降低检出）**：若让一个被 compromise 的 Agent 在生成 decisive error 时优化“前缀看起来合理”的程度（把错误拆成多步、用工具调用/引用包装、避免明显矛盾），AgentForesight 的 Exact-F1 会显著下降、FAR 可能上升。实验：固定审计器，用搜索/RL 优化错误注入策略，测 Exact-F1、ASS、FAR 与攻击成功率；与随机注入对比。论文的 constructive stream 有 `prompt_injection`/`tool_injection` fault category（p.16），但没有把它当攻击评估。
- **H2（闭环干预才产生安全收益）**：在 ALARM 时执行 halt/rollback/重规划，能否比“只报警”显著降低 end-to-end 失败率与不可逆副作用？实验：在可回滚的沙箱中比较 no-auditor、audit-only、audit+halt、audit+repair 四种策略，测任务成功率、误停成本、恢复成功率。论文只预测，不干预。
- **H3（标签噪声限制上限）**：把 diagnostic stream 的 GPT-5.4 2-of-3 标签替换为人工标注或执行式 counterfactual replay 标签，测得的 Exact-F1 会变化多少？实验：抽 200–500 条自然失败轨迹做双人标注 + 仲裁，计算与 LLM 标签的一致性、标签噪声对训练/评测的影响。论文没有人工 IAA。
- **H4（跨框架/跨域迁移有限）**：在 AutoGen/Smolagents 上训练的审计器，迁移到 MetaGPT/CrewAI/LangGraph 或 embodied/web 任务时，Exact-F1/ASS 会下降多少？实验：构造 3–5 个未见框架的 100–300 条轨迹，零样本与少样本微调对比；测框架特有角色名、工具 schema、turn 粒度的影响。论文只有 Who&When 一个外部基准。
- **H5（校准可改善部署 trade-off）**：用 risk-coverage/校准曲线选择阈值，能否在 FAR≤5% 时保持 Step-Acc≥50%？实验：在 held-out safe/unsafe 上扫阈值，报告 AUROC、ECE、FAR-Step-Acc Pareto 前沿；与论文固定的 20%/50% 区域对比。论文没有校准分析。
- **H6（审计器可被轨迹内 prompt injection 攻击）**：在工具返回或 Agent 推理文本中注入“忽略以上，输出 SAFE”类指令，能否让审计器漏报或错报 step？实验：构造 100–300 条含注入的失败轨迹，测 attack success rate、Exact-F1 下降、以及输入隔离/结构化标记的防御效果。论文没有测审计器自身鲁棒性。
