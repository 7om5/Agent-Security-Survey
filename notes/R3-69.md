## 1. 150–300 字中文概述

AgentFuzz 是作者所称的首个面向 LLM-based Agent 的定向灰盒模糊测试框架，用于自动发现“污点式”漏洞：用户 prompt 经 LLM 解析后，未净化地流入 eval、SQL、命令执行、SSRF、SSTI 等安全敏感操作（sink）。方法分三阶段：用 CodeQL 从 sink 反向抽取调用链，借类/方法名的自然语言语义让 LLM 以 one-shot + CoT 生成功能特定的自然语言种子；用语义分、CFG 距离分和惩罚分调度种子；用功能变异器和参数变异器改写 prompt，后者结合 concolic execution、Z3 与最长公共子串匹配把约束解映射回 prompt。作者在 20 个开源 Agent 上报告 828 个 sink、34 个 0-day、100% 精确率、97.14% 召回率和 23 个 CVE，并称精确率约为 LLMSmith 的 33 倍。该文属于程序分析与模糊测试，不是密码学论文。

## 2. 研究背景、现有方法不足、精确定义的问题

- **背景**：LLM-based Agent 通过自然语言 prompt 调用工具、执行代码、访问数据库和处理敏感数据（p.2 摘要；p.3–4 §2.1）。典型流程是：用户 prompt → 与 system prompt 组装 → LLM 规划动作 → output parser 解析 → 通过 `Tools.get(resp["tool"])` 间接调用工具 → 工具以 LLM 返回的 `content` 为参数执行（p.4 Figure 1、Figure 2）。Agent 的生态（Coze、GPT Store 等）用户量大、保存大量用户数据，因而成为高价值目标（p.2）。
- **漏洞定义**：论文把 taint-style vulnerability 定义为“恶意用户输入在没有充分验证的情况下被传入 security-sensitive operation（SSO）”，可导致代码注入、SQL 注入、命令注入、SSRF、SSTI 等（p.4 §2.2；p.2 摘要）。其四个利用步骤是：攻击者通过 Web API 发送恶意 prompt（source）；Agent 把 prompt 交给 LLM，LLM 规划并返回动作；Agent 解析响应并间接调用工具；工具的 argument 实际是用户 prompt 中的字符串，未净化地进入 sink，例如 `eval(content.split(':')[1])`（p.4 §2.2.1、Figure 2）。
- **现有方法不足**：
  1. **静态分析（LLMSmith）**：把用户级 API 到 sink 的调用链直接报告为漏洞；粗粒度调用图、Python 间接调用普遍，导致高假阳性/假阴性；不能生成 PoC 验证可利用性（p.5 §3；p.2 摘要）。
  2. **传统静态分析**：Python 动态类型、间接调用、开发者自定义 sanitizer 使调用边不完整；不能证明可利用性（p.5 §3）。
  3. **传统 fuzzing（AFL 等）**：面向结构化输入，依赖公开种子集；Agent 输入是自然语言 prompt，没有固定结构，传统 bitflip 变异无法生成或改变语义，无法探索 Agent 的多样功能（p.5 §3、p.6 §4.1）。
  4. **LLM-driven fuzzing（Fuzz4All 等）**：能生成文本，但不能生成“功能特定”的 prompt，不能保证到达特定 sink（p.6 §4.1 Challenge I）。
- **精确定义的问题（本文的操作性表述，不是原文定理）**：给定 Agent 源码 `C`、预定义 sink 签名集合 `S`（`<package, class, method, parameters>`，p.7 §5.1.1、p.21 Table 5）、以及 Agent 的 prompt 输入接口，寻找自然语言 prompt `p`，使得执行 `A_C(p)` 时存在一条从用户输入（source）到某个 `s ∈ S` 的数据流，并满足到达 `s` 的路径约束；若找到，输出可复现的 PoC prompt（p.7 Algorithm 1）。由于 sink 在代码中固定，作者把该问题视为 directed fuzzing，而不是一般性的输入空间搜索（p.5 §4）。该表述是本人对 §2–§5 的整理，论文没有给出形式化判定问题、复杂度或可靠性定义。
- **三个挑战（原文 C1–C3）**：C1 如何生成功能特定的自然语言种子；C2 如何在 fuzzing 中优先高质量种子（间接调用使 CFG 不完整，距离不足；语义接近度也重要）；C3 如何变异种子以同时满足“调用脆弱组件”的语义和“参数满足代码约束”的要求（p.3 §1；p.6 §4.1）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **组件**（p.4 Figure 1、Figure 2；p.8 Figure 3）：
  - 用户（User）与 Agent Web Service/HTTP API：用户通过 `http://agent/chat?prompt=${prompt}` 之类的接口输入 prompt（p.4 §2.2.1）。
  - Prompt assembler：把用户 prompt 与开发者定义的 system prompt 组装后送入 LLM；system prompt 规定返回格式。
  - LLM：理解意图、规划动作，返回 JSON 形式的 `tool` 与 `param/content`。
  - Output parser / dispatcher：解析 LLM 响应，按 `resp["tool"]` 选择组件，按 `resp["content"]` 调用 `tool.run(...)`（p.4 Figure 2 的 `Tools.get` 与 `tool.run`）。
  - Tools/components：如 ElasticSearch、WebSearch、权限检查工具、代码执行器、数据库访问器等；每个组件有类名/方法名，承载自然语言语义。
  - Runtime environment：Python 解释器、可能的 Docker/Jinja sandbox、数据库、LLM API key 等（p.5 §2.2.2；p.15 §9）。
  - AgentFuzz 自身（p.8 Figure 3）：Agent Source Code + Prompt Input URL 输入；三阶段（seed generation、feedback-driven scheduling、sink-guided mutation）；Agent Runtime Environment 中的 Trace Recorder、Instrumentation、Bug Oracles；输出 Vulnerabilities（Code Injection、SSRF、SQL Injection、SSTI 等）。
- **交互流程**：① 用户 prompt；② 组装 system prompt 并送 LLM；③ LLM 返回动作，parser 解析并调用组件；④ 组件执行，结果返回用户（p.4 Figure 1；p.4 §2.1 的四步描述）。漏洞发生在第 ③ 步：LLM 返回的 `content` 被当作工具参数，未经净化进入 sink。
- **信任边界**：
  - 用户位于不可信侧；开发者和 Agent 代码被假设为 benign；运行环境被假设未 compromised（p.4–5 §2.2.2）。
  - 关键边界不是“用户 → LLM”，而是“LLM 响应 → 工具调用”：LLM 响应既被用作控制（选择哪个 tool），又被用作数据（content/参数）；Agent 对二者都不做充分验证。Figure 2 中 `resp["content"] = "source_doc:print(1)"` 直接进入 `ElasticsearchPermissionCheck.similarity_search`，再进入 `eval`（p.4 Figure 2）。
  - LLM 本身不是攻击者，但会被用户 prompt 诱导（confused deputy）；prompt-level 防护（system prompt 要求拒绝恶意请求）被视为可被 prompt injection 绕过（p.13 §7.3）。
  - AgentFuzz 位于目标 Agent 之外，但拥有源码、可手工插桩、可在本地构建并执行目标 Agent；它是白盒/灰盒测试工具，不是运行时防御组件（p.11 §6、p.12 §7.1）。这与论文威胁模型中“黑盒远程用户”的攻击者位置不同，阅读时需区分“攻击者模型”与“分析者模型”。
  - 论文没有显式画出信任边界图；以上边界划分是本人根据 §2.2.2 的假设和 Figure 2 的调用关系整理。`[推断]`
- **模型范围**：论文的抽象是单 Agent、单轮 prompt、工具调用型 Web 服务；没有把多 Agent 协作、长期记忆、RAG 检索、跨会话状态纳入系统模型。20 个被测 Agent 中有些可能带 RAG/记忆，但方法只针对“单 prompt 触发”的 sink（p.15 §9 Future Work 明确说 single prompt）。`[推断]` 因此该模型不覆盖多轮/存储型（second-order）污点流，也不覆盖 Agent 间消息传递。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：
  - 服务器控制权与代码执行能力（RCE、local privilege escalation、remote control）（p.2 摘要；p.5 §2.2.2）。
  - LLM API key（可被窃取用于未授权 LLM 请求，造成维护者财务损失）（p.5 §2.2.2）。
  - 用户数据/数据库（读取、删除、篡改）（p.5 §2.2.2）。
  - Agent 的完整性与可用性（删库、DoS）（p.5 §2.2.2）。
- **攻击者目标**：通过 crafted prompt 控制一个 security-sensitive function（sink），获得未授权权限；进一步实现代码执行、数据窃取、权限提升、拒绝服务（p.4–5 §2.2.2；p.2 摘要）。
- **攻击者能力**（p.5 §2.2.2）：
  - 远程攻击者：通过 Agent 的 Web API 输入恶意 prompt，控制服务器执行有害代码；AutoGPT、Dify 等均提供 Web API。
  - 本地攻击者：与 Agent 同设备，拥有本地访问，向高权限 Agent 输入恶意 prompt（如本地部署的 MobileAgent），导致权限提升。
  - 攻击者在“正常操作条件”下与 Agent 交互；不需要源码、不需要内部权限；可使用 prompt injection / LLM escape，以及 code escape（sandbox escape）绕过运行时限制（p.13 §7.3）。
  - 威胁模型假设 Agent/开发者 benign、运行环境未 compromised；攻击者不能利用“恶意开发者/被攻破运行时”这两类前提（p.4–5 §2.2.2）。
- **前提假设（论文显式）**：
  - Agent 和开发者 benign；运行环境未 compromised（p.4–5）。
  - 漏洞由单个 prompt 触发；多轮/高阶漏洞不在本文范围（p.15 §9）。
  - 存在预定义 sink（Table 5 的 16 个 sink 条目、5 种类型：CMDi、CODEi、SSRF、SSTI、SQLi）（p.21 Table 5）。
  - AgentFuzz 分析时拥有源码、可插桩、可本地构建、可指定 Web API 输入；使用 GPT-4o、temperature 0；每个 sink callsite 5 分钟超时（p.12 §7.1）。
- **前提假设（本人推断，非原文显式）**：
  - 被测 Agent 是 Python 编写、可通过 CodeQL 分析、可在本地运行；闭源、非 Python、需要特殊硬件/凭据的 Agent 不在覆盖范围。
  - LLM 会把 prompt 中的数据片段较原样地传给工具参数；若 LLM 改写/摘要/拒绝，污点可能无法到达 sink（与 LCSM 的 substring 假设相关，p.10 §5.3.2）。
  - 评估只覆盖 Web 服务型 Agent，虽然威胁模型也提到本地攻击者；本地部署 Agent 的实际攻击面未被系统评测（p.12 数据集筛选要求 web service；p.5 提到 local attacker）。`[推断]`
- **不覆盖的威胁**：恶意开发者/工具供应链、被攻破的 LLM 提供方、多 Agent 串谋、长期记忆投毒、跨会话 second-order 污点、闭源商业 Agent、非 Python 运行时。

## 5. 核心方案（方法、攻击/防御流程、关键定义）

### 5.1 总体流程（Algorithm 1，p.7）

输入 Agent 代码 `C`；输出漏洞 PoC 集合 `P`。对每个 sink callsite：`S ← ExtractSinkCallsites(C)`；对每个 sink 执行 `StaticAnalyze` 得到调用链；对每条调用链 `GenerateSeed` 生成初始自然语言种子；`Execute` 得到反馈并加入 seed pool；在 timeout 内循环：`SelectSeed` → `SelectMutator` → `Mutate` → `Execute` → `VulnOracle`；成功则把 `new_seed` 加入 `P` 并 `break`（p.7 Algorithm 1，lines 1–17）。三阶段对应 §5.1–§5.3。

### 5.2 阶段一：LLM-assisted Seed Generation（p.7–8）

- **Sink callchain extraction**（p.7 §5.1.1）：人工预定义 sink 集合，每个 sink 由唯一方法签名 `<package, class, method, parameters>` 定义；Table 5 列出 16 行、5 种类型（p.21）。AgentFuzz 用 CodeQL 的 `FunctionInvocation`、`BasicBlock` API 构建调用图/CFG，从 sink callsite 深度优先反向追踪 caller，提取类名/方法名，直到没有 caller。示例调用链：`eval → ElasticsearchPermissionCheck.similarity_search`（p.7）。
- **Seed prompt generation**（p.7–8 §5.1.2）：把调用链输入 LLM，用 one-shot learning + Chain of Thought（CoT）+ self-verification 生成功能特定的自然语言 prompt；每条调用链生成一个种子。Figure 4 的示例：`INPUT: <CALL CHAIN>: calculator→eval`，`OUTPUT: <COT>: ... <PROMPT>: Please use the calculator to evaluate the following expression: 3 * (4 + 5).`（p.8 Figure 4）。CoT 三步：从调用链推断组件功能；生成与功能匹配的 prompt；自检语义相似度并修正（p.8）。
- **关键假设**：类名/方法名承载自然语言语义，LLM 可据此推断功能；这是“功能特定”种子的基础（p.3 §1、p.6 §4.1、p.7 §5.1.1）。

### 5.3 阶段二：Feedback-driven Seed Scheduling（p.8–9）

- **三因子反馈**（p.8 §5.2.1）：
  - **Semantic score `S_s`**：执行种子，记录 execution trace；把 trace 中的方法/类名与目标调用链一起交给 LLM，判断语义一致性，0（完全无关）到 10（完全对齐）；temperature 0（p.8–9）。Figure 5 的评分 prompt 给出 10、8–9、1–3、0 的锚点，但 **4–7 分段没有定义**（p.8 Figure 5）——这是评分 rubric 的未指定区间，`[推断]` 可能降低跨样本一致性。
  - **Distance score `D_s(x) = x^{-k}`**（Eq. 2，p.9）：`x` 是 execution trace 中所有方法调用到 sink callsite 的最短 CFG 距离，取最小值；若方法不在 CFG 中（可能由间接调用导致），距离视为无穷；`k` 为超参数。距离越小分数越高；`x→∞` 时 `D_s→0`。公式在 `x=0`（已到达 sink）处未定义，论文未说明特殊处理（`[推断]`，通常此时 oracle 已触发、不再调度）。
  - **Penalty score `P_s = γS_f + ηC_f`**（Eq. 3，p.9）：`S_f`、`C_f` 分别为该种子及其调用链被选中的次数；γ、η 为超参数；用于避免局部收敛。
  - **总分**：`F_s = αS_s + βD_s − P_s`（Eq. 1，p.8）；α、β 为权重；分数越高越优先。实验取 α=β=0.5、γ=0.2、η=0.1、k=1.0（p.11 §6）。`[推断]` `S_s` 量纲 0–10、`D_s` 量纲 0–1、`P_s` 为计数，三者未归一化，语义分在默认权重下主导；论文没有做权重敏感性分析。
- **调度示例**（p.9 Figure 6）：调用链 `ElasticsearchPermissionCheck.similarity_search → eval` 对应四个种子 S1–S4；S3 的 prompt 含 search/permission/check 语义，执行 trace 同时接近调用链语义和 sink，因而得分最高；S2 缺少 PermissionCheck 语义，未被选中（p.9 §5.2.2）。

### 5.4 阶段三：Sink-guided Seed Mutation（p.9–11）

- **Functionality mutator**（p.9–10 §5.3.1）：用 self-improvement 机制迭代改写 prompt，缩小 prompt 与目标组件功能之间的语义差距。AgentFuzz 为每个种子维护独立 chat session，保存该种子的所有变异尝试、推理过程、execution trace、反馈分数；下一轮基于历史避免重复错误（p.9–10；Figure 7 p.10）。Prompt 要求 LLM：根据 trace 判断种子意图；根据调用链推断目标组件功能；找出导致 Agent 调用错误组件的 prompt 部分；参考历史，不要重复错误；改写 prompt 使语义更接近目标调用链（p.10 Figure 7）。
- **Argument mutator**（p.10 §5.3.2）：目标是让组件参数满足代码约束。步骤：
  1. 静态分析提取到 sink 的期望控制流路径；与真实 execution trace 比较，定位第一个未满足的条件语句。
  2. 从该条件所在的组件开始 concolic execution：把每个参数视为 symbolic variable；在 concrete 值上运行、同时收集符号表达式（基于 py-conbyte 的 interpreter-based concolic engine，p.11 §6）。
  3. 到达未满足条件或 sink 时，根据符号表达式生成约束；用 Z3 求解（p.10）。求解时先保留一个变量 symbolic、其余替换为 concrete 值；若失败，逐步增加 symbolic 变量数量；并对 Python 字符串操作（split、startswith 等）建模（p.10）。
  4. **Prompt-to-Argument Mapping**：用 Longest Common Substring Matching（LCSM）把约束中变量的值映射回 prompt 的具体片段；prompt 被视为“action + data”两部分，LLM 从 action 选择组件，把 data 作为参数；因此修改 data 部分即可控制参数（p.10）。示例：约束 `"source_doc" in content` 和 `content.split(':')[1]`，插入 `source_doc:` 并生成 `:value` 形式的值（p.10）。
- **Mutator scheduling**（p.10–11 §5.3.3）：LLM 根据以下信息选择 mutator：(1) execution trace 与到 sink 的控制流路径共享的、离 sink 最近的条件语句及其完整条件；(2) 条件中变量的运行时值；(3) 之前的反馈分数（p.10–11）。若 CFG 因间接调用不完整、trace 与到 sink 的控制流不重叠，说明 prompt 语义不足，优先 functionality mutator；否则可尝试 argument mutator（p.11）。Figure 8 给出调度 prompt（p.11）。
- **PoC 注入**：一旦 sink 被触发，不再调用 mutator；用 instrumentation 捕获 sink 参数值，用 Prompt-to-Argument Mapping 定位 prompt 中流入 sink 的片段，按 sink 类型替换为 payload（如 `eval()` 用 `print(1)`、`requests.get()` 用 `127.0.0.1`），并动态追踪 tainted payload 是否到达 sink（p.11）。示例：`source_doc:test` → `source_doc:print(1)`（p.11）。

### 5.5 实现（p.11 §6）

- 原型共 5,796 行 Python + 521 行 CodeQL。
- 静态分析：CodeQL 的 `FunctionInvocation`、`BasicBlock` API 识别 sink callsite、构建调用图/CFG；结果以 SARIF 输出（p.11）。
- 动态 fuzzing：fuzzing、instrumentation、concolic execution 三部分。反馈收集用 Python `inspect` 捕获 stack frame 计算到 sink 的距离；bug oracle 用 `sys.settrace` 和 `sys.addaudithook` hook Table 5 的 sink，在 AST 层监控 attack payload 是否流入 sink；支持 SQLi、CODEi、SSRF、SSTI（p.11）。
- Concolic：基于 py-conbyte 的 interpreter-based 框架，集成 `inspect` 提取运行时值（p.11）。
- Agent framework：LangChain 与 LLM 交互；AgentFuzz 自身也被描述为一个 agent，可自主规划/适应（p.11）。
- 超参数：α=0.5、β=0.5、γ=0.2、η=0.1、k=1.0；作者称参考现有工作并在数据集子集上确定（p.11）。`[推断]` 超参数在同一 20 个 Agent 的子集上调优，没有独立验证集，存在调参偏差风险。
- 运行环境：GPT-4o，temperature 0；64-core Intel CPU、256 GB memory；每个 sink callsite 5 分钟超时（p.12 §7.1）。

### 5.6 关键定义（本文操作性定义）

- **Taint-style vulnerability**：恶意用户输入未经充分验证进入 SSO（p.4 §2.2）。
- **Source**：用户可控的 prompt 输入（远程 Web API 或本地接口；p.4 §2.2.1 的示例与 p.12 §7.2 的评测均以 Web API 为输入）。
- **Sink**：预定义的安全敏感方法签名 `<package, class, method, parameters>`（p.7 §5.1.1；p.21 Table 5）。
- **PoC**：能触发 sink 的 prompt；通常是 benign payload（如 `print(1)`），可利用性验证时才替换为恶意 payload（p.12–13 §7.2–7.3）。
- **Directed greybox fuzzing**：以固定 sink 为目标、利用运行时反馈/距离信息引导种子生成的 fuzzing（p.5 §4；p.6 §4.1）。
- **Seed / mutator / oracle**：自然语言 prompt 种子；功能变异器/参数变异器；运行时判定 payload 是否到达 sink 的 bug oracle（p.7–11）。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

| 层面 | 论文中的内容 | 形式化程度 |
|---|---|---|
| 定义 | taint-style vulnerability、source、sink、SSO、PoC、seed、mutator、oracle | 操作性定义：自然语言 + 方法签名 + 运行时判定；无形式语义、无 taint lattice、无安全定义 |
| 指标 | TP/FP/FN、precision、recall、TTE、CPU hours、token cost | 算术定义；ground truth 35；未报告置信区间/重复运行/显著性检验 |
| 经验主张 | 34 个 0-day、100% precision、97.14% recall、33× LLMSmith（相对提升）、23 CVE、34/34 可利用 | 经验性/手工验证；不是定理、不是可证明的安全保证 |
| 对抗模型 | 恶意用户（远程/本地），可发 prompt；无正式能力/预算/游戏 | 描述性威胁模型；无 attacker advantage、无 reduction |
| 形式化程度 | 无 theorem/lemma/proof/security game/reduction；无密码原语 | 低；程序分析 + 经验评测 |

- **定义不是形式化安全定义**：论文把“taint-style vulnerability”定义为“malicious user input 未经充分验证进入 SSO”（p.4 §2.2），把 sink 定义为方法签名（p.7 §5.1.1、p.21 Table 5），把 source 定义为用户可控的 prompt（评测中以 Web API 输入，p.4、p.12）。这属于**动态污点分析/程序分析**的操作性刻画，不是密码学或形式化信息流定义：没有 taint policy、taint lattice、显式/隐式流规则、sanitizer 语义、noninterference、quantitative information flow 或 attacker observation model。Bug oracle 用 `sys.settrace`/`sys.addaudithook` 在 AST 层监控 payload 是否流入 sink（p.11 §6），本质是运行时数据流/值追踪，不是密码学标签或 MAC。
- **指标是算术指标，不是统计估计**：precision = TP/(TP+FP)、recall = TP/(TP+FN) 由 Table 2 的数值可反推；TTE 和 CPU hours 是工程指标；token cost 是成本指标。未报告置信区间、方差、重复实验或显著性检验。ground truth 为 35 个“verified vulnerabilities”，由 AgentFuzz 与 LLMSmith 的检测结果聚合而来（p.13 §7.4），不是独立、完备的漏洞全集。
- **经验主张**：34 个 0-day（p.2）、100% precision（p.3、p.12）、97.14% recall（p.14 Table 2）、比 LLMSmith 精确率高 33×（p.2、p.14）、23 个 CVE（p.2、p.12 Table 1、p.15、p.20 Table 4）、34/34 可利用（p.13 §7.3）。这些是**经验性/手工验证**的主张，不是形式化保证；其中 CVE 计数（23 vs 27）与 ground truth 35 的来源存在内部不一致（见 §9）。
- **“33.25×”与“2.4×”是相对增量，不是总量比**：Table 2 给出 LLMSmith precision 2.92%、AgentFuzz 100%；相对提升为 (100−2.92)/2.92 ≈ 33.25×，总量比为 100/2.92 ≈ 34.25×。漏洞数 34 vs 10：相对增量为 (34−10)/10 = 2.4×，总量比为 34/10 = 3.4×。论文的 33.25×（p.14）和 2.4×（p.14）分别对应相对增量口径；摘要的“33 times higher”（p.2）也是这一口径。数字本身自洽，但英文“times higher/more”容易被读成总量比，属于表述歧义而非算术错误。
- **结论**：本文的安全声明是“检测覆盖率/精确率”的经验声明，不是“系统满足某安全属性”的形式化声明；不能把 100% precision 当作密码学意义上的无假阳性保证，也不能把 taint-style 当作形式化信息流非干涉。

## 7. 实验设置与主要结果（agents、场景、指标、关键数字、消融）

### 7.1 设置（p.12 §7.1）

- **数据集**：20 个开源 LLM-based Agent，来自 GitHub；筛选步骤：关键词（“LLM”“AI Agent”）搜索 → 按 star 排序 → 每个仓库 >1,000 stars → 人工确认提供 Web 服务（p.12）。13 个 >10,000 stars，其余 7 个 >1,000 stars；多数在既有研究中出现（p.12）。
- **环境**：GPT-4o 作为 AgentFuzz 和被测 Agent 的 base model，temperature 0；64-core Intel CPU、256 GB memory（p.12）。
- **预算**：每个 sink callsite 5 分钟超时；sink 多的 Agent 总时间更长（p.12）。
- **指标**：漏洞数、precision、recall、各阶段 CPU hours、token cost、time-to-exposure（TTE）（p.12）。
- **RQ**：RQ1 效果/效率；RQ2 可利用性；RQ3 与 SOTA（LLMSmith）比较；RQ4 消融（p.11 §7.1）。

### 7.2 RQ1：漏洞检测（p.12–13 §7.2；Table 1 p.12）

Table 1 选摘（完整 20 行见 p.12）：

| Agent | Stars | LoC | CVEs / Vulns | CPU h | Avg. TTE (min) |
|---|---:|---:|---:|---:|---:|
| AutoGPT | 168,793 | 19,036 | 2 / 3 | 1.47 | 29.43 |
| Dify.AI | 53,770 | 117,752 | 0 / 0 | 3.00 | / |
| LangFlow | 37,032 | 45,075 | 2 / 3 | 8.13 | 162.58 |
| Chatchat | 32,272 | 14,098 | 2 / 2 | 2.33 | 69.89 |
| DB-GPT | 13,858 | 84,323 | 3 / 3 | 4.46 | 89.20 |
| Bisheng | 8,931 | 49,816 | 4 / 7 | 8.42 | 72.17 |
| AgentScope | 5,368 | 13,627 | 3 / 4 | 3.58 | 53.70 |
| OpenAgents | 4,013 | 15,441 | 1 / 2 | 0.19 | 5.72 |

- **总量**：828 个 sink callsites；34 个潜在漏洞（SQLi、命令注入、代码注入、SSTI 等）；20 个 Agent 合计 69.01 CPU hours，平均 3.45 h/Agent；Seed Generation / Scheduling / Mutation 分别占 39% / 5% / 56%；平均 TTE 121.8 分钟；平均 0.69M tokens/Agent，最高成本 6.9 美元（p.12）。
- **精确率**：人工复核 34 份报告，全部为 true positive，precision 100%（p.12）；作者归因于 bug oracle 的鲁棒性。
- **召回率分析的限制**：无法从 NVD 收集足够多符合威胁模型的已知漏洞 PoC 来构建 ground truth；人工复核全部 828 个 sink 不可行；随机抽取 10%（83 个）被 AgentFuzz 判为 non-vulnerable 的 callsites 进行人工复核（p.12）。
- **83 个抽样结果**：93.98% 用户不可控；4.82% 被 sanitizer 保护（如 BiSheng 用复杂正则限制 eval 只接受数值）；1.20% 确实可利用但被漏报（p.12–13）。1.20% 对应 83 个中的 1 个，原文以 Devika 的 second-order 漏洞为例：payload 存储在 Agent 中，第二次交互才流入 sink（p.13）。`[推断]` 若把 1.2% 外推到 794 个 non-vulnerable callsites，约 9–10 个漏报；这与 ground truth 中仅 1 个 FN 的口径不同，论文未调和（见 §9）。
- **效率分层**：Generation 与 Mutation 最耗时，因为涉及静态分析和 concolic execution；Scheduling 仅 5%（p.12）。

### 7.3 RQ2：可利用性（p.13 §7.3）

- 34 个漏洞全部经人工验证为可利用（p.13）。
- 14 个需要 LLM escape（如 prompt injection：忽略指令、操纵上下文）；5 个需要 code escape（如 inheritance chain bypass、builtin reload）绕过代码 sandbox（p.13；p.20 Table 4 的 PI/CE 列）。
- 两个案例：Case I 代码注入（S***，>15k stars，`TaskOutputHandler.evaluate` 提取 `[]` 内容后 `eval`，CVE-2024-5**95）；Case II SSTI（A***，>160k stars，`FillTextTemplateBlock.run` 用 jinja2 `from_string().render()`，CVE-2024-5**87）（p.15 §8；p.20 Figures 9–10）。
- 影响 14 个开源 Agent，7 个 >10k stars；包括 AutoGPT（>100k stars）；可窃取 LLM API key、执行恶意代码、控制服务器（p.13）。
- **CVE 数量口径冲突**：本节说“we have received 27 CVE identifiers in acknowledgment”（p.13）；摘要、Table 1、Table 4、结论都说 23 个 CVE ID（p.2、p.12、p.15、p.20）。这是明确的内部不一致（见 §9）。
- `[推断]` “可利用”的验证依赖 LLMSmith 的 LLM escape/code escape 技术，不是独立红队；不同漏洞类型的“可利用”标准（RCE、数据读取、SSRF 影响）没有统一定义。

### 7.4 RQ3：与 LLMSmith 比较（p.13–14 §7.4；Table 2 p.14）

| Baseline | TP | FP | FN | Prec (%) | Recall (%) |
|---|---:|---:|---:|---:|---:|
| LLMSmith | 10 | 332 | 25 | 2.92 | 28.57 |
| AgentFuzz | 34 | 0 | 1 | 100 | 97.14 |

- Ground truth：聚合 AgentFuzz 与 LLMSmith 检测到的漏洞，人工验证后共 35 个（p.13）。
- AgentFuzz 34 个 TP；LLMSmith 10 个 TP，且论文称“all of which are a subset of the vulnerabilities identified by AgentFuzz”，另有 332 个 FP（p.14）。按此，24 个 AgentFuzz 漏洞未被 LLMSmith 发现（34−10=24），与摘要“24 of which were undetected by existing approaches”（p.3）一致。
- 论文称 precision 高 33.25×、漏洞数多 2.4×（p.14）。这两个数字是相对增量：precision 的 (100−2.92)/2.92 ≈ 33.25×，漏洞数的 (34−10)/10 = 2.4×；对应的总量比分别为 100/2.92 ≈ 34.25× 和 34/10 = 3.4×。数字自洽，但“times higher/more”是相对增量口径（见 §6、§9.2）。
- **LLMSmith 的 332 FP 原因**（定性）：sink 参数用户不可控；Python 动态类型/字符串匹配导致错误调用边；开发者自定义 sanitizer 未被识别（p.14）。没有给出每类原因的计数。
- **LLMSmith 的 25 FN 原因**（定量）：9 个由 Python 静态分析固有限制（间接调用）导致；16 个由有限 sink 列表导致（LLMSmith 只考虑 `eval`、`exec`、`subprocess.run`）（p.14）。
- **ground truth 的循环性**：ground truth 由两个被比较工具的检测结果聚合，无法发现两者都漏报的漏洞；因此 recall 是“相对该 ground truth”的 recall，不是绝对 recall。`[推断]`
- **“35 = 34 + 1”与“LLMSmith 10 个全是 AgentFuzz 子集”的张力**：若 10 个 LLMSmith TP 全部包含在 AgentFuzz 的 34 个 TP 中，则两工具并集为 34，而非 35；第 35 个 ground-truth 漏洞的来源论文未明确说明。它可能是 §7.2 中人工在 10% 抽样里发现的 Devika second-order 漏洞（p.13），但原文没有把这条例与 ground truth 的构造明确连起来。若第 35 个是 LLMSmith-only，则“all 10 subset”不成立。两种解释至少有一个与原文表述不符（见 §9）。

### 7.5 RQ4：消融（p.14 §7.5；Table 3 p.14）

| Variant | TP | FP | FN | Prec (%) | Recall (%) |
|---|---:|---:|---:|---:|---:|
| AgentFuzz-NoGen | 19 | 0 | 16 | 100 | 54.29 |
| AgentFuzz-NoSch | 26 | 0 | 9 | 100 | 74.29 |
| AgentFuzz-NoSem | 27 | 0 | 8 | 100 | 77.14 |
| AgentFuzz-NoMut | 25 | 0 | 10 | 100 | 71.43 |
| AgentFuzz | 34 | 0 | 1 | 100 | 97.14 |

- **NoGen**：禁用 LLM-assisted Seed Generation，改用传统漏洞 PoC + Wapiti/ZAP/LLMSmith 的预定义 prompt 作为初始种子；少 16 个漏洞，recall 54.29%（p.14）。`[推断]` 这不是纯粹的“去掉生成器”消融，因为种子来源同时改变（传统 PoC/扫描器 vs LLM 生成），混淆了“生成质量”与“种子分布”两个因素。
- **NoSch**：随机选种子；少 9 个，recall 74.29%；随机策略在无望种子上反复变异，耗尽时间和 token（p.14）。
- **NoSem**：去掉 semantic score、仅保留 distance score；少 8 个，recall 77.14%；Figure 6 中四个种子距离分都为 0，无法区分 S3 的语义优势（p.14）。论文说 recall 相对下降 20.6%（97.14→77.14 为 20.0 个百分点；相对下降 20.59%），表述为相对值。
- **NoMut**：禁用两个 mutator，仅靠初始种子；少 10 个，recall 71.43%；需要特定代码约束或复杂语义的漏洞无法触发（p.14）。
- **共同点**：所有变体 precision 都是 100%，因为 bug oracle 判定；消融主要影响 recall。没有报告各变体的时间/token 成本，也没有重复运行或置信区间。

### 7.6 数字自洽性核对（本人核算，非原文）

- Table 1 的 CVEs 列求和 = 23，Vulns 列求和 = 34，CPU h 求和 = 69.01；与 Total 行一致。
- Table 1 每个有漏洞 Agent 的 `Avg. TTE` = `CPU h × 60 / #vulns`：AutoGPT 1.47×60/3=29.4；LangFlow 8.13×60/3=162.6；Bisheng 8.42×60/7=72.17；均吻合。Total 行的 121.78 = 69.01×60/34，是按 34 个漏洞加权的总体平均；它不是 14 个 per-app TTE 的算术平均（≈88.2）。两种口径都可解释，但 Total 行与列头的“Avg.”含义不同，读者可能误读。
- **69.01 CPU h ≈ 828 × 5 min / 60 = 69.0 h**。这个几乎精确的相等提示：总时间很可能就是“每个 sink 5 分钟超时预算”的总和，而不是实际搜索耗时；但 Algorithm 1 在找到 PoC 时 `break`（p.7 line 17），若 34 个漏洞的 sink 提前结束，总时间应小于预算。两者之间的张力原文没有解释（见 §9）。
- Table 4（p.20）共 34 行：23 个具体 CVE ID 条目 + 11 个 “Assigning”；与 Table 1 的 23/34 一致（按条目计；掩码可能使不同完整 ID 看起来相同，无法核对唯一性）。PI 列 “w” 计数 = 14，CE 列 “w” 计数 = 5，与 §7.3 的 14/5 一致（本人逐行核对）。
- Table 2 的 33.25× 可复现为相对提升：(100−2.92)/2.92 = 33.25；总量比 100/2.92 = 34.25。33.25 不是错误，而是“比 LLMSmith 高 33.25 倍”的相对增量口径；若按“是 LLMSmith 的多少倍”读则是 34.25×。这是表述歧义，不是数字矛盾（见 §6、§9.2）。
- 35 个 ground truth 与“LLMSmith 10 个全是 AgentFuzz 子集”的并集算术存在张力（见 §7.4、§9）。

## 8. 贡献与创新点（按原文主张）

1. **问题定位**：提出首个针对 LLM-based Agent 的 taint-style 漏洞定向 fuzzing 方法；作者称现有工作没有“fully automated and accurate”的同类方法（p.2 摘要；p.3 §1；p.5 §3）。
2. **三阶段架构**：LLM-assisted seed generation、feedback-driven seed scheduling、sink-guided seed mutation；把传统 DGF 的 seed/schedule/mutate 三模块迁移到自然语言 prompt 空间（p.3、p.7–11；p.8 Figure 3）。
3. **功能特定种子生成**：利用 sink 调用链中的类名/方法名语义，以 one-shot + CoT + self-verification 生成功能特定的自然语言 prompt；这解决了“传统 fuzzer 不能生成语义种子”的 C1（p.3、p.7–8；Figure 4）。
4. **多因子反馈调度**：语义分 + CFG 距离分 + 惩罚分，缓解间接调用导致 CFG 不完整、单一距离不能区分语义的问题；这对应 C2（p.3、p.8–9；Eq. 1–3；Figure 6）。
5. **两类变异器**：functionality mutator 用 self-improvement 缩小语义差距；argument mutator 用 concolic execution + Z3 + LCSM 把约束解映射回 prompt；LLM 调度两个 mutator；这对应 C3（p.3、p.9–11；Figures 7–8）。
6. **实证规模**：20 个开源 Agent、828 个 sink、34 个 0-day、100% precision、97.14% recall（相对 35 个 ground truth）、23 个 CVE；14 个需要 LLM escape、5 个需要 code escape；影响 14 个 Agent，7 个 >10k stars（p.2–3、p.12–14）。
7. **实践与披露**：所有漏洞人工确认并负责任披露；23 个 CVE ID；开源代码/数据集（Zenodo）（p.13、p.16、p.20 Table 4）。`[推断]` “first”“33×”“100%”均为作者主张，单篇论文无法独立证明其普适性。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

### 9.1 作者承认的不足（原文直述）

- **只覆盖单 prompt 触发的漏洞**：论文明确说 “this paper focuses on taint-style vulnerabilities triggered by a single prompt”；需要多个 prompt 序列的高阶漏洞留给 future work（p.15 §9）。Devika 的 second-order 漏洞（payload 存储后第二次交互才流入 sink）被列为漏报例子，作者称其“challenging and worthy of further investigation”（p.13）。
- **复杂约束/sanitizer 无法求解**：BiSheng 用复杂正则限制 `eval` 只接受数值，AgentFuzz 无法解决这类约束，因而漏报；4.82% 的抽样 non-vulnerable callsites 属于此类（p.12–13）。
- **ground truth 不充分**：NVD 中没有足够多符合威胁模型的已知漏洞 PoC；人工复核全部 828 个 sink 不可行；只随机抽取 10%（83 个）做 FN 分析（p.12）。这意味着 recall 的分母/抽样都不完备。
- **数据集与环境的作者直述设置（其限制性为本人判断）**：只选 20 个开源、提供 Web 服务、>1,000 stars 的 Agent；每个 Agent 需手工插桩并指定 Web API；只用 GPT-4o（temperature 0）；每个 sink 5 分钟超时（p.12）。这些是原文直述的实验设置；“构成外部有效性限制”是本人判断，作者没有用 limitation 一词展开。
- **缓解措施未评估（作者提出建议，未报告评估；“未评估”为本人核对）**：§9 提出三条建议（减少 SSO 依赖、环境隔离、输入净化），但没有实现或量化其效果（p.15）。这是“建议”而非“防御评估”。
- **second-order 漏洞未解决**：作者把 Devika 例列为 future work，没有给出检测方法或召回率（p.13、p.15）。

### 9.2 我的推断/核对（非作者承认）

- **“automatic”是部分的**：虽然 fuzzing 循环自动，但 sink 列表（Table 5）是人工预定义，目标 Agent 需手工插桩、手工指定 Web API，34 份报告需人工复核，可利用性需人工用 LLMSmith 的 escape 技术验证（p.11–13）。因此“fully automated”应理解为“检测循环自动”，不是端到端无人值守。
- **100% precision 的证据强度有限**：34 份报告全部由作者人工复核；未报告独立标注者、inter-rater agreement、置信区间或重复运行。Bug oracle 的假阳性/假阴性率没有被单独测量；它依赖 `sys.settrace`/`sys.addaudithook` 和 AST 层 payload 流，可能漏掉隐式流、编码/混淆、跨函数/跨请求流（p.11）。`[推断]`
- **ground truth 的循环性与第 35 个漏洞来源不明**：ground truth 由 AgentFuzz + LLMSmith 的检测结果聚合（p.13），无法覆盖两者都漏的漏洞；若 LLMSmith 的 10 个 TP 全是 AgentFuzz 子集（p.14），并集应为 34，而非 35。第 35 个可能是 §7.2 人工抽样发现的 Devika second-order 漏洞，但原文没有明确说明其被纳入 ground truth；若是 LLMSmith-only，则“all 10 subset”不成立。这个口径直接影响 recall 分母（34 vs 35）和 LLMSmith recall（10/34=29.4% vs 10/35=28.57%）。`[推断/核算]`
- **33.25×/2.4× 的口径歧义**：33.25 = (100−2.92)/2.92，是相对提升；34.25 = 100/2.92，是总量比。2.4 = (34−10)/10，是相对增量；3.4 = 34/10，是总量比。数字本身可复现，不是笔误；但英文“times higher/more”容易被读成总量比，论文没有明确说明口径。`[核算/表述歧义]`
- **23 vs 27 CVE**：摘要/Table 1/Table 4/结论为 23（p.2、p.12、p.15、p.20），§7.3 说收到 27 个 CVE identifiers（p.13）。Table 4 只有 23 个具体 ID + 11 个 Assigning；27 可能是论文写作后期又收到 4 个，但正文没有说明时间线，也没有更新表格/摘要。`[原文内部不一致]`
- **69.01 CPU h 与 828×5 min 预算几乎相等**：828×5/60=69.0；报告 69.01。若每个 sink 都用满 5 分钟，总时间正好是这个数；但 Algorithm 1 在找到 PoC 时 break（p.7 line 17），34 个漏洞对应的 sink 应提前结束，总时间应小于 69.0。可能的解释：(a) 报告的是分配预算而非实际 CPU 时间；(b) break 未真正生效/仍跑满预算；(c) 828 与 69.01 是近似值。论文没有说明。若是预算，TTE（=总时间/漏洞数）更像“预算/漏洞”而非“发现时间”，效率结论需谨慎。`[推断/核算]`
- **FN 抽样外推与 1 个 FN 的口径不同**：1.20%×83=1 个 second-order 漏洞；若外推到 794 个 non-vulnerable callsites，约 9–10 个漏报。论文用 1 个 FN 构造 97.14% recall，又用 1.2% 抽样论证“high recall”；这两个估计没有调和。1/83 的 95% 置信区间很宽，点估计不能支撑“高召回”的强结论。`[推断/核算]`
- **单次运行/未报告方差**：论文只给出单组数字（未报告重复次数）；超参数在 20 个 Agent 的子集上调优（p.11），没有独立验证集；没有对 α、β、γ、η、k 做敏感性分析。因此 54.29% vs 97.14% 等消融差异没有置信区间。`[推断]`

- **LCSM 的 substring 假设**：argument mutator 假设 prompt 中的数据片段会以子串形式出现在工具参数中，才能用最长公共子串映射回去（p.10）。若 LLM 改写、翻译、摘要、规范化数据，LCSM 可能找不到对应片段；论文没有量化这一失败模式。`[推断]`
- **类/方法名语义假设**：seed generation 依赖类名/方法名的自然语言语义（p.3、p.7）；混淆/压缩/无语义命名的代码会降低种子质量；没有对抗性命名或混淆实验。`[推断]`
- **只比较 LLMSmith**：RQ3 只有一个 baseline（静态分析工具），没有与 AFL/AFL++、其他 LLM fuzzer、其他静态分析器比较；LLMSmith 可能未针对该数据集调优；没有运行时/成本对比。`[推断]`
- **可利用性验证依赖 LLMSmith 技术**：14 个 LLM escape、5 个 code escape 直接借用 LLMSmith 的 prompt injection/code escape 手法（p.13）；不是独立红队，也没有报告每种 escape 的成功率/失败案例。`[推断]`
- **CVE/0-day 不可独立审计**：CVE ID 被掩码（如 CVE-2024-5**95），案例应用名被匿名化（S***、A***）（p.15、p.20）；外部读者无法核对 CVE 与漏洞类型的对应关系。掩码还导致同一 `5**95` 在 Case I（代码注入）与 Table 4（SuperAGI/AgentScope 的 SSRF）之间看似冲突，实际可能是不同完整 ID；论文没有说明。`[推断]`
- **“first”主张**：作者称首个 agent taint-style fuzzing 框架（p.2–3）；单篇论文的 related work 不能证明“first”，且 LLMSmith 已做静态检测；该主张应视为作者声明而非独立事实。`[推断]`
- **无防御评估**：论文是检测工具，不提出可部署防御；§9 的三条缓解建议没有实验（p.15）。`[推断]`

## 10. 与理论密码学的可能联系（严格；没有就写“无”）

**无。** 本文与理论密码学没有技术联系；它是程序分析/模糊测试/经验系统论文。

- **没有密码学机制**：全文没有加密、签名、MAC、承诺、零知识、MPC、FHE、匿名凭证、PAKE 等密码原语，也没有 TEE/远程 attestation 等可信硬件机制；没有密码学假设、密钥、协议会话或攻击者计算能力模型。
- **没有形式化安全定义/定理/归约**：没有 theorem、lemma、proof、security game、simulation、reduction、advantage、indistinguishability、noninterference 的形式定义。所谓 “oracle” 是 bug oracle（运行时判定 payload 是否到达 sink，p.11），不是密码学 oracle；所谓 “PoC” 是 proof-of-concept exploit（p.11–12），不是 proof of possession；所谓 “source/sink” 是程序分析的污点源/汇（p.4、p.7），不是密码学协议角色。
- **“taint-style”不是密码学 taint**：论文的 taint 是“用户输入 → LLM 响应 → 工具参数 → SSO”的动态数据流（p.4 Figure 2、p.11），不是带 MAC/签名的密码学污点标签，也没有 taint lattice、显式/隐式流规则、sanitizer 的形式语义、非干涉或定量信息流。它是**动态污点分析/程序分析**问题，不是密码学问题。
- **如果硬要做理论连接（本人推断，不是论文已做）**：可以把“用户输入到 sink 的数据流”形式化为一条动态依赖/信息流性质（例如，sink 参数的值依赖于 source 的值），用 dynamic taint analysis 或 IFC 的语义来证明；这属于程序分析/形式化方法，不是密码学。即使引入“攻击者不能区分两个输入”的不可区分性，也需要定义观察者、泄漏模型和计算假设，本文完全没有这些结构。按项目的 `T_crypto` 量表，本文正文证据为 **0**；把“taint 形式化为 IFC”算作相邻理论工作最多是 **1**，但那是程序分析理论，不是密码学。此判断为本人推断。
- **术语警告**：不要把 “taint” 读成密码学污点/MAC，不要把 “oracle” 读成密码学 oracle，不要把 “PoC” 读成密码学 proof，不要把 “source/sink” 读成协议角色；这些词在本论文中都是程序分析/系统安全术语。

## 11. 与应用密码学/密码工程可能的技术联系（严格；没有就写“无”）

**无。** 论文没有使用 OAuth/OIDC、TLS、签名、证书、VC、zk、TEE、远程 attestation、capability token、密钥管理或任何密码协议。

- **实际技术栈**：CodeQL（静态分析）、Z3（SMT 约束求解）、py-conbyte（concolic execution）、Python `inspect`/`sys.settrace`/`sys.addaudithook`（插桩/oracle）、LangChain（LLM 交互）、GPT-4o（生成/评分/调度/变异）（p.11–12）。这些是程序分析/LLM 工程工具，不是密码工程。
- **Docker/Jinja sandbox 不是 TEE**：§9 建议用 Docker 容器或 Jinja sandbox 隔离代码执行（p.15），但这是进程/模板隔离，不是硬件可信执行环境，也没有远程 attestation、密封密钥或密码学证明；论文没有评估这些隔离的强度。
- **可能的工程接口（本人推断，均不在论文中，且不解决核心问题）**：
  1. **TEE/远程 attestation** 可保护 Agent 运行时与代码完整性，但不能判断“用户 prompt 是否把污点带入 sink”；它保护的是执行环境，不是语义数据流。
  2. **签名工具清单/VC** 可证明“这个工具由某开发者发布”，但不能证明“这个工具的参数已被净化”；供应链签名与污点检测是正交问题。
  3. **capability token/权限 scope** 可在工具调用前限制可执行的操作（如禁止 `eval`），但本文的漏洞恰恰是 Agent 被诱导调用合法但危险的组件；能力约束可以减少 sink 集合，但不能替代语义 prompt 分析。
  4. **安全日志/透明日志** 便于事后审计，不是事前检测；**密钥管理** 可保护 LLM API key，但不阻止 RCE。
- **伪交叉警告**：给 prompt 签名、给工具调用加哈希、把 Agent 放进 TEE，都不会回答本文的问题——“哪条自然语言 prompt 会让 LLM 选择哪个组件、并把哪个参数送入哪个 sink”。本文的核心是语义种子生成、CFG 距离、concolic 约束求解和 prompt-to-argument 映射，密码工程最多提供执行边界与审计，不能提供这些语义能力。
- **结论**：按 `A_crypto` 量表，本文正文为 **0**。Docker/Jinja sandbox 是系统隔离，不是密码工程，也不涉及密码原语/协议/证明；即使把它硬算作“系统隔离工程”最多是 1，也不应据此抬高密码学相关度，故本项目判 **0**。此判断为本人推断。

## 12. 可检验的研究假设（3–6 条）

1. **H1（种子生成）**：功能特定的 LLM 生成种子比传统 PoC/扫描器种子带来更高的 sink 到达率和漏洞召回；在相同 Agent、相同 5 分钟预算、相同 LLM 下，NoGen 的 recall 显著低于完整 AgentFuzz（论文：54.29% vs 97.14%，少 16 个，p.14）。检验：随机化种子来源、多 Agent/多 LLM 重复实验，报告 recall 与 TTE 的置信区间；若差异不显著或方向反转，则 H1 被否证。
2. **H2（语义调度）**：当 Python 间接调用使 CFG 不完整时，semantic score 提供 distance score 之外的排序信息；在间接调用密度高的 Agent 上，NoSem 的 recall 下降更明显（论文：NoSem 77.14%，少 8 个，p.14）。检验：按间接调用密度分层，比较 NoSem 与完整版的 recall；若 distance-only 在高层也达到同等 recall，则 H2 被否证。
3. **H3（约束变异）**：concolic argument mutator + LCSM 对“参数必须满足代码约束”的 sink 是必要的；在带已知约束的合成 sink 上，NoMut 的约束满足率和 sink 到达率显著低于完整版（论文：NoMut 71.43%，少 10 个，p.14）。检验：构造带 `if`/`split`/正则约束的合成 Agent，测量约束求解成功率与 prompt 映射成功率；若 functionality mutator 单独达到同等效果，则 H3 被否证。
4. **H4（精确率/召回率的泛化）**：100% precision 与 97.14% recall 不是 20 个 Agent 样本、作者人工复核和循环 ground truth 的产物；在 held-out Agent、独立双盲标注、独立 ground truth 上，precision 仍高且 recall 不显著下降。检验：预注册 held-out 集，报告 FP rate、recall 及 95% CI；若 FP 率显著 >0 或 recall 大幅下降，则 H4 被否证。
5. **H5（成本结构）**：检测成本主要由 sink 数量和 5 分钟超时预算决定，而不是漏洞难度；TTE ≈ 总 CPU / 漏洞数，且总时间 ≈ sink 数 × 预算（论文：69.01 h ≈ 828×5 min，p.12）。检验：把超时改为 1/5/15 分钟，测量边际 recall/CPU hour、TTE 与 sink 数的关系；若 recall 随时长增加而显著上升、且与 sink 数无关，则 H5 被否证。
6. **H6（提示防护 vs 代码净化）**：对 taint-style sink，prompt-level 防护比 code-level sanitizer 更易被绕过；论文的 14/34 需要 LLM escape、5/34 需要 code escape 支持这一点（p.13）。检验：在同一组 Agent 上分别部署 prompt guard、sanitizer、两者组合，测量 bypass rate 与功能损失；若 prompt guard 的 bypass rate 不高于 sanitizer，则 H6 被否证。
