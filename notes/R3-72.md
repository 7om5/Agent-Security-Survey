## 1. 150–300 字中文概述

作者称本文为首篇系统研究 Agent 浏览器/扩展进程隔离安全性的工作。作者分析 2 个开源 Agent 浏览器与 7 个 Chrome 扩展，归纳共同架构：受信任的 background process 处理用户提示与 LLM 操作，不可信 renderer 渲染网页，二者通过经 browser process 代理的 IPC 通信。作者提出 MPI 与 SLI 两个端到端攻击：前者伪造 task panel→background 的 IPC 消息注入恶意 prompt；后者伪造 content script→browser process 的存储请求，读取 API key、邮箱与聊天历史。二者只需 renderer 任意代码执行，无需 sandbox escape。在 Chromium 130 上对 9 个系统验证，每个系统至少有一个攻击面成功；并用 HotCRP 论文窃取与 Gmail 鱼叉钓鱼演示。防御提出四项准则；guardrail LLM 在 WebArena 100 任务上把 BrowserOS/Nanobrowser 的 IPI ASR 从 89%/52% 降到 0，TSR 为 0.14/0.29。全文无密码学机制或形式化安全定义（pp.1–2、4–12）。

## 2. 研究背景、现有方法不足、精确定义的问题

**背景**：Agent 浏览器把 LLM 驱动的导航与操作集成进浏览器，已用于购物、任务自动化、抓取、网页助手等；Perplexity Comet 发布前 waitlist 超过一百万，OpenAI 与 Google 也推出 beta 版 Agent 浏览器（p.1）。这些系统按设计要跨多个 origin 读取内容、把内容送给 LLM、再在另一个站点执行认证操作，因此把"跨站"从传统扩展的边缘行为变成核心执行路径（p.2）。

**现有浏览器安全机制**：sandboxing、site isolation、same-origin policy（SOP）用于把不可信网页的影响限制在 renderer 内（p.3）。传统扩展通常只服务单一 origin，不根本改变跨站边界；Agent 浏览器/扩展则是一个"cross-site control plane"，攻陷其 Agent 操作进程等于控制多个相互隔离的 origin（p.3）。已有工作包括 UXSS 检测（FuzzOrigin）、Spook.js 对 Chrome strict site isolation 的推测执行攻击、Kim et al. 的扩展 IPC 伪造提权、以及大量 prompt injection/guardrail 研究（pp.13–14）；但作者称此前**没有工作系统分析 Agent 浏览器/扩展如何实现进程隔离、以及 renderer 被攻陷后这些隔离是否保护 LLM 操作**（p.1–2；这是原文的新颖性主张，非本人独立文献核查）。

**精确定义的问题**：在"攻击者控制网页并能在渲染该网页的 renderer 中取得任意代码执行"的前提下，(1) Agent 浏览器/扩展的进程隔离设计是否仍能保证用户 prompt 的真实性与 LLM 操作的完整性；(2) 不可信 renderer 能否通过 IPC 读取 Agent 的敏感存储（LLM 聊天历史、API key、身份信息）；(3) 若不能，根因是什么、应如何修复（pp.2、4–5）。论文的答案是：现有实现把"来自内部组件的 IPC 消息"默认为可信，导致两类攻击；修复需要 origin 校验、选择性存储访问控制、最小化信息暴露与 prompt 完整性保护（pp.2、9–12）。

**关键术语**（p.3）：*agentic extension* 指接受用户指令与网页内容、用 LLM 导航/交互/抽取/回答的浏览器扩展；*agentic browser* 把同样能力实现为浏览器原生功能；*action* 是点击、导航、输入等原语；*agent operation / LLM operation* 是由多个 action 组成的高层 Agent 行为。论文把二者混用。

## 3. Agent 系统模型（组件、交互流程、信任边界）

论文的架构分析基于 2 个开源 Agent 浏览器（BrowserOS 0.28.1、Vibe 0.1.8）与 7 个 Chrome 扩展（Nanobrowser 0.1.12、Sider 5.21.1、Eko 3.1.1、Magical 3.117.1、WebPilot 0.10.0730、HARPA AI 11.4.0、Bardeen 3.36.0）（p.3, Table 1）。

**组件与职责**（pp.3–4, Fig.2）：

| 组件 | 职责 | 信任级别 | 证据 |
|---|---|---|---|
| Browser process | 浏览器主进程：UI、文件操作、IPC 分发、网络；维护 process→origin 的可信映射表；代理 content script 与 background 之间的消息、代理存储访问 | 受信任 | p.3–4、p.9 |
| Renderer process | 按站点分配，渲染网页、执行 rendering/JS 引擎；承载网页脚本与注入的 content script（二者在不同 JS context） | 不可信（网页内容 + content script 同进程） | p.3–4、p.6 |
| Background process | 扩展 background script 与 task panel；拥有独立扩展 origin（`chrome-extension://<extensionId>`）、完整扩展 API；构造 LLM 查询并处理结果 | 受信任 | p.4 |
| Task panel | 接收用户指令的 UI；扩展中位于 background process；BrowserOS 为内置扩展；Vibe 把它放在独立 renderer（唯一 origin），并把 LLM 任务交给 browser/utility process | 受信任 | p.4、p.10 |
| LLM service | 外部 LLM，经 HTTP(S) 访问 | 外部服务（不作为本文攻击者；[推断]） | p.4 |
| Storage | 扩展 local/sync/IndexedDB；由 browser process 经 IPC 代理访问 | 敏感数据载体 | p.4、p.7 |

**交互流程**（p.4）：用户通过 task panel 输入指令 → task panel 用 `chrome.runtime.sendMessage` 把 prompt 发给 background script（内部经 browser process 代理）→ background script 构造 LLM 查询并经 HTTP(S) 发给后端 LLM → 收到响应后执行 LLM 指示的操作（读网页内容、输入文本等）→ 通过 IPC 让 content script/renderer 执行。Content script 需要存储时调用 `chrome.storage.local.get` 等扩展 API，同样由 browser process 代理并落到文件系统（p.4）。

**信任边界**：renderer 是不可信的，即使其中的 content script 是扩展代码；background process 与 task panel 是可信的；browser process 是可信中介，负责给 IPC 消息标注来源 origin；LLM 服务是外部依赖。论文明确假设攻击者**不能**在 background process 中取得任意代码执行（p.9）。这正是本文的核心：content script 与网页共享 renderer，renderer 被攻陷后，content script 的 IPC 能力可被攻击者冒用。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

**资产（由后果反推）**：
- 用户 prompt 的真实性与完整性，以及由 prompt 驱动的 Agent 操作完整性（p.2、p.5）；
- 其他 origin 的网页内容与已登录会话（跨站数据检索/交互）（p.6–7）；
- LLM 对话历史、LLM 服务 API key、用户姓名/邮箱等 PII、扩展设置（p.4、p.7）；
- 扩展/Agent 的存储条目（local、sync、IndexedDB）（p.7）。

**攻击者目标**（p.4, §3）：(1) 恶意 prompt injection，使受害者 Agent 以受害者身份执行攻击者选择的动作（发帖、访问恶意站点、点击广告、发送私有数据等）；(2) 窃取 Agent 可访问的私有信息（聊天历史、API key、PII、扩展设置）。论文用 HotCRP 论文摘要窃取与 Gmail 鱼叉钓鱼作为端到端目标（p.8）。

**攻击者能力**（pp.4–5）：
- Web attacker：控制自己的网站，诱导受害者 Agent 访问；
- 利用 renderer 的内存破坏漏洞（如 use-after-free、out-of-bounds）取得任意代码执行；论文引用 CVE 数据：2023-01 至 2025-12 Chrome 共 295 个 CVE，平均每月约 6 个内存破坏漏洞，平均每两个月至少一个可导致 renderer 任意代码执行的 CVE（p.5）；
- 在 JS API 之下直接使用 C++ 层 Mojo IPC 对象伪造消息（p.5、p.8）；
- **不需要**额外的 browser sandbox escape（这是与经典跨站攻击链的关键区别）（p.5）；
- 可逆向开源实现，知道消息格式与字段（p.5）。

**前提假设**（pp.4–8）：
- 受害者在启用 Agent 的情况下访问攻击者页面，且该页面的 content script 已加载；
- 受害者在目标站点（HotCRP、Gmail 等）已登录，Agent 拥有相应操作权限；
- background process 与 task panel 未被攻陷；browser process 可信并正确标注 IPC 来源；
- 攻击者不掌握 LLM 服务内部；论文未讨论攻击 TLS/服务器证书，这是从其 "web attacker + renderer RCE" 威胁模型推出的范围（[推断]）；
- 攻击者可以托管页面、接收 HTTP 请求、在页面中放置 exploit（p.8 的 HotCRP 场景）。

**不在威胁模型内**（其中只有"可信组件自身被攻陷"是作者明说，其余为[推断]）：background/task panel 被攻陷（p.9 明确排除）、恶意扩展更新、网络中间人、LLM 服务被攻陷、OS/浏览器进程外的攻击、侧信道、用户恶意。

## 5. 核心方案（方法、攻击/防御流程、关键定义）

### 5.1 架构观察与两个根因

作者先归纳共同模式：background process 处理 prompt 与 LLM 操作，renderer 渲染不可信网页，browser process 代理 IPC 与存储（pp.3–4, Fig.2）。随后指出两个根因（p.9）：(1) 对用户 prompt 的来源没有真实性验证；(2) renderer 进程对存储条目有不受限的访问。二者都源于"来自扩展/浏览器内部组件的 IPC 消息默认可信"这一隐含假设。

### 5.2 MPI（malicious prompt injection）攻击

**前提**：攻击者已在渲染自己页面的 renderer 中取得任意代码执行；content script 已注入该页面。**步骤**（pp.5–6, Fig.3 左一）：
1. 攻击者伪造一条本应由 task panel 发给 background script 的 IPC 消息，例如 Nanobrowser 的 `{'type': 'new_task', 'task': 'Go to gmail.'}`（p.5；这是论文中的不可信示例数据，未执行）；
2. 通过 C++ Mojo IPC 对象把消息发给 background script；
3. background script 不校验来源，把 `task` 字段当作合法用户 prompt 转给 LLM；
4. LLM 按注入的 prompt 生成动作，Agent 执行任意允许的操作。

**根因**：background script 盲目信任内部 IPC；实现假设只有 task panel/background script 会发这类消息，因此不做授权或 origin 校验（pp.5–6）。JS 层虽然只把扩展 API 暴露给 content script、不暴露给网页脚本，但 renderer 被攻陷后攻击者可在 C++ 层绕过 JS 隔离（p.6）。

**后果**（p.6, Table 2）：可读网页内容、点击按钮、URL 导航、输入文本、让 Agent 参考聊天历史；进而实现跨站数据检索、跨站交互与数据外泄。论文称这"effectively bypasses site isolation"，因为无需 sandbox escape 就能让 Agent 执行跨站操作（p.5）。

### 5.3 SLI（stealing LLM-accessible information）攻击

**前提**：同 MPI；攻击者页面已加载目标扩展的 content script。**步骤**（p.7, Fig.3 左三）：
1. 攻击者伪造 content script 发往 browser process 的存储访问 IPC 请求；
2. browser process 校验"发送消息的 renderer 是否加载了该扩展的 content script"；由于受害者确实在攻击者页面启用了 Agent，校验通过；
3. browser process 无法区分伪造消息与合法 content script 消息，返回请求的存储条目；
4. 攻击者读取 API key、姓名、邮箱、LLM 聊天历史等。

**根因**：实现假设只有可信内部组件会访问扩展/Agent 存储，但 content script 默认也有 `chrome.storage.local.get` 等访问权；browser process 只验证"该 renderer 加载了 content script"，不验证"这条消息是否由该 content script 的合法逻辑发起"（p.7）。HARPA AI 把数据放在 IndexedDB（origin-scoped），但仍实现了一个允许 content script 请求 IndexedDB 条目的 IPC 通道，因此仍可被 SLI 读取（p.7）。

### 5.4 组合利用与可行性

- **HotCRP 论文摘要窃取**（p.8, Fig.4）：MPI 让 BrowserOS 依次导航到 HotCRP、点击下载、打开论文文件 URL、读取并总结摘要、再导航到攻击者页面并把摘要放进 URL query；攻击者服务器收到含摘要的请求。作者在测试 HotCRP 实例上完成 PoC。
- **Gmail 鱼叉钓鱼**（p.8, Fig.5）：先 SLI 读取 Nanobrowser 的聊天历史，再 MPI 让 Agent 起草钓鱼邮件、打开 Gmail、点击 compose、填收件人/主题/正文、点击发送。邮件内容贴合受害者真实身份与近期活动，且由合法邮件提供商签名，因此更具可信度（p.8）。
- **可行性**（pp.8–9, §4.4）：在 Chromium 130.0.6723.160 上安装 7 个扩展；2 个浏览器基于同一 Chromium 本地构建；攻击页面利用 CVE-2025-0291 与 Issue 379140430 取得 renderer RCE，再用 Mojo IPC 伪造消息；作者称验证了 Table 2 的全部后果，且无需 sandbox escape。

### 5.5 四项防御准则

1. **检查用户 prompt 来源（§5.1, pp.9–10, Fig.6）**：background script 只接受来自 task panel 的 `new_task` 消息；检查 `sender.origin === SELF_ORIGIN` 且 `sender.url === TASK_PANEL_URL`。消息 origin 由 browser process 根据可信的 process→origin 映射赋值，renderer 不能篡改。论文给出 PoC 代码（p.9）。
2. **选择性存储访问控制（§5.2, pp.9–10, Fig.7）**：禁止 renderer 直接访问存储；使用 IndexedDB（按 origin 隔离）或在 `chrome.storage.local` 上启用 `TRUSTED_CONTEXTS`；content script 通过 IPC 向 background script 请求数据，background 只返回 `SAFE_KEYS` allowlist 中的条目。Vibe 没有 `setAccessLevel` API，需由 browser process 对来自 task panel 可信 origin（如 `http://localhost:5173`）的请求放行，对其他 origin 应用同一 allowlist（p.10）。
3. **最小化信息暴露（§5.3, pp.10–11）**：allowlist 应保守，只暴露 content script 严格需要的数据；隐私敏感操作尽量留在 background script。反例是 Sider 允许 content script 直接读取 LLM API key 来验证 LLM 可用性（p.11）。
4. **保持 prompt 完整性（§5.4, pp.11–12, Fig.8）**：origin 校验不能防间接 prompt injection（IPI）。作者提出 guardrail LLM：对 planner，阻断网页内容→高层计划的直接信息流；对 navigator，把新 action 与可信的 plan、用户原始 prompt、已执行 action 历史一起交给 guardrail LLM，判断一致性并输出 ALLOW/BLOCK、风险分、mismatch level、证据与理由（pp.11–12；系统 prompt 见 p.16, Table 4）。

### 5.6 Guardrail 的实现与评测

在 Nanobrowser 与 BrowserOS 上实现，guardrail 是一个额外的 LLM 实例，充当分类器；输入为可信数据（用户 prompt、已完成计划、当前计划、已执行 action）与待验证的新 action；输出 JSON（decision、risk_score、mismatch_level、evidence、short_rationale）（p.11、p.16, Table 4）。评测用 WebArena 的 100 个任务（从 5 个可正常运行的网站随机采样），TSR 衡量正常任务成功率；IPI 用 InjecAgent 为每个任务生成单步（URL 导航）注入 prompt，并修改 prompt 以绕过 BrowserOS 的 XML 标签隔离（如 `</browser-state>`）（p.11–12）。

### 5.7 讨论中的 MCP 重构

作者报告后，BrowserOS 改为用本地 MCP server（而非 background script）处理用户 prompt，task panel 通过 HTTP 请求把 prompt 发给该 server。作者称已确认类似的 MPI 攻击仍可行：攻击者网页可向 local server 发伪造 HTTP 请求注入 prompt，且不再需要内存破坏漏洞（p.13）。但正文没有给出该验证的实验设置、样本或数据，因此这里把它记为作者主张而非可复现实验。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

**没有形式化安全模型。** 全文没有密码学或系统安全意义上的 security game、adversary advantage、theorem、lemma、proof、reduction 或安全参数；没有给出"site isolation 安全"的精确定义，也没有证明任何防御满足某个定义（pp.5–12 全文核查）。所谓"authenticity verification"是 background script 对 `sender.origin`/`sender.url` 的检查，是**系统级的来源元数据校验**，不是密码学认证（无签名、MAC、证书或密钥）（pp.9–10）。

**非形式化定义**只有术语定义（agentic extension/browser、action、agent operation）与攻击分类（MPI/SLI）（pp.3、5、7）。安全属性是隐含的：
- prompt 的真实性/完整性（只有 task panel 能发起 LLM 指令）；
- Agent 操作的完整性/授权（不可信网页不能借 Agent 的权限执行跨站动作）；
- 存储的机密性/访问控制（renderer 只能拿到 allowlist 数据）。

**指标**：Table 2 是二值成功矩阵（✓/–），不是概率或比率；guardrail 用 TSR 与 ASR（p.12, Table 3）。论文没有定义 ASR 的分母/置信区间/重复次数；从上下文看 ASR 是 100 个 IPI 尝试中成功的比例（p.12）。Table 2 的每个单元格是"是否验证成功"的 PoC 结果，不是统计估计（p.8–9）。

**经验主张**：
- "所有被分析的 Agent 浏览器/扩展都易受攻击"（p.2；但按 Table 2，更准确的说法是"每个系统至少对 MPI 或 SLI 之一易受攻击"，WebPilot 不易受 MPI，Vibe 在表中没有 SLI 成功项，见 §9）；
- "两个根因"（p.9）；
- "四项防御可修复"（pp.9–12；其中 §5.1/§5.2 只有设计/PoC 代码，没有对真实攻击的端到端评测；只有 guardrail 有 100 任务评测）；
- "guardrail 完全阻断 IPI，ASR 降到 0"（p.12, Table 3；仅在特定 100 任务、单步 IPI、非自适应攻击者下）。

**关于 "site isolation is dead" 的准确含义**（pp.2、5、13）：论文不是说 Chromium 的进程隔离机制本身被密码学或内存安全攻破；renderer 仍然被隔离，攻击也没有 sandbox escape。它说的是：Agent 浏览器/扩展**故意**把跨站能力暴露给 Agent，renderer 被攻陷后可借 Agent 的合法权限执行跨站操作，因此"不可信站点不能导致跨站访问"这一安全目标不再成立。更准确的分类是 **confused deputy / 授权边界失败**，而不是进程隔离实现失败。见 §10 的严格区分。

## 8. 贡献与创新点（按原文主张）

1. **首个系统研究**：据作者所知，首次系统调查 Agent 浏览器/扩展如何实现进程隔离，并归纳出"background 处理 LLM 操作、renderer 渲染不可信网页、IPC 为桥"的共同架构（pp.1–2、3–4）。
2. **两个新端到端攻击**：MPI（伪造 task panel→background 的 IPC，注入 prompt）与 SLI（伪造 content script→browser process 的存储请求，窃取 LLM 相关数据）；二者只需 renderer 内存破坏 RCE，不需要 sandbox escape（pp.2、5–8）。
3. **覆盖全部被测系统**：2 个浏览器 + 7 个扩展均至少有一个攻击面成功；Table 2 给出后果矩阵（pp.2、6）。
4. **四项防御准则**：origin 校验、选择性存储访问控制、最小化信息暴露、prompt 完整性保护；并给出 guardrail 原型与评测（pp.2、9–12）。
5. **开源 artifact**：guardrail 实现与端到端攻击演示视频，GitHub `WSP-LAB/Site-Isolation-is-Dead`（p.2）。

**与直接相关工作的差异**（pp.13–14）：Kim et al. [43] 伪造 content script→extension page 的 IPC 以访问扩展存储；本文把伪造目标扩展到 task panel→background（在 Agent 系统中被视为可信的组件），并展示跨站 site isolation 绕过；Spook.js [16] 是推测执行侧信道，不是 IPC 伪造；UXSS/FuzzOrigin [42]、[50] 是浏览器实现漏洞；prompt injection 文献 [35]、[72] 关注内容注入，本文的 MPI 是 IPC 层伪造，guardrail 则针对 IPI。作者还区分了 GuardAgent [66]、AirGapAgent [18]、Task Shield [40]、AgentSentinel [38] 等防御（pp.13–14）。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 我的推断）

**作者承认/明说的不足**：
- **可信组件不可被攻陷**：安全性只在 renderer 不可信、task panel/background 可信且未被任意代码执行的假设下成立；可信组件自身被攻陷超出范围（p.9）。
- **人工验证**：攻击分析依赖手工逆向与 PoC，自动化检测留作 future work（p.13）。
- **IPI 不稳定**：简单 IPI 在不同系统上 ASR 差异大（BrowserOS 89%、Nanobrowser 52%），多步 IPI 实验失败；因此 guardrail 评测只用单步 URL 导航注入（pp.12–13）。
- **MCP 重构缺少实验细节**：BrowserOS 改为本地 MCP server + HTTP 后，作者称已确认类似 MPI 仍可行且不需要内存破坏，但正文没有给出实验设置/数据（p.13）。
- **Guardrail 的代价**：BrowserOS TSR 下降（正文称 6%）；planner 信息减少会影响任务成功率；guardrail 是额外 LLM 调用（p.12）。
- **传统恶意软件/磁盘访问**：能访问受害者磁盘的恶意软件仍可窃取存储中的聊天历史；作者建议加密存储（p.12）。
- **Confidential computing / sandboxing / 用户同意**：作为未来方向，未实现（p.12）。
- **伦理**：已向所有厂商披露；BrowserOS 已修复；其余等待回复（p.16, Appendix A）。

**论文附带的 PC meta-review 关注点（非作者自述，p.18, Appendix E）**：
- 威胁模型要求 zero-day 内存破坏漏洞才能形成攻击链；
- 与既有 IPC 伪造工作相比，新颖性区别不够清楚（task panel→background 的伪造是否只是目标组件不同）。

**我的推断/补充批评**（不是作者原话）：
- **"all tested vulnerable" 的表述过强**：摘要与 §1 说所有系统易受"these attacks"，但 §4.1 明确 WebPilot 不易受 MPI，Table 2 中 Vibe 没有 SLI 成功项、BrowserOS 没有 SLI 成功项。准确说法是"每个系统至少对一种攻击易受攻击"；这不影响论文的核心，但影响摘要的精确性（pp.1–2、6–7）。
- **"6% decrease" 与 Table 3 矛盾**：0.20→0.14 是 6 个百分点（相对 30%），不是 6%（p.12）。这是明确的数字表述错误，不能当作"轻微性能损失"的证据。
- **Table 2 的 "–" 语义不清**：表注说 "–" 表示功能不支持，但对 SLI 的 "Read name/email/chat history"，"–" 可能表示未存储、不可访问或未测试；论文没有区分。因此不能把 "–" 一律解读为"安全"（p.6）。
- **攻击矩阵是二值 PoC，不是统计**：每个单元格只说明"验证成功/未成功"，没有重复次数、成功率、不同版本/配置的方差；"all vulnerable" 是定性结论（pp.6、8–9）。
- **旧版 Chromium + 已知 CVE**：实验固定在 130.0.6723.160，利用 CVE-2025-0291 与 Issue 379140430；在已修补的当前 Chrome 上，攻击是否仍成立取决于是否有新的 renderer RCE，论文没有回答（p.8）。Meta-review 也指出这一点（p.18）。
- **§5.1/§5.2 防御未端到端评测**：Fig.6/Fig.7 是代码级 PoC，论文没有报告"开启 origin check 后 MPI 成功率"或"开启 TRUSTED_CONTEXTS 后 SLI 成功率"的测量；只有 guardrail 有 100 任务评测（pp.9–12）。
- **Guardrail 的对抗鲁棒性未知**：guardrail 本身是 LLM 分类器，论文没有测试针对 guardrail 的自适应注入（例如伪造可信 plan/action history、污染 guardrail 输入），也没有报告延迟/成本/误报率；"ASR=0" 只是在固定 100 任务、单步 IPI、非自适应条件下（pp.11–12）。
- **"site isolation is dead" 是修辞性框架**：真正失败的是 Agent 的授权/来源校验，不是 Chromium 的进程隔离；renderer 仍被隔离，攻击也没有 sandbox escape。作者自己在 p.5 说"effectively bypassing site isolation"，但标题容易被误读为 OS 隔离机制本身失效（pp.2、5、13）。这是本文最重要的概念澄清点。
- **术语 "site" 与 "origin" 混用**：SOP 的 origin 是 scheme+host+port（p.13，引 RFC 6454），而 Chrome site isolation 按 site（eTLD+1）分配进程（p.13 引 Spook.js）；论文有时说"each website"、有时说"origin"，严格性不足（pp.3–4、13）。
- **选择偏差与外部效度**：只分析 2 个开源浏览器、7 个扩展、Chromium；闭源 Comet/Atlas/Gemini 未测；商店前 40 结果的选择不能代表生态（p.3）。
- **缺少对扩展权限模型、MV3 service worker、CSP、isolated world、process reuse、site isolation 模式（strict/partial）的讨论**；这些都会影响攻击可行性（全文未涉及）。
- **没有多 Agent/MCP/A2A 的实验**：MCP 只在讨论中出现，作者主张但无实验细节（p.13）。
- **对 "LLM 服务" 的信任假设未展开**：论文把 LLM 服务当外部黑盒，没有分析 LLM 输出被污染、API 被中间人、或模型拒绝等情况（pp.3–4）。

## 10. 与理论密码学的可能联系（严格；没有就写"无"）

### 10.1 先厘清：site isolation 不是密码学

Site isolation 是浏览器的**进程/源隔离架构**：按 site 分配 renderer 进程、用 OS sandbox 限制进程、用 IPC 和 browser process 做中介（pp.3–4）。它依赖的信任边界是：
- **origin** 的定义是 scheme + host + port（p.13 引 RFC 6454）；
- HTTPS 的 origin 认证在现实中依赖 **TLS/服务器证书/PKI**（一般 Web 安全背景，论文未展开，也未把它作为分析对象）；
- SOP 的执行是浏览器策略（DOM 访问控制、IPC 来源检查），不是密码协议（一般背景；论文 pp.3–4 只描述机制）；
- site isolation 的进程边界由 OS/浏览器实现，不是密码原语（pp.3–4）。

本文的攻击**没有**破坏 TLS、证书、签名或任何密码认证（[推断]，因为论文没有分析这些机制）：攻击者在 renderer 取得 RCE 后，在 C++ 层伪造 IPC，browser process 仍按可信映射标注来源；攻击利用的是 Agent 的合法跨站权限（confused deputy），不是伪造密码学凭证（pp.5–7）。因此必须区分：
- **SOP/授权被绕过**：是。Agent 代表攻击者执行跨 origin 读写，安全目标失败（pp.5–7）。
- **密码学认证失败**：否。没有证书伪造、TLS 降级、签名伪造、MAC 伪造。
- **进程隔离实现失败**：否。renderer 仍在自己的进程内，攻击不需要 sandbox escape（p.5）。
- **授权/来源校验失败**：是。background 信任 task panel 消息、browser 信任 content script 存储请求（pp.5–7）。

### 10.2 形式化密码机制：无

全文没有：
- 安全定义/游戏（IND-CPA、INT-CTXT、authenticated channel、capability unforgeability 等）；
- 构造（签名、MAC、KEM、PAKE、VC、zk、MPC、FHE、承诺等）；
- 定理、引理、证明、归约、安全参数、敌手优势；
- 密钥、证书、nonce、会话、身份凭证、attestation 报告。

唯一出现 "signed" 的地方是 p.8 描述钓鱼邮件"由合法邮件提供商签名"，这是社会工程可信度因素，不是本文分析或构造的密码机制。因此 **T_crypto = 0（偏 0；若把"来源真实性"硬类比为认证，最多 1/5，但本文没有形式化模型，也不存在需要密码学理论解决的核心问题）**。

### 10.3 按交接文档 §6.1 的五个问题

1. **保护什么、抵抗何种对手？** 保护用户 prompt 的真实性/完整性与 LLM 可访问存储的机密性；对手是控制网页、能在 renderer 取得任意代码执行的 Web attacker（pp.4–5）。这是一个**系统授权/进程隔离**问题，不是密钥/密文问题。
2. **是否需要密码学原语，而非普通访问控制？** **不需要**（[推断]）。论文的四项防御是 origin 校验、存储 ACL/allowlist、最小化暴露、LLM guardrail；它们都不依赖密码原语。密码学也无法直接解决核心问题：renderer 与 content script 同进程，攻击者取得 RCE 后可以调用 content script 的合法 IPC 能力；即使给 IPC 消息加 MAC，密钥若在同一 renderer 内也会被攻击者拿到（[推断]）。真正的修复是把**策略执行点**放在不受 renderer 控制的 browser/background 进程，并限制 renderer 可请求的能力（pp.9–10）。
3. **适用原语/工具（推断）**：若要把该系统"密码化"，可考虑对 task panel↔background 的 IPC 做基于 OS 密钥库/TPM 的 MAC 或签名、对扩展代码做签名/attestation、对存储做加密、对 Agent 动作做 capability token；但这些都**不是论文实现的**，而且不能解决"合法 content script 被 RCE 冒用"的问题。把它们写进本文会构成过度包装。
4. **能否形成严谨的安全定义与证明义务？** 可以形式化"来源真实性"与"存储访问授权"作为系统级访问控制属性（例如：任何不可信 renderer 产生的消息都不能改变 background 的 prompt 状态），但这更像**访问控制/信息流**定义，不是密码学游戏（[推断]）。若硬做成密码学定义，需要定义"compromised renderer 与诚实 content script 不可区分"的认证目标；但在同进程模型下，攻击者拥有 content script 的全部能力，认证无法区分"合法调用"与"恶意调用"，定义会退化为能力限制问题（[推断]）。**因此本文不适合作为理论密码学选题。**
5. **哪些问题不是密码学能解决的？** prompt injection 的语义、Agent 对网页内容的意图理解、confused deputy、IPC 信任、进程隔离、guardrail 分类器的误报/漏报、用户授权语义。这些是系统/PL/ML 问题；签名、加密、TEE 只能保护"谁说了什么"，不能保证"这句话是否符合用户意图"（pp.5–12）。

## 11. 与应用密码学/密码工程可能的技术联系（严格；没有就写"无"）

### 11.1 论文已实现/研究的密码机制：无

- **TLS/HTTPS**：论文提到 background script 经 HTTP(S) 访问 LLM 服务（p.4），Web 站点自然是 HTTPS；但论文没有分析 TLS 配置、证书校验、pinning、握手或中间人，也没有把 TLS 作为防御测量。
- **加密存储**：p.12 只建议"properly encrypting these sensitive entries"以防磁盘恶意软件，没有给出加密方案、密钥管理、性能或评测。
- **Confidential computing**：p.12 只把"preserving the integrity of user prompts through confidential computing"列为有前景的未来方向，没有设计、原型或实验。
- **代码签名/扩展签名**：Chrome 扩展部署天然涉及签名，但论文没有讨论，也没有将其纳入威胁模型或防御。
- 没有 OAuth/OIDC、VC、TEE attestation、zk、MPC、PAKE、签名日志等。

因此 **A_crypto ≈ 1/5**：有一般安全功能（浏览器隔离、访问控制、HTTPS 背景），但没有识别/实现/评测具体密码机制；不能因为出现 "authenticity"、"integrity"、"confidential computing"、"encrypt" 等词就抬高相关度。

### 11.2 可自然扩展的密码工程接口（明确标"研究推断"）

- **IPC 消息认证**：在 browser/background 之间对"用户 prompt"消息做 MAC/签名，绑定 task panel 身份与消息序号；但前提是密钥不在 renderer 内，且 content script 不能代表用户。该机制只能防"外部伪造"，不能防"被 RCE 的 renderer 冒用合法 content script 通道"。
- **扩展/Agent 代码签名与 attestation**：验证 task panel/background 代码完整性；与本文的 renderer 威胁模型配合有限，因为攻击者攻击的是网页渲染进程，不是扩展代码。
- **OS 密钥库/TPM 保护 API key**：把 LLM API key 存在 OS keychain/TPM，content script 只能通过受控 IPC 使用而不导出明文；这能缓解 SLI 的 API key 窃取，但不能阻止 Agent 代表攻击者调用 LLM。
- **存储加密 + 每扩展密钥**：防止磁盘上的聊天历史被离线读取（p.12 的建议），但对在线 SLI（renderer 通过合法 IPC 请求解密）无效，除非访问策略在 background 强制执行。
- **Capability/least privilege**：把 Agent 的跨站动作拆成细粒度 capability（读哪个 origin、能否点击、能否输入），在 browser process 强制；这比密码原语更贴近本文根因，但属于授权系统/PL 方向。
- **TEE/confidential computing**：把 background/LLM 调用放入 TEE，保护 prompt 与密钥不被 renderer 读取；但 renderer 仍可通过合法 IPC 请求动作，TEE 不能判断语义意图；且论文没有实现。

### 11.3 伪交叉警告

- **"给 prompt 签名"**：只能证明"这条 prompt 来自某个 key"，不能证明它是用户真实意图；本文的 MPI 是 renderer 冒用 task panel 的通道，签名密钥若在 renderer/扩展内仍可能被滥用。
- **"给执行日志签名"**：只能事后取证，不能阻止跨站动作。
- **"用 ZK 证明模型运行了某步"**：不解决用户授权与 prompt 注入。
- **"把 OAuth/TLS 包在 Agent 外"**：不解决 renderer 已取得代码执行、Agent 自愿执行恶意动作的问题。
- **"TEE 跑整个浏览器"**：如果 renderer 仍在 TCB 外，TEE 只能保护 TEE 内的 background/密钥；如果 renderer 在 TCB 内，则 RCE 直接破坏 TEE 保证。本文没有讨论这种划分。

## 12. 可检验的研究假设（3–6 条）

- **H1（版本依赖性）**：在已修补 CVE-2025-0291 / Issue 379140430 的当前 Chrome 上，原 PoC 的 MPI/SLI 成功率应降到 0；攻击只在存在新的 renderer RCE 时复现。检验：在 Chromium 130 与最新稳定版上跑同一 exploit，比较 Table 2 单元格。若最新版仍成功，说明还有未修补路径（pp.8–9）。
- **H2（防御覆盖互补性）**：§5.1 的 origin 校验只阻断 MPI，不阻断 SLI；§5.2 的存储访问控制只阻断 SLI，不阻断 MPI；两者同时启用才能覆盖 Table 2 的两类攻击。检验：2×2 开/关实验，分别在 Nanobrowser/BrowserOS 上测 MPI/SLI 成功率（pp.9–10）。
- **H3（功能代价）**：启用 `TRUSTED_CONTEXTS`/IndexedDB + allowlist 后，依赖 content script 直接读存储的合法功能（如 Sider 的 API key 可用性检查）会出现功能回归；回归程度与 allowlist 保守程度正相关。检验：在 7 个扩展上跑正常任务集，测 TSR/功能通过率与 SLI 成功率（pp.10–11）。
- **H4（guardrail 自适应脆弱性）**：guardrail LLM 的 ASR=0 在自适应攻击下不成立；攻击者若能把伪造的"可信 plan/action history"注入 guardrail 输入，或针对 guardrail 的 system prompt 做注入，ASR 会显著上升。检验：在 WebArena 100 任务上加入自适应 IPI，比较 ASR 与延迟/token 成本（pp.11–12、16）。
- **H5（"all vulnerable" 的分解）**：按攻击类型分解后，WebPilot 的 MPI 成功率为 0、Vibe 的 SLI 成功率为 0；因此"所有系统都易受两种攻击"不成立，只有"每个系统至少易受一种"成立。检验：重复 Table 2 的 9×9 矩阵（每格 N≥10），报告每格成功率与置信区间（p.6）。
- **H6（MCP 重构的可迁移性）**：BrowserOS 的本地 MCP server + HTTP 设计，若无 origin/token 校验，可被攻击者网页通过伪造 HTTP 请求（含 DNS rebinding/CSRF）注入 prompt，且不需要 renderer RCE；若有严格的 Origin/CSRF token 校验，则攻击失败。检验：对 BrowserOS 新版本做黑盒/白盒测试（p.13；作者称已确认可行，但正文无实验设置/数据）。
