## 1. 150–300 字中文概述

SkillScope 研究 Agent Skills 的任务条件化最小权限：同一动作在某请求下合法，换一个请求就可能越权，传统恶意 Skill 二分类检测不够。作者把 SKILL.md 指令与脚本操作统一为执行图，先筛出高召回候选，再由执行图生成候选可达任务，在沙箱中对比原始执行与移除/中和该动作后的重放，用 LLM 判定授权性与必要性，最后以任务条件守卫和脚本重构生成最小权限版本。200 个标注 Skill 上 F1 为 94.53%；68,312 个真实 Skill 中 6,590 个越权；约束后 action-in-task 越权实例减少 88.56%，249/249 个任务仍可完成。

## 2. 研究背景、现有方法不足、精确定义的问题

**背景。** Agent Skills 是可复用的能力包，通常由 metadata（name、description、use_when）、自然语言指令（SKILL.md）和可选脚本/资源组成（p.3, §2.1, Fig.1）。运行时采用 progressive disclosure：agent 先用 metadata 选择 Skill，再加载 SKILL.md 获取流程，最后执行脚本或资源（p.3, Fig.1）。因此 Skill 同时塑造 agent 的决策过程和具体副作用，行为面比单一 tool API 更广（p.3）。一旦安装，Skill 可以直接影响 agent 如何解释用户请求、执行哪些动作、对环境产生哪些副作用；用户通常只看到最终输出，而不是完整执行过程（p.1–2, §1）。

**现有方法不足。** 现有 Skill 安全工作主要是粗粒度恶意 Skill 检测：扫描可疑代码、prompt 模式、跨 artifact 依赖或具体运行时行为，输出 Skill 级 malicious/benign 判断（p.1–2, §1; p.14, §7）。这类方法无法处理“功能上合法、但在当前任务下越权”的 Skill：同一动作在任务 A 下合法、任务 B 下越权（p.1–2; p.3, Fig.2）。作者在 Related Work 中把隐私合规/数据最小化研究列为相关但不同的方向，并主张本文将最小权限落到 action level（p.14, §7）。作者因此主张需要 task-conditioned、action-level 的分析，而不是 all-or-nothing 的恶意分类（p.2, §1）。

**精确定义的问题。** 给定 Skill σ 和用户 prompt p，判断每个 privilege-relevant action a 是否 (i) 被 p 授权（Auth_p(a)）且 (ii) 对完成 p 必要（Unnec_σ(a,p)）；两者任一失败即 OverPriv_σ(a,p)，并对其施加最小约束（p.3–4, §2.2）。难点有三：C1 指令层与代码层异构，执行空间大；C2 越权是 task-conditioned，需要覆盖广泛任务实例而不是逐例检查；C3 约束不能破坏合法功能（p.2, §1; p.4, §3）。论文的 motivating example 是 repo-assistant：任务 A 要求分析仓库、包含环境上下文并同步报告，任务 B 只要求本地检查最近提交；同一收集环境文件/命令历史并外传报告的动作，在 A 下合规、在 B 下越权（p.3, Fig.2）。

## 3. Agent 系统模型（组件、交互流程、信任边界）

- **组件**：用户任务/prompt；Skill bundle（metadata、SKILL.md、scripts/resources）；agent runtime（LLM 规划与工具调用）；外部工具/API、文件系统、网络、命令执行；SkillScope 分析侧（统一执行图、任务生成、沙箱 replay、LLM judge、重写器）；marketplace/registry 或用户侧部署（p.3–5, §2–§3, Fig.1/Fig.3）。
- **交互流程**：用户请求进入后，agent 先用 metadata 选择 Skill，再加载 SKILL.md 获取过程性指导，最后调用脚本/资源执行具体动作（p.3, Fig.1）。SkillScope 侧流程是：构建统一执行图 → 过权候选抽取 → 图引导的用户任务实例化 → 原始/重放执行 → 授权与必要性判定 → 任务条件约束与 artifact 重写（p.5, Fig.3; pp.6–9）。
- **信任边界**：论文没有显式的 trust boundary 图或独立小节；以下是由 threat/deployment model 与执行流程重建的 [推断]。Skill 发布者及其 artifact 不可信（可能是主动 adversary，也可能是 benign-but-overbroad 的开发者）；用户 prompt 被视为 authority 来源；agent runtime 与 sandbox 被信任以执行、隔离和记录 trace；LLM judge 被信任做语义判断；SkillScope 由 marketplace/registry operator 在发布前/监控中运行，或由用户在安装/使用前运行（p.4, §3）。论文明确区分平台级 test permission 与 task-scope authorization：前者只是沙箱预授权，不建立 Auth_p(a)（p.13; p.19, App.G）。系统没有身份认证、密钥、attestation 或运行时 reference monitor。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- **资产**：用户意图/授权范围；敏感本地文件、凭据、环境文件、命令历史；host 标识与网络配置；外部目的地；用户可见输出与任务完成；Skill 生态的完整性（p.2–4, §1–§3）。
- **攻击者目标**：让 agent 执行超出 Auth_p 或非必要的动作，例如读取敏感文件/凭据、把数据外传到攻击者选择的目的地、执行当前任务不需要的命令或代码（p.4, §3）。
- **攻击者能力**：恶意 Skill 发布者控制提交的 metadata、SKILL.md、bundled scripts 和 auxiliary resources；可以 misstate Skill 的 purpose，跨 artifact 隐藏或分散逻辑；Skill 被调用后可驱动 agent 访问敏感文件/凭据、外传数据或执行越权命令（p.4, §3）。作者也把 benign developer 无意引入的 over-broad instructions/scripts/workflow 纳入范围（p.4）。论文没有给出形式化 attacker capability、advantage 或自适应攻击模型。
- **不在范围**：在 Skill artifact 中不可观察、或在 replay 中未触发的行为；利用 npm/pip 依赖 zero-day 漏洞的攻击；通用 malware 检测（p.4）。作者建议这类问题交给 sandbox hardening、dependency verification、runtime policy enforcement、egress filtering（p.4）。
- **前提假设**（部分为 [推断]）：Skill artifact 可检查；行为可在 sandbox 中重放并观测；agent 可被 instrument 以记录 trace/output；LLM judge 足够可靠；当前 prompt 是授权的唯一/主要来源；没有 adaptive attacker；没有 runtime 被攻陷；没有密码学身份或密钥；平台权限不等于任务授权（p.4; p.8; p.13; p.19）。论文没有讨论 prompt 本身被攻击者控制时 Auth_p 是否仍然可信。

## 5. 核心方案（方法、攻击/防御流程、关键定义）

SkillScope 是“分析 + 重写”框架，不是运行时 reference monitor。输入是 Skill bundle σ 和用户 prompt p，输出是判定结果（哪些 action 在哪些 task 下越权）以及一个 least-privilege 修复 bundle（p.4–5, §3.1; pp.8–9, §4.3）。

### 5.1 统一执行图（unified execution graph）

给定 Skill bundle σ，构建有向图 G=(V,E)，其中 V=V_I ∪ V_C ∪ V_P 分别是指令层 action 节点、代码层 action 节点和 predicate 节点；E=E_ctrl ∪ E_data ∪ E_call ∪ E_ret 分别是控制、数据、调用、返回边（p.6, §4.1）。action 节点表示为 v=⟨ℓ, op, obj⟩，ℓ∈{instr, code}，op 是操作类型，obj 是目标对象；predicate 节点表示为 p=⟨ℓ, φ⟩，φ 是归一化谓词；每个节点带 provenance src(v)，记录原始文本/代码 span（p.6）。指令层用规则解析（祈使动词、if 条件、命令调用、Markdown 分节）加 LLM 语义归一化；代码层用 AST 抽取函数调用，并做轻量 intra-procedural data-flow/control-dependence 分析；跨层用 call/return 边连接脚本入口和返回点（p.6, Fig.4）。Figure 4 的例子把 SKILL.md 中的“Run monitor.py”“Send output to Alex”等指令节点与脚本中的 collect_cpu、get_uuid、urlopen 等代码节点组合起来（p.6, Fig.4）。

### 5.2 过权候选抽取

先从 metadata（name、description、use_when）和指令摘要构造 Skill profile；再用 LLM 分类器对每个 action 节点判断“是否与声明功能一致”。分类器输入包括 Skill profile、action summary、以及双向图上下文（前驱、后继、predicate）；后向上下文解释 action 为何可达，前向上下文解释其输出/副作用如何被使用（pp.6–7, §4.1）。该阶段是高召回筛选，保留“task-ambiguous action node”：动作与 Skill 声明功能兼容，但其权限状态取决于具体用户任务，可能在任务 A 下授权且必要、在任务 B 下越权（p.6）。Table 2 显示候选抽取在 GPT-5.1 下 recall 97.23%、precision 68.54%、F1 80.31%（p.10, Table 2）；作者明确接受低 precision，交由后续动态验证过滤（p.10）。

### 5.3 图引导的任务实例化与 replay 验证

对每个候选 action，从入口节点做候选感知的前向遍历，只抽取能到达该候选的 action chain；每条 chain 对应一个可能的 task variant（p.7, §4.2, Fig.5）。LLM 根据 chain 和 Skill profile 生成语义一致、结构上能触发该 chain 的用户 prompt；对需要外部输入的 Skill，用 MCP 工具生成最小 synthetic fixture（toy repo、CSV/JSON、文档、配置、图片等），只有当 prompt+fixture 能触发目标 chain 时才把该 task 用于验证（p.7; p.17, App.B, Table 14）。Table 3 显示 GPT-5.1 在 261 条 chain 中触发 249 条，coverage 95.40%；Gemini 91.19%、Claude-Sonnet-4.6 最高 96.17%、DeepSeek 93.49%（p.10, Table 3）。

对每个 task，SkillScope 在 sandbox 中执行两次：original run 得到 (τ_original, o_original)=τ(σ,p), o(σ,p)；replay run 得到 (τ_replay, o_replay)=τ(σ⊖a,p), o(σ⊖a,p)（pp.7–8, §4.2, Fig.6）。指令层候选直接删除对应指令步骤；代码层候选只中和候选行为（例如把目标函数体替换为 immediate return），避免破坏依赖导致人为失败（p.7）。sandbox 隔离文件系统、网络、命令执行等外部副作用，并 instrument agent 记录 trace 和最终输出（p.8）。授权检查只对实际执行的候选做：固定 schema 的 LLM scope judge 比较 prompt 所传达的 authority 与 τ_original 中实现的 action（operation、data source、sink/destination、side effects）（p.8）。必要性检查用 LLM-as-a-judge 评估 CorePres_p（replay 是否保留 prompt 要求的核心流程和外部可观察效果）与 GoalSat_p（replay 输出是否仍满足用户目标；不要求与原始输出完全相同）（p.8, §4.2）。确认规则是 ¬Auth_p(a) ∨ Unnec_σ(a,p)（p.8）。

### 5.4 控制流约束与 artifact 重写

**LLM 的角色与 hallucination 处理。** SkillScope 不把整个检测交给一个无约束 LLM，而是只在语义接口处调用 LLM（动作归一化、候选分类、prompt 生成、scope judge、necessity judge）；每次调用都 grounded 在 Skill artifact 和 pipeline state 的证据上，输出 verdict、rationale 和 evidence references；validator 检查字段、证据引用范围和组件一致性；失败最多重试五次，持续失败标为 unresolved（p.5, §3.1）。

对被确认的 action，先生成 task-context descriptor（task intent、requested operation、target object、execution scope、destination、是否显式请求该副作用、该 task 下的 validation verdict），归一化同义槽位后聚类成 task-context clusters，再对比式地生成 allow condition C_a：允许“显式要求该 operation/object/scope/side effect”的上下文，排除被判定为越权的上下文（p.8; pp.19–21, App.H, Tables 18–19）。约束节点为 v_a^c=⟨C_a, a⟩；运行时只有当前 task 满足 C_a 才路由到 a，否则跳过（p.8）。指令层把 C_a 作为 semantic guard 写回 SKILL.md；代码层则识别越权分支，用 LLM-assisted refactoring（extract-method、method-level restructuring）把耦合脚本重组为 task-specific execution units，再由指令层告诉 agent 在当前任务下调用哪个脚本单元；高层任务理解留在指令层，代码层变得模块化、确定性（p.9）。最终输出是更新后的 SKILL.md 和受约束脚本组成的 least-privilege bundle（p.9）。

### 5.5 “capability”的含义与执行位置（本项目重点）

**结论：不是形式化 capability 模型，也不是密码学 capability token，也不是独立的运行时执行强制；而是“动作级语义授权 + 静态/动态策略检查 + artifact 重写”。** 具体证据与推理如下。

- 文中的 “capability” 有三种日常含义：摘要里的 “capability bundles” 指 Skill 打包的功能（p.1）；正文里的 “capabilities” 指动作类型/操作，例如敏感数据访问、外传、命令执行、持久状态修改（p.4）；“authority conveyed by the current user task/prompt” 指用户请求所授予的动作范围（p.3）。没有主体/客体 capability 表、不可伪造 token、权限委托/衰减/撤销、reference monitor（[推断]，基于全文未出现这些机制；pp.3–4, pp.8–9）。
- 形式对象是 action a=⟨ℓ,op,obj⟩ 和谓词 Auth_p(a)、Unnec_σ(a,p)、OverPriv_σ(a,p)（pp.3–4, §2.2）。Auth_p 不是可执行检查，而是由 LLM scope judge 根据 prompt 与 realized action 判断的语义谓词（p.8）。CorePres/GoalSat 同样由 LLM-as-a-judge 估计（p.8）。
- 策略由谁执行：SkillScope 在发布前/使用前离线运行（ecosystem-side 或 user-side，p.4）；它把约束写回 SKILL.md 的 semantic guard 和重构后的脚本（pp.8–9）。运行时，指令层 guard 由 agent 的底层 LLM 解释和路由，作者明确说“keeps this guard at the instruction layer rather than converting it into a rigid keyword check, because semantically equivalent user tasks may differ in wording and should be routed by the agent’s underlying LLM”（p.9）；代码层是重构后的 if/else 分支。没有独立于 agent 的运行时监视器，也没有对修复后 bundle 的完整性绑定（[推断]，依据 pp.8–9 的机制描述）。
- 能否被绕过：可以，至少有五类 [推断]。(1) 语义 guard 是自然语言、由 LLM 解释，prompt injection、改写或歧义请求可能让 guard 误判/被覆盖；论文没有做针对 guard 的对抗测试。(2) 修复后的 SKILL.md/scripts 没有签名或 attestation，扫描后篡改（或发布新版本）可以重新引入越权；论文的部署模型是发布前/监控时分析，不是运行时完整性校验（p.4）。(3) 自适应恶意 Skill 可以规避高召回分类器和 LLM judge；论文没有 adaptive attacker 实验。(4) 不可观察/不可 replay 的行为、混淆/动态拉取代码、外部服务、zero-day 依赖不在范围内（p.4）。(5) 任务本身歧义时，C_a 可能过宽或过窄；作者承认 code-level separation 对高度耦合脚本不完美，约束可能被复杂上下文稀释（p.13–14）。作者报告的残余失败是 13/95 skills、54/472 action-in-task 实例仍触发（p.12, Table 10; p.13）。
- **OS/应用层权限的位置**：论文只在评测 sandbox 和真实 agent 的 permission setting 中使用 OS/应用层权限；作者明确说 platform-level test permission 不建立 Auth_p(a)（p.13; p.19）。因此本文的 least-privilege 不是 OS 权限系统/ACL 的实现，而是任务语义层的策略分析与 artifact 重写。
- 因此，若把“capability”理解为 OS/密码学意义上的不可伪造权限，本文没有建立这种模型；若理解为“当前任务允许的动作范围”，本文给出了定义、LLM 判定和 artifact 级约束。代码层 if/else 对脚本内部路径有局部强制，但 agent 仍可选择不调用或调用别的脚本，指令层 guard 仍是 LLM 语义路由；整体执行强制依赖 agent 的指令跟随，而不是可信引用监视器。

### 5.6 端到端小例子

对 a=send(report, Telegram)，验证阶段把“只生成本地报告”“本地热图”标为 rejecting context（over-privileged），把“生成报告并发送给 Alex on Telegram”“同步到配置的 Telegram 接收者”标为 allowing context（not over-privileged）（p.21, Table 19）。由此得到 C_a: explicit_request(send/sync) ∧ object=report ∧ destination=Telegram；约束节点 v_a^c=⟨C_a, send(report, Telegram)⟩；当前任务只要求本地报告时 C_a 不满足，send 被跳过；显式要求发送时 C_a 满足，send 仍可达（p.20, App.H）。

## 6. 安全声明与形式化程度（定义/指标/经验主张）

- **定义层**：论文给出了 Unnec_σ(a,p) ≜ CorePres_p(τ(σ,p), τ(σ⊖a,p)) ∧ GoalSat_p(τ(σ,p), τ(σ⊖a,p))，以及 OverPriv_σ(a,p) ≜ type(a)∈T ∧ (¬Auth_p(a) ∨ Unnec_σ(a,p))（p.4, §2.2）。T 是 privilege-relevant action types，例如敏感数据访问、外传、命令执行、持久状态修改（p.4）。
- **非形式化部分**：Auth_p、CorePres_p、GoalSat_p 没有形式语义、没有可判定算法、没有公理；它们由 LLM scope judge / LLM-as-a-judge 估计（p.8）。σ⊖a 的“移除/中和”是实现层操作（指令删除、函数体 immediate return、脚本重构），没有形式化定义（p.7; p.9）。
- **无定理/证明/归约**：全文没有 theorem、lemma、proof、soundness/completeness、cryptographic game、adversary advantage 或 reduction；也没有 proof appendix。论文的 “formulate” 是给出定义式表述（definitional formalization），不是密码学或程序语义的形式化验证（pp.3–4; p.6）。
- **经验主张**：检测 94.53% skill-level F1、94.74% action-level F1、93.28% action-in-task F1（p.9, Table 1）；大规模 6,590/68,312 验证为越权（p.12, Table 8）；约束后 88.56% action-in-task 抑制、95→13 skills、279→31 actions、472→54 instances（p.12, Table 10）；真实 agent 上 86.38–90.32% reduction（p.13, Table 11）；utility 249/249 task completion、94.78% output equivalence、93.17% core trace equivalence（p.13, Table 12）；post-hoc audit 94.16%/92.97%/93.53% weighted validity（p.19, Table 16）。
- **安全声明的边界**：这些是“与人工标注/定义的一致度”和“在 benchmark 上的抑制率”，不是“对任意自适应攻击者不可绕过”的安全保证。论文没有声称 soundness/completeness，也没有给出“约束后一定不会越权”的定理；作者承认残余越权和 LLM 不稳定性（p.13–14）。因此不能把 94.53% F1 或 88.56% suppression 当作密码学意义上的安全归约。

## 7. 实验设置与主要结果（agents、场景、指标、关键数字、消融）

**数据与场景。** 两个数据集：(1) 大规模测量：从 Clawhub、Agent Skills Marketplace 等抓取 110,046 个 Skill，去重/可用性过滤后得 68,312 个有效 bundle（p.9, §5.1; p.12, Table 8）。(2) 有效性/约束评测：从上述语料分层抽样 200 个 Skill，100 个含越权行为、100 个 benign；按 marketplace、category、artifact composition、observable operation type 分层；两名标注者独立标注，分歧由第三名复核，证据不足的 action-in-task 保守标为 not confirmed（p.9, §5.1; p.17, App.C）。标注基准包含 2,113 个 action 节点（289 over-privileged、1,824 non）、261 条 task chain、737 个 action-in-task 实例（507 over-privileged、230 non）（p.17, App.C）。作者强调人工验证的 graph/prompts 只用于构造 ground truth，不作为 SkillScope 的输入（p.17, App.C）。

**指标。** skill/action/action-in-task 三级的 precision、recall、F1、accuracy；task-chain coverage；约束后的 reduction/suppression rate；utility 用 task completion、output equivalence、core trace equivalence；token cost；post-hoc validity（p.9–13; p.18–19）。

**主结果。** Table 1：skill-level 95/6/94/5，P 94.06%、R 95.00%、F1 94.53%、Acc 94.50%；action-level 279/21/1,803/10，P 93.00%、R 96.54%、F1 94.74%、Acc 98.53%；action-in-task 472/33/197/35，P 93.47%、R 93.10%、F1 93.28%、Acc 90.77%（p.9, Table 1）。错误主要归因于 LLM agent 的不稳定、hallucination 和偶尔不遵循预期指令路径（p.10）。

**候选抽取与 judge 的跨模型结果。** Table 2：GPT-5.1 281/129/1,695/8，P 68.54%、R 97.23%、F1 80.31%（表中值；按行内数字重算约 80.40%，见 §9.3）、Acc 93.52%；Gemini-3.1-Flash-Lite 247/203/1,621/42，P 54.89%、R 85.47%、F1 66.86%、Acc 88.40%；Claude-Sonnet-4.6 286/187/1,637/3，P 60.47%、R 98.96%、F1 75.08%、Acc 91.01%；DeepSeek-V3.2 269/151/1,673/20，P 64.05%、R 93.08%、F1 75.88%、Acc 91.91%（p.10, Table 2）。Table 4 的 judge 结果：GPT-5.1 472/33/197/35，P 93.47%、R 93.10%、F1 93.28%、Acc 90.77%；Gemini 85.17% F1；Claude 90.95% F1（最高 precision 95.05%）；DeepSeek 89.31% F1（p.10, Table 4）。

**与基线比较。** Table 5：MalSkills 86.87% F1，Skill Scanner 78.26%，Caterpillar 61.08%，Skill-Sec-Scan 49.45%，MASB 25.85%，Nova-Proximity 19.18%；SkillScope 94.53%（p.10, Table 5）。作者对 LLM-based baselines 使用同一 GPT-5.1 以公平比较（p.10），并认为基线多为 coarse-grained Skill 级判断，无法处理 task-conditioned 细粒度越权（p.10–11）。

**消融。** Table 6：w/o Unified Graph 73.74% F1；w/o Graph-guided Task Generation 82.16%；w/o Dynamic Validation 79.22%；full SkillScope 94.53%（p.11, Table 6）。说明图建模、图引导任务覆盖、动态 replay 三者互补（p.11）。

**图构建质量。** Table 13：instruction nodes F1 98.07%、instruction edges 97.15%、code nodes 95.02%、code edges 92.62%、cross-layer links 95.57%；code edges 因 control/data 依赖更复杂而略低（p.16, Table 13）。

**大规模测量。** Table 8：68,312 个有效 Skill 中 8,328 个至少有一个越权候选，6,590 个被最终确认越权；统一图共 77,190 个 action 节点，其中 11,588 个是越权候选；16,743 个实例化用户任务中 7,033 个触发越权（p.12, Table 8）。指令层候选 6,997、确认 5,541；代码层候选 1,891、确认 1,498；两者交集 560/449（表中 instruction/code 行非互斥，Both levels 为交集，Overall 为去重计数）；指令层是主要载体，代码层仍是重要隐藏通道（p.12）。模式上，over-execution 影响 3,629 skills（55.07%）/3,875 tasks（55.10%），over-collection 影响 2,961 skills（44.93%）/3,158 tasks（44.90%）（p.12, Table 9）。类别集中在 tools（2,211, 33.55%）、productivity-tools（1,608, 24.40%）、llm-ai（750, 11.38%）（p.12; p.19, Table 17）。

**Post-hoc 人工校验。** 对 300 个 skill-level positives、200 个 graph-level candidate nodes、200 个 user-task-level positives 做分层抽样；加权 validity 分别为 94.16% [91.47, 96.85]、92.97% [89.41, 96.52]、93.53% [90.13, 96.93]（p.19, Table 16）。code-involving 样本被 oversample，报告为 population-weighted（p.18–19）。作者说明该审计不是重新评测端到端效果，而是对大规模统计的人工 sanity check（p.18）。

**约束效果。** Table 10：skills w/ over-privilege 95→13（-82；rate 100.00%→13.68%，-86.32）；actions 279→31（-248）；action-in-task 472→54（-418）；task chains 249→27（-222）；action-in-task suppression rate 88.56%（p.12, Table 10）。四个真实 agent runtime：Claude Code 279→34（-245，87.81%）、Codex 279→29（-250，89.61%）、Cursor 279→38（-241，86.38%）、Trae 279→27（-252，90.32%）（p.13, Table 11）。Utility：SkillScope 249/249 task completion（100.00%）、236/249 output equivalence（94.78%）、232/249 core trace equivalence（93.17%）；direct removal baseline 仅 144/249（57.83%）、130/249（52.21%）、112/249（44.98%）（p.13, Table 12）。

**成本。** 200-skill benchmark 上 5,451 次 LLM 调用、9.337M tokens（8.292M input + 1.045M output）、平均 46.69K tokens/skill；over-privilege validation 占 4.389M，privilege constraining 的平均成本 6.67K/repaired action（p.11, Table 7; p.18, Table 15）。作者强调分析是发布/准入时离线做一次，可缓存复用（p.11）。

**环境与模型。** Mac M4 Max、36 GB RAM；默认 GPT-5.1；sandbox 隔离文件系统、网络、命令执行（p.9, §5.1）。跨模型只覆盖候选抽取、task generation、judge 三个阶段；端到端默认仍是 GPT-5.1（p.10, Tables 2–4）。

## 8. 贡献与创新点（按原文主张）

- **问题表述**：识别并形式化（定义式）Agent Skills 中的 task-conditioned over-privilege：动作是否超出当前用户任务允许的范围、是否对完成任务必要；把问题从 all-or-nothing 恶意检测推进到 action-in-task 级最小权限（p.1–2, §1; pp.3–4, §2.2）。
- **框架设计**：提出 SkillScope，将统一执行图、过权候选抽取、action over-privilege validation、control-flow privilege constraining 组合起来；用图连接指令层过程与代码层操作，用图引导任务生成，用 replay 做必要性验证，用任务条件 guard + 脚本重构做 utility-preserving 约束（p.2, §1; p.4–9, §3–§4）。
- **评测与测量**：200-skill 人工标注评测（94.53% skill-level F1）、68,312 个真实 Skill 的大规模测量（6,590 个确认越权）、约束评测（88.56% suppression、249/249 task completion）以及四个真实 agent runtime 的迁移评测（86.38–90.32% reduction）（p.1–2, Abstract/§1; pp.9–13, §5）。
- **完整版**：论文是 ACM CCS 2026 的 full version，包含正文因页限省略的 appendices（A–H），覆盖图质量、fixture、数据集构造、token 成本、post-hoc 审计、类别分布、真实 agent 部署、约束节点细节（p.1; pp.16–21）。
- **设计建议**：作者建议 Skill 设计遵循 data minimization 和 least privilege，避免“collect sufficient context”这类模糊指令，把功能模块组织为任务边界清晰的 atomic operation，敏感行为只在显式需要时调用（p.13, §6）。这是从测量结果推出的规范性建议，不是新的技术机制。
- **与直接相关工作的差异（作者主张）**：先前 Skill 安全工具多做 coarse-grained malicious Skill 检测；隐私合规工作关注数据最小化但没有 action-in-task 级任务条件判定；SkillScope 的差异是 fine-grained、task-conditioned、necessity-aware、utility-preserving（p.1–2; p.10; p.14, §7）。作者没有明确声称这是首个 Skill 安全系统（全文未见 “first ... system” 式主张），而是强调问题表述与细粒度约束的组合。

## 9. 局限、失败案例、作者承认的不足（区分作者承认 vs 你的推断）

### 9.1 作者承认的局限

- **LLM/agent 执行不稳定**：nondeterministic run-to-run variation 会影响 replay 一致性和最终判断（p.14, Limitations）。Table 1 的小量 FP/FN 也归因于 hallucination 和偶尔不遵循指令路径（p.10）。
- **代码层约束依赖 LLM-assisted program separation**：对高度耦合的脚本可能不完美（p.14）；p.13 进一步说残余越权来自“constraints diluted by surrounding complex context”和“LLM-based program separation 仍不能完美隔离所有 task-specific over-privileged logic”。
- **fixture 生成是 ad hoc**：当前依赖若干 fixture-generation 工具的临时集成，难以扩展到复杂领域输入或需要认证的外部服务（p.14）。
- **范围限制**：不是通用 malware detector；不可观察/不可 replay 的行为、npm/pip 依赖 zero-day 漏洞不在范围内（p.4）。
- **残余越权**：约束后仍有 13/95 skills、54/472 action-in-task 实例触发越权（p.12, Table 10; p.13）。
- **效用损失**：少量 borderline task 中，插入的约束让 agent 更保守，导致行为轻微变化（p.13）；Table 12 的 output/trace equivalence 也不是 100%（94.78%/93.17%）。
- **平台权限与任务授权不同**：真实 agent 评测使用统一的非交互 sandbox 预授权；这不建立 Auth_p(a)，只是测试设置（p.13; p.19, App.G）。

### 9.2 本笔记推断的局限/失败模式

- **语义 guard 可被绕过**：guard 是自然语言并由 agent LLM 路由（p.9），不是可证明的引用监视器；prompt injection、改写、歧义任务可能让 guard 误判或失效。论文没有对 guard 做对抗性评测（[推断]，依据 pp.8–9 的机制）。
- **没有完整性绑定**：修复后的 SKILL.md/scripts 未签名、未 attestation；发布者可在扫描后修改 artifact 或发布新版本，重新引入越权。论文的部署是发布前/监控时分析，不是运行时校验（[推断]，依据 p.4 的 deployment model）。
- **自适应攻击者未评估**：论文的威胁模型是“artifact 中可观察/可 replay 的越权”，没有 adaptive attacker 规避分类器/judge 的实验；候选抽取 recall 97.23%、precision 68.54%，说明它宁可多报。攻击者若要规避，需要落在被漏掉的少数区域，或针对后续 LLM judge 做语义规避（[推断]，依据 p.10, Table 2）。
- **Benchmark 构造效度**：ground truth 由作者按同一套 Section 2.2 定义人工标注；检测器与标注者共享定义，94.53% F1 衡量的是“与标注者应用该定义的一致性”，不是与独立危害结果的关联；论文没有报告 inter-annotator agreement（[推断]，依据 p.9, p.17）。作者说明 ground-truth graph/prompts 不作为 SkillScope 输入（p.17），这缓解了直接泄漏，但不消除定义共享与标注主观性。
- **200-skill 评测规模有限**：相对 68,312 的生态语料，200 个 Skill 很小；虽然分层抽样，但不能保证覆盖长尾；大规模测量的 post-hoc audit 也只有 300/200/200 样本，且由作者复核（[推断]，依据 p.9, p.17–19）。
- **真实 agent 上未报告 utility**：Table 11 只报告 over-privileged action reduction；utility preservation 的 249/249 等数字来自 sandbox/benchmark 的 Table 12，不是四个真实 runtime 的 utility（[推断]，依据 p.13 的表述）。
- **单一默认模型**：端到端默认 GPT-5.1；跨模型只覆盖候选抽取、task generation、judge，且不同模型 F1 差异明显（候选 F1 66.86–80.31，judge F1 85.17–93.28），说明对模型选择敏感（p.9; p.10, Tables 2–4）。
- **“capability”不是可强制执行的安全能力**：见 §5.5；没有 token、签名、attestation 或 reference monitor，因此“least-privilege enforcement”是 artifact 级修复 + agent 指令跟随，而不是不可绕过的运行时强制（[推断]，依据 pp.8–9）。
- **“ecosystem-side”部署依赖 marketplace 合作**：论文假设 marketplace/registry operator 愿意在发布前运行并接受修复；没有讨论激励、治理、对抗性发布者拒绝修复等问题（[推断]，依据 p.4）。

### 9.3 原文内部不一致与口径问题

- **Table 2 的 GPT-5.1 F1**：表中写 80.31%，但按同一行 281/129/1,695/8 重算 P=281/410=68.54%、R=281/289=97.23%，F1=2×281/(2×281+129+8)=562/699≈80.40%。差 0.09 pp，可能是笔误或使用了未展示的中间值；本笔记不把 80.31 当作精确证据（p.10, Table 2）。同表 Gemini F1 66.85 vs 66.86、Claude 75.07 vs 75.08 是 0.01 pp 级舍入；Table 6 的 w/o Dynamic Validation F1 164/207=79.23% 写 79.22%（p.11, Table 6）。
- **Table 13 的舍入**：Instruction nodes 1,441/32/25，按定义 P=1,441/1,473=97.83%、R=1,441/1,466=98.29%、F1=2,882/2,939=98.06%，表中写 97.84/98.31/98.07；Instruction edges recall 1,480/1,520=97.37% 写 97.38%；Code nodes recall 617/647=95.36% 写 95.41%；Code nodes F1 1,234/1,299=95.00% 写 95.02%；Code edges P=765/830=92.17% 写 92.18%；Cross-layer P=194/204=95.10% 写 95.11%。均为 0.01–0.05 pp 级，可能是舍入/笔误，不影响主结论（p.16, Table 13）。
- **249 的计数口径**：Table 3 说 261 条 chain 中 249 条成功触发；Table 10 说 “# Task chains w/ over-privilege” 249→27；Table 12 又说 “249 legitimate tasks”。这三个 249 数值相同，但论文没有逐项说明“triggered chain”“chain w/ over-privilege”“legitimate task”是否严格同一集合；读数字时应保留这一口径不确定性（p.10, Table 3; p.12, Table 10; p.13, Table 12）。这不是数值矛盾，而是术语/口径未完全对齐。
- **抽取层面的错位（非原文矛盾）**：Tables 2–7、8–10、13–16、18–19 在 `pdftotext` 中因多行表头/合并单元格出现整体错行；已用 150/300 dpi 渲染核对。尤其 Table 7 的 # LLM Calls 列、Table 15 的 Processed Unit/# Units/Input/Output 列、Table 19 的 Extracted Context/Relation 列在纯文本中不可直接引用（p.11; p.18; p.21）。

## 10. 与理论密码学的可能联系（严格；没有就写“无”）

**无。** 论文没有定义密码学安全游戏、构造、定理、归约或原语；没有使用或假设签名、MAC、哈希承诺、零知识、TEE、attestation、OAuth/TLS/VC 等机制。`Auth_p(a)` 是语义授权谓词，由 LLM judge 估计（p.8）；`capability` 是“Skill 打包的功能/动作范围”的日常用法，不是不可伪造的密码学 capability（pp.1, 3–4）。Least privilege 引用的是 Saltzer–Schroeder 与 NIST 的经典访问控制原则（p.3），属于系统安全/访问控制，不是理论密码学。

若要把该问题提升为理论密码学问题，至少需要定义授权凭证的不可伪造性、敌手能力、委托/衰减、不可绕过性游戏和归约；本文没有做这些，因此不建立理论密码学联系。按三分法，本文属于**纯语义/系统方法**（图分析 + LLM judge + artifact 重写），不属于形式化密码机制，也不属于密码技术的工程应用。本笔记不因文中出现 “authorization”“verification”“enforcement”“capability” 等词而抬高相关度。

## 11. 与应用密码学/密码工程可能的技术联系（严格；没有就写“无”）

**无。** 论文没有使用 OAuth、TLS、签名、VC、TEE、zk、密钥管理、PKI、安全信道或任何密码学工程组件。唯一的隔离/权限机制是 sandbox（文件系统、网络、命令执行隔离，p.8; p.16）和真实 agent 评测中的平台级 permission setting（p.13; p.19），二者都是 OS/应用层系统安全措施，不是密码学工程；作者还明确说平台 permission 不等于 task-scope authorization（p.13; p.19）。

从工程角度，若要让修复后的 bundle 具备可验证完整性，需要签名/attestation 或可信分发；若要让 capability 不可伪造，需要 token/MAC 等机制。但这些都是本笔记的 [推断]，论文没有实现或评估，不能算作本文的应用密码学联系。

## 12. 可检验的研究假设（3–6 条）

1. **任务条件化翻转假设**：对同一 Skill 构造“授权该动作”和“不授权该动作”的成对 prompt，SkillScope 的 action-in-task 判定应在成对样本上显著翻转，而静态恶意 Skill 扫描器的 Skill 级判定不会翻转。可用翻转率、配对 McNemar 检验验证（依据 pp.3–4, §2.2; p.9, Table 1）。
2. **模型敏感性假设**：把候选抽取/judge 从 GPT-5.1 换成 Claude/DeepSeek 会改变 precision/recall，但不会改变 Skill 级排序的前若干名；候选阶段 F1 的跨模型差异（66.86–80.31）可分解为 precision 与 recall 的贡献，需检验哪一维方差更大（依据 p.10, Tables 2–4）。可用 rank correlation 和 bootstrap CI 验证。
3. **语义 guard 可绕过假设**：对约束后的 Skill 构造包含“本地生成 + 附带发送”的歧义/注入式 prompt，能在不满足 C_a 真实意图的情况下让 agent 执行被 guard 的动作；绕过率应显著高于 0。可用人工对抗 prompt 集和真实 agent 验证（依据 p.9 的 semantic guard 设计；这是 [推断] 的对抗测试，论文未做）。
4. **无完整性绑定假设**：在 SkillScope 扫描并修复后，直接修改修复 bundle 的 SKILL.md/scripts 重新加入越权动作，约束应完全失效；因为论文没有签名/attestation/运行时校验（依据 p.4 的 deployment model; pp.8–9 的重写机制）。可用 tamper test 验证。
5. **耦合度–效用假设**：代码层脚本的耦合度越高，LLM-assisted separation 的 utility preservation 越差，残余越权越多；可按 coupling metric 分层比较 Table 12 的 task completion/output equivalence 和 Table 10 的残余实例（依据 p.13–14 的作者承认）。
6. **标注主观性假设**：对“必要性（Unnec）”的 inter-annotator agreement 应低于对“授权性（Auth）”的 agreement；因为必要性需要反事实判断（移除动作后任务是否仍完成），而授权性只需比较 prompt 与 action。可用重标注 + Cohen's kappa 验证（依据 p.8 的 LLM judge 设计和 p.17 的标注流程）。
