## 1. 150–300 字中文概述

zkAgent 是首个面向完整 Agent 执行的 SNARK 系统。它指出，生产环境中的 LLM 推理与 provider 托管工具都在 API 之后，用户无法验证 provider 是否偷换模型或伪造工具观测，形成"执行完整性缺口"。现有 zkLLM 只证明 Transformer block 内的单 token 计算，不覆盖 embedding lookup、位置编码、解码、长序列自回归以及外部工具交互。zkAgent 为前三者设计 zkEmbed、zkPosEnc、zkDecode，使完整推理管线可证明；利用 decoder-only Transformer 的因果注意力掩码，把整段 transcript 的所有生成 token 合并为一次前向证明（one-shot transcript proving），并证明其与逐步自回归的"前缀等价"；再用 zkTLS/zkVM 子证明把工具观测绑定到已认证的执行，用 Coral 证明工具调用符合公开 schema。GPT-2、512-token transcript 上，证明 142.45 s（0.30 s/token），相对 zkGPT 加速 1,047.4×，验证 2.63 s；真实 weather/coding agent 端到端约 93–95 s。

## 2. 研究背景、现有方法不足、精确定义的问题

- 背景：Agent 把 LLM 推理与工具调用交织；provider 托管模型和 server-side 工具（web search、code execution），用户只能看到最终响应。恶意 provider 可 (i) 用更便宜/后门模型替换宣称模型；(ii) 伪造工具观测（搜索结果、沙箱输出）（p.8, §2.6）。
- 现有 zkLLM 不足（p.2–3, §1）：只证明 Transformer block；不覆盖 token→embedding、位置编码、logit→token 解码；不支持多轮、工具交织的执行；逐 token 证明开销巨大（zkGPT 对 482-token continuation 需 41 小时、~934 MiB）。
- 精确定义的问题：如何让客户端获得一个简洁证明，确认"整段 Agent transcript 是按承诺的模型、承诺的解码规则、在真实工具执行结果上生成的"，且证明成本可实用？（p.1–2, Abstract；p.8, §2.6）

## 3. Agent 系统模型（组件、交互流程、信任边界）

- 部署形态（p.8, §2.6; p.2, Fig.1）：
  (i) 全托管聊天产品（ChatGPT、Claude.ai）：整个 agent loop 在 provider 侧；
  (ii) API-driven agents（Claude Code、Codex CLI）：orchestration 在客户端，但 LLM 推理与 server-side 工具在 provider API 后。
- 组件：Client/Verifier（用户，运行 agent loop，持有本地工具）、Model Provider/Prover（LLM + server tools，恶意）、本地工具（文件/shell，被信任，排除在证明外）。
- Transcript tr = 用户输入、模型输出、工具观测的拼接；客户端收到 tr + proof bundle。
- 信任边界（Fig.1, p.2）：provider 侧（LLM、server tools）在 trust boundary 之上，需要证明；客户端与本地工具在边界之下，被信任。模型参数 W 私有，但 provider 发布绑定承诺 c_W。
- 信任根：KZG/KZH 多项式承诺、GKR/sumcheck、zkTLS 对 TLS 会话的认证、zkVM（SP1）对 RISC-V 执行的证明、Coral 对 CFG 解析的证明。

## 4. 资产、攻击者目标/能力、威胁模型和前提假设

- 资产：模型身份/参数承诺、推理计算完整性、工具观测真实性、工具调用 schema 合规性、transcript 绑定性。
- 攻击者：**唯一的恶意 provider**（p.8, §2.6），可任意偏离规定 Agent 流程：替换承诺模型、伪造 server-tool 观测、错误报告沙箱输出；可控制 prover 的全部输入/见证。
- 攻击者不能：攻破底层密码学假设（KZG、哈希、zkTLS/zkVM 的 soundness）、篡改客户端本地工具（被信任）、伪造客户端持有的承诺。
- 目标：让 verifier 接受一个与承诺模型/真实工具执行不一致的 transcript。
- Out-of-scope（p.8, §2.6）：(i) prompt injection——注入内容会出现在 transcript 中、可审计，识别/过滤是 alignment/policy 问题，不是密码学问题；(ii) 网络工具的业务逻辑正确性——只证明 provenance，不证明 server 业务逻辑。
- 前提假设：tokenizer 公开、从 token ID 开始证明；解码规则公开（greedy/top-k/top-p）；工具调用语法公开；zkTLS/zkVM 子协议 sound；模型承诺在 setup 时正确绑定。

## 5. 核心方案：算法、协议、架构、公式、关键步骤

### 5.1 完整推理证明（p.9–17, §3）
- **zkEmbed**（§3.1, p.9–12）：证明 H_0[i,:] = W_E[t_i,:]。把矩阵 lookup 用随机线性组合 ρ 折叠为标量 lookup：b_u = u + Σ_j ρ^{j+1} W_E[u,j]，a_i = t_i + Σ_j ρ^{j+1} H_0[i,j]（式 5–6），再用 cq（cached quotients）预处理 lookup 证明 {a_i}⊆{b_u}（式 2、7–12）。预处理 O(dN log N)，在线 O(Td)，与词表大小 N 无关。KZG 线性使各列预处理承诺可在 ρ 固定后聚合（式 8–9）。
- **zkPosEnc**（§3.2, p.13–14）：APE 是线性加法；RoPE 把每个 2×2 旋转块重写为两个 Hadamard 积 q_m^rot = q_m∘c_m + π(q_m)∘s_m（式 14），把 O(T d_h^2) 降到 O(T d_h)；用专用二次 sumcheck 验证，π 的符号置换通过两个 opening 绑定（p.14）。
- **zkDecode**（§3.3, p.14–17）：greedy 用 δ_i=ℓ_i−ℓ_y 的 range check 证明 argmax；top-k 用布尔选择子 χ（Σχ_i=k, χ_i(χ_i−1)=0）和 masked range checks 证明候选集，用 shift ζ 和 exp lookup 证明 softmax 归一化（式 15–17），用逆 CDF 和由承诺前缀派生的随机数 r=H(tr_{<t}) mod Θ 证明采样正确（式 16–18），防止 prover 重掷随机数。

### 5.2 One-shot transcript proving（p.18–21, §4.1–4.2）
- 关键观察：decoder-only Transformer 中只有 self-attention 跨位置混合信息；对每层施加下三角因果掩码 M^cau（j≤i 为 0，j>i 为 −∞），则一次全长前向 pass 的每个位置 logit 只依赖前缀。
- **Prefix equivalence**（Appendix E, p.52–53）：Lemma 1 证明因果掩码 attention 的前缀不变性；Theorem 1 归纳证明 length-T teacher-forced run 与 length-(i+1) online run 在位置 i 的 logit 相同。这是本文的形式化核心之一。
- **Weight-dependent quantization**（§4.1, p.18–20）：为使 batch 与 stepwise 的量化轨迹一致，要求 per-layer scale 输入无关且对所有诚实执行 complete。用权重 ℓ1 范数给出 |Y^(l)| ≤ B_l = max_j(2^Q||W^(l)[:,j]||_1 + |b_j^(l)|)（式 19–20），S_out^(l)=S_a^(l)·B_l/2^Q（式 21）；LayerNorm 提供与输入无关的 √(d−1) 界（p.19–20），避免动态范围跨层累积。
- **Shift consistency**（§4.2, p.21）：验证每个位置 i 的预测 token t̂r_i = t_{i+1}，i∈{T_0−1,…,T−2}（式 24）；对工具交织 transcript 用 generation mask g_i∈{0,1} 只约束模型生成位置：g_i(t̂r_i − t_{i+1})=0（式 25）。g 必须由公开 transcript 语法唯一确定，不能由 prover 选；隐藏 CoT 时用承诺 c_R 与长度 L_R 绑定（p.22）。
- **附录补充（审计补读）**：Appendix B（pp.35–38）给出 tokenization→embedding→位置编码→Transformer→解码的完整张量流程（Fig.3）；Appendix C.2–C.3（pp.41–43）给出 sumcheck 与 ML-friendly GKR 的跨层选择谓词/层关系（式 32–33）；C.4（pp.43–45）用 advice+零检查+随机 ρ_i 把 lookup 与 GKR 组合，零检查额外 soundness error ≤ (s_i+1)/|F|；C.5（pp.45–46）用前缀指示 MLE 的 O(log N) 求值；C.6（pp.46）给出 top-p 的质量约束与最小性论证；Appendix D（pp.47–51）完整复述 cq 预处理 lookup（式 35–43、Protocol 3），并证明在线成本与表大小 N 无关。

### 5.3 工具绑定（p.21–23, §4.3; Appendix G, p.56–57）
- Tool-call 解析：用 Coral 证明模型生成的调用 span 符合公开 CFG/schema，解析出结构化请求 req_i（p.22）。
- 网络工具：zkTLS 证明 (id_i, req_i, resp_i, π_i^io) 通过验证，resp_i 绑定到 transcript 的观测 span（明文相等）。
- 计算工具：模型生成的 Python 程序经 Depyler 转 Rust、编译 RISC-V，在 zkVM（SP1）中执行并证明；程序与转译公开可复跑，转译本身不入 circuit（p.56）。
- 端到端 soundness statement（p.56–57）：模型完整性、schema 完整性、工具完整性、绑定性四项；**注意：这是陈述性的组合保证，不是带归约的定理**（论文未给出完整组合 soundness 定理与证明）。

## 6. 安全属性与安全性论证

- 目标属性：**execution integrity**（模型完整性、工具观测真实性、调用 schema 合规、transcript 绑定），零知识（隐藏模型参数/权重；论文主体为清晰起见先不给 ZK，称可用标准范式以很小开销添加，p.7）。
- 形式化部分：
  - Definition 1（zk argument of knowledge：correctness, knowledge soundness, zero knowledge，p.39）；
  - Definition 2（zkPC：completeness, knowledge soundness, zero knowledge，p.40）；
  - Lemma 1 + Theorem 1（prefix equivalence，p.52–53，有证明）；
  - Appendix G 的 end-to-end soundness statement（p.56–57，四项保证，无完整归约/定理编号）。
- 论证结构：把完整推理拆成 GKR + lookup 子证明，工具子证明通过明文相等绑定；若任一子证明 sound 且绑定成立，则 verifier 接受的 transcript 必对应承诺模型与真实工具执行。
- **未提供**：完整的组合 soundness 定理与归约（例如把 zkTLS/zkVM 的 soundness error 与 GKR 的 soundness error 合成为一个全局 bound）；对恶意 prover 自适应选择工具/模型的组合攻击的完整分析；对 zkTLS 信任假设（CA、TLS 终结、server 合谋）的深入讨论。
- Out-of-scope 明确排除 prompt injection，这在安全边界上很重要：zkAgent 证明"模型确实按输入执行"，不证明"输入/输出是安全的"。

## 7. 实验细节：模型、环境、数据集、对照方法、指标、核心结果、消融

- 实现：C++；GKR 基于 zkGPT 开源代码；KZG（单变量）与 KZH（多线性）；lookup 后端 Shout 与 LogUp；BN254 + mcl；32 线程（p.23, §5.1）。
- 硬件：Intel Xeon 6982P-C（3.20 GHz, 32 cores）、512 GB RAM（p.23）。
- 模型：GPT-2（N=50,257, d=768）；量化 Q=20 bits（p.24）。
- 基线：ZKML、zkGPT、zkLLM；zkLLM 无 GPT-2 实现，按 [60] 的 per-step A100 成本外推（p.26）。
- **One-shot 主结果**（p.26–27, Table 5）：T=512（482 generated tokens）：
  - zkAgent(Shout)：prove 142.45 s（0.30 s/token），verify 2.63 s，proof 84,589.13 KiB；
  - zkAgent(LogUp)：prove 200.63 s，verify 1.50 s，proof 3,932.09 KiB；
  - zkGPT：prove 149,192.60 s（~41h），verify 4,361.09 s，proof 956,043.99 KiB；
  - 相对 zkGPT：prover 1,047.4×，verifier 1,657.5×；即使按 ~13× 硬件差距折算，Shout 仍快 53.5×（p.27, Appendix H）。
- **微基准**：
  - zkEmbed：预处理 942.43 s / 4.52 GiB；在线 T=2^10 时 0.27 s；比 Segment Lookup 快 311.3×（T=2^5），比 Campanelli 快 70×（p.24, Tables 1–2）。
  - zkEmbed 跨模型：GPT-2 942 s/4.52 GiB；DeepSeek-V3 18,219.96 s/84.04 GiB（p.25, Table 3）。
  - zkPosEnc：比朴素 matmul 快 15.7–30.1×；Llama-2-7B T=512 每层 5.49→0.13 s（~42×），32 层省 ~172 s（p.25, Table 4）。
  - zkDecode：greedy 0.033 s/token、1.60 ms verify、18.04 KiB；top-k 0.15 s/token、3.84 ms、82.48 KiB（Shout，p.26）。
- **端到端**（p.27–28, Table 6）：
  - Weather agent（152 tokens，zkTLS）：Shout 95.23 s / 1.45 s / 47,249.10 KiB；LogUp 124.99 s / 0.82 s / 3,189.97 KiB。
  - Coding assistant（143 tokens，zkVM）：Shout 93.18 s / 1.63 s / 49,841.50 KiB；LogUp 122.65 s / 1.00 s / 5,776.28 KiB。
  - 推理证明占主导；Coral + 工具子证明仅 6.18–7.62 s。
- **量化精度**（p.56, Table 8）：Q=20 时 PPL 与 FP32 基本一致（WikiText-2 24.36 vs 24.36）；朴素维度界在 Q=18/20 时 PPL 爆炸（3.86e23 / 1.12e11），说明 weight-dependent bound 的必要性。
- 无传统消融（每个组件有微基准，但未做端到端 remove-one 消融）。

## 9. 局限性、失效场景、作者未解决的问题

作者显式/隐含的限制：
- **只在 GPT-2 上端到端评估**；更大模型（Llama、DeepSeek）只有 zkEmbed 预处理微基准，没有完整推理证明（p.24–26）。实用性外推需谨慎。
- 证明仍很重：GPT-2 512 tokens 需 142 s（32 核）；真实 Agent 多轮、长上下文、大模型会显著更慢。
- 依赖 zkTLS 与 zkVM 的 soundness/信任假设；zkTLS 的 server 合谋、TLS 终结、CA 信任未深入分析。
- 端到端 soundness 只是 statement，无完整组合定理与归约（p.56–57）。
- Out-of-scope：prompt injection、工具业务逻辑正确性、客户端本地工具（p.8）。
- 隐藏 CoT 时依赖承诺与长度，语义正确性仍依赖 provider 诚实选择 R（p.22）。
- 零知识属性在主体构造中未实现，仅称可加（p.7）。
- 没有形式化的"模型承诺正确性"（谁保证 c_W 对应宣称模型）与模型替换攻击的完整讨论。
- 吞吐/成本：32 核 CPU 服务器、512 GB RAM；未讨论移动端/低资源 verifier 的实际部署。

## 10. 与理论密码学可能的技术连接（区分原论文已做 / 个人推断）

**原论文已做**：
- 使用 zkSNARK/GKR/sumcheck、KZG/KZH 多项式承诺、lookup arguments（LogUp、Shout、cq、Lasso 风格分解）、Fiat–Shamir、随机预言机（哈希派生采样随机数）（pp.6–17）。
- 形式定义 zk argument of knowledge 与 zkPC（p.39–40）；证明 prefix equivalence（p.52–53）。
- 使用 zkTLS 与 zkVM 作为工具子证明（p.22–23）。

**个人推断（明确标为推断）**：
- 这是 124 篇中理论密码学相关度最高的论文之一：它把"Agent 执行完整性"转化为一个明确的 NP 关系，并给出可组合的证明系统。可研究的理论问题：
  1. **组合 soundness**：把 GKR、lookup、zkTLS、zkVM、Coral 的 soundness error 合成为一个端到端 bound，并证明在恶意 prover 自适应选择子协议输入时仍成立；
  2. **模型承诺的语义**：c_W 只绑定参数，不绑定"这是宣称的模型架构/训练过程"；需要定义并证明 model identity 的更强概念（例如架构 + 权重 + tokenizer + 解码规则的完整承诺）；
  3. **零知识下的审计**：当前主体不隐藏权重；若加 ZK，如何仍让 verifier 确认模型是"某个已认证模型"而不泄露参数；
  4. **工具绑定的信任模型**：zkTLS 证明"与某 server 的 TLS 会话"，但不证明 server 业务逻辑；可形式化 provenance vs correctness 的边界；
  5. **增量/流式证明**：多轮 Agent 的 transcript 增长，如何做增量证明而不重证全部前缀；这是 proof-carrying data / recursive composition 的自然问题。
- 注意：这些是**基于论文的推断**，不是论文已解决的开放问题；需查证后续文献。

## 11. 与应用密码学/密码工程可能的技术连接（同上）

**原论文已做**：
- C++ 实现、GKR + KZG/KZH、Shout/LogUp 后端、BN254、mcl、32 线程；端到端 weather/coding agent 证明（pp.23–28）。
- 工具集成：zkTLS（网络 API）、Depyler + SP1 zkVM（Python 沙箱）、Coral（CFG/schema）（pp.22–23, 56）。
- 性能数据：prove/verify/proof size、预处理成本、跨模型 zkEmbed 成本（Tables 1–6, 8）。

**个人推断**：
- 与密码工程团队高度匹配：SNARK 实现、承诺方案、lookup argument、zkTLS/zkVM 集成都属于密码工程核心能力；不需要训练大模型。
- 可落地的工程问题：为真实 Agent 框架（Claude Code/MCP）做 proof bundle 格式与 verifier SDK；优化 prover 并行/GPU；增量证明与缓存；proof 大小/验证时间权衡；与 TEE 混合（TEE 做工具执行、SNARK 做推理）。
- 可测量：不同模型规模、transcript 长度、工具类型的 prove/verify 时间与内存；端到端 Agent 任务的可用性阈值。
- 伪交叉风险：只证明"某一步模型输出"而不绑定完整 transcript/工具；只做 benchmark 包装而不解决 soundness 组合；把 zkTLS 当万能工具而不分析其信任假设。这些价值有限。
- 关键限制：GPT-2 上的 142 s 离生产可用仍有距离；大模型证明成本可能是数量级问题。任何应用研究必须先做成本可行性分析。

## 12. 后续可以验证的研究假设（不得仅因论文没提就判断领域没人做过）

- H1：对 Llama-3-8B/70B 的完整 one-shot transcript 证明，prove 时间是否随参数量/层数线性增长到不可接受；能否用递归/增量证明控制在分钟级。
- H2：端到端组合 soundness 能否给出严格定理；各子协议 error 的合成是否可忽略。
- H3：模型承诺 c_W 能否扩展为"架构 + 权重 + tokenizer + 解码规则"的完整承诺，并防止 provider 用同参数不同架构冒充。
- H4：zkTLS 的信任假设在 Agent 工具场景下是否可接受；server 合谋/伪造响应能否被检测。
- H5：零知识版本对 prover 开销的影响；能否在隐藏权重的同时支持模型认证。
- H6：增量证明多轮 Agent transcript 的摊销成本是否优于全量重证。
- 以上需后续实验/文献验证，当前仅为假设。
