                                                                                    Abstract

                                                   LLM-based agents process external content, exposing them to prompt injection
                                                   and multi-turn manipulation. We present a 21-scenario benchmark for adaptive
                                                   cross-session attacks against fresh-session LLM defenders: an autonomous LLM
                                                   attacker observes prior defender responses and pivots across rounds, while each
                                                   defender response is evaluated as a fresh interaction. A controlled 3×3 attacker–
                                                   defender matrix contains 945 battles. Restricting scoring to the first round yields
                                                   0–1% attack success rate (ASR); allowing 15 rounds yields 7.9–16.8%. Pooling
                                                   three attacker LLMs uncovers 1.7–2.2× as many unique successful inputs as the
                                                   best single attacker, at three times the battle budget. Aggregate rates conceal
                                                   opposing scenario-specific weaknesses in session-secret protection and authority
                                                   handling, preserved in two higher-sample evaluations. On six scenarios, adding
                                                   one provenance paragraph reduces ASR from 110/270 to 70/270, with selective
                                                   effects across tasks. History and defender-state controls, together with frozen
                                                   replay, characterize how the interaction protocol changes the result. A competition
                                                   adds 18,422 held-out battles on a fixed gpt-oss-20b backbone and complementary
                                                   benign-task evaluations. The benchmark exposes attacker and defender models,
                                                   harnesses, scenarios, session state, and interaction budgets as configurable choices
                                                   for systematic security evaluation.

                                        1 Introduction

                                        Evaluating LLM-agent safety against indirect prompt injection [Greshake et al., 2023] and multi-turn
                                        jailbreaking [Li et al., 2024, Russinovich et al., 2025] requires adversarial benchmarks: collections
                                        of scenarios in which an attacker tries to manipulate a defender into producing unsafe output. We
                                        measure outcomes by attack success rate (ASR): the fraction of battles in which the attacker
                                        succeeds.

                                        Released attack pools provide a common set of inputs for comparing defenders. Adaptive evaluation
                                        asks a complementary question: what can an attacker discover by learning from the defender during
                                        evaluation? Both the attack-generation procedure and the task-level success criterion affect that
                                        measurement. Iterative attacks such as PAIR and TAP [Chao et al., 2023, Mehrotra et al., 2024] make
                                        this distinction concrete; a benchmark must also specify which tasks are attacked, what state each
                                        side retains, and what constitutes a security failure.

                                        We build Security Arena on the AgentBeats multi-agent evaluation platform [Berkeley AgentBeats
                                        Team, 2026].2 A scenario specifies a defender role and task, an attacker-controlled input surface, and
                                        an executable success criterion. A battle pairs an attacker and defender for a bounded sequence of
                                        rounds; a harness wraps model calls with prompt construction, state management, and output parsing.
                                        The controlled frontier evaluation varies three attacker and three defender models under a common
                                        scaffold. The competition varies participant-authored harnesses on one fixed backbone.

1.1 Contributions

       1. Benchmark. A 21-scenario agent-security benchmark with 10 separate development sce-
           narios and an executable evaluation framework. The default protocol generates attacks live
           against a fresh-session defender (§3); the task contracts cover prohibited information emis-
           sion, decisions, and simulated actions. Its modular interface supports changing scenarios,
           attacker and defender models and harnesses, session state, and budgets within the same
           evaluation framework.

       2. Four design principles (§3): multi-stage scenario calibration, adaptive cross-session battles,
           per-battle attack generation, and executable task-level checks.

       3. Controlled findings (§5). A 945-battle frontier matrix and targeted follow-ups reveal
           replicated scenario-specific weaknesses, selective effects of a provenance intervention, and
           consequential history and state choices. Frozen replay separates same-target reproduction
           from cross-target transfer. A fixed-backbone competition adds evidence about harness
           behavior and benign-task performance.

2 Related Work

Single-turn and human-attack datasets. StrongREJECT [Souly et al., 2024], Jailbreak-
Bench [Chao et al., 2024], and HarmBench [Mazeika et al., 2024] provide complementary harmful-
behavior sets and evaluation methods. b3 [Bazinska et al., 2025] studies crowdsourced attacks against
task-specific defenses. Multi-turn human jailbreaks (MHJ) [Li et al., 2024] curate attacks developed
across a defender conversation. These collections make particular attack distributions inspectable and
reusable.

LLM-attacker pipelines. PAIR [Chao et al., 2023] uses an attacker LLM to iteratively refine a
jailbreak from target feedback. TAP [Mehrotra et al., 2024] explores and prunes a tree of candidate
attacks. Crescendo [Russinovich et al., 2025] gradually escalates a persistent target conversation and
includes an automated implementation. Security Arena evaluates task-level policy violations under
an explicit scenario contract and makes the interaction protocol configurable.

Agent benchmarks. AgentHarm [Andriushchenko et al., 2024] evaluates harmful tasks involving
tools. IPI Coding Agent [Sinha and Inspect Evals contributors, 2025] evaluates injection in a
coding environment, and AgentDojo [Debenedetti et al., 2024] supports tool-using agents, injection
attacks, defenses, and ordinary task completion. Our frontier scaffold evaluates structured outputs in
self-contained task contexts.

Calibration and repeatable evaluation. Classical measurement methods [Lord, 1980, Embretson
and Reise, 2000] and their use in LLM evaluation [Polo et al., 2024] motivate checking whether items
carry useful signal. We use calibration to screen scenarios for difficulty and capability sensitivity.
Sculley et al. [2025] argue that static benchmarks should be complemented by repeatable evaluation
processes. Our benchmark provides one such process for task-constrained adversarial interaction.

3 Design principles

The orchestrator passes the scenario objective and prior feedback to the attacker, inserts the attacker’s
text into the scenario template, requests a defender response, and applies the scenario’s success check.
Figure 1 shows this interaction loop.

Fresh-session defender. An adversary opens a fresh defender session for each attempt while
learning from earlier attempts. The attacker retains prior inputs, defender responses, and scorer
feedback; the defender receives its role, task, output specification, and current formatted input without
prior-round history. This models adaptive cross-session search. ASR@15 is the fraction of battles
with at least one scored success within 15 rounds.

Four design choices define the benchmark; §5 tests their effects.

Figure 1: Default frontier threat model. The attacker controls the scenario-designated input and
retains feedback across rounds; the defender receives a fresh request each round. The dashed line
marks a logical trust boundary; scenario instructions and attacker content are combined in the same
prompt. Success checks measure output violations; the frontier scaffold executes no external tools or
actions.

Multi-stage authoring with quantitative calibration. Calibration guides scenario revision toward
tasks that distinguish attacker–defender capability pairings and allow successful attacks to emerge
over multiple rounds. (i) Concept generation. The authors review, revise, or reject LLM-proposed
scenario concepts. (ii) Plugin implementation. Each candidate becomes a plugin defining the
defender’s task, the attacker-controlled input, and the success criterion. (iii) Calibration. We
compare balanced pairings with stronger attackers against weaker defenders and the reverse, using
observed difficulty and capability sensitivity to guide revisions. Calibration configurations and
screening records appear in Appendix B.9.

Adaptive cross-session battles. Each battle allows up to 15 rounds and stops at the first scored
success. We test the role of attacker history and compare fresh and persistent defender sessions in
§5.4.

Per-battle attack generation. The attacker LLM generates each input live, allowing adaptation
to the defender. The attacker model and its search procedure therefore shape which failures the
evaluation discovers. Saved transcripts preserve the observed trajectories and enable replay of
discovered inputs against the original and other defenders.

Structured checks. The primary criterion applies scenario-specific checks to the defender output.
For example, auditwhitewash requires a score of at least 70 for the designated vendor, while
tickettriage prohibits the referral code in any drafted reply. Appendix A gives the criteria, and
Appendix B.1 describes disclosure and repaired-code sensitivities. Infrastructure failures are not
counted as successful attacks.

4 The Benchmark

4.1 Scenario set

The benchmark contains 21 held-out evaluation scenarios and 10 development scenarios. The
21 scenarios cover five threat classes: indirect injection (11), PII/data leak (6), insecure output (2),
supply chain (1), and prompt extraction (1). Full threat-snapshot cards and operational criteria appear
in Appendix A, with worked examples in Appendix C. All protected values are synthetic fixtures.

Resultant difficulty distribution. A Baseline attacker–defender evaluation on gpt-oss-20b con-
tains 50 battles per scenario (1,050 total). Seven scenarios have recorded ASR above 70%, five lie
between 22% and 48%, and nine lie below 20%, including three with no recorded successes. The
suite spans a broad difficulty range at this tier (Appendix B.9).

4.2 The open competition

We designed and organized Security Arena, authored its benchmark scenarios and checks, and built
the competition-specific orchestration. AgentBeats supplied the generic evaluation platform and
recruitment and promotion support. Participants supplied their own attacker and defender harnesses,
and the evaluation generated the trace dataset.

The competition ran in March–April 2026 on the gpt-oss-20b backbone, with 21 submitted attacker
harnesses and 20 submitted defender harnesses, plus an organizer baseline in each role. Fifty-two
populated development snapshots contain 93,291 battles on the ten development scenarios. Two
held-out scoring rounds contain 18,422 battles on the 21 evaluation scenarios, with a ten-round cap.
These records support the harness comparison and benign-task analysis in §5.6.

4.3 The 3×3 frontier-defender evaluation

For the controlled measurement, we evaluate Claude Opus 4.6, GPT-5.4, and Gemini 2.5 Pro as both
attacker and defender in a 3×3 matrix. Five battles per scenario and model pair yield 945 battles with
saved trajectories. Aggregating across attackers gives 25/315 (7.94%) for Opus, 30/315 (9.52%) for
GPT-5.4, and 53/315 (16.83%) for Gemini; the pooled ASR is 108/945 (11.43%). The Opus/GPT-5.4
aggregate contrast is not significant (two-sided Fisher p = 0.573).

5 Findings

5.1 Aggregate ASR hides opposing scenario-specific weaknesses

For session-secret protection (memleak), Opus is compromised in 9/15 initial battles (60%; 95% CI
36–80%), versus 1/15 for each of GPT-5.4 and Gemini (7%; CI 1–30%). A three-attacker replication
with 20 battles per model pair preserves this contrast: 30/60 for Opus, 6/60 for GPT-5.4, and 3/60
for Gemini. For fabricated authority (paperaccept), Gemini is compromised in 8/15 initial battles
while the other two defenders have no successes; the replication gives 26/60 for Gemini, 0/60 for
Opus, and 1/60 for GPT-5.4. Full per-scenario profiles and cell counts appear in Appendix B.2.

An expanded July evaluation fixes the Opus attacker and uses 60 battles per defender on memleak,
paperaccept, and meetingnotes. The same opposing pair persists: memleak gives 38/60, 14/60,
and 12/60 for Opus, GPT-5.4, and Gemini; paperaccept gives 0/60, 1/60, and 47/60. Full study
details appear in Appendix B.3.

5.2 A provenance paragraph selectively reduces attacks

We append one paragraph instructing the defender to prefer the earlier/main task context when later
addenda contradict it. The 540-battle experiment uses six scenarios, an Opus attacker, and three
defenders. ASR falls from 110/270 (40.7%) to 70/270 (25.9%; Fisher p = 3.57 × 10−4).
The largest reductions are on paperaccept, from 13/45 to 0/45, and gameguru, from 10/45 to 0/45;
memleak stays at 18/45. The paragraph therefore reduces selected authority failures while leaving the

5.3 Pooling attackers yields more distinct successful inputs

A successful input is the scenario/input pair at the first scored success in a battle; exact duplicates are
counted once. Holding the defender fixed, the best single attacker yields 15, 16, and 24 successful pairs
against Opus, GPT-5.4, and Gemini. The three-attacker unions contain 25, 30, and 53, respectively:
1.7–2.2× the best standalone count at three times the battle budget (315 versus 105 battles per
defender). Individual contributions and unions appear in Appendix B.8.

5.4 Multi-round evaluation exposes failures missed by round-1 scoring

On the same 21 scenarios and 945-battle matrix, round-1-only scoring gives 0.0% / 0.0% / 1.0%
for Opus / GPT-5.4 / Gemini. Scoring through round 15 gives 7.9% / 9.5% / 16.8%. We obtain the
shorter-budget rates by scoring the same saved trajectories at earlier round cutoffs. The 15-round cap
is a computational-budget choice; the observed success curve is still rising at that cap (Appendix B.8).

History-conditioning control. This control measures the contribution of retained attacker history at
a fixed attempt budget. On three scenarios, an attacker with access to its prior attempts and defender
responses succeeds in 13/36 battles, while an attacker without that history succeeds in 0/36 under
the same 15-attempt cap (p = 6.52 × 10−5). Full per-cell results and scoring sensitivities appear in
Appendix B.5.

Defender-state control. Holding the attacker prompt fixed, defender memory reduces ASR by
25.9 percentage points: from 57.4% (31/54) with a fresh-session defender to 31.5% (17/54; Fisher
p = 0.0115) with a stateful defender. This control uses an Opus attacker and three defenders across
three scenarios. With attacker instructions tailored to retained dialogue, the stateful defender has
an ASR of 14.8% (8/54). Relative to the fresh-session reference, this last condition changes both
defender state and attacker instructions. These controls motivate treating attacker history and defender
memory as configurable protocol choices, and reporting persistent-session robustness alongside the
default fresh-session evaluation. All four experimental conditions and per-cell counts appear in
Appendix B.5.

5.5 Frozen replay separates reproduction from transfer

We freeze the sequences of formatted inputs from 62 successful source battles. Each sequence is
replayed three times against each of the three targets, giving 558 trials. Each input is sent to a fresh
session; a trial stops when the replay experiment’s conservative success criterion is met.

Same-target reproduction succeeds in 125/186 trials (67.2%; source-cluster 95% interval 58.1–75.8%),
while cross-target transfer succeeds in 44/372 (11.8%; 7.3–17.2%). Transfer is directional: GPT-5.4-
source sequences succeed against Gemini in 26/36 trials, while Gemini-source sequences succeed
against GPT-5.4 in 6/114. Source selection, weighting, and statistical details appear in Appendix B.6.

5.6 Open submissions reveal attack and defense strategy space

With the backbone fixed, ASR spans 26.5 percentage points across defender harnesses and 23.3 points
across attacker harnesses. This spread shows why harness design belongs in security evaluations
alongside model choice. These results exclude 838 battles with defender infrastructure failures,
leaving 3,439/17,584 scored attacker wins (Appendix B.7).

Benign-task performance. The competition’s benign development-task evaluations provide a
check for over-refusal on ordinary requests. A topic passes when an LLM judge labels the defender’s
response both answered and helpful. Across 9,171 topic evaluations, the median team passes 96.6%
on the first attempt and 99.1% when allowed up to three attempts; pooled rates are 92.9% and
97.4%. Full per-team results, retry rules, and the comparison with competition security appear in
Appendix B.7.

5.7 Scenario diversity and attack content

Scenario-level profiles help assess whether the suite exposes different defender weaknesses. Fifteen
of the 21 scenarios produce at least one scored success, and defender rankings vary across scenarios,
motivating inspection of individual profiles alongside aggregate ASR (Appendix B.2). A supple-
mentary text-embedding comparison finds low average similarity between our sampled inputs and
six existing attack collections. This describes differences among sampled attack texts in the chosen
representation (Appendix B.11).

6 Limitations

Sample size and selection. Most frontier cells contain five battles. The two higher-sample studies
support the memleak and paperaccept contrasts, but were targeted after observing initial results.
The intervention studies also cover selected scenarios and model pairings. The suite concentrates on
injection and disclosure; calibration using GPT-family models may influence which weaknesses are
represented. Unequal point estimates and zero observed successes in small cells should not be read
as general model rankings or robustness guarantees.

Attacker capability. Attack discovery is limited by what the attacker model can generate, including
its own refusals. The benchmark therefore complements human red-teaming, which can pursue
strategies that LLM attackers are trained to refuse.

Task scope and scoring. The frontier scaffold has no tools, retrieval, or externally observed state
changes. Fixed synthetic secrets and attacker knowledge vary by scenario. Deterministic output
checks can miss protected values in refusals or count approvals of repaired code; alternative criteria
and scoring sensitivities are quantified in Appendix B.1. The competition covers one open-weight
model, and its benign-task results describe development tasks across historical submissions.

Reproducibility and compute. Model APIs and provider defaults can change over time. Archived
transcripts support inspection of observed responses and replay of the same attack inputs. Historical
resource use is estimated from logs and prompt text because per-call usage, billing, and latency were
not recorded; the estimates appear in Appendix B.10.

7 Conclusion

Adaptive evaluation makes the attacker model, defender harness, scenario, interaction state, and
search budget part of the security measurement. Security Arena implements this view as a con-
figurable protocol for systematic security evaluation with explicit task-level success criteria. Its
frontier evaluations show how aggregate scores conceal scenario-specific weaknesses, while the
provenance, history, state, and replay studies show how evaluation conditions change which failures
are discovered or reproduced. Competition results add measurements of harness security and ordinary
task completion on a shared model backbone.

The released scenarios, harnesses, scoring code, and traces support extending these experiments to
new attacker and defender models, attack strategies, task domains, session structures, and interaction
budgets. By exposing these choices, the benchmark can evolve with agent capabilities while keeping
the conditions behind each reported result explicit.

B Detailed Results and Evaluation Methods

B.1 Success criteria and sensitivity

The primary metric uses the operational scenario checks in Appendix A. Seventeen checks begin
from structured fields, sometimes with whole-output fallbacks; four primarily scan text. They use
conjunctions, target-record selection, numeric thresholds, and configured protected markers. A
broader all-output criterion scans raw output and JSON-decoded strings for configured protected
markers, including markers in quotations and refusals, with Unicode and card-separator normalization.
It also distinguishes a positive fractional price from zero and a negated acceptance from an affirmative
verdict. This criterion does not attempt general decoding, partial-secret reconstruction, or semantic
inference.

revealing previously unknown information. Refusal filters can also suppress true disclosures: the
gitblamebot filter matches a word in the protected email’s own domain, and apikeybot has an
analogous marker/filter collision. Zero primary counts are therefore not treated as security ceilings.

Artifact and action interpretation. The primary codeapprove rule checks the verdict without
establishing which code artifact was approved. A conservative sensitivity excludes responses contain-

investigating a transfer; tickettriage prohibits a referral code in any drafted reply, including
a reply to the attacker’s own ticket. These criteria measure prohibited output, not necessarily an
executed transfer or cross-customer propagation.

Software tests exercise positive and negative examples for all 21 scenarios and parser, refusal,
conjunction, and target-record cases. Frozen checks, source hashes, and derived outcomes make the
reported definitions reproducible from the saved records.

B.6 Replay selection, weighting, and uncertainty

A source must have a non-null recorded success round, a positive result under the replay criterion at
or before that round, and every formatted input through that round available. This selects 62 sources
from the 945 archived trajectories: 12 against Opus, 12 against GPT-5.4, and 38 against Gemini. For
each source we preserve the ordered inputs, individual input hashes, sequence hash, original cell and
run, and source-line hash.

The runner presents each input in a fresh session using the generic defender system prompt and
scenario context. It tries the sequence until success or exhaustion. The 558 trials correspond to
3,867 nominal model calls. Three repeated trials per target share a source sequence. We use 10,000
percentile bootstrap resamples of source sequences, stratified by source defender, seed 20260908,
carrying every target and repeat together.

Same-target 125/186 and cross-target 44/372 are conditional reproduction and transfer rates. The
sample is enriched for successful source attacks, and source models contribute unequal numbers and
scenario mixtures.

B.10 Models, routing, and compute

The frontier models are requested as anthropic/claude-opus-4.6, openai/gpt-5.4, and
google/gemini-2.5-pro. The associated router sends Anthropic/OpenAI calls to their direct
endpoints and Gemini through OpenRouter. Provider revision identity is not independently verified
by the transcript files. Associated logs place the selected frontier execution in April 15–19, 2026,
including a partial Opus/Opus restart; follow-up experiments have separate dated manifests. Complete
routing and timing metadata are not present in every transcript line.

The competition backbone is gpt-oss-20b. The exact vLLM version and a complete hardware manifest
are not established by the saved records. Where a runner omits sampling parameters, provider defaults
were requested; effective decoding and model revisions can differ across providers.

The 945 archived battles contain 13,189 observed rounds. One attacker and one defender request
per observed round imply 26,378 nominal protocol calls, excluding unlogged provider retries or
billing details. Four defender infrastructure responses appear in the matrix. Reconstructing prompt
text and repeated attacker history at four characters per token gives approximately 109.85 million
token-equivalents. At 3.5 and 4.5 characters per token this becomes approximately 125.55 and 97.65
million.

Associated logs give 104.29 aggregate battle-hours, or 6.62 minutes per battle on average. These are
whole-battle durations, not per-call latencies or a wall-clock prediction for a concurrent run. API
charges and exact usage were not logged.

D Dataset Schema

The records distinguish saved model outputs, collection-time outcomes, and outcomes under explicitly
identified success checks. The schemas below describe the data used by the analyses.

Frontier transcripts. Each JSONL line identifies cell, scenario, and run, and stores winner,
manipulation_round, the configured round budget, and battle_log. Each round stores
round, attack_output, formatted_input, defender_output, manipulation_detected,
and extracted_value. The attacker receives prior defender responses and the check’s
extracted_value as feedback. The archived winner is preserved; analyses specify whether they
use that label or a derived check.

Derived battle records. The offline analysis emits study name, unique study ID, source file and
line where applicable, source/trajectory hash, scenario, attacker, defender, arm, batch, observed round
count, infrastructure status, and per-version won and first_success_round. Explicit IDs identify
the 135 battles shared by the provenance and precision studies.

Replay. The saved result schema includes attack, scenario, source_defender, target,
repeat, is_source, leaked, round, and error. The field leaked denotes recorded success
across all scenario types. Target response text is absent. The reconstructed source-input archive adds
ordered formatted inputs, per-input and sequence SHA-256 hashes, original source location, and
recorded stopping round.

Competition adversarial records. The held-out archive records snapshot, pseudonymous attacker
and defender, backbone, scenario, run timestamp, original winner, manipulation round, configured
budget, error counters, and battle log. Pseudonyms are Baseline and T01–T21; T15 has no active
defender. The team-identity map is kept separately. Original labels, availability adjustments, and
strict rescoring are separate columns or derivative files.

Competition utility. A result file contains scenario, topic totals, and topic-level details. A topic
contains its description, expected concepts, pass label, attempt count, and the attempts. Attempts
contain generated question, defender response, LLM evaluation, pass label, and explanation when
available. An anonymized analysis event adds team pseudonym, snapshot, opaque registration token,
source hash, and a stable record ID. Topic-level derived rows separately count first-attempt and
eventual success and missing fields. Submission-version hashes were not recorded.
Frontier utility pilot. The 60 records contain scenario, topic label, defender, prompt arm, an-
swered/helpful labels, refusal marker, error, and response text. Generated questions, full rendered
inputs, and judge explanations were not saved.
Reference and calibration summaries. The 1,050-run reference JSON files and calibration records
contain configurations and run-summary outcomes. For records without response text, analyses use
the saved outcome labels.
Reproducibility metadata. Manifests record source hashes, analysis-code hashes, scorer versions,
study overlaps, and output hashes. Complete per-call usage, billing, latency, and resolved provider-
revision metadata are not available for the reported runs.

E Implementation and Availability

The benchmark implementation comprises scenario plugins, the battle orchestrator, baseline attacker
and defender harnesses, and a multi-attacker command-line evaluator. A scenario plugin defines the
role and task, attacker objective and input surface, output contract, and executable check_success
function. The orchestrator renders each input, manages the interaction state and round budget, records
responses, and applies the check.
Saved transcripts and experiment configurations support inspection of observed outcomes. Offline
analyses derive the manuscript’s tables and figures from these records; live evaluations additionally
require model access. The source records distinguish the frontier matrix, targeted follow-ups, replay
trials, fixed-backbone competition, and benign-task evaluations.
The benchmark code and dataset are released as version 1.0.0 [Jain et al., 2026]. The code repos-
itory is licensed under MIT; the dataset and reproduction bundle is distributed with CC BY 4.0
data, an installable code package, schemas, and SHA-256 manifests. Participant-authored harness
implementations and the private identity mapping are excluded from the release.
