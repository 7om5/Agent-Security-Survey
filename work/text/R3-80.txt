         Abstract. LLM-based agents, which interleave large language model
         inference with external tool calls, are increasingly deployed in high-stakes
         settings. In real-world deployments, both model inference and provider-
         hosted tool execution occur behind provider APIs and are therefore opaque
         to users. This opacity creates an execution-integrity gap: a malicious
         provider may substitute the advertised model or fabricate tool observa-
         tions to steer subsequent agent behavior. Existing zero-knowledge proof
         systems for LLMs prove only the Transformer computation of a single
         token, leaving the rest of the inference pipeline, long-form autoregressive
         generation, and external tool interactions outside the proof.
         We present zkAgent, the first SNARK system for verifiable agent execution.
         zkAgent proves the complete inference pipeline, from token-to-embedding
         lookup and positional encoding to Transformer computation and decoding.
         It further binds each tool observation to an authenticated execution via
         zkTLS or zkVM subproofs, yielding a single end-to-end proof. To scale
         beyond per-token proving, we introduce one-shot transcript proving: by
         exploiting the Transformer’s causal attention mask, zkAgent proves an
         entire multi-step agent transcript in a single forward pass, avoiding the
         substantial overhead incurred by one-proof-per-token generation. We
         make this batched proof sound with a weight-dependent quantization
         scheme that is both input-independent and unconditionally complete.
         On GPT-2 with a 512-token transcript, zkAgent achieves a 1,047.4×
         prover speedup over the state of the art (zkGPT, USENIX Security ’25),
         amortizing to 0.30 s/token. On a real-world coding-assistant execution,
         zkAgent completes end-to-end proving in 93.18 s with 1.63 s verification,
         making verifiable agent execution practical.

    In modern agent deployments, each LLM invocation executes behind the
provider’s API, along with an increasingly rich set of server-hosted tools (e.g., web
search and code execution in managed sandboxes [6]) bundled into that API. Even
when the agent loop runs entirely on the user’s device, these provider-executed
steps remain opaque to the user, as illustrated in Fig. 1. This opacity creates
an end-to-end execution-integrity gap [43]: an untrusted provider may deviate
arbitrarily from the prescribed agent procedure: (i) by silently substituting the
advertised model with a cheaper or backdoored alternative; or (ii) by fabricating
tool observations, such as forging web-search results or misreporting sandbox
outputs.

    Recent works on zero-knowledge proofs for large language models [69,60,13,63]
(zkLLM) have demonstrated the feasibility of verifiable outsourced LLM inference.
These systems encode core LLM computations as an arithmetic circuit and
leverage SNARK techniques [16,29,9,7,30] to generate succinct proofs that the
committed model was faithfully executed on a given input. Despite recent progress,
existing zkLLM approaches remain insufficient for verifiable agent execution. In
particular, they focus primarily on computations within Transformer blocks, and
therefore do not capture the full inference pipeline from input tokens to decoded
output tokens. Moreover, they do not support multi-round agent executions that
interleave model inference with external tool use. Closing these gaps poses several
fundamental challenges.

Challenge 1: Proving complete inference beyond Transformer blocks.
Completing the full inference pipeline requires proving three components generally
omitted by prior zkLLM systems: token-to-embedding lookup [73,48], positional
encoding [67], and logit-to-token decoding [34]. Each poses a distinct proving
challenge. First, embedding lookup maps each input token to a high-dimensional

vector via a vocabulary-sized table, which can contain tens of millions of entries
even for GPT-2 [61]. Direct applications of generic lookup arguments [28,32]
and offline memory-checking techniques [66,65] incur proving overhead linear
in the table size, making online proving impractical at this scale. Second, posi-
tional encoding injects position information through a position-dependent linear
transformation. RoPE [67] and its extensions [59,23] are widely used in modern
LLMs [71,80,20], but a direct arithmetization [69] compiles each rotation into a
per-token dh ×dh matrix–vector multiplication, incurring Θ(T d2h) overhead per
head even with time-optimal matmul protocols [70]. Finally, decoding maps a
logit vector to the next output token according to a public rule such as top-
k sampling [34]. Beyond proving correct candidate-set extraction and correct
Softmax-distribution computation, the prover must additionally show that the
output token was drawn from this distribution at the correct probability. No
existing proof system provides a construction for this complex random sampling.

Challenge 2: Proving long-form generation efficiently. Even for a single
query, LLM may generate a multi-token continuation over many autoregressive
steps, each requiring a forward pass conditioned on all preceding tokens. Thus,
a proof of LLM inference must ensure the correctness of each autoregressive
step. For a 482-token continuation on GPT-2, stepwise proving with zkGPT [60]
requires over 41 hours and produces proofs totaling ∼934 MiB. Recursive proof
composition [72,17,9] can compress the resulting proof size but does not reduce the
dominant stepwise prover work, and folding-based batching [39,38] still requires
prover work proportional to the total cost of all forward passes. Although it
may seem natural to evaluate the model once on the full transcript and prove
all token predictions in a single pass, doing so without additional constraints
may allow future tokens to influence earlier predictions, violating the causal
structure of autoregressive generation. Enforcing causal dependence within a
single batched proof while guaranteeing equivalence to stepwise autoregressive
generation remains an open problem in prior zkLLM work [69,60,77,13]. In
quantized inference, such equivalence further requires input-independent per-
layer scales so that corresponding prefix computations in the batched and stepwise
executions are quantized identically. Prior zkML quantization schemes do not
simultaneously ensure input independence and completeness: data-dependent
dynamic schemes [44] use input-specific scales, whereas fixed calibration-based
schemes [77] may reject valid executions whose activations exceed the calibrated
range.

Challenge 3: Proving external tool interactions. Unlike standalone LLM
inference, an agent execution interleaves model-generated content with externally
injected tool observations (e.g., web search results, APIs responses, or sandbox
outputs). Once incorporated into the model context, these observations can
directly influence subsequent model outputs and agent actions. Existing zkLLM
systems [69,60,13,77] do not model these tool interactions and therefore establish
neither the integrity of the observations nor their binding to subsequent model
inference. This leaves a critical gap: a malicious provider could tamper with tool
results or fabricate plausible-looking tool traces while still producing a seemingly

1.1 Our Contributions

To address these challenges, we present zkAgent, a zero-knowledge proof system for
end-to-end agent executions with tool use. We give an overview of its architecture
in Fig. 1.
Complete inference proof. We design dedicated protocols for each component
omitted by prior zkLLM systems, thereby providing a complete inference proof
from input tokens to decoded output. For token-to-embedding lookup, we present
zkEmbed, a preprocessing-based matrix-lookup protocol that exploits the highly
rectangular structure of embedding tables in modern LLMs [61,80,71]. After
one-time preprocessing on the fixed table, it achieves the online proving cost in-
dependent of the vocabulary size. zkPosEnc provides efficient positional-encoding
proofs; for RoPE [67], it exploits the structural sparsity of the rotation matrix
to reduce overhead from O(T d2h) to O(T dh) over prior method [69]. zkDecode
provides efficient decoding proofs; for top-k sampling, it introduces a verifiable
random sampling subprotocol based on inverse-CDF selection with a coin deter-
ministically derived from the committed prefix, achieving asymptotically optimal
proving cost.
One-shot transcript proving via causal masking. We introduce one-shot
transcript proving, which verifies all model-generated tokens with a single proof of
a causally masked forward pass rather than one proof per token. The construction
relies on the fact that, in a decoder-only LLM, self-attention is the only sublayer
that mixes information across positions. By applying a lower-triangular causal
attention mask [73] at every attention layer, we enforce autoregressive causality
within a single batched forward pass: each position t attends only to positions
≤ t, so its logits depend only on preceding tokens and all logits can be computed
in parallel in one full-transcript pass. We also formally prove that this one-shot
causally-masked forward pass yields the same per-position logits as stepwise
autoregressive generation—a property we call prefix equivalence (Appendix E).
To preserve prefix equivalence in quantized arithmetic, we design weight-dependent
quantization, deriving each layer’s scale from a worst-case bound determined solely
by the committed model parameters rather than the input (§4.1). The resulting
scales are input-independent and ensure completeness for honest executions. For
tool-interleaved transcripts, we further introduce a transcript-derived generation
mask that restricts next-token consistency checks to model-generated positions.
To our knowledge, zkAgent is the first work to formally establish prefix equivalence
and to design a protocol that avoids the one-proof-per-token structure, enabling
long, multi-round agent traces to be proved via a single forward-pass proof.
Verifiable tool observations and execution. We design tool-specific protocols
that bind each tool invocation and observation into the transcript proof, covering
the two dominant categories of provider-hosted tools: remote API calls and

sandboxed code execution. For remote API calls, we incorporate zkTLS-style

Prototype and evaluation. We implement zkAgent in C++ and evaluate it on
GPT-2 with two interchangeable lookup backends, Shout [65] and LogUp [32,58].
Given a 30-token prompt and a final transcript length of T = 512 (482 generated
tokens), zkAgent(Shout) proves the entire transcript in a single shot in 142.45 s,

2.63 s for the entire transcript. This yields a 1,047.4× prover-time and 1,657.5×

and 4,361.09 s, respectively). zkAgent(LogUp) offers a complementary tradeoff,
shrinking the proof to 3.84 MiB and verification to 1.50 s at 1.4× slower proving
against zkAgent(Shout), still much faster than zkGPT.

    Microbenchmarks further validate the efficiency of the additional components
needed for complete inference beyond Transformer blocks: After a one-time prepro-
cessing step taking 942.43 s and requiring 4.52 GiB of auxiliary storage,zkEmbed
proves a batch of 1,024 embedding queries online in 0.27 s; zkPosEnc reduces
proving time by 15.7×–30.1× versus the naive matmul arithmetization used in
zkLLM [69]; zkDecode amortizes greedy decoding to 0.033 s/token and top-k to
0.15 s/token of prover overhead.

    Finally, we evaluate zkAgent on two representative tool-using agent traces: a
152-token weather-agent trace (zkTLS-attested API call) and a 143-token coding-
assistant trace (zkVM-attested sandbox execution). With the Shout backend,
zkAgent generates the corresponding end-to-end proof bundles in 95.23 s and
93.18 s, respectively, while verification takes 1.45 s and 1.63 s. In both cases,
the inference proof dominates the proving cost; the schema and tool subproofs
together add only 7.62 s and 6.18 s, respectively.

2.2 Lookup Arguments

Lookup arguments [32] are a cryptographic primitive for proving that a committed
vector of query values is drawn from a committed table. Formally, given a
committed table b ∈ FN and a committed query vector a ∈ Fℓ, a lookup
argument proves the multiset inclusion {ai}i∈[ℓ] ⊆ {bj}j∈[N]. This primitive is
widely used in zkML [69,60,33] to prove non-arithmetic operations (e.g., exp(·)).

    The appropriate lookup strategy depends on the size and structure of the
table. For small tables, direct protocols such as LogUp [32] and Shout [65]
remain practical even though their online prover costs scale with N . Papini et
al. [58] further use GKR to verify the LogUp identity without committing to the
reciprocal polynomial. For large structured tables, Lasso-style decomposition [66]
reduces a lookup over the full table to lookups over smaller subtables derived
from the original query, making the prover cost depend on the decomposed
representation rather than the full table size. For large unstructured tables,
preprocessing-based lookup arguments such as cached quotients (cq) [24] and
Baloo [82] shift the N -dependent work to a one-time preprocessing phase, so that
the online prover cost scales with ℓ rather than N . zkAgent combines all three
strategies: for large structured tables, we first applies Lasso-style decomposition
to reduce each lookup to lookups over smaller subtables, and then proves the
resulting lookup relations using GKR-optimized LogUp and Shout (§5.1). For
the large unstructured vocabulary-sized embedding table, our zkEmbed protocol
instead uses preprocessing based on cq (Appendix D).

2.3 GKR Protocol for ML

The GKR protocol [30] is an interactive proof for layered arithmetic-circuit
evaluation. Unlike SNARKs such as HyperPlonk [14] and Spartan [64], which
commit to the full execution trace, GKR iteratively reduces a claim at one layer
to a claim at the preceding layer via the sumcheck protocol [46], continuing
until it reaches the input layer. The prover therefore commits only to the input
layer and uses a polynomial commitment scheme (PCS) to answer the verifier’s
resulting random evaluation queries. This feature is particularly valuable in
zkML [44,69,60], where the forward-pass trace is too large to commit to directly.

GKR variant adopted in zkAgent. Classical GKR restricts each gate to

reading only from the immediately preceding layer, forcing model weights and

residual inputs to be relayed through every intervening layer. We instead adopt

the variant of Zhang et al. [84], which permits each gate also read from any

earlier layer, so that computation layers directly access committed weights and

earlier hidden states. To prove non-arithmetic operations within this backend, we

additionally use the advice pattern [44,60]. For each such operation y = f (x), the

prover places both x and y in the committed input layer as advice values. GKR

verifies that x matches the value produced by the preceding computation and

that y is consumed by the subsequent computation, while a lookup argument

verifies that (x, y) is valid for f . The shared input-layer commitment binds the

values checked by the lookup argument to those consumed by GKR. For clarity of

presentation, we present our construction without the zero-knowledge property;

however, this property can be added with only minor overhead using the standard

paradigm [78,84]. Formal constructions are given in Appendices C.3 and C.4.

2.4 Quantization for zkML

Since the GKR backend operates over a finite field F, every real-valued acti-
vation and weight must first be encoded as a field element. Prior zkML sys-
tems [44,13,69,60] follow the fixed-point quantization of Jacob et al. [35]: a real
value x is approximated as x ≈ q · s, where q ∈ [−2Q, 2Q] is a signed integer with
magnitude bounded by 2Q and s is a scale. We embed q into F via the natural
modular map: q ≥ 0 is represented by q, and q < 0 by p+q. Since |q| ≪ |F|/2, this
representation preserves signed arithmetic as long as all intermediate magnitudes
stay below |F|/2. Matrix multiplications and additions accumulate into wider
integers, so after every layer a rescale step that maps the accumulator back to
magnitude ≤ 2Q under a layer-specific output scale Sout (l) . Appendix F gives the
full protocol.

2.5 LLM Inference Pipeline

A decoder-only LLM first applies a public tokenizer to the input prompt to
obtain a sequence of token IDs. Each autoregressive step then comprises four

stages: (i) token-to-embedding lookup, (ii) positional encoding, (iii) a stack of
Transformer blocks, and (iv) an output head plus a public decoding rule to select
the next token, which is appended to the context for the next step. On an input
sequence of length T , the forward pass produces a logit matrix in FT ×N with
one row per position, but sequential generation decodes only the last row to
obtain the next token. Since tokenization is public, we exclude it from the proved
computation and start from the token IDs. Prior zkLLM proof systems [69,60,77]
cover only stage (iii), leaving stages (i), (ii), and (iv) unproved. In contrast,
zkAgent proves the complete post-tokenization pipeline comprising stages (i)–(iv).
Appendix B gives the detailed inference pipeline.

2.6 System and Threat Model

An LLM agent couples a language model with external tools and coordinates
their interaction in a loop. Starting from the user input, the agent repeatedly
(i) invokes the LLM on the current context, (ii) executes any tools requested
by the model, and (iii) appends the resulting tool observations to the context.
The loop terminates when the model produces a final response. We represent the
resulting execution as a growing transcript tr, namely the concatenation of the
user input, model outputs, and tool observations.

Threat model. We consider LLM agents operated by a model provider that
performs LLM inference and hosts server-side tools such as web search and code
execution [6,53], as illustrated in Fig. 1. Our model covers two deployment classes.
(i) Fully hosted chat products (e.g., ChatGPT, Claude.ai [54,6]) execute the entire
agent loop on provider-controlled infrastructure. (ii) API-driven agents (e.g.,
Claude Code, Codex CLI [3,51]) execute the orchestration loop on the client,
but LLM inference and server-side tools remain hidden behind the provider’s
API. Tools executed on the client machine (e.g., file or shell operations) are
inherently trusted and excluded from the proof. In both cases, the provider
holds private model parameters W and publishes a binding commitment cW .
For each query, the client submits an input and receives an execution transcript
tr together with a proof bundle. We model the provider as the sole adversary:
it may deviate arbitrarily from the prescribed agent procedure, e.g., replacing
the committed model with a cheaper or backdoored alternative, or fabricating
server-tool observations, such as forged web-search results or misreported sandbox
outputs, to steer the subsequent agent behavior.

Out-of-scope attacks. zkAgent targets execution integrity; several orthogonal
threats are deliberately excluded. (i) Prompt injection. Attacks that steer the
model through valid-looking inputs [1] are orthogonal to execution integrity: the
injected content appears in the transcript and is auditable by the client, but
identifying and filtering it is an alignment/policy task rather than a cryptographic
one. (ii) Network-tool semantics. For network tools, we prove provenance rather
than the correctness of the server’s business logic. Further discussion is deferred
to Appendix A.

3 Complete Inference Proof for LLM

As described in Section 2.5, prior zkLLM proof systems cover only the compu-
tations within Transformer blocks, leaving three components of the inference
pipeline unverified. We close this gap with three dedicated sub-protocols: zkEmbed
for token-to-embedding lookup, zkPosEnc for positional encoding, and zkDecode
for logit-to-token decoding.

3.1 zkEmbed: Token-to-Embedding Lookup

Let N and d denote the vocabulary size and embedding dimension, respectively.
Given a tokenized transcript tr = (ti)i∈[T ] ∈ [N ]T and the model’s private
embedding table WE ∈ FN×d, the prover must show that each row of the
embedding output H0 ∈ FT ×d equals the embedding vector indexed by the
corresponding token:

                              ∀i ∈ [T ], H0[i, :] = WE[ti, :].                      (1)

    For the polynomial encoding below, let N¯ := 2⌈log2(N+1)⌉ denote the padded
table size. We append N¯ − N fixed zero rows to WE, obtaining WEpad ∈ FN¯×d.
Since every transcript token satisfies ti ∈ [N ], this padding leaves the target

relation in Eq. (1) unchanged.

    The lookup arguments used in prior zkLLM schemes [69,60] can in principle

be extended to matrix lookup, but they incur prover overhead linear in the

embedding table size N d (about 225 entries for GPT-2), rather than the number

of queries T . In light of this inefficiency, zkEmbed instead builds on the cq

preprocessing-based lookup argument [24], shifting all table-size-dependent work

to a one-time preprocessing phase and reducing the online prover cost to O(T d),
independent of N and N¯ . At a high level, we reduce the matrix lookup to a scalar

lookup via a random linear combination of the d columns. Then, we keep the

table side univariate to preserve preprocessing, while expressing the query side

over multilinear extensions to enable composition with the downstream GKR

proof.

One-time preprocessing of the embedding table. Since cq operates on a

scalar table while WE has d columns, we fold the columns by random linear
combination with random challenge ρ ∈ F, reducing the matrix lookup to a
scalar one. However, by Fiat-Shamir [27], ρ must be sampled only after the

prover commits to H0, foreclosing direct preprocessing of the folded table. We
instead preprocess each column of WE independently; by the F-linearity of KZG

Absolute positional embeddings (APE). For APE-style models (e.g., GPT-

4.1 Weight-Dependent Quantization

Our one-shot transcript proof batches all generation step into a single forward
pass. For the batched pass to be equivalent to the stepwise autoregressive one it
replaces, the quantized arithmetic circuit must produce identical traces under
both evaluation modes, imposing two requirements on the quantization scheme:

– Input-independence: per-layer output scales Sout (l) must be fixed independently
   of the input and prefix length, so the batched and stepwise passes produce
   identical quantized traces.

– Completeness: all honest rescaled values stay inside the fixed lookup range, so
   lookups never reject on honest executions.

    Prior zkML quantization schemes fail to satisfy at least one of these properties.

Calibration-based schemes [77] choose the smallest scale fitting a calibration set;

they can violate completeness when benign activations exceed the calibration

range, a common phenomenon in LLMs with activation outliers [21]. Data-

dependent dynamic schemes [44] derive Sout (l) for each inference, avoiding such
failures but breaking input-independence. A third option—a purely dimension-
only bound d · 22Q—satisfies both properties mechanically but assumes every
coordinate’s input and weight simultaneously saturate at 2Q, a configuration

real LLM weights never approach. On GPT-2 this may collapses perplexity at

practical bit-widths (Appendix F).

    We introduce weight-dependent quantization, the first zkML quantization

that attains input-independence and unconditional completeness without severe

precision loss.

4.2 One-Shot Transcript Proving via Masking

With the quantization scheme of §4.1 in place, we batch all model-generated

transitions into a single proof (Fig. 2). The key idea is a causal attention mask: it

forces each position’s logit to depend only on preceding tokens, so a single forward

pass on the full transcript evaluates all positions in parallel while preserving

autoregressive semantics. We formally prove the equivalence in Appendix E.

agreed decoding rule.

4.3 Tool Binding for Verifiable Agent Execution

Tool observations are injected into the transcript and can influence subsequent
agent operations, so transcript-level model integrity alone is insufficient: a ma-
licious prover could fabricate tool outputs while still producing a valid tran-
script [43]. We additionally require tool integrity and binding: every injected


===== PAGE 22 / 59 =====

22  L. Wang et al.

observation must be tied to an authenticated execution of the claimed tool on
the request parsed from the transcript.
Gated shift consistency. We extend shift consistency to interleaved transcripts
via a generation mask g = (g0, . . . , gT −2) ∈ {0, 1}T −1 that identifies which
transitions are model-generated:

               gi = 1 ⇐⇒ ti+1 is produced by LLMW from prefix tr≤i,

               gi = 0 ⇐⇒ ti+1 is injected externally.

With tˆ︁r denoting the predicted-token sequence, we enforce

                     gi(︁tˆ︁ri − ti+1)︁ = 0 for all i ∈ {0, . . . , T − 2}. (25)

leaving injected tokens unconstrained.
    A crucial requirement is that g is derived from the transcript structure, not

chosen by the prover (otherwise the prover could set g = 0 and satisfy Eq. (25)
vacuously). When the full transcript tr is public, g is uniquely determined by
a public, unambiguous transcript grammar. When deployments hide internal
reasoning tokens (e.g., chain-of-thought) [15], we distinguish tr from a public
transcript trpub containing all user/tool tokens and only the user-visible model
outputs. Let R denote the hidden span; the provider publishes a binding com-
mitment cR := Com(R) and length LR := |R|. Given (trpub, cR, LR) and the
grammar, the verifier reconstructs the unique segmentation and hence g. Any
substitution R → R′ either alters a subsequent model output (and is rejected by
Eq. (25)) or leaves trpub unchanged (and is therefore harmless to the guarantee).

    To rule out early termination, we require in the grammar that every model-
generated span ends with a designated terminator (e.g., EOS/EOT) that is itself
model-generated; premature truncation then either fails parsing or fails Eq. (25).
Tool-call parsing and binding. Each tool step consists of (1) a model-generated
tool-call span that deterministically parses to a structured request reqi, and (2)
a externally injected tool-observation span. To ensure that the tool-call schema
is correctly followed, we leverage Coral [2], a system for verifying a committed
stream corresponds to a structured object, to guarantees that each tool-call
span conforms to the expected structure and that all necessary parameters are
present and valid. We bind tools via plaintext equality: the observation span in
tr must equal the cleartext token sequence of the authenticated response object
respi opened from the tool subproof. Thus, subsequent verified generation is
guaranteed to condition on the same observation whose provenance and execution
are proven. we defer the formal observation-injection attack model and the
resulting end-to-end soundness statement to Appendix G.

    Consistent with the threat model (§2.6), provider-hosted tools fall into two
classes whose integrity reduces to distinct guarantees: networked APIs need
response authenticity under a designated endpoint, and deterministic sandboxed
computations need execution correctness. We realize the two classes via zkTLS
and zkVM subproofs, respectively, each invoked as a standard protocol with a
(Prove, Verify) interface and bound to tr via plaintext equality.

6 Related Work

ZKPs for ML have progressed from decision trees [83] and CNNs [44,40] to
full LLM inference [69,60]. A dominant approach expresses quantized models
as arithmetic circuits over finite fields and applies specialized proof systems.
zkCNN [44] introduced the GKR-based approach with the advice pattern for
non-linear layers; Zen [26] and ZKML [13] provide compiler-oriented frameworks;
zkLLM [69] proposed the first ZKP tailored for Transformer inference with
dedicated protocols for attention (zkAttn) and non-arithmetic operation (tlookup);
and zkGPT [60] further optimized the GKR-based pipeline for LLMs. ZIP [63]
demonstrates high-precision (IEEE-754) ZK inference for non-linear activations.
NANOZK [74] and Jolt Atlas [10] explore layerwise proofs and lookup-centric
approaches, respectively. All of the above focus on proving a single forward pass
and do not address the multi-inference, tool-interleaved setting that zkAgent
targets. Conversely, these single-forward-pass protocols are orthogonal to and
composable with our design: any of them can serve as the Transformer-block
backend of our one-shot transcript proof, and our one-shot-with-tool-binding
framework immediately lifts single-inference integrity to the multi-inference,
tool-interleaved agent setting.

    zkPytorch [77] observes that LLM inference can in principle be batched into
a single circuit, but its construction neither implements a causal mask to enforce
autoregressive dependence, nor proves equivalence to sequential autoregressive
generation. Furthermore, its calibration-based quantization lacks completeness on
heavy-tailed LLM activations (Appendix F, Table 7). zkPytorch therefore leaves


===== PAGE 29 / 59 =====

zkAgent: Verifiable LLM Agent Execution  29

the problem unresolved; we close both gaps via one-shot transcript proving with
formal prefix equivalence under causal masking (§4.2), and weight-dependent
quantization that provably keeps every honest activation within the lookup
domain (§4.1).

    In parallel, VOLE-based interactive proof approaches [75,33,45] show scalable
techniques for non-linear functions but impose substantially higher communi-
cation and verification overheads than SNARKs. Complementary to inference
verification, VeriLoRA [42] provides verifiable LoRA fine-tuning via ZKPs.

A Deployment Variants

This appendix expands on §2.6, which covers two default deployment classes
under a single provider-side adversary: fully hosted chat products and API-driven
agents. We describe a third class in which the provider-side is split across two
independent operators, and show that our construction accommodates it with no
protocol changes.
Independent agent-framework operator. In this class, an agent-framework
operator, distinct from the model provider, runs the agent loop on its own
infrastructure and hosts additional tools, while still delegating LLM inference to
the model provider’s API. SaaS agent platforms and emerging trustless-agent
proposals in the Ethereum ecosystem [19] target precisely this pattern.

    The operator is a separate principal from the model provider, and the client
does not implicitly trust either party. The operator may fabricate tool observations,
just as the model provider may fabricate LLM outputs. Our construction of
Section 4 accommodates this with no protocol changes. The zkTLS and zkVM
primitives of Section 4.3 apply verbatim to operator-hosted tools. The model
provider’s one-shot inference proof composes into the same bundle unchanged: it
yields a claim on the LLM-generated spans of tr, while the operator produces
claims on the tool-observation spans it controls. The verifier checks every subproof
against ctr, so neither operator can present a consistent bundle without faithfully
executing the components it controls.

C.2 Sumcheck Protocol

The sumcheck protocol [46] enables a verifier V to verify that the sum of a
poly∑n︁omial f : Fn → F over the boolean hypercube equals a claimed value v, i.e.
v = x∈{0,1}n f (x0, . . . , xn−1), by delegating the heavy computation to a prover
P. Directly evaluating the sum requires 2n evaluations, which is prohibitive for
the verifier. In each of the n rounds, the prover sends a univariate polynomial of
degree d (the maximum per-variable degree of f ), yielding a proof size of O(dn)
field elements. The verifier time is O(dn) plus one evaluation of f at a random
point. With the dynamic programming technique of [70,78], the prover time is
O(d · 2n). The protocol is complete and sound with soundness error ϵ = |F| dn . We
provide a detailed description in Protocol 1.

C.6 Top-p Decoding Protocol

Top-p sampling [34] selects the smallest set S ⊆ [N ] whose Softmax mass exceeds
a public threshold p. The protocol mirrors top-k (§3.3), with two differences:
(a) the cutoff is defined by cumulative probability mass under the full-vocabulary
Softmax distribution, so S must be verified against that distribution before
truncation and renorm∑a︁lization; (b) the size |S| is not fixed by a public k, so the
structural constraint χ = k is replaced by a pair of mass constraints that pin
|S| implicitly.
Setup. After the (full) Softmax is computed and committed (denote the integer-
scaled probabilities (pi)i with public scale), the prover supplies a boolean selector
χ ∈ {0, 1}N for S and a separator µ playing the role of the probability cutoff.
Constraints. The prover proves

                    χi(χi − 1) = 0 ∀i ∈ [N ],

together with the masked range checks

    χi · (pi − µ) ∈ [0, θ], (1 − χi) · (µ − pi) ∈ [0, θ] ∀i ∈ [N ],

and the two mass constraints               (︂∑︂  )︂
                    ∑︂
                         χi · pi ≥ p · θ,        χi · pi − µ < p · θ.

                                i          i

Soundness. As in top-k, the masked range checks force pi ≥ µ for i ∈ S and
pi ≤ µ for i ∈/ S, hence µ ≤ minu∈S pu. The first mass constraint asserts S
covers m∑a︁ss at least pθ (coverage); the second, combined with µ ≤ minu∈S pu,
implies u∈S pu − minu∈S pu < pθ (minimality: removing the smallest selected
probability drops the mass below pθ). Together these pin |S| implicitly without

an explicit cardinality constraint. No pinning of µ is required (the honest prover

takes µ = minu∈S pu); the link to the sampled token y is established transitively
by the sampling proof.

on the corresponding prefix. This equivalence justifies using teacher-forced logits
to enforce the shifted next-token constraints in Eq. (25).

G Tool Binding Details

This appendix expands on §4.3, covering the Depyler transpilation step, the
observation-injection attack that motivates Coral, the end-to-end soundness
statement, and our tool taxonomy.
Depyler-based transpilation. Depyler [57] is a public open-source transpiler
that compiles annotated Python to Rust while preserving program semantics.
Given a model-emitted script programi, Depyler produces Rust(programi), which
is then compiled to RISC-V and proved correct under SP1 [68]; semantic preser-
vation makes a proof of the Rust execution a valid proof of the original Python
execution. Both programi and Rust(programi) are public artifacts and can be
re-run by any third party, so the transpilation step itself need not be proved
in-circuit, avoiding substantial prover overhead.
Observation-injection attack and schema integrity. Without proving tool-
call well-formedness, a malicious prover could label a model-generated span
tr[a] that does not satisfy the public tool-call schema as an invocation, execute
a prover-chosen request, and insert the authenticated response as an external
observation tr[b]. The tool subproof and all subsequent model-generation checks
could then remain valid even though the prescribed agent parser would not have
invoked a tool on tr[a]. We prevent this attack by using Coral [2] to prove that the
committed call span admits a valid parse under the public tool-call grammar. The
request extracted from this parse is bound to the request authenticated by the
corresponding zkTLS or zkVM subproof, while the transcript grammar permits
an observation span only immediately after such a valid call. Consequently,
malformed or ordinary model-generated text cannot authorize an externally
injected observation.
End-to-end soundness statement. Let g be the transcript-derived generation
mask defined in §4.3. Given commitments cW and ctr to the model parameters
W and the full token transcript tr, respectively, zkAgent’s composed proof attests
to:

1. Model integrity: every gi=1 position satisfies Eq. (25) under LLMW and Dec;


===== PAGE 57 / 59 =====

zkAgent: Verifiable LLM Agent Execution  57

2. Schema integrity: every tool-call span parses to a structured request reqi under
   the public grammar;

3. Tool integrity: every tool-observation span is the authentic output of executing
   the claimed tool on reqi, attested by a zkTLS proof πioi for I/O tools or a
   zkVM proof πvm i for computation tools (verification predicates given in §4.3);

4. Binding: the requests, programs, responses, and outputs carried by the sub-
   proofs equal the canonical encodings of the corresponding spans of tr.

Tool taxonomy. zkAgent’s two-class tool taxonomy follows the threat model
of §2.6, which targets provider-hosted tools (client-side tools are trusted and
excluded). Provider-hosted tools split into two classes whose integrity reduces
to distinct guarantees, as stated in §4.3: (i) networked API tools (e.g., web
search and other REST/RPC endpoints [6]), where integrity reduces to response
authenticity under a designated endpoint and is realized by a zkTLS subproof;
and (ii) computation tools (e.g., Python sandboxes [53,31]), where integrity
reduces to execution correctness under a deterministic machine model and is
realized by a zkVM subproof.

H Peak-Compute Estimate

This appendix details the ∼ 13× peak-compute gap quoted in §5.3 between the
A100 GPU on which zkLLM is measured and our CPU testbed.
Why field-multiplication throughput, not FP32 or TF32. zkLLM [69]
carry out their arithmetic in the BLS12-381 scalar field, whose elements are
∼ 256-bit integers. Inspecting zkLLM’s reference implementation, each scalar
is represented as 8 limbs of 32 bits, and field multiplication is implemented
entirely using 32-bit integer multiply-add and carry operations. Because A100
Tensor Cores do not support INT32 operands, zkLLM executes these limb-level
operations on the CUDA-core integer pipelines rather than on Tensor Cores [50].
CPU-side, our implementation uses the mcl library, whose optimized x86-64 path
represents approximately 256-bit field elements as 4 limbs of 64 bits and performs
Montgomery multiplication over this representation [49]. Our implementation
uses this scalar path and does not batch field multiplications through AVX-512
SIMD. Floating-point execution units do not participate in either implementation.
Consequently, the appropriate metric is field-multiplications per second, derived
from each platform’s native integer instruction throughput and Montgomery cost,
not FP32 or TF32 TFLOPS.
Departure from prior work. Prior work [60] positions the A100 and CPU
comparison using the A100’s TF32 Tensor-Core peak (312 TFLOPS) against a
CPU estimate (10.2 TFLOPS), yielding a ∼ 30× ratio. The A100 figure assumes
2:4 structured sparsity (its dense TF32 peak is 156 TFLOPS), and neither TF32
nor CPU floating-point throughput directly represents the field-arithmetic paths
used by the two systems. We therefore use this comparison only as evidence of
the A100’s substantially greater parallel compute capacity and derive a more
workload-aligned, back-of-the-envelope estimate below.

GPU side. The A100 contains 64 INT32 execution lanes per SM, 108 SMs, and
a peak clock frequency of approximately 1.41,GHz [50]. As a coarse upper-bound
proxy, assuming that each lane issues one 32-bit integer limb operation per cycle
gives

            64 × 108 × 1.41 GHz ≈ 9.75 × 1012 integer limb-operations/s.

In zkLLM’s CUDA field-multiplication path, an eight-limb multiplication performs
approximately 128 low/high multiply-add operations for the full product, another
128 for Montgomery reduction, and eight additional limb multiplications for the
reduction factors, before accounting for carry propagation and final modular
correction. Using the resulting 264 multiplication-related limb operations gives
the optimistic estimate

                    9.75 × 1012/264 ≈ 36.9 G field-multiplications/s.

CPU side. Our testbed is an Intel Xeon 6982P-C (32 cores at 3.20 GHz). For the
four-limb scalar representation used by mcl on x86-64, a CIOS-style Montgomery
multiplication requires approximately 2n2 + n = 36 64-bit limb multiplications
for n = 4. As a coarse upper-bound proxy, assuming that each core issues one
64-bit limb multiplication per cycle and that the workload scales perfectly across
all 32 cores gives

                  32 × 3.20 × 109/36 ≈ 2.84 G field-multiplications/s.

Ratio. Dividing the two idealized estimates gives

                                          36.9/2.84 ≈ 13,

the ∼ 13× figure quoted in the main text. We note that this estimate would be
substantially smaller had we engaged mcl’s vectorized AVX-512 IFMA path. Even
without this optimization, however, zkAgent with the Shout backend remains
53.5× faster to prove and 98.9× faster to verify at T = 512, indicating that
algorithmic improvements rather than hardware advantage drive the comparison.
